# 01 故事线:从一次 push 到集群收敛

> **这份的用法**:面试官说"你具体讲讲这条链路是怎么走的",你就按这十四环往下走。每一环都配了"**他可能在这儿问什么,你怎么答**"。
>
> 全部内容基于一次真实执行:推送 `81cc34e` → 构建 **#16** → 写回 `bf43ff9` → 自动触发 **#17** 被闸门跳过。数字都是当次观测到的,不是估算。

---

## 一、全景:一次 push 之后的十四环

```
[本机] git push
   ↓
[Gitea] 收到 push → 查这个仓库挂了哪些 webhook → 投递
   ↓
[Jenkins] 收到 → 排队 → 起一个一次性的 Pod agent
   ↓
Checkout → Trigger Guard → Resolve Tag → Lint → Build → Push → Verify In Registry → Update GitOps
   ↓
[Gitea] 收到 CI 的写回 push → 又触发一次 → 被 Trigger Guard 挡住
   ↓
[ArgoCD] 拉到新声明 → 收敛 → 新 Pod 起来
   ↓
[运行时] 程序自报版本号,证明"跑的确实是这个版本"
```

---

## 二、逐环:发生了什么 + 他可能问什么

### 第 1 环:本机 `git push`

**发生了什么**:推到的是**集群内的 Gitea**,不是 GitHub。GitHub 上那个 `origin` 只是对外镜像。

> **他可能问:"为什么推到 Gitea 不推 GitHub?"**
>
> 答:**因为外网的可用性不由我控制,也不由我观测**。"我们之前踩过一次——集群里 `github.com` 解析到一个被阻断的 IP,ArgoCD 拉取超时。我先用 `curl --resolve` 逐个 IP 试,用的是 git 协议真正请求的那个 `info/refs` 端点而不是首页;**8 个 IP 里有的通有的不通**。结论是针对特定域名和 IP 的阻断,不是整体断网。我在 CoreDNS 里钉了一个可用 IP,ArgoCD 恢复了,但 **20 分钟后我钉的那个 IP 也被封了,8 个只剩 1 个活着——换 IP 是打地鼠,这条路的稳定性本身不成立**。所以我改成集群内自建 Gitea。"
>
> **他可能追问:"那 Gitea 自己不就成单点了?"**
>
> 答:"对,而且更麻烦的一点是——**Gitea 跑在同一个 k3d 实例里,而它管的正是这个集群的期望状态**。严格说这动摇了'Git 是集群外唯一真相来源'这个前提。**真正的生产形态是 Git 在集群之外**,集群内自建是本地资源约束下的折中。这个边界我在文档里是主动写了的。"

### 第 2 环:Gitea 投递 webhook

**发生了什么**:Gitea 的 POST-receive 钩子触发,它按仓库配置的 webhook 列表,逐个投递。我们的 hook 指向:

```
http://<节点容器名>:30080/generic-webhook-trigger/invoke?token=<凭据>
```

> **他可能问:"token 为什么放 URL 里?这不是泄露吗?"**
>
> **这是个陷阱题,但对你有利——因为你真踩过。** 答:
>
> "对,**这里确实有泄露面,而且我实测到了**:有一次投递失败,Gitea 把**完整的 URL 连同 token 明文**打进了自己的错误日志。这就是'密钥放 URL 里'的具体代价——**URL 会被日志、代理、浏览器历史、Referer 头记录,而请求体里的东西通常不会**。
>
> 我现在的缓解是:这个 token 只对一个 Jenkins 凭据有效、且**只能触发构建**,不能读任何东西。**但我要说清楚:这是访问范围的控制,不是不泄露的控制。** 更好的做法是把令牌放 header 或请求体里。"

> **他可能问:"为什么不用 Jenkins 自带的远程触发(`/build?token=X`)?那是标准做法。"**
>
> 答:"我试过,**走不通**。任务里配好了 `BuildAuthorizationToken`,三种写法——GET 带 token、POST 带 token、POST 带 token 加管理员账号密码——**全部 403**,报错统一是 `No valid crumb was included`。
>
> 根因是**两层独立机制**:凭证令牌管'你是谁',CSRF crumb 管'这个请求是不是从本系统页面发出来的'。我配好了第一层,但命令行裸请求没有会话,拿不到绑定会话的 crumb,被第二层拦住了。**报错里根本没有'token'这个词,它从来没在质疑我的令牌。**
>
> 顺带一提,配那个令牌本身也费了劲——`BuildAuthorizationToken` 不是 `JobProperty`,`addProperty` 用不了,反射塞字符串类型也不对,最后是直接 set 成对象才成功。**折腾到那一步的结论就是:此路不通,换插件。**"

### 第 3 环:Jenkins 收到,起一次性 Pod

**发生了什么**:Jenkins 把构建排进队列,**为这次构建起一个一次性的 Pod**(里面三个容器:jnlp / buildah / lint),构建结束就销毁。

> **他可能问:"为什么用一次性 Pod,不用常驻 agent?"**
>
> 答:"资源。构建是**脉冲式**负载,常驻 agent 大部分时间是空闲的。而且构建 Pod 不请求 GPU,我用 `nodeSelector` 把它固定到 CPU 节点——**这条是资源纪律,不是优化**:我们有个节点是唯一带 GPU 的,长期高负载,CI 构建没有任何理由占它。"
>
> ⚠️ **这里如果面试官懂 Jenkins,可能会问:"临时 agent 有什么代价?"** —— **这是你最有东西可答的一问**,直接进 `02_深挖弹药` 第一条。

### 第 4 环:Trigger Guard(闸门)

**发生了什么**:流水线**第一件事**是判"这次推送值不值得构建":

- 有没有碰到 `ci/` 或 `03-ollama-exporter/`?→ 有就继续
- 没碰到?→ 后面所有 stage 全部 `when` 跳过

> **他可能问:"为什么要这一层?"**
>
> 答:"因为我们这条链有个**结构性矛盾**:CI 构建完之后会把新镜像 tag **写回同一个仓库的清单文件**,而那次写回**也是一次 push**——所以它会再触发一次自己。**触发源和写入目标是同一个仓库,天然就是反馈回路。**
>
> 闸门的作用是让循环**只走一次就停**,而不是无限。实测:#16 构建完写回,写回的 push 触发 #17,#17 判定'只改了 `sre-lab-gitops/`'直接早退,**没有 #18**。"

> **他可能问:"那为什么不在触发层做路径过滤?Jenkins 原生就支持。"**
>
> **这问到了今晚最值钱的那个坑。** 答:"我第一版就是那么做的,在轮询配置里加路径过滤。**它引出了一个更严重的问题**——过滤需要算 diff,算 diff 需要工作区,而工作区在**已经销毁的一次性 agent 上**。结果就是轮询**静默失效**:不触发、不报错、面板全绿。**修好了循环,弄死了触发。**
>
> 所以我把判定从**触发层**下沉到**执行层**——流水线里它自己刚 checkout 完,`git diff` 随手就能算。**同一个判断放在不同的层,可靠性完全不同:放在触发层,它得依赖'上下文还在';放在执行层,上下文是它自己刚准备的。**"

### 第 5 环:Resolve Tag —— 镜像 tag 用什么

**发生了什么**:`env.SHORT_SHA = git rev-parse --short=7 HEAD`,镜像 tag 就是**源码仓那次提交的 7 位短 SHA**。

> **他可能问:"为什么不用 `latest` 或递增版本号?"**
>
> 答:"三个理由。**第一,`latest` 是不可追溯的**——你看到 `latest`,不知道它是哪个 commit 构建的。**第二,SHA 天然一一对应**:同一个 commit 反复构建,产物应该覆盖自己而不是产生两个。**第三,它让'代码版本'和'制品版本'是同一个标识**,排查的时候不用做一次映射。
>
> 版本号我得另外维护一套语义化版本,**而这个项目里语义化版本给不了我任何信息**——我要的是'这个镜像是从哪次提交来的',不是'它兼容不兼容上一个版本'。"

### 第 6 环:Build —— 关键的一处设计

**发生了什么**:

```
buildah bud --build-arg GIT_SHA=${SHORT_SHA} ...
```

Dockerfile 里 `ARG GIT_SHA` → `ENV GIT_SHA=${GIT_SHA}` → 程序启动时读 `os.environ["GIT_SHA"]`。

> **他可能问:"这个 SHA 为什么不干脆运行时用环境变量注入?那样更灵活。"**
>
> 答:"**那样镜像内容就不再自含版本了。** 同一个镜像,换个 env 就'变成'另一个版本——于是又回到'标签说了算'。
>
> **构建期注入意味着:镜像内容本身就携带版本信息,它跑起来必然会报出它是谁。** 这才是不可变制品——**你没法让一个镜像假装自己是另一个镜像。**"

### 第 7 环:Push 到 registry + Verify In Registry

**发生了什么**:推到本地 registry(集群内地址 `k3d-sre-registry:5000`),然后**回读一次 tags 列表**,确认新 tag 真的登记上了。

> **他可能问:"push 命令返回 0 不就说明成功了吗?为什么还要回读?"**
>
> 答:"**写入命令自己的返回值,不能证明远端收到了。** 这是我的一条通用原则。同一类事还有:CI 的 `git push` 之后应该用 `git ls-remote` 独立读一次,而不是相信 push 的退出码。
>
> 而且这一步特别便宜——就是一个 HTTP GET。**用一次几乎免费的读回,换掉一整类'以为成功了'的可能,这个买卖很划算。**"

### 第 8 环:Update GitOps —— 唯一会改仓库的那一步

**发生了什么**:`sed` 把清单里的 image 换成新 tag → `git diff --quiet` 判空(没变就不提交)→ commit → push。**push 带 3 次重试,失败就 `fetch` + `rebase` 重放本地提交**。

> **他可能问:"这里最容易出什么问题?"**
>
> 答:"**写回失败是静默的。** 因为流水线的成功标准和集群的成功标准是两个系统——CI 全绿只说明它的 stage 过了,**不说明集群变了**。所以我在这里放了一个 `set -e` 让它硬失败,再加一次独立的读回验证。
>
> 另一个是并发:两个人同时推、或者我推的时候 CI 正好也在写回,`push` 会被拒。所以有 `disableConcurrentBuilds` 串行化**加上** push 失败后的 rebase 重放。**两层都要有**——串行化管同一个 Job 内部,rebase 管和别人的冲突。"

### 第 9 环:写回的 push 又触发一次(闸门挡住)

**发生了什么**:这套机制在这里表现得很清楚——**CI 的写回和被挡住的第二次构建,是同一件事的两面**。

实测(#17 控制台原文):

```
本次推送范围: 81cc34e..bf43ff9(由 webhook 提供)
本次推送涉及的文件: sre-lab-gitops/production/monitoring/ollama-exporter.yaml
本次推送未触及 ci/ 或 03-ollama-exporter/,跳过构建
```

> **他可能问:"`81cc34e..bf43ff9` 这两个值哪来的?"**
>
> 答:"**webhook 载荷里带的。** Gitea 的 push payload 有 `before` 和 `after` 两个 revision,我直接拿来算 diff。
>
> 这一点其实回答了一个更深的问题——**如果只是为了触发,轮询也能触发。为什么一定要换 webhook?** 因为轮询**只能告诉我们'变了'**,它给不出两个 revision。有了 `before`/`after`,闸门才能算'**整次推送**改了哪些文件',而不是只看最后一个提交。**这是推送模型结构上才有、轮询模型给不了的东西。**"

### 第 10 环:ArgoCD 收敛

**发生了什么**:ArgoCD 拉到新声明,把 Deployment 的 image 改掉,滚动更新。

> **他可能问:"ArgoCD 多久拉一次?"**
>
> **小心,这里有个我踩过的坑。** 答:"默认轮询是 3 分钟一次,但**关键的一点是:对我这条链上那个已经被 ArgoCD 管起来的应用,它不靠轮询**——它对**自己管理的资源**有 watch 通道,一有变化立刻发现、立刻施加。3 分钟只是兜底的全量对账。
>
> 我是被这个教训过的:我手工 `kubectl set image` 换了个镜像,**命令返回成功,5 秒后再看,已经被拉回去了**,没有任何报错。**如果我只看了那两秒,我会得出'改成功了'的结论。**"

### 第 11 环:Pod 起来

**发生了什么**:新 Pod 用新镜像起来。

> **他可能问:"你怎么确认新版本真的在跑?"**
>
> 答:"**这一步我会多做一件很多教程不做的事**——不是看 Pod 上的 tag 字符串,而是**让程序自己报版本号**。"

### 第 12 环:运行时自报版本(收口)

**发生了什么**:

```
sre_lab_build_info{revision="81cc34e"} 1
```

**这是从容器内部、经真实数据面取回来的。**

> **他可能问:"看 Pod 的 image 字段不就知道了吗?"**
>
> 答:"**不够。** Pod 上的 tag 只证明**调度器让它跑这个 tag**,不证明**它真的起来了**,更不证明**镜像内容是对的**。
>
> 而自报版本是从容器内部取回来的——**它同时证明了三件事:容器起来了、程序在跑、跑的是这个版本。**
>
> 而且这个设计在**回滚**的时候价值最大,你听我说回滚那部分就知道为什么。"

> ⚠️ **这里还可以主动补一个坑(很能加分):**
>
> "**这个指标也不是万能的,我自己在采样上翻过车。** 滚动更新期间集群里**同时存在新旧两个 Pod**,我第一次采到的是**正在退场的旧 Pod**,拿到一个**过期的、但看起来完全正常的版本号**。
>
> 所以我现在的习惯是:采之前先确认**我在采哪个 Pod**。**'从容器里采到的'不等于'是对的'**——这也正是我坚持让程序自报版本的原因:至少值对不上能暴露出来,而只看 Pod 上的 tag 字符串连暴露的机会都没有。"

### 第 13 环:回滚(如果面试官问"出事怎么办")

**发生了什么**:回滚 = **`git revert` 那次 CI 的 bump 提交**,然后等 ArgoCD 收敛。**不是 `kubectl rollout undo`。**

> 答:"**回滚本身在 GitOps 下是免费的**,因为'上一个版本'就是 Git 历史里的上一个提交,`git revert` 一下就回到了。不需要 `rollout undo`,而且 `rollout undo` 会被 ArgoCD 拉回去——**你会看到自己白忙一场**。"

> **他可能问:"那怎么证明真的退回去了?"**
>
> **这是你整条链上最漂亮的一个回答。** 答:"回滚后我会**再采一次那个自报版本指标**。当时的结果很有意思——**那个指标不是'变成了旧值',而是整行消失了**。
>
> 因为旧镜像**根本没有这个能力**——这个指标是在新版本里才加进去的。所以回滚后的证据不是'值变了',是'**这个能力整个不存在了**'。**这是一个结构性差异,不可能是缓存、不可能是我看错了 tag。**
>
> 这比'值变回去了'强得多——**值是可以被污染的,能力的有无不行。**"

### 第 14 环:整条链的自证(收束)

> **怎么收尾**:"所以整条链最后是可自证的:**我推了一个 commit,最后我能从集群里取回一个字符串,那个字符串等于我推的那个 commit 的前 7 位。** 中间经过了两个仓库、一次构建、一次跨系统的写回、一个 GitOps 控制器——**但我不用相信任何一环的'成功'回报,我有终端证据。**"

## 三、一张表:这条链上每一步的"成功标准"

**如果面试官问"你怎么定义这一步成功",拿这张表答。它比任何描述都更能说明你的思维方式。**

| 环节 | 弱的标准(大家都用) | 我用的标准 |
|---|---|---|
| 推送 | `git push` 返回 0 | 远端 `ls-remote` / 分支确实前进 |
| 触发 | 我手动点了构建 | **构建的触发原因是 `Gitea push ...`**,不是我手动点的 |
| 构建 | 流水线绿 | **registry 里回读到新 tag** |
| 写回 | commit 成功 | push 成功 + 失败时 rebase 重放 |
| 收敛 | ArgoCD 显示 `Synced` | **核对它的 `revision`**,而不是只看那个绿字 |
| 运行 | Pod `Running` | **从容器内部取回自报版本号,值对得上** |

> **一句话版本**:"**我在这条链上的每一处,都尽量把'我以为成功了'换成'我能证明成功了'。** 因为这条链上大部分环节的失败形态是静默的——**没有报错,只有'什么都没发生'。**"
