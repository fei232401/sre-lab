# 02 深挖弹药:静默失效专题

> **这是三份里最值钱的一份。**
>
> 今晚抓到的五个问题,**表面上是五件事,底下是同一个模式**。面试里能讲清这个模式,比讲清任何一个具体技术点都更能说明你到了什么段位。
>
> 每一条的结构:**现象 → 我当时怎么想的(包括想错的)→ 决定性证据 → 通用形态**。

---

## 〇、先把模式说破:什么叫"静默失效"

**监控系统只对"发生的事"报警。它对"没发生的事"不报警。**

于是存在一整类故障,它们的形态是:

```
命令返回成功 · 面板全绿 · 日志无报错 · 一切都"正常"
—— 但事情根本没发生
```

**这类故障的可怕之处在于:'什么都没发生'和'本来就没事',在监控上长得一模一样。**

而你手上正好有五个这样的真实案例——**这就是你这个项目最大的面试资产。**

## 一、CI 静默不触发(`Took 0 ms`)

### 现象

推了源码变更,**6 分钟没有任何动静**。Jenkins 没报错、没告警、UI 全绿。

轮询日志里只有:

```
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
Done. Took 2 ms
No changes
```

### 我一开始怎么想的(包括想错的)

我的第一判断是:**路径过滤(`PathRestriction`)需要工作区来算 diff,而工作区在一次性 agent 上,所以拿不到。**

**方向是对的。** 于是我按这个判断**摘掉了任务配置里的路径过滤,重新触发轮询**——

**照样 `0 ms`。**

**判断被实验证伪。**

### 决定性证据:`Took 2 ms`

在构建 #11 **正在跑**的时候手动触发一次轮询:

```
ERROR: no such computer sre-lab-ci-10-1fsrd-r2tv3-bp24r   ← #10 的 agent,早就没了
Done. Took 0 ms
No changes
```

两个点:

1. **`0-2 ms` 这个数字物理上不可能。** 一次网络往返(去问"远端 HEAD 是什么")不可能在这个量级完成。**这个数字本身就宣告了'它压根没去问'。**
2. **#11 的 agent 明明活着,轮询报的却是 #10 的节点。** 它固定去找"**上一次已完成构建**"的 agent——**不是节点碰巧没了,是它取节点的逻辑本身就取错了地方。**

### 我后来又是怎么被推翻的(这段是最值钱的)

当晚稍晚,Jenkins 因为装 webhook 插件**重启了一次**。重启之后,**轮询自己好了**——构建 #14 的触发原因就是 `Started by an SCM change`,而且控制台里没有任何 webhook 载荷。

所以我当时写下的那句"**轮询模型和临时 agent 架构根本不兼容,这不是配置问题,是模型问题**"——**是错的。**

修正后的解释同时能解释**所有**观测:

| 观测 | 解释 |
|---|---|
| 推了代码,轮询 `Took 2ms / No changes` | 路径过滤要求工作区,而 agent 节点已销毁 |
| **摘掉路径过滤,重试,还是 0ms** | 那个"上次构建的节点"引用**缓存在 JVM 内存里**,改配置文件清不掉 |
| Jenkins **重启后**,轮询忽然能用了 | **重启清掉了那份内存缓存** |

**一句话:这是"缓存"问题,不是"模型不兼容"问题。** 轮询慢、脆、要重启才能清缓存——**它不该用,但它是能用的。**

> ⚠️ **这段的诚实边界要主动说**:修正后的解释**没有做受控实验验证**。"重启清了缓存"是我从三个观测里推出来的**最简解释**,不是被我单独证明过的。要证伪它,得在保留路径过滤的前提下重启一次、看轮询是否恢复。**我没做,我在文档里标了。**

### 通用形态

> **第一,当失败的表现是"什么都没发生"时,先去找一个"物理上不可能的数字"。** `0 ms`、`2 ms`、`0.58 sec` 这种时间量级异常,比任何日志文本都直接——**它在告诉你"这一步根本没执行",而不是"执行了但结果是没变化"。**
>
> **第二,也是更要紧的:我下过一个结论,而且我把它写得很有把握。** 推翻它的不是我重新想了一遍,是**环境重启后它自己好了**——一个我完全没在测的变量。
>
> **这让我得出一个习惯:凡是"模型不兼容""架构冲突"这种级别的结论,先问自己——我真的排除掉所有'更平庸的解释'了吗?** "缓存没清"就是个平庸得多、但正确得多的解释。**而我把一个平庸的解释,说成了一条架构级的规律。**

### 最终处置

触发方式从**拉(SCM 轮询)**换成**推(webhook)**。但请注意理由:

> **不是为了"能用"——是为了"能给"**:轮询只能告诉我们"变了";webhook 载荷里有 `before` 和 `after` **两个 revision**,所以闸门能算"**整次推送**改了哪些文件",而不是只看最后一个提交。**这是推送模型结构上才有、轮询给不了的东西。**

## 二、Gitea 拒绝投递:手动能通,系统不能通

### 现象

webhook 链路**全部配好了**:插件装了、凭据建了、Gitea 的 hook 也建了,**手动从 Gitea 容器里 `wget` 那个端点,返回 200 + `triggered:true`**。

然后推代码——**没反应**。

### 我一开始怎么想的

"端点通了,那链路应该是通的。" **我差点就卡在这里。**

### 决定性证据:Gitea 自己的日志

```
Unable to deliver webhook task[3]: ...
dial tcp 172.18.0.5:30080: webhook can only call allowed HTTP servers
(check your webhook.ALLOWED_HOST_LIST setting), deny 'k3d-ai-cluster-server-0(172.18.0.5:30080)'
```

**根因:Gitea 默认只允许 webhook 发往公网地址。**

这是 **SSRF 防护**——webhook 这个功能的本质是"**让服务器替我发起一个 HTTP 请求**",而这类功能天然可以被拿来**探测内网**(比如让 Gitea 去请求云环境的元数据地址 `169.254.169.254`,或者内网里任意一台机器的管理端口)。所以默认策略是"不许往内网发"。

### 为什么手动能通、它不能

> **手动测试绕过的是 Gitea 的客户端策略,不是网络。**
>
> **网络一直是通的,是 Gitea 自己不肯发。**

### 通用形态

> **"我手动测过了,是通的",是一个很容易骗过自己的证据。** 手动测试用的是**你的**身份、**你的**路径、**你的**策略;而系统自动投递用的是**它的**。**两者能通的路径可能根本不重叠。**
>
> 由此推出一条更普适的规律:**"同一台机器上,我手动能通、它自动不能通"——第一反应应该是"某个组件自己的策略",而不是"网络问题"。** 这类问题的表现几乎总是 403 / deny / silent drop,而不是 timeout。

### 处置

```ini
[webhook]
ALLOWED_HOST_LIST = 172.18.0.0/16
```

**注意放行的是本环境网段,不是 `*`。** 改完重启 Gitea,**之前排队失败的那次投递会自动重投**——下一次构建就是这么起来的。

## 三、一个"没发作的 bug":`core.quotePath`

### 现象

排查上一个问题时,我去看构建日志里"本次推送涉及的文件"列表,看到:

```
本次推送涉及的文件: CHANGELOG.md
"sre-lab-local/01_\346\216\222\351\232\234\350\256\260\345\275\225/..."
"sre-lab-local/03_runbook/03_Jenkins_\350\277\220\350\241\214\346\211\213\345\206\214.md"
```

**git 把含中文的路径转义了,还加了引号。**

### 这意味着什么

闸门的判定逻辑是:

```groovy
changed.readLines().any { p -> p.startsWith('ci/') || p.startsWith('03-ollama-exporter/') }
```

**被转义的路径首字符是 `"`,不是 `c`——匹配必然失败。**

也就是说:**只要构建路径下出现一个中文名的文件,它就会被静默漏掉。流水线不报错,只是不构建。**

### 我当时怎么发现的

**不是靠读代码逻辑,是靠去看真实输出长什么样。**

我原本只是想确认"文件列表全不全",结果看到那一行带引号的转义——**这一眼顺带暴露了一个我原本没在找的 bug。**

### 通用形态

> **这是"没发作的 bug"的典型样本。** 当前 `ci/` 和 `03-ollama-exporter/` 下都是 ASCII 文件名,**所以它现在不发作**;它只会等到某个特定的人往那个目录放了一个特定名字的文件,然后**安静地什么都不发生**。
>
> **这类 bug 不会在测试里暴露**——因为测试用的是别人起好的名字。**它只会暴露在'有人做了你没想到的事'的那一刻。**
>
> **能发现它的方式只有一种:去看系统真实吐出来的东西长什么样,而不是去想它应该长什么样。**

**修法**:所有 `git` 调用加 `-c core.quotePath=false`。

## 四、ArgoCD 的 selfHeal 是秒级的

### 现象

```bash
kubectl set image deployment/ollama-exporter ollama-exporter=<...>:ea96824
# deployment.apps/ollama-exporter image updated    ← 命令成功了
```

**t+5 秒再看,镜像已经变回原来的了。** 没有任何报错,命令也返回成功。

### 我一开始怎么想的

我一直以为"ArgoCD 是轮询的(默认 3 分钟),所以手工改动大概能活几分钟"。

**错。**

### 决定性证据

那 3 分钟是**兜底的全量对账周期**;对于 ArgoCD **已经管理的资源**,它**有 watch 通道**——集群里一有变化**立刻**发现、**立刻**拉回。

> **`selfHeal` 不是"每 3 分钟修一次",是"发现即修"。**

### 通用形态

> **两个层次。**
>
> **表层**:GitOps 下,手工 `kubectl` 改动是"**无效动作**",不是"临时有效动作"。回滚时如果用 `rollout undo`,**你会看到自己白忙一场**。由此得到一条排障纪律:**看到"我明明改了啊",先问一句"这个资源归 ArgoCD 管吗?"**
>
> **深层,也是我更想讲的那层**:**它的危险不在"被拉回",在于"它不报错"。** 命令返回成功、`kubectl get` 头两秒也确实显示新值——**如果我只看了那两秒,我会得出"改成功了"的结论,并且会把它写进文档。**
>
> **一个错误结论被写下来,比一次操作失败严重得多**——失败会被人发现,错误结论会被人**继承**。

## 五、自激循环:触发源和写入目标是同一个仓库

### 现象

```
有人改代码 → 触发构建 → 构建成功 → CI 写回清单 → 又触发构建 → 又写回 → 又触发……
```

### 根因(这是结构性的,不是配置错误)

**CI 的写回也是一次 push,而 push 就是触发条件。**

> **只要"构建产物"和"触发信号"共用一条通道,就会形成反馈回路。**

### 第一版修法(错的)

在触发层加路径过滤。**它引出了第一条那个"静默不触发"。** —— **修好了循环,弄死了触发。**

### 正解:把判定下沉到"能算 diff 的地方"

| | 触发层(路径过滤) | 执行层(Trigger Guard) |
|---|---|---|
| diff 从哪来 | 要**工作区**,而 agent 已销毁 | 自己刚 checkout 完,随手就能算 |
| 失败形态 | **静默**:不触发、不报错 | 看得见:日志里直接打印改了哪些文件 |

### 通用形态

> **同一个判断,放在不同的层,可靠性完全不同。**
>
> 放在**触发层**,它必须依赖"上下文还在";放在**执行层**,上下文是它自己刚刚准备的。**能算 diff 的地方就算 diff,不要指望上游替你算好。**

> **另一个可以主动交代的边界**:手写闸门容易只比对 `HEAD~1..HEAD`(只看最后一个提交)——多提交推送时,若最后一个提交不触及构建路径而前面的触及,会**漏构建**。我后来改成用 webhook 给的 `before`/`after` 算整次推送,**但这条简化在"手动触发构建"那条路径上还在。**

## 六、把五条收成一个模式(面试收束口径)

**这是这段的落点。面试官听完五个案例,你要主动把它收掉——不然他只是听了五个故事。**

> "这五个问题表面上是五件事:CI 触发、webhook 投递、git 的路径转义、ArgoCD 同步、构建循环。
>
> **但它们底下是同一个模式:失败的表现都是'什么都没发生'。**
>
> 它们的共同点有三个:
>
> **第一,骗你的信号都长得很正常。** 命令返回 0、面板全绿、手动测试通过、UI 显示 `Synced`——**每一个都在告诉你'没问题'。**
>
> **第二,决定性证据都是'互相矛盾'或者'物理上不可能'的观测。** `0 ms` 太快了、手动通但系统不通、路径首字符是引号、命令成功但 5 秒后值变了。**都不是靠多看日志看出来的,是靠'这个数字/这个现象解释不通'看出来的。**
>
> **第三,解法都是把验证从'过程'挪到'终点'。** 不看流水线绿不绿,看 registry 里有没有那个 tag;不看 Pod 是不是 Running,看从容器内部能不能取回自报的版本号。
>
> **所以我在这个项目上真正学到的一句话是:一个'健康的信号'如果它的失败形态也是'没信号',那它就不是一个可以依赖的信号。** 我现在判断一个监控项有没有用,会先问一句:**它坏了的话,它的表现形式是什么?** 如果答案是'跟正常一样',那它现在就是无效的。"

### 如果面试官追问"那你具体怎么防?"

> "两条,都不新,但我是真的照着做的。
>
> **一是主动构造"应该发生的信号"。** 不要让系统只在出错时说话——那你就永远只能等它说话。我那个 `sre_lab_build_info{revision}` 指标就是干这个的:它**平时就一直在说话**(我跑的是 81cc34e),于是当它**突然不说话了**,这件事本身就是故障。
>
> **二是验证走真实路径,不走那条我'能控制'的路径。** 判断 webhook 通不通,不是我去手动打一次端点(那次通了,链路是断的),是**推一次真代码,然后去看构建的触发原因是不是 `Gitea push ...`**——**如果触发原因显示的是'Started by user',那说明是我手动点的,链路根本没验到。**"
