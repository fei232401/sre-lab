# 发布与回滚运行手册

> 回答四个问题:**谁触发**、**制品怎么来的**、**怎么证明部署成功**、**出事怎么退回去**。
>
> 完整演练过程与证据见 `01_排障记录/M4_发布回滚演练.md`。

---

## 一、先分清两条路

| | 命令式(不要用) | 声明式(本手册) |
|---|---|---|
| 怎么发布 | `kubectl set image deploy/... image=xxx` | 改 Git 里的清单,让 ArgoCD 收敛 |
| 怎么回滚 | `kubectl rollout undo` | `git revert` 那次 bump 提交 |
| 谁能知道 | 只有动手的人 | Git 里有记录 |
| 会不会被拉回 | — | **会被 ArgoCD 秒级拉回** |

> **GitOps 下的铁律:手工 `kubectl` 改动是"无效动作"。** 实测:手工 `set image` 改成别的 tag,**t+5s 就被拉回**。ArgoCD 对**它管理的资源**有 watch,3 分钟只是兜底的全量对账。
>
> 所以在排障时看到"我明明改了啊",先问一句:**这个资源归 ArgoCD 管吗?**

## 二、一次标准发布

### 触发
推送到 **Gitea**(`http://127.0.0.1:3001/fei232401/sre-lab.git`),webhook 会通知 Jenkins。

> ⚠️ **不是 GitHub。** `origin`(GitHub)只是对外镜像,CI 环路走的是 Gitea。

### 流水线做了什么(`ci/Jenkinsfile`)

```
Checkout → Trigger Guard → Resolve Tag → Lint → Build → Push → Verify In Registry → Update GitOps
```

| 阶段 | 要点 |
|---|---|
| Trigger Guard | 本次提交**没触及** `ci/` 或 `03-ollama-exporter/` 就直接早退(见第四节) |
| Resolve Tag | 镜像 tag = **源码仓 7 位提交哈希**(`git rev-parse --short=7 HEAD`) |
| Build | `buildah bud`,并注入 `--build-arg GIT_SHA=${SHORT_SHA}` |
| Verify In Registry | 回读 registry 的 tags 列表,确认镜像**真的登记上了** |
| Update GitOps | `sed` 改清单里的 image → commit → push(带 3 次重试 + rebase 重放) |

### 观测点(发布后逐条确认)

```bash
# 1) 声明侧:Gitea main 是否前进
curl -s http://127.0.0.1:3001/api/v1/repos/fei232401/sre-lab/branches/main

# 2) 收敛侧:ArgoCD 认到的 revision
kubectl --context k3d-ai-cluster -n argocd get application monitoring-app \
  -o jsonpath='{.status.sync.revision}{"\n"}'

# 3) 运行侧:Pod 实际用的镜像
kubectl --context k3d-ai-cluster -n ai-platform get pods --no-headers | grep ollama-exporter
kubectl --context k3d-ai-cluster -n ai-platform get pods \
  -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.containers[0].image}{"\n"}{end}' | grep ollama-exporter

# 4) 行为侧:让程序自己报版本(见第三节)
```

**收敛耗时**:约 1–2 分钟,取决于 ArgoCD 3 分钟轮询的相位。

## 三、怎么证明"跑的是新版本"

exporter 暴露:

```
sre_lab_build_info{revision="a14ce79"} 1
```

版本号是**构建期**注入的(`--build-arg GIT_SHA`),因此**镜像内容本身携带版本**,换个 env 并不会"变成"另一个版本。

取值方式(**容器里没有 `wget`/`curl`,用 python**):

```bash
POD=$(kubectl --context k3d-ai-cluster -n ai-platform get pods --no-headers | grep ollama-exporter | awk '{print $1}')
kubectl --context k3d-ai-cluster -n ai-platform exec $POD -- python -c "
import urllib.request
t = urllib.request.urlopen('http://127.0.0.1:9101/metrics', timeout=10).read().decode()
print([l for l in t.splitlines() if 'build_info' in l])"
```

**为什么要这一步**:Pod 上的 tag 只能证明"调度器让它跑这个 tag",不能证明**它真的起来了**、更不能证明**镜像内容对**。指标是从容器内部经真实数据面取回来的。

## 四、回滚

### 正确做法:改声明

```bash
cd ~/projects/sre-lab
git fetch gitea main && git merge --ff-only gitea/main      # 先对齐 CI 写回的提交
git revert --no-edit <bump-commit>                          # 例:ci: bump ollama-exporter to a14ce79
git push <gitea-url> HEAD:main
```

然后**等 ArgoCD 收敛**(1–2 分钟),再按第三节采行为证据。

- ✅ 用 `git revert`,**不要** force push:历史保留,谁在什么时候退的、为什么退的,可追溯
- ✅ 回滚后证据应表现为"**新指标消失**"(旧镜像没有这个能力)——这是结构性差异,比"值变回去了"更硬
- ❌ 不要 `kubectl rollout undo`、不要 `set image`:会被 ArgoCD 拉回,而且**你会在日志里看到自己白忙一场**

### 应急:真的要绕过 ArgoCD 时

只能临时关掉该 Application 的自动同步(`kubectl -n argocd patch app ...`),**并且必须知道这是一次例外**,事后要么把改动补进 Git、要么把 auto-sync 打开。手册不推荐这条路,列出来只是为了在真出事时别乱。

## 五、触发方式(webhook)

**为什么不用轮询**:轮询需要"上一次构建的工作区"来计算变更路径,而构建 agent 是**即用即销的 Pod**——轮询运行的那一刻那个节点必然已不存在,于是每次都 `Took 0-2 ms` 直接返回 `No changes`,**不报错、不告警**。详见 `06_踩坑记录.md` 的 P18。

现状:**Gitea push → webhook → Jenkins**。

| 项 | 值 |
|---|---|
| 端点 | `/generic-webhook-trigger/invoke`(由 `generic-webhook-trigger` 插件提供) |
| 令牌 | Jenkins 凭据 `gitea-webhook-token`(值不入 Git) |
| Jenkins 入口 | NodePort `30080`(`http://172.18.0.5:30080`,Gitea 容器按节点容器名可达) |

> ⚠️ **已知偏差**:Gitea 侧的 webhook 配置**不在 Git 里**。集群重建后需要手动补(或用 API 重建,命令见本节末)。这是本环境唯一一处"配置不在版本控制内"的地方,如实记录,不假装它是 IaC。

**自激循环的防护**:webhook 不认路径,所以 CI 自己写回配置仓的那次提交**也会触发一次**流水线;由 **Trigger Guard** 认出"本次只改了 `sre-lab-gitops/`"并早退——循环**只走两步就停**,而不是无限。见第四节。

## 六、Trigger Guard(为什么需要它)

```groovy
def changed = git diff --name-only HEAD~1 HEAD
relevant  = changed 里是否有 ci/ 或 03-ollama-exporter/ 开头的文件
```

- **命中** → 继续构建
- **不命中** → `env.SHOULD_BUILD=false`,后续 stage 全部 `when { expression { env.SHOULD_BUILD == 'true' } }` 跳过
- **无法比对**(比如首个提交)→ **照常构建**(fail-open)

> **为什么 fail-open**:漏构建比多构建风险大;而且我们刚刚才被"静默跳过"坑过一次。
>
> **已知简化**:只比对 `HEAD~1..HEAD`,即**只看最后一次提交**。推送多个提交时,若最后一个提交不触及构建路径、前面的触及,会被漏掉。生产做法是与"上一次构建的 revision"比对,本环境从简。**这是一个已知边界,面试被问到要主动说。**

## 七、故障速查

| 症状 | 先查什么 |
|---|---|
| 推了代码但没构建 | webhook 是否还在(Gitea 仓库设置页的 Recent Deliveries);Jenkins 是否可达 |
| 构建成功但集群没变 | ArgoCD 的 `sync.revision` 前进没有;清单里的 image 改没改 |
| 手工改了镜像又被还原 | 正常——ArgoCD selfHeal,见第一节 |
| 部署了但"看起来没变" | 用第三节的指标证明,别只看 tag |
| 循环构建 | Trigger Guard 是否失效;CI 写回是否被误判成构建路径 |
| Jenkins 起不来 | init 容器在重下插件,**分钟级**,先等(见 `03_Jenkins_运行手册.md` 第四节) |
