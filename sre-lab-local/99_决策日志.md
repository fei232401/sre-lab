# 决策日志(ADR)

> **这是什么**:ADR = Architecture Decision Record,架构决策记录。工程界真实存在的实践——**每个重要技术决策都留下一份"当时有哪些选项、为什么选这个"的记录**。
>
> **为什么要有它**:
> 1. 三个月后你会忘记为什么这么选,只剩"当时好像是这么定的"
> 2. 面试官问"你为什么选 X 不选 Y",翻这篇就有答案
> 3. 写 ADR 这个习惯本身就是加分项——大部分应届生没有
>
> **格式**:每条决策记录 背景 / 考虑过的选项 / 决定 / 理由 / 后果与代价 / 何时应该重新评估

## D1:CI 引擎选 Jenkins

- **日期**:2026-09-15(v1 曾选 GitHub Actions,v2 推翻)
- **状态**:✅ 已决定

### 背景

需要为「游戏运维工程师」岗位搭建可实操的 CI 流水线。本机无任何 CI 组件。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **GitHub Actions(托管)** | 零搭建,与仓库天然集成 | 企业内网/私有部署场景覆盖不到;面试官可能觉得"没自己搭过" |
| **GitHub Actions + self-hosted runner** | 兼顾:写 workflow(CI 能力)+ 维护 runner(运维能力) | 国内游戏行业实际很少用 |
| **Jenkins on K8s** | 国内游戏/传统企业事实标准,K8s Plugin 动态 agent 是生产标准姿势;官方 Helm Chart 一条命令即起 | 引入成本(约 +0.5 天);内存占用 |
| **GitLab CE 自建** | 全家桶 | 单体吃 4-6G 内存,与监控栈抢资源 |
| **Tekton** | K8s 原生,CNCF,与 ArgoCD 同生态 | 学习曲线陡,面试官未必熟 |
| **Drone / Woodpecker** | 轻量 | 社区活跃度下降,不投入 |

### 决定

**Jenkins on K8s(官方 Helm Chart)+ Kubernetes Plugin 动态 agent。**

### 理由

1. **岗位对口**:国内游戏行业 Jenkins 是事实标准,用户本人判断"真实环境绕不开",这是准确的
2. **一次拿下两个面试维度**:写 Jenkinsfile 是 CI 能力;维护 Jenkins 本体(controller 单点、agent 资源隔离、构建缓存)是运维能力
3. **动态 agent 是核心价值**:每次构建起一个 Pod,用完销毁——构建环境隔离、不用常驻一堆 agent 机器

### ⚠️ 被推翻的错误判断(v1 → v2)

**v1 否决 Jenkins 的理由是"Jenkins + ArgoCD = 两套 CD 混乱"——这个理由是错的。**

正确认知:**Jenkins 做 CI(构建/测试),ArgoCD 做 CD(部署),这是标准分工,不是重叠。** 只要 Jenkins 不碰部署,就没有任何冲突。

**教训**:否决一个方案的"理由"本身需要被审视。理由站不住,结论就要重来。

### 后果与代价

- 工期 +0.5 天(M3 从 1 天 → 1.5 天)
- 本机内存压力增加(约 1-1.5 GB),需要停掉闲置的 `k3d-ew-cluster`
- 新增一个待掌握的知识面:Jenkinsfile 语法、Kubernetes Plugin、agent Pod 模板

### 何时重新评估

如果本机内存实在吃紧,退路是:Jenkins 跑在宿主机 docker(而非集群内),省掉 controller 的集群内开销。

## D2:CD 引擎与同步策略

- **日期**:2026-09-15 提出,2026-09-16 细化
- **状态**:✅ 已决定(含一处修正)

### 背景

用户对 ArgoCD 有负面体验:

> "之前开了 synced,很多改了的配置没有 git commit 都被应用失败,导致让我对他没什么好感。一旦用它管理 apps,所有修改都要走 git,个人开发环境我觉得比较麻烦,要么是不开 auto synced,要么换个方案。"

备选疑问:"Jenkins 本身不就能 CD 吗?"

### 诊断

用户遇到的现象**不是 ArgoCD 故障,是 `selfHeal: true` 在正确工作**——手动改的配置被自动纠正回 Git 版本。用户当年大概率把三个开关(`auto-sync` / `selfHeal` / `prune`)全开了。

详见 `05_学习笔记/01_ArgoCD到底是什么.md`。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| 保留 ArgoCD,关掉 auto-sync | 不烦了 | 失去 GitOps 的便利性(每次都要手动点同步) |
| 换回 Jenkins push CD | 简单,已会 | 丢失漂移检测;凭证风险;少一个高价值面试素材 |
| **保留 ArgoCD + 按应用性质分级配置同步策略** | ✅ 兼顾 | 需要理解三个开关的作用 |
| 两个都做,做对照实验 | 素材最全 | +0.5 天 |

### 决定

1. **保留 ArgoCD 作为 CD 主线**
2. **同步策略按应用性质分级**:
   - 基础设施类(monitoring / jenkins / argocd 自身):`selfHeal: true` — 防漂移 = 保命
   - 开发中的应用(game-server):`selfHeal: false` + `prune: false` — 允许手动调试
3. **先做一组对照实验再固定配置**(全关 → 开 selfHeal → 开 prune,观察行为差异)
4. **额外做一条 Jenkins push CD 作为对照组**,同一次发布两条路都跑

### 理由

1. **用户的痛点是真实的,但不是 ArgoCD 的必然**——是配置问题,有第三条路
2. **"开发环境半开 / 生产环境全开"的配置差异本身是高价值面试素材**——大多数候选人答不上"GitOps 在个人环境不麻烦吗"这个问题
3. **push vs pull 对照实验直接回答"Jenkins 能不能 CD"**,这是面试必问

### 后果与代价

- M1 需要增加对照实验环节
- M3 Jenkinsfile 需要加一个 push 部署的 stage(约 +0.5 天)

### 何时重新评估

无。这是本设计里最"生产对齐"的一块。

## D3:镜像构建方式(Buildah rootless)

- **日期**:2026-09-16
- **状态**:✅ 已决定

### 背景

Jenkins agent 是动态 Pod,**在 Pod 里怎么构建容器镜像**?这是 Jenkins on K8s 最经典的坑。

### 考虑过的选项

| 选项 | 安全性 | 复杂度 | 说明 |
|---|---|---|---|
| 挂载宿主机 `docker.sock` | ❌ **极差** | 最低 | 等于把宿主机 root 权限交给构建容器 |
| DinD(docker-in-docker) | ❌ 差 | 中 | 需要 `privileged` |
| **Buildah(rootless)** | ✅ 好 | 中 | CNCF Sandbox(2025-01 加入),daemonless + rootless 优先 |
| BuildKit / buildx | ✅ 好 | 中 | 构建性能最好,缓存强;rootless 部分环境受限 |
| ~~Kaniko~~ | — | — | ⚠️ **2025 年 6 月已被 Google 归档**,不再维护,新项目不应选 |

### 决定

**Buildah rootless。**

### 理由

1. **不挂 docker.sock**——生产大忌,写进 runbook 当反面教材
2. Buildah 被 GitLab 等主流平台推荐为 Kaniko 的替代(2025 年社区共识)
3. 契合 K8s Job 模型:起 Pod → 构建 → 推送 → 退出

### 后续影响

- 需要研究 Buildah 在 Pod 内的运行配置(`--storage-driver vfs --isolation chroot`)
- "为什么不能挂 docker.sock"作为面试素材写进 runbook

## D4:改造存量集群 vs 清场重建

- **日期**:2026-09-15
- **状态**:✅ 已决定

### 背景

本机有一个运行 43 天的 `k3d-ai-cluster`,其中 `ai-platform` 命名空间有 6 个异常 Pod(vllm-3b 全烂),各组件重启 6~24 次。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 清场重建 | 干净、可重复、一条命令起环境 | 丢掉真实的脏数据;**没有真故障素材** |
| B. 改造存量 | 有真实故障可排障;复用已有监控栈省半天 | 集群脏,需要纪律 |
| C. 双集群全做 | 两个故事都有 | 工作量翻倍 |

### 决定

**B — 改造存量**,把 A 的脚本化作为 M5 收尾产出。

### 理由

**面试官想听的"运维"不是"我搭了个新东西",而是"线上出事了我怎么定位和恢复"。**

本机躺着一个 43 天没人管、Pod 重启 24 次、vllm 全烂的集群——这是白送的、**真实的**排障素材。

### 佐证:盘点已挖出三个真问题

1. `helm list -A` 返回空 → 根因是 **kubeconfig context 错配**(Helm 一直在查另一个集群)
2. **M1 其实是两件事**:monitoring/kube-system 由 Helm 管理,ai-platform 由手工 `kubectl apply` 管理——**两套接管策略**
3. PushPlus token 明文硬编码在公开仓库

→ **"M0 可能没料"的风险已显著降低。**

### 翻车预案

如果 M0 诊断下来发现故障确实平淡(如仅因 WSL 无 GPU 导致 vllm 起不来),**如实告知用户并立即转 A**,不硬凑素材。

## D6:M1 处理存量 GitOps 结构的方式

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 发现 5

### 背景

M0 盘点发现 `sre-lab-gitops/production/` 下有 **31 个文件**,最后提交于 **2026-06-29**,集群里**一个对象都没部署**。包括完整的 App-of-Apps bootstrap、Loki/Promtail/sealed-secrets 清单,以及两个专门解决 k3s 告警假阳性的补丁。

同时存在一个结构性问题:**同一份内容有四份副本**。

```
sre-lab-gitops/manifests/monitoring-stack/wechat-adapter.yaml
sre-lab-gitops/production/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/environments/prod/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/wechat-adapter.yaml
```

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 审计后修复复用** | 省时间;能对照"当时思路错在哪",本身是排障素材 | 需要先花时间审计 |
| B. 清掉重写 | 干净、口径统一 | +0.5 天;丢掉 6/29 的思路 |
| C. 先只接管 monitoring | 风险最低 | 丢失 GitOps"纳管全部"的价值;面试故事弱 |

### 决定

**A — 审计后修复复用。**

### 理由

1. **"已有的不等于正确的"**——6/29 那一版显然卡在某一步没走完。**搞清楚它为什么没走完,比重新写一遍有价值**:这正是运维岗最核心的能力(接手别人的烂摊子并理清)
2. **那套结构里有真东西**:App-of-Apps 的 bootstrap 骨架、k3s 假阳性补丁、Sealed Secrets 模板——重写等于把已有的思考扔掉
3. **面试素材**:"我接手了一个半年前同事留下的 GitOps 目录,发现它有四份重复副本,我先做的不是部署而是理清哪份是真相来源"——这比"我从零搭了套 ArgoCD"更接近真实工作

### 必须先解决的两件事

1. **四份重复目录 → 定出唯一真相来源**
2. **`root-app.yaml` 开着 `prune: true` + `selfHeal: true`,且指向 `bootstrap/` 目录**——一旦部署会创建 6 个子 Application,**部署前必须 dry-run**

### 对 `k3s-alert-patches.yaml` 的评价

原文用一条同名 `PrometheusRule` 覆盖默认规则,表达式写成:

```promql
absent(up{job="kube-proxy", namespace="k3s-does-not-have-kube-proxy"} == 1)
```

**靠一个不存在的 namespace 让规则永远为 false。** 注释里自称"降维打击"。

**这能工作,但手法值得商榷。** 问题不在于能否工作,在于**读者需要理解"为什么这个 namespace 不存在"才能看懂它在干什么**——这是典型的"聪明但不可维护"。

**更干净的路径**:在 Helm values 里直接关掉对应的 rule group。kube-prometheus-stack 的 values 支持逐条启用/禁用默认规则。

**留待 M1 拍板。**

### 后果与代价

- M1 工期 +0.5 天(审计)
- 需要用户在若干拍板点确认

## D7:内存硬约束的解法

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 发现 6

### 背景

```
agent-0   6.499GiB / 8GiB   81%  ← 唯一有 GPU,被监控栈(Prometheus)占满
agent-1   871MiB  / 8GiB   11%  ← 几乎空着
ew-cluster 746MiB               ← 闲置(项目二,已暂缓)
```

**加 Jenkins(~1-1.5G)+ ArgoCD(~0.5G)会顶爆 agent-0。**

### 考虑过的选项

| 选项 | 收益 | 代价 |
|---|---|---|
| **A. 停 ew-cluster + nodeSelector 钉 agent-1** | 避开瓶颈,零重建 | 需要验证 agent-0 负载是否需重新平衡 |
| B. 停 ew-cluster + 提高 agent-0 上限到 12G | 直接扩容 | **需重建集群容器 → 丢 43 天真实状态** |
| C. 两个都做 | 最保险 | 同样触发重建 |

### 决定

**A。**

### 理由

1. **B/C 会推翻 D4。** D4 明确决定"改造存量",M0 又刚刚证明那批脏数据(6 个僵尸 Pod、43 天监控历史)就是核心排障素材。**为了省事重建集群,等于把 M0 的最大产出扔掉**
2. **瓶颈根本不是"总量不够",是"分布不均"。** agent-1 空着 7G,ArgoCD 和 Jenkins **本来就不需要 GPU**,没有任何理由跑在 agent-0 上
3. **nodeSelector 是生产标准姿势**:按资源特征给工作负载选节点。这本身就是面试点

### 实施

1. `k3d cluster stop ew-cluster`
2. ArgoCD / Jenkins 的清单加 `nodeSelector: {kubernetes.io/hostname: k3d-ai-cluster-agent-1}`

### 何时重新评估

如果 agent-1 也逼近上限——那时说明 WSL 的 19G 总量真的不够,需要减少组件或换机器。

## D8:PushPlus token 泄露的处理

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 安全发现

### 背景

M0 实测:明文 token 在**公开仓库**的 **4 个文件**、**3 个 commit** 里。

```
sre-lab-gitops/manifests/monitoring-stack/wechat-adapter.yaml
sre-lab-gitops/production/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/environments/prod/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/wechat-adapter.yaml
```

**关键缓解因素:这个 adapter 从未部署**(集群里 0 个对象),所以没有正在运行的服务因此受影响,也没有服务中断风险。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 吊销 + Sealed Secrets,不清历史** | 零风险,代价小;旧 token 失效后留在历史里无害 | 历史里仍能看到失效 token |
| B. A + `git filter-repo` 重写历史 | 彻底干净 | 所有 commit hash 重写;需临时关分支保护;公开仓库强推有风险窗口 |
| C. 先记待办,M2 再处理 | 现在省事 | 期间 token 持续公开 |

### 决定

**A。**

### 理由

1. **凭证安全的第一原则是"让它失效",不是"让它看不见"。** 吊销之后,历史里那串字符就是一个无意义的字符串
2. **B 的代价与收益不成比例**。重写公开仓库的 3 个历史 commit,风险(强推失败、协作者混乱)大于收益
3. **C 不可接受**:token 虽然危害有限(能被用来给别人发消息),但"已发现却不处理"在安全上是不可辩护的

### 实施(有严格顺序)

1. **用户**登录 pushplus 后台吊销旧 token
2. **用户**生成新 token(**不要告诉我**,也不写进任何文件)
3. 部署 sealed-secrets controller
4. **用户**用 `kubeseal` 把新 token 加密成 `SealedSecret`
5. 删除 4 个明文文件
6. M2 的告警通道改为消费这个 Secret

### 教训(写进 runbook)

**这次泄露的形态本身值得记录**:token 不是"不小心提交的",而是**被硬编码进一个 shell heredoc,再被复制成四份**。原始设计就有问题:

```yaml
image: python:3.9-slim
args:
- |
  pip install flask requests
  cat << 'PYEOF' > /app.py
  PUSHPLUS_TOKEN = "28eae0..."
```

**三个问题叠加**:
1. **凭证硬编码进清单** — 清单是要进 Git 的,凭证不是
2. **启动时 `pip install`** — 依赖互联网、无版本锁定、Pod 重启就重装一遍
3. **内容重复四份** — 一份泄露 = 四份泄露

**正确姿势**:凭证走 Secret(再经 Sealed Secrets 加密),adapter 打成不可变镜像。

## D9:ollama 的 GitOps 定义与现场冲突的解法

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M1 审计雷 1

### 背景

| | GitOps 定义 | 集群现状 |
|---|---|---|
| 工作负载 | `StatefulSet/ollama` | `Deployment/ollama` |
| Service | `Service/ollama-service` ← **同名** | `Service/ollama-service` |
| Service | `Service/ollama-headless` | (无) |
| selector | `app: ollama` | `app: ollama` |

ArgoCD 会接管同名 Service,同时新建 StatefulSet。两边 Pod 都带 `app: ollama` → **一个 Service 选中两套 Pod**。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 改 GitOps 对齐现场** | 零风险,不碰生产 | GitOps 里少一个 StatefulSet 教学点 |
| B. 迁移到 StatefulSet | 有状态服务理论上更适合 | 需停机、重挂 PVC、过渡期双跑(agent-0 已 82%) |
| C. 暂不纳入接管 | 最安全 | GitOps 覆盖不全,面试故事弱 |

### 决定

**A。**

### 理由

1. **接管存量系统的第一原则:让 Git 描述现实,而不是让现实服从 Git。**

   集群里的 Deployment 已经稳定跑了 43 天,是**事实**;GitOps 里的 StatefulSet 从未部署过,是**设想**。用一个未经验证的设想,去替换一个稳定运行的事实,**方向和风险都反了**。

2. **顺序不能颠倒**:先接管(建立可见性和漂移检测)→ 稳定之后再谈迁移。一开始就"顺手把它改对",等于在一次变更里同时做两件事——**出问题无法归因**。

3. **这本身就是高价值面试点**:面试官问"接管存量时清单和现状不一致怎么办",能答出"先让 Git 对齐现实"的人不多,大多数人会本能地说"以 Git 为准"。

### 实施

`production/apps/ai-platform/ollama-stack.yaml`:

- `StatefulSet/ollama` → `Deployment/ollama`,字段对齐集群现状(副本数、镜像、资源、探针、selector)
- 删除 `Service/ollama-headless`(集群里不存在,也没有消费者)
- 保留 `Service/ollama-service`,确保 selector 为 `app: ollama`

### 何时重新评估

接管稳定、有了漂移检测之后,可以**单独**评估"Deployment → StatefulSet"的迁移,作为一次**独立的、可回滚的**变更。

### 副作用

`volumes` / `volumeClaimTemplates` 的差异需要逐项核对——Deployment 用的是 PVC + volumes,StatefulSet 用 `volumeClaimTemplates`。

## D10:Namespace 资源的接管方式

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M1 审计雷 2

### 背景

`apps/ai-platform/namespace.yaml` 声明了 `Namespace/ai-platform`,而 `ai-platform-app` 的 `syncPolicy` 是 `prune: true` + `selfHeal: true`。

**后果**:命名空间本身成了被 ArgoCD 管理的资源。一旦 `namespace.yaml` 从 Git 移除或改名,**ArgoCD 会 prune 掉整个 `ai-platform` 命名空间,连同里面所有工作负载和 PVC。**

### 决定

**从清单里删除 `namespace.yaml`,改用 ArgoCD 的 `CreateNamespace=true`。**

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

### 理由

1. **声明式工具管"存在性",但不该管"删除边界"。**

   `Namespace` 是 cluster-scoped 的删除边界。把它交给 `prune: true`,等于在仓库里放一个"删一行 YAML 就删库"的开关。**声明式的价值是让期望状态可见,而不是让破坏性操作变得更容易触发。**

2. **这是 ArgoCD 官方推荐做法。** `CreateNamespace=true` 的设计意图正是:命名空间由 ArgoCD **按需创建**,但不纳入生命周期管理。

3. **`Destructive: prune` 的危险不在"它会不会删",在"它删的时候你不在场"。** 命名空间级联删除是不可逆的,且有几十秒的延迟——等你发现,已经来不及。

### 实施

- 删除 `production/apps/ai-platform/namespace.yaml`
- 在 `ai-platform-app.yaml` 的 `syncPolicy.syncOptions` 加 `CreateNamespace=true`
- 同样检查其余 5 个子 Application 的 `CreateNamespace` 配置

### 附带修正

其余子 Application(monitoring / loki / promtail / nginx-demo / sealed-secrets)的目标命名空间同样需要 `CreateNamespace=true`,否则首次同步会失败。
