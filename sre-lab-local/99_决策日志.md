# 决策日志(ADR)

> **这是什么**:ADR = Architecture Decision Record,架构决策记录。工程界真实存在的实践——**每个重要技术决策都留下一份"当时有哪些选项、为什么选这个"的记录**。
>
> **为什么要有它**:
> 1. 三个月后你会忘记为什么这么选,只剩"当时好像是这么定的"
> 2. 面试官问"你为什么选 X 不选 Y",翻这篇就有答案
> 3. 写 ADR 这个习惯本身就是加分项——大部分应届生没有
>
> **格式**:每条决策记录 背景 / 考虑过的选项 / 决定 / 理由 / 后果与代价 / 何时应该重新评估

---

## D1:CI 引擎选 Jenkins

- **日期**:2026-09-15(v1 曾选 GitHub Actions,v2 推翻)
- **状态**:✅ 已决定

### 背景

需要为「游戏运维工程师」岗位搭建可实操的 CI 流水线。本机无任何 CI 组件。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **GitHub Actions(托管)** | 零搭建,与仓库天然集成 | 企业内网/私有部署场景覆盖不到;面试官可能觉得"没自己搭过" |
| **GitHub Actions + self-hosted runner** | 兼顾:写 workflow(CI 能力)+ 维护 runner(运维能力) | 国内游戏行业实际很少用 |
| **Jenkins on K8s** | 国内游戏/传统企业事实标准,K8s Plugin 动态 agent 是生产标准姿势;官方 Helm Chart 一条命令即起 | 引入成本(约 +0.5 天);内存占用 |
| **GitLab CE 自建** | 全家桶 | 单体吃 4-6G 内存,与监控栈抢资源 |
| **Tekton** | K8s 原生,CNCF,与 ArgoCD 同生态 | 学习曲线陡,面试官未必熟 |
| **Drone / Woodpecker** | 轻量 | 社区活跃度下降,不投入 |

### 决定

**Jenkins on K8s(官方 Helm Chart)+ Kubernetes Plugin 动态 agent。**

### 理由

1. **岗位对口**:国内游戏行业 Jenkins 是事实标准,用户本人判断"真实环境绕不开",这是准确的
2. **一次拿下两个面试维度**:写 Jenkinsfile 是 CI 能力;维护 Jenkins 本体(controller 单点、agent 资源隔离、构建缓存)是运维能力
3. **动态 agent 是核心价值**:每次构建起一个 Pod,用完销毁——构建环境隔离、不用常驻一堆 agent 机器

### ⚠️ 被推翻的错误判断(v1 → v2)

**v1 否决 Jenkins 的理由是"Jenkins + ArgoCD = 两套 CD 混乱"——这个理由是错的。**

正确认知:**Jenkins 做 CI(构建/测试),ArgoCD 做 CD(部署),这是标准分工,不是重叠。** 只要 Jenkins 不碰部署,就没有任何冲突。

**教训**:否决一个方案的"理由"本身需要被审视。理由站不住,结论就要重来。

### 后果与代价

- 工期 +0.5 天(M3 从 1 天 → 1.5 天)
- 本机内存压力增加(约 1-1.5 GB),需要停掉闲置的 `k3d-ew-cluster`
- 新增一个待掌握的知识面:Jenkinsfile 语法、Kubernetes Plugin、agent Pod 模板

### 何时重新评估

如果本机内存实在吃紧,退路是:Jenkins 跑在宿主机 docker(而非集群内),省掉 controller 的集群内开销。

## D2:CD 引擎与同步策略

- **日期**:2026-09-15 提出,2026-09-16 细化
- **状态**:✅ 已决定(含一处修正)

### 背景

用户对 ArgoCD 有负面体验:

> "之前开了 synced,很多改了的配置没有 git commit 都被应用失败,导致让我对他没什么好感。一旦用它管理 apps,所有修改都要走 git,个人开发环境我觉得比较麻烦,要么是不开 auto synced,要么换个方案。"

备选疑问:"Jenkins 本身不就能 CD 吗?"

### 诊断

用户遇到的现象**不是 ArgoCD 故障,是 `selfHeal: true` 在正确工作**——手动改的配置被自动纠正回 Git 版本。用户当年大概率把三个开关(`auto-sync` / `selfHeal` / `prune`)全开了。

详见 `05_学习笔记/01_ArgoCD到底是什么.md`。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| 保留 ArgoCD,关掉 auto-sync | 不烦了 | 失去 GitOps 的便利性(每次都要手动点同步) |
| 换回 Jenkins push CD | 简单,已会 | 丢失漂移检测;凭证风险;少一个高价值面试素材 |
| **保留 ArgoCD + 按应用性质分级配置同步策略** | ✅ 兼顾 | 需要理解三个开关的作用 |
| 两个都做,做对照实验 | 素材最全 | +0.5 天 |

### 决定

1. **保留 ArgoCD 作为 CD 主线**
2. **同步策略按应用性质分级**:
   - 基础设施类(monitoring / jenkins / argocd 自身):`selfHeal: true` — 防漂移 = 保命
   - 开发中的应用(game-server):`selfHeal: false` + `prune: false` — 允许手动调试
3. **先做一组对照实验再固定配置**(全关 → 开 selfHeal → 开 prune,观察行为差异)
4. **额外做一条 Jenkins push CD 作为对照组**,同一次发布两条路都跑

### 理由

1. **用户的痛点是真实的,但不是 ArgoCD 的必然**——是配置问题,有第三条路
2. **"开发环境半开 / 生产环境全开"的配置差异本身是高价值面试素材**——大多数候选人答不上"GitOps 在个人环境不麻烦吗"这个问题
3. **push vs pull 对照实验直接回答"Jenkins 能不能 CD"**,这是面试必问

### 后果与代价

- M1 需要增加对照实验环节
- M3 Jenkinsfile 需要加一个 push 部署的 stage(约 +0.5 天)

### 何时重新评估

无。这是本设计里最"生产对齐"的一块。

## D3:镜像构建方式(Buildah rootless)

- **日期**:2026-09-16
- **状态**:✅ 已决定

### 背景

Jenkins agent 是动态 Pod,**在 Pod 里怎么构建容器镜像**?这是 Jenkins on K8s 最经典的坑。

### 考虑过的选项

| 选项 | 安全性 | 复杂度 | 说明 |
|---|---|---|---|
| 挂载宿主机 `docker.sock` | ❌ **极差** | 最低 | 等于把宿主机 root 权限交给构建容器 |
| DinD(docker-in-docker) | ❌ 差 | 中 | 需要 `privileged` |
| **Buildah(rootless)** | ✅ 好 | 中 | CNCF Sandbox(2025-01 加入),daemonless + rootless 优先 |
| BuildKit / buildx | ✅ 好 | 中 | 构建性能最好,缓存强;rootless 部分环境受限 |
| ~~Kaniko~~ | — | — | ⚠️ **2025 年 6 月已被 Google 归档**,不再维护,新项目不应选 |

### 决定

**Buildah rootless。**

### 理由

1. **不挂 docker.sock**——生产大忌,写进 runbook 当反面教材
2. Buildah 被 GitLab 等主流平台推荐为 Kaniko 的替代(2025 年社区共识)
3. 契合 K8s Job 模型:起 Pod → 构建 → 推送 → 退出

### 后续影响

- 需要研究 Buildah 在 Pod 内的运行配置(`--storage-driver vfs --isolation chroot`)
- "为什么不能挂 docker.sock"作为面试素材写进 runbook

## D4:改造存量集群 vs 清场重建

- **日期**:2026-09-15
- **状态**:✅ 已决定

### 背景

本机有一个运行 43 天的 `k3d-ai-cluster`,其中 `ai-platform` 命名空间有 6 个异常 Pod(vllm-3b 全烂),各组件重启 6~24 次。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 清场重建 | 干净、可重复、一条命令起环境 | 丢掉真实的脏数据;**没有真故障素材** |
| B. 改造存量 | 有真实故障可排障;复用已有监控栈省半天 | 集群脏,需要纪律 |
| C. 双集群全做 | 两个故事都有 | 工作量翻倍 |

### 决定

**B — 改造存量**,把 A 的脚本化作为 M5 收尾产出。

### 理由

**面试官想听的"运维"不是"我搭了个新东西",而是"线上出事了我怎么定位和恢复"。**

本机躺着一个 43 天没人管、Pod 重启 24 次、vllm 全烂的集群——这是白送的、**真实的**排障素材。

### 佐证:盘点已挖出三个真问题

1. `helm list -A` 返回空 → 根因是 **kubeconfig context 错配**(Helm 一直在查另一个集群)
2. **M1 其实是两件事**:monitoring/kube-system 由 Helm 管理,ai-platform 由手工 `kubectl apply` 管理——**两套接管策略**
3. PushPlus token 明文硬编码在公开仓库

→ **"M0 可能没料"的风险已显著降低。**

### 翻车预案

如果 M0 诊断下来发现故障确实平淡(如仅因 WSL 无 GPU 导致 vllm 起不来),**如实告知用户并立即转 A**,不硬凑素材。

## D6:M1 处理存量 GitOps 结构的方式

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 发现 5

### 背景

M0 盘点发现 `sre-lab-gitops/production/` 下有 **31 个文件**,最后提交于 **2026-06-29**,集群里**一个对象都没部署**。包括完整的 App-of-Apps bootstrap、Loki/Promtail/sealed-secrets 清单,以及两个专门解决 k3s 告警假阳性的补丁。

同时存在一个结构性问题:**同一份内容有四份副本**。

```
sre-lab-gitops/manifests/monitoring-stack/wechat-adapter.yaml
sre-lab-gitops/production/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/environments/prod/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/wechat-adapter.yaml
```

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 审计后修复复用** | 省时间;能对照"当时思路错在哪",本身是排障素材 | 需要先花时间审计 |
| B. 清掉重写 | 干净、口径统一 | +0.5 天;丢掉 6/29 的思路 |
| C. 先只接管 monitoring | 风险最低 | 丢失 GitOps"纳管全部"的价值;面试故事弱 |

### 决定

**A — 审计后修复复用。**

### 理由

1. **"已有的不等于正确的"**——6/29 那一版显然卡在某一步没走完。**搞清楚它为什么没走完,比重新写一遍有价值**:这正是运维岗最核心的能力(接手别人的烂摊子并理清)
2. **那套结构里有真东西**:App-of-Apps 的 bootstrap 骨架、k3s 假阳性补丁、Sealed Secrets 模板——重写等于把已有的思考扔掉
3. **面试素材**:"我接手了一个半年前同事留下的 GitOps 目录,发现它有四份重复副本,我先做的不是部署而是理清哪份是真相来源"——这比"我从零搭了套 ArgoCD"更接近真实工作

### 必须先解决的两件事

1. **四份重复目录 → 定出唯一真相来源**
2. **`root-app.yaml` 开着 `prune: true` + `selfHeal: true`,且指向 `bootstrap/` 目录**——一旦部署会创建 6 个子 Application,**部署前必须 dry-run**

### 对 `k3s-alert-patches.yaml` 的评价

原文用一条同名 `PrometheusRule` 覆盖默认规则,表达式写成:

```promql
absent(up{job="kube-proxy", namespace="k3s-does-not-have-kube-proxy"} == 1)
```

**靠一个不存在的 namespace 让规则永远为 false。** 注释里自称"降维打击"。

**这能工作,但手法值得商榷。** 问题不在于能否工作,在于**读者需要理解"为什么这个 namespace 不存在"才能看懂它在干什么**——这是典型的"聪明但不可维护"。

**更干净的路径**:在 Helm values 里直接关掉对应的 rule group。kube-prometheus-stack 的 values 支持逐条启用/禁用默认规则。

**留待 M1 拍板。**

### 后果与代价

- M1 工期 +0.5 天(审计)
- 需要用户在若干拍板点确认

## D7:内存硬约束的解法

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 发现 6

### 背景

```
agent-0   6.499GiB / 8GiB   81%  ← 唯一有 GPU,被监控栈(Prometheus)占满
agent-1   871MiB  / 8GiB   11%  ← 几乎空着
ew-cluster 746MiB               ← 闲置(项目二,已暂缓)
```

**加 Jenkins(~1-1.5G)+ ArgoCD(~0.5G)会顶爆 agent-0。**

### 考虑过的选项

| 选项 | 收益 | 代价 |
|---|---|---|
| **A. 停 ew-cluster + nodeSelector 钉 agent-1** | 避开瓶颈,零重建 | 需要验证 agent-0 负载是否需重新平衡 |
| B. 停 ew-cluster + 提高 agent-0 上限到 12G | 直接扩容 | **需重建集群容器 → 丢 43 天真实状态** |
| C. 两个都做 | 最保险 | 同样触发重建 |

### 决定

**A。**

### 理由

1. **B/C 会推翻 D4。** D4 明确决定"改造存量",M0 又刚刚证明那批脏数据(6 个僵尸 Pod、43 天监控历史)就是核心排障素材。**为了省事重建集群,等于把 M0 的最大产出扔掉**
2. **瓶颈根本不是"总量不够",是"分布不均"。** agent-1 空着 7G,ArgoCD 和 Jenkins **本来就不需要 GPU**,没有任何理由跑在 agent-0 上
3. **nodeSelector 是生产标准姿势**:按资源特征给工作负载选节点。这本身就是面试点

### 实施

1. `k3d cluster stop ew-cluster` ✅ **已完成**(2026-09-16,释放 ~811MB)
2. ArgoCD / Jenkins 的清单加 `nodeSelector: {node-role: cpu}`

### ⚠️ 实施中的修正(2026-09-16)

**原方案写的是 `kubernetes.io/hostname: k3d-ai-cluster-agent-1`,实施时发现应该改掉。**

排查雷 1 时读取 `Deployment/ollama` 的实际规格,发现集群**已经有现成的节点标签约定**:

| 节点 | 关键标签 | 角色 |
|---|---|---|
| `agent-0` | `nvidia.com/gpu: "true"` | GPU 节点 |
| `agent-1` | `node-role: cpu` | CPU 节点 |
| `server-0` | `node-role.kubernetes.io/control-plane: "true"` | 控制面 |

而 `Deployment/ollama` **已经在用 `nodeSelector: {node-role: cpu}`** —— 正是 D7 想做的事。

**改用 `node-role: cpu` 的三条理由**:

1. **沿用已有约定**,不引入第二套说法
2. **节点重建后名字会变,角色不会变**。k3d 集群重建时 agent 名字可能不同,"CPU 节点"这个角色是稳定的
3. 与集群里已有的工作负载保持一致

> **教训:先看现场有什么约定,再决定新增什么。** 用自己的方式解决问题不算错,但和已有写法并存就是自找混乱。

### 何时重新评估

如果 agent-1 也逼近上限——那时说明 WSL 的 19G 总量真的不够,需要减少组件或换机器。

## D8:PushPlus token 泄露的处理

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M0 安全发现

### 背景

M0 实测:明文 token 在**公开仓库**的 **4 个文件**、**3 个 commit** 里。

```
sre-lab-gitops/manifests/monitoring-stack/wechat-adapter.yaml
sre-lab-gitops/production/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/environments/prod/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/wechat-adapter.yaml
```

**关键缓解因素:这个 adapter 从未部署**(集群里 0 个对象),所以没有正在运行的服务因此受影响,也没有服务中断风险。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 吊销 + Sealed Secrets,不清历史** | 零风险,代价小;旧 token 失效后留在历史里无害 | 历史里仍能看到失效 token |
| B. A + `git filter-repo` 重写历史 | 彻底干净 | 所有 commit hash 重写;需临时关分支保护;公开仓库强推有风险窗口 |
| C. 先记待办,M2 再处理 | 现在省事 | 期间 token 持续公开 |

### 决定

**A。**

### 理由

1. **凭证安全的第一原则是"让它失效",不是"让它看不见"。** 吊销之后,历史里那串字符就是一个无意义的字符串
2. **B 的代价与收益不成比例**。重写公开仓库的 3 个历史 commit,风险(强推失败、协作者混乱)大于收益
3. **C 不可接受**:token 虽然危害有限(能被用来给别人发消息),但"已发现却不处理"在安全上是不可辩护的

### ⚠️ 修订(2026-09-16):本决定的第 1 步已被推翻

**用户否掉了"吊销"。** 理由:项目已不再使用 PushPlus,该 token 事实上已是一串死凭证,吊销它的收益为零,而且会牵出一轮多余的账号操作。

> **取代本条的决策见 D11。**
>
> 本 ADR 保留原文不删 —— **决策日志的价值在于记录"当时是怎么想的",而不是只记录最终答案。** 这里保留是为了留下一个真实的判断失误样本:我当时按"标准安全流程"给出了吊销建议,没有先问"这个凭证还在不在用"。

### 实施(有严格顺序)

## D9:ollama 的 GitOps 定义与现场冲突的解法

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M1 审计雷 1

### 背景

| | GitOps 定义 | 集群现状 |
|---|---|---|
| 工作负载 | `StatefulSet/ollama` | `Deployment/ollama` |
| Service | `Service/ollama-service` ← **同名** | `Service/ollama-service` |
| Service | `Service/ollama-headless` | (无) |
| selector | `app: ollama` | `app: ollama` |

ArgoCD 会接管同名 Service,同时新建 StatefulSet。两边 Pod 都带 `app: ollama` → **一个 Service 选中两套 Pod**。

### 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 改 GitOps 对齐现场** | 零风险,不碰生产 | GitOps 里少一个 StatefulSet 教学点 |
| B. 迁移到 StatefulSet | 有状态服务理论上更适合 | 需停机、重挂 PVC、过渡期双跑(agent-0 已 82%) |
| C. 暂不纳入接管 | 最安全 | GitOps 覆盖不全,面试故事弱 |

### 决定

**A。**

### 理由

1. **接管存量系统的第一原则:让 Git 描述现实,而不是让现实服从 Git。**

   集群里的 Deployment 已经稳定跑了 43 天,是**事实**;GitOps 里的 StatefulSet 从未部署过,是**设想**。用一个未经验证的设想,去替换一个稳定运行的事实,**方向和风险都反了**。

2. **顺序不能颠倒**:先接管(建立可见性和漂移检测)→ 稳定之后再谈迁移。一开始就"顺手把它改对",等于在一次变更里同时做两件事——**出问题无法归因**。

3. **这本身就是高价值面试点**:面试官问"接管存量时清单和现状不一致怎么办",能答出"先让 Git 对齐现实"的人不多,大多数人会本能地说"以 Git 为准"。

### 实施

`production/apps/ai-platform/ollama-stack.yaml`:

- `StatefulSet/ollama` → `Deployment/ollama`,字段对齐集群现状(副本数、镜像、资源、探针、selector)
- 删除 `Service/ollama-headless`(集群里不存在,也没有消费者)
- 保留 `Service/ollama-service`,确保 selector 为 `app: ollama`

### 何时重新评估

接管稳定、有了漂移检测之后,可以**单独**评估"Deployment → StatefulSet"的迁移,作为一次**独立的、可回滚的**变更。

### 副作用

`volumes` / `volumeClaimTemplates` 的差异需要逐项核对——Deployment 用的是 PVC + volumes,StatefulSet 用 `volumeClaimTemplates`。

## D10:Namespace 资源的接管方式

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M1 审计雷 2

### 背景

`apps/ai-platform/namespace.yaml` 声明了 `Namespace/ai-platform`,而 `ai-platform-app` 的 `syncPolicy` 是 `prune: true` + `selfHeal: true`。

**后果**:命名空间本身成了被 ArgoCD 管理的资源。一旦 `namespace.yaml` 从 Git 移除或改名,**ArgoCD 会 prune 掉整个 `ai-platform` 命名空间,连同里面所有工作负载和 PVC。**

### 决定

**从清单里删除 `namespace.yaml`,改用 ArgoCD 的 `CreateNamespace=true`。**

```yaml
syncPolicy:
  syncOptions:
    - CreateNamespace=true
```

### 理由

1. **声明式工具管"存在性",但不该管"删除边界"。**

   `Namespace` 是 cluster-scoped 的删除边界。把它交给 `prune: true`,等于在仓库里放一个"删一行 YAML 就删库"的开关。**声明式的价值是让期望状态可见,而不是让破坏性操作变得更容易触发。**

2. **这是 ArgoCD 官方推荐做法。** `CreateNamespace=true` 的设计意图正是:命名空间由 ArgoCD **按需创建**,但不纳入生命周期管理。

3. **`Destructive: prune` 的危险不在"它会不会删",在"它删的时候你不在场"。** 命名空间级联删除是不可逆的,且有几十秒的延迟——等你发现,已经来不及。

### 实施

- 删除 `production/apps/ai-platform/namespace.yaml`
- 在 `ai-platform-app.yaml` 的 `syncPolicy.syncOptions` 加 `CreateNamespace=true`
- 同样检查其余 5 个子 Application 的 `CreateNamespace` 配置

### 附带修正

其余子 Application(monitoring / loki / promtail / nginx-demo / sealed-secrets)的目标命名空间同样需要 `CreateNamespace=true`,否则首次同步会失败。

## D11:**不**吊销 PushPlus token(取代 D8 的吊销部分)

- **日期**:2026-09-16
- **状态**:✅ 已决定(**用户拍板**)
- **触发**:D8 的实施步骤 1 被推翻

### 背景

D8 里我给出的第一建议是"去后台吊销这个 token"。用户否掉了,原话:

> "不用吊销,我们已经不用 pushplus 了不是吗,干脆扔着不受影响,之前也是因为频繁无效告警加上项目当时完工集群不必维护,索性把告警打入黑洞。"

### 决定

**不吊销。** 同时**不再讨论**这个 token 的处置。

### 理由

1. **它已经不在任何调用路径上。** 项目早已不用 PushPlus,通道已废,这串字符在功能上等同于一串随机文本。**吊销一个没人用的凭证,收益是零**
2. **吊销不是一个孤立动作。** 它牵出一串后续:登录后台 → 找到应用 → 确认影响面 → 执行吊销。而 D8 的方案还要求"再生成一个新 token"——为了一个已经废弃的通道,做两轮账号操作
3. **它不构成实际威胁。** 危害上限是"别人能往我的个人 PushPlus 发消息",而那个账号本身已处于弃用状态

### 仍然执行的部分

**明文文件照样删。** 吊销与否和"文件该不该留在仓库里"是两个独立问题:

- 吊销解决的是"凭证还能不能用"
- 删文件解决的是"仓库里不该有凭证"

**后者不因前者作废而作废。** 删掉它们,顺带解决一个真实的维护问题:这四份文件是 `python:3.9-slim` + 启动时 `pip install` 的最坏范式(D8 教训节),本来就要换掉。

### 我的判断失误(要记住)

**我按"标准安全流程"给出了吊销建议,却没有先问一句"这个凭证还在用吗"。**

安全建议里有一条容易被忽略的前置:**处置的前提是"它还有价值"。** 对一个已经失效的凭证执行吊销,属于仪式性动作——看起来专业,实际只是在走流程。

> **教训:提安全建议之前,先问"这个资产现在是什么状态"。** 一个 43 天前就废弃的 token 和一个正在服务的 token,处置方案完全不同。

## D13:降噪方式 = 从源头关掉组件(而非静默或覆盖)

- **日期**:2026-09-16
- **状态**:✅ 已执行并实测验证
- **触发**:M2 降噪,告警数 **39 → 1**

### 背景

`KubeProxyDown` / `KubeSchedulerDown` / `KubeControllerManagerDown` 三条在 k3s 上永远 firing(原因见踩坑 P5:k3s 把这三个组件编译进单进程,而默认规则假设它们是独立 Pod)。

### 考虑过的选项

| 选项 | 评价 |
|---|---|
| **A. Helm values 关 `enabled`** | ✅ **选中**。一次砍掉 Service + ServiceMonitor + 空 target + **整组 PrometheusRule** |
| B. `defaultRules.disabled` 逐条禁 | ⚠️ 有效,但**保留空 target**。Prometheus UI 里仍是缺口 |
| C. Alertmanager 静默 / 黑洞路由 | ❌ 规则仍在求值(白烧 CPU);且实测**静默路由本身是失效的**(踩坑 P8) |
| D. 同名 PrometheusRule 覆盖 | ❌ **已实验证伪**(踩坑 P7):Prometheus 里同名规则**并存不覆盖** |

### 决定

**A。** 三个组件全部 `enabled: false`。

### 理由

1. **它解决的是根因,不是症状。** 真正的错误是"这些 target 在 k3s 上根本不该存在",关 `enabled` 修正的正是这个;静默只是假装它不存在
2. **副作用全部是正向的**:少 3 个 scrape target(省 Prometheus 资源)、少一整组规则(省求值开销)、少 3 个空 Service
3. **可逆且显式**:将来若换成 kubeadm 集群,把三行改回 `true` 即可

### 一个存放位置上的坑

values 文件放在 **`production/helm-values/`**,而**不是** `production/monitoring/`。

原因:`production/monitoring/` 在 `monitoring-app.yaml` 的 `source.path` 里,ArgoCD 会把该目录下**所有 YAML 当成 k8s 清单去 apply**。一个 Helm values 文件放进去,会变成"ArgoCD 尝试创建一个不存在的 kind"。

> **规律:GitOps 监视目录里不能放非清单文件。** 目录边界就是语义边界。

### 实测验证

| 检查项 | 结果 |
|---|---|
| 渲染结果里三个组件的任何资源 | 0 个 |
| 渲染结果里三条 alert 名 | 0 次 |
| 集群里对应 Service / ServiceMonitor / PrometheusRule | 已全部清除 |
| **Prometheus 实际告警数** | **39 → 1**(仅剩 `Watchdog`,设计上永远 firing) |

## D14:监控栈保持 Helm 管理,不进 GitOps

- **日期**:2026-09-16
- **状态**:✅ 已决定
- **触发**:M1 接管存量时梳理"哪些该交给 ArgoCD"

### 背景

存量集群里 `monitoring` 是 **Helm release**(`kube-prometheus-stack-87.19.1`,rev 4),而 `ai-platform` 是**手工 apply** 的。两种管理方式需要两套接管策略。

### 决定

**混合模式**——监控栈"主体"由 Helm 管理,不交给 ArgoCD;但**补充对象**走 GitOps。

| 层 | 管理方式 | 内容 |
|---|---|---|
| 主体 | **Helm**(手工 upgrade) | kube-prometheus-stack 的全部内置资源:Prometheus / Alertmanager / Grafana / node-exporter / kube-state-metrics / 默认规则 |
| 补充 | **ArgoCD**(`monitoring-app.yaml`,监视 `production/monitoring/`) | cluster-alerts / nginx-monitor / ollama-exporter / ingress / 适配器 等后加的东西 |

### 理由

1. **避免双重管理。** 同一个对象被 Helm 和 ArgoCD 同时管,两边都会认为对方"漂移"了,互相 reconcile——这是 GitOps 落地时最常见的冲突来源
2. **Helm chart 的 values 是这类栈的天然接口。** kube-prometheus-stack 有 800+ 个配置项,拆成 k8s 原生清单会失去 chart 的升级路径
3. **补充对象本来就是清单形态**,且经常变动,适合 GitOps

### 代价(要诚实标注)

**这个分界不是免费的**,它引入了一个持续存在的风险:

> **Alertmanager 的 receiver 配置属于"主体",在 Helm values 里 —— 也就是说它在 GitOps 之外。**

后果很具体(见 D12):接告警通道时,密钥(webhook URL)会落到一个**不在 Git 里、也没有版本历史**的地方。

**这是 D12 里那个"前置问题"的根源。** 可能的解法(未定):
- 把 Alertmanager 配置整体迁进 GitOps(代价:要接管 chart 的一个子部分)
- 用 `alertmanager.config` 引外部 Secret(需要解决"Secret 怎么进 Git")
- 接受这个边界,用 SealedSecret 手工维护并文档化

**M2 接通道之前必须先把这条定下来。**

## D15:告警接收端改用邮件(取代 D12 的适配器方案)

- **日期**:2026-09-16
- **状态**:✅ 已实施并实测验证
- **触发**:企微群机器人方案被物理阻断,重新评估"最小可用接收端"

### 背景

D12 选定了 `bougou/alertmanager-webhook-adapter` 作为企微告警适配器。但它有一个前置条件:**必须先有一个群,才能建群机器人。** 用户用的是个人版企微,**无法创建群聊**,因此拿不到 webhook key。这条路径在物理上走不通,不是配置问题。

### 考虑过的选项

| 选项 | 结论 |
|---|---|
| 企微群机器人 | ❌ 个人账号无法建群,拿不到 key |
| 企微应用消息(`weixinapp`) | 需要企业管理员权限创建自建应用,个人版同样受限 |
| PushPlus 等第三方推送 | 已有 token,但要经第三方服务器中转;D11 决定不吊销它,也不扩大其使用面 |
| 钉钉 / 飞书群机器人 | 同样需要先建群或建组织,注册成本高于收益 |
| **邮件(SMTP)** | ✅ 不需要群、不需要组织、不需要第三方服务 |

### 决定

**用邮件作为告警接收端。** `to` / `from` / `authUsername` 均为 `599512147@qq.com`,`smarthost` 为 `smtp.qq.com:465`(`forceImplicitTLS: true`),凭据由 SealedSecret 提供。

### 理由

1. **它是这个环境里唯一"零前置"的通道。** 企微要群、钉钉要组织、PushPlus 要过第三方——邮件什么都不要
2. **密钥是原生 SecretKeyRef。** `AlertmanagerConfig.emailConfigs.authPassword` 直接就是 `SecretKeySelector`,配合 Sealed Secrets,D12 里那个"token 会不会落进 Git"的问题**从设计上就不存在了**。(对比:`webhookConfigs.urlSecret` 也能做到同样的事——那是 D12 走的弯路)
3. **不需要额外部署适配器。** 省掉一个 Deployment、一份镜像、一个要跟踪上游更新的第三方项目
4. **面试口径更干净。** "用 Alertmanager 原生 email receiver + SealedSecret 接通道"比"我装了一个社区适配器"更能体现对工具边界的理解

### 代价(要诚实标注)

1. **邮件不是即时通道。** 手机邮件推送延迟显著高于 IM,不适合 P1 级故障的实时响应。真上生产,邮件通常只做**兜底与留痕**,IM / 电话才是主通道
2. **邮件没有天然的限频与聚合。** 这次靠在 Alertmanager 侧做聚合(`groupWait: 30s` / `groupInterval: 5m` / `repeatInterval: 4h`)来替代企微那套"20 条/分钟"的硬约束
3. **QQ 邮箱 SMTP 有外部配额**,超限会被限制;本地实验量级无影响

### 实施

**第一步必须是改 `alertmanagerConfigMatcherStrategy`。**

`AlertmanagerConfig` 是**命名空间级** CRD,而 prometheus-operator 默认的 `OnNamespace` 策略会往它生成的**每一条子路由**注入 `namespace = "<CR 所在命名空间>"` 匹配器。我们的 CR 在 `monitoring` 命名空间 —— 不改这个设置的话,**只有带 `namespace=monitoring` 标签的告警能匹配到邮件路由**,其余全部回落到根路由的 `null` receiver。这是一个**完全静默的黑洞**,不报任何错。

所以在 `production/helm-values/monitoring-values.yaml` 里加了:

```yaml
alertmanager:
  alertmanagerSpec:
    alertmanagerConfigMatcherStrategy:
      type: None
```

**其余步骤**:

| 步骤 | 内容 |
|---|---|
| 1 | `monitoring-values.yaml` 加 `alertmanagerConfigMatcherStrategy: None`,`helm upgrade` |
| 2 | 写 `production/monitoring/alertmanager-config.yaml`(`AlertmanagerConfig`,route + email receiver) |
| 3 | 用 `kubeseal` 生成 `production/monitoring/sealed-alertmanager-smtp.yaml`(strict scope,name=`alertmanager-smtp`,ns=`monitoring`) |
| 4 | **先单独 apply SealedSecret**,确认 Secret 先于 Alertmanager 引用它而存在 |
| 5 | 再 apply `production/bootstrap/monitoring-app.yaml`,由 ArgoCD 接管 |

**第 4 步的顺序不是洁癖。** `AlertmanagerConfig` 引用一个不存在的 Secret 时,operator 生成的配置里 `auth_password` 解析失败;而 **Alertmanager 对配置加载失败的处理是保留上一份配置**——表现是"改了但没生效",极难定位。

### 验证(三层各自独立取证,全部为实测)

| 层次 | 取证方式 | 结果 |
|---|---|---|
| 配置生成 | 解出 `alertmanager-monitoring-kube-prometheus-alertmanager-generated` 里的 `alertmanager.yaml.gz` | 子路由 `receiver: monitoring/sre-lab-alerting/email`,**无注入的 namespace 匹配器**;`auth_password` 已解析 |
| 通道可达 | `alertmanager_notifications_total{integration="email"}` | **2** |
| 投递失败 | `alertmanager_notifications_failed_total{integration="email",reason=~".*"}` | **全 0** |
| 端到端 | 向 v2 API `POST /api/v2/alerts` 注入真实告警 | HTTP 200 → 进入 `active` → 触发 1 次投递 |
| **人工确认** | 用户查看 `599512147@qq.com` 收件箱 | ✅ **收到** |

**最后这一行不能省。** 前三层共同的极限是"SMPT 服务器**接受了**这封信"。"SMTP 接受了"和"进了收件箱"之间还隔着垃圾邮件过滤、灰名单、域名信誉——而这一段的失败对发送方是**完全静默**的:返回 250、计数器加一、`failed_total` 保持 0,邮件却躺在垃圾箱里。**链路的最后一跳如果是人,就只能由人来验证。**

**为什么用 `notifications_total` 而不是看日志**:Alertmanager 默认 `log.level=info`,**成功的通知不写日志**,只有失败才写。所以"`kubectl logs` 里没有 error"完全不能证明消息发出去了——那一刻它可能一条都没发。计数器是这里唯一可信的证据。

### 何时重新评估

拿到企业内部权限(能建群 / 能建自建应用)时切回 IM 通道,邮件降级为兜底。

## D16:镜像仓库选型 —— 本地 k3d registry(而非 GHCR)

- **日期**:2026-09-16
- **状态**:✅ 已决定并跑通
- **触发**:M3 需要一个可供集群拉取的镜像仓库

### 背景

原计划用 **GHCR**(GitHub Container Registry)。但被一个很具体的事卡住了:

> **GHCR 的经典 PAT(classic personal access token)迟迟没拿到。**

排查到的细节:`gh` CLI 拿到的 OAuth token **只有 `write:packages`,没有 `read:packages`**,于是 `docker login` 直接被:

```
DENIED
```

### 考虑过的选项

| 选项 | 评价 |
|---|---|
| **A. 本地 `k3d registry create`** | ✅ **选中** |
| B. 继续等 GHCR PAT | ❌ 被外部流程阻塞,且不是技术问题,无法预估何时解开 |
| C. 公网私有 registry 服务 | ❌ 引入第三方依赖与账号成本,对"本地可复现实验"没有增益 |

### 决定

**用 `k3d registry create` 起本地仓库(GHCR 留作第二站)。**

### 理由

1. **不被外部 token 阻塞。** 上面那个 `DENIED` 的根因是**权限范围**问题,不在本项目能控制的范围里。继续等它,是把项目进度押在一个外部流程上 —— **一个实验要用到的组件,不该被它自己的认证流程卡住**
2. **对 K8s 来说它就是真实私有仓库。** 认证、tag、拉取语义**和企业内网 Harbor 完全一致** —— 也就是说,本项目练到的"配私有仓库、给 containerd 加 `certs.d`、处理 HTTP/HTTPS 不一致"(见踩坑 P16)**是真实技能,不是玩具**
3. **自包含、可复现。** 本地仓库随 k3d 一起起、一起清,没有外部状态残留 —— 契合 D4 选定的"可重复 + 保留真实状态"路线

### 代价(诚实标注)

- **本地 registry 没有访问控制**,任何能访问 `localhost:5111` 的东西都能推送/拉取。仅适用于本机实验环境
- 集群重建后仓库内容需要重建(镜像不在,但仓库本身由 `k3d registry create` 一条命令恢复)

### 何时重新评估

拿到 GHCR 的 `read:packages` 权限后,把 GHCR 作为"第二站"接上 —— 那时本项目就有**两条镜像分发路径**可对照(本地 registry = 内网私有仓库,GHCR = 公网托管),这本身是更好的面试素材。

## D17:GitOps 写回用**仓库级 deploy key**(而非 Jenkins 原生凭据)

- **日期**:2026-09-16
- **状态**:✅ 已实施(含两处诚实边界)
- **触发**:M3 Jenkins 要向 GitOps 仓库写回镜像 tag

### 背景

**GitOps 写回必须要有 git 写凭据,这一条绕不过去。**

D2 定的分工是 Jenkins 做 CI、ArgoCD 做 CD。但"CI 构建出新镜像后,把新 tag 写回 GitOps 仓库"这个动作,**需要一个能 push 到该仓库的身份** —— ArgoCD 是 pull 模型,它不会替 Jenkins 做这件事。

### 考虑过的选项

| 选项 | 评价 |
|---|---|
| **A. 仓库级 deploy key + K8s Secret 挂载** | ✅ **选中** |
| B. Jenkins 原生 Credentials(`GitSSHUserPrivateKey`) | ⚠️ 尝试过,**REST API 创建返回 500**,时间原因改用挂载 |
| C. 个人账号 PAT / 长期 SSH key | ❌ 权限范围是整个账号,对"一个仓库的写回"来说**过宽** |

### 决定

**生成专用 ed25519 密钥对:**

- **公钥**注册为该仓库的 **deploy key**,**`read_only=false`**(= 可写)
- **私钥**以 **K8s Secret** 形式挂进构建 Pod 的 git 容器,挂载路径 `/root/.ssh/id_ed25519`,`defaultMode: 0400`

### 理由

1. **deploy key 的权限锁死在单个仓库。** 它**只能**读写这一个仓库,拿不到账号下别的东西 —— 这是 GitHub **专门为 CI 设计**的机制,权限边界和需求正好对齐
2. **对比 C:一个 PAT 泄露 = 整个账号泄露。** 一个 deploy key 泄露 = **一个仓库**泄露。**凭证的权限范围应该等于它要做的事的范围** —— 不要大于
3. **用 K8s Secret 挂载而不是塞进环境变量**:私钥以**文件**形态出现(`0400`,只读),符合 SSH 对私钥文件权限的要求,也避免它出现在 `kubectl describe pod` / 进程 env 里

### ⚠️ 诚实边界(两条,都是待办)

**边界 1:当前是普通 K8s Secret,没有走 Sealed Secrets 封存。**

> **集群里没装 `kubeseal` 二进制**,所以这次是直接创建 Secret 的。

后果很具体:**k3d 重建后这个 Secret 会丢,需要重新创建。** 这直接违背了 D4 选的"可重复重建"路线 —— 重建集群之后,CI 会因为找不到私钥而 push 失败,而**失败点离根因很远**(表现为"git push 报错",而不是"Secret 不存在")。

**待办:把 kubeseal 补上,把这份 Secret 封存进 GitOps 仓库。**

**边界 2:没有走 Jenkins 原生的 Credentials 机制。**

尝试过用 Jenkins REST API 创建 `GitSSHUserPrivateKey` 类型凭据,**返回 500**,时间原因改用挂载。两条路的差异:

| | 挂载 K8s Secret | Jenkins 原生 Credentials |
|---|---|---|
| 凭据存在哪 | **K8s**(集群里) | **Jenkins**(controller 上) |
| 谁能用 | 只有挂了它的 Pod | 任何有权限的 Job |
| 轮换 | 改 Secret + 重启 Pod | Jenkins 界面里改 |

**挂载这条路的权限边界更窄**(只有构建 Pod 能看到私钥),代价是**轮换麻烦**。当前选择它是因为它先跑通了。

### 何时重新评估

1. 补上 `kubeseal` 之后 —— Sealed Secrets 封存私钥,解决边界 1
2. 若之后需要多个 Job 共享该凭据 —— 重新评估是否切回 Jenkins 原生 Credentials(边界 2)
