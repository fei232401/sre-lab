# 学习笔记 01:ArgoCD 到底是什么

> 记录日期:2026-09-16
> 起因:用户提问「argocd 到底是干嘛的?之前开了 synced,很多改了的配置没有 git commit 都被应用失败,让我对它没什么好感」

---

## 一、一句话定义

**ArgoCD 是一个"对账机器人":它持续对比 Git 仓库里写的集群配置(期望状态)和集群里实际在跑的东西(实际状态),发现不一致就报告——或者自动纠正。**

它属于 **GitOps** 这个流派:Git 仓库是集群状态的唯一事实来源。

---

## 二、没有 ArgoCD 的时候,世界是什么样

传统的 CD 是"CI 跑完,执行 `kubectl apply` / `helm upgrade`":

```
问题清单:
├─ 谁改的?什么时候改的?改了啥?   → 只能翻 CI 日志
├─ 有人手动 kubectl edit 改了参数 → 没人知道,下次部署被静默覆盖
├─ 线上出问题想回滚             → 得记得上个版本号,重跑一遍 CI
└─ 时间久了,集群实际状态和代码库里的定义慢慢就不一样了(这叫"配置漂移")
```

---

## 三、有 ArgoCD 之后

```
        期望状态                      实际状态
   ┌──────────────┐            ┌──────────────┐
   │ Git 仓库      │  ← 对比 →  │ K8s 集群      │
   │ (唯一真相源)  │            │ (真正在跑的)  │
   └──────────────┘            └──────────────┘
                    ↑
                ArgoCD 在这里

   不一致 = OutOfSync
   ├─ 只报告,不动手          ← 默认行为
   └─ 自动把集群拉回 Git 状态  ← 开了 auto-sync + self-heal
```

### 三个核心价值

| 价值 | 具体含义 |
|---|---|
| **可审计** | 集群的所有变更 = git log,谁改的、什么时候、为什么,一清二楚 |
| **可回滚** | `git revert` 一下,整个集群状态就回去了(不是"重跑一遍部署") |
| **防漂移** | 有人绕过流程手动改线上 → 被检测到并纠正 |

---

## 四、⚠️ 你当年踩的坑:同步策略的三个开关

**这是本文最重要的一节。**

`Application` 资源里 `spec.syncPolicy.automated` 下有三个开关,新手最容易全开:

| 开关 | 作用 | 全开后的后果 |
|---|---|---|
| `auto-sync` | Git 变了就自动同步到集群 | ✅ 一般是你想要的 |
| **`selfHeal`** | **集群里手动改的,自动纠正回 Git 版本** | ⚠️ **你手动改的东西会被"抹掉"** |
| `prune` | Git 里删掉的资源,集群里也删掉 | ⚠️ 容易误删 |

### 用户遇到的现象

> "开了 synced,很多改了的配置没有 git commit 都被应用失败"

**判断:这不是 ArgoCD 坏了,是它在正确工作。**

`selfHeal: true` 的行为就是:检测到集群状态偏离 Git → 几秒内改回去。

在**个人开发/试验环境**,这个行为极其烦人(改一个参数想试试效果,几秒后被还原)。
在**生产环境**,这个行为是救命的(防止有人绕过流程手动改线上)。

### 关键认知:不是"开"与"关"二选一

第三条路——**按应用性质分级配置**(企业里的真实做法):

| 应用类型 | 同步策略 | 理由 |
|---|---|---|
| **基础设施**(monitoring / jenkins / argocd 自身) | `selfHeal: true` | 这些不该有人手动改,防漂移 = 保命 |
| **正在开发的应用**(game-server) | `selfHeal: false`,`prune: false` | 允许手动试参数,不闹心 |

---

## 五、本项目的处理方式:M2/M1 做一组对照实验

**不直接把开关关掉就算完,而是先做实验亲眼看清行为**,再固定配置:

| 实验 | 操作 | 预期观察 |
|---|---|---|
| ① 全关 | 手动 `kubectl scale` 改副本数 | ArgoCD 显示 `OutOfSync`,但**不动作** |
| ② 开 `selfHeal` | 再手动改一次 | **几秒内被改回 Git 的值** |
| ③ 开 `prune` | 从 Git 删一个资源 | 集群里真的被删除 |

**这三个观察做完,对 GitOps 的理解就从"读过文档"升级到"见过它干活"。**

而且——**这套"开发环境半开 / 生产环境全开"的对比本身是高价值面试素材**。面试官问"GitOps 在个人开发环境不麻烦吗?",大多数候选人答不上来;能答"我按应用性质分级配,并实测过两种配置的行为差异",直接区分开。

---

## 六、什么场景该用 / 不该用

| 该用 | 不该用 |
|---|---|
| 多环境(dev/staging/prod)需要保持一致 | 一次性试验,做完就删 |
| 合规要求变更审计 | 单人项目,集群本身就是草稿纸 |
| 团队协作,需要防止有人手动改线上 | 快速原型阶段,配置每天都在变 |
| 需要快速回滚能力 | — |

**判断标准**:如果你会问"线上现在跑的是什么版本?谁改的?",你就需要它。

---

## 七、面试怎么讲

> "ArgoCD 是 GitOps 的 CD 实现,核心是**拉模式**——集群内的 agent 主动去 Git 拉期望状态,持续对比实际状态。它的三个价值是可审计、可回滚、防漂移。
>
> 我们实际用的时候注意了一个点:同步策略的三个开关(`auto-sync` / `selfHeal` / `prune`)不能一刀切。基础设施类应用开 `selfHeal` 防漂移,开发中的应用关掉 `selfHeal` 允许手动调试——这个配置差异我实测对比过。"
