### 2.4 ⚠️ 发现的安全缺陷(必修)

`sre-lab-gitops/production/monitoring/wechat-adapter.yaml` 中:

```python
PUSHPLUS_TOKEN = "28ea****(明文硬编码,已公开泄露)"
```

**问题**:仓库为 public,token 等同公开。任何人可调用该 PushPlus 账号推送消息。

**修复路径**:
1. 轮换 PushPlus token(旧 token 作废)
2. 改用 **Sealed Secrets** 加密存储
3. 修正 Pod spec 从 Secret 挂载环境变量,而非内联明文

**价值**:这是一次真实的自我安全审计 + 修复闭环,面试素材价值高于任何"我学过 XX"的表述。

## 三、架构设计

### 3.1 拓扑

```
┌─ WSL2 本机 ────────────────────────────────────────────────┐
│                                                            │
│  k3d-ai-cluster(现有,原地改造)                          │
│  ├─ kube-system     (不动)                                 │
│  ├─ monitoring      Prometheus / Grafana / Alertmanager    │
│  │                  kube-state-metrics / node-exporter     │
│  │                  gpu-exporter                           │
│  │                  ➕ Loki ➕ Promtail                      │
│  │                  ➕ 业务指标 ServiceMonitor + 告警规则    │
│  ├─ ai-platform     ai-infra-gateway(存量,待接管)         │
│  │                  ollama / cyberrouter-operator          │
│  │                  ➕ game-server(Go,发布演练用)          │
│  └─ ➕ argocd        App-of-Apps → 指向 GitHub GitOps 仓库  │
│                                                            │
│  ➕ self-hosted runner(docker 容器,挂宿主 docker socket) │
└────────────────────────────────────────────────────────────┘
                            ↕
┌─ GitHub: fei232401/sre-lab ────────────────────────────────┐
│  .github/workflows/    ← CI(新建)                         │
│  sre-lab-gitops/       ← CD 期望状态(存量,接进来)       │
│  sre-lab-local/        ← 本次产出(排障/runbook/话术)     │
│  ghcr.io/fei232401/*   ← 镜像仓库(新建)                   │
└────────────────────────────────────────────────────────────┘
```

### 3.2 数据流

```
① git push 代码
      ↓
② GitHub Actions 触发 workflow
      ↓
③ self-hosted runner(本机)接单
      ├─ lint / test
      ├─ build 镜像
      ├─ push 到 ghcr.io(镜像 tag = git short sha)
      └─ 回写 GitOps repo:更新 image tag → commit + push
                                    ↓
④ ArgoCD 轮询/webhook 发现期望状态变化
      ↓
⑤ ArgoCD 同步进 k3d 集群(自愈 / 漂移纠正 / 可回滚)
      ↓
⑥ Prometheus 抓指标 + Promtail 收日志 → Loki
      ↓
⑦ Grafana 面板 → 阈值触发 → Alertmanager → 通知网关 → 企业微信 → 手机
```

### 3.3 每个箭头对应的面试考点

| 箭头 | 面试官会问 | 实操素材来源 |
|---|---|---|
| ②→③ | 为什么用 self-hosted runner?托管的不香吗? | runner 掉线重连、并发上限、资源抢占、缓存 |
| ③ | 镜像 tag 用什么策略?`latest` 有什么问题? | 真实回滚演练 |
| ③→④ | **为什么 CI 不直接 `kubectl apply`?** | GitOps 立身之本:可审计/可回滚/防漂移 |
| ④→⑤ | ArgoCD 卡住 / `OutOfSync` 怎么查? | M1 接管存量时**必然**踩到 |
| ⑤ | 滚动更新卡住不回滚怎么办? | M4 灰度演练 |
| ⑥→⑦ | 告警为什么没发出来?告警风暴怎么治? | M2 亲手调通 + 故意触发 |

## 五、技术选型与理由

| 项 | 选择 | 理由 | 备选与否决原因 |
|---|---|---|---|
| CI 引擎 | **GitHub Actions + self-hosted runner** | 一次拿下两个维度:写 workflow(CI 能力)+ 维护 runner(运维能力)。runner 在集群内可直连服务,无需暴露端口 | Jenkins:搭建成本高,且与 ArgoCD 形成两套 CD 混乱。GitLab CE:单体吃 4-6G 内存,与本机监控栈抢资源。Gitea:面试官不熟,讲不出共鸣 |
| CD 引擎 | **ArgoCD(GitOps)** | sre-lab 现成资产,复活成本远低于重建,且是行业主流 | Flux:无存量资产 |
| 镜像仓库 | **GHCR** | 零搭建,Actions 原生集成,私有免费;与云厂商 registry 同构 | 本机 registry:insecure registry / 证书 / 存储坑多。**列为盲点专题,在复盘文档中讲透** |
| 告警渠道 | **企业微信机器人** | 一个 webhook 即可,零依赖零费用,支持 Markdown 卡片;国内企业真实在用 | PushPlus:第三方中转,企业不采用,且需先修 token 泄露 |
| 游戏服语言 | **Go** | 标准库 `net` + 每连接一 goroutine,~100 行教科书级实现;JD 加分项明列 Go,与个人战略一致 | Python asyncio:写入更快但少一次 Go 实践 |
| 监控栈 | 复用 kube-prometheus-stack + 补 Loki/Promtail | 已在本机运行,省至少半天 | 重建:无收益 |

## 六、生产级对齐清单(最小但真实可用)

- [ ] 镜像 tag 使用 **git short sha**,禁用 `latest`(否则回滚无从谈起)
- [ ] 每个工作负载配 `resources.requests/limits`
- [ ] 每个工作负载配 `livenessProbe` / `readinessProbe`
- [ ] Secret 走 **Sealed Secrets**,不落明文
- [ ] **构建失败时 GitOps 仓库绝不动** —— 保证期望状态永远可用(GitOps 铁律)
- [ ] Alertmanager 配 **group / route / inhibit**,防告警风暴
- [ ] 保留 `PodDisruptionBudget` / `HPA`(存量 YAML 已有,纳入接管范围)
- [ ] 命名空间隔离 + 资源配额
- [ ] 一键重建脚本 `bootstrap.sh`,证明环境可复现

## 七、风险与诚实边界

| 风险 | 应对 |
|---|---|
| M0 诊断发现故障"太平淡"(如仅因 WSL 无 GPU 导致 vllm 起不来) | 如实告知用户,立即转为"清场重建"方案,不硬凑素材 |
| 企业微信机器人需要用户提供 webhook(需要企业微信群) | M2 开始前向用户索取;若不可得,退化为 PushPlus |
| k3d 集群重启后 ArgoCD/监控状态丢失 | 所有配置入 Git,GitOps 的意义正在于此;写进 runbook |
| 本机内存 19 GiB,监控栈 + Loki + runner 并存可能吃紧 | 不引入 Jenkins 类重型组件;Loki 设 retention 上限;持续盯内存水位 |
| 接管存量资源时 ArgoCD 可能误删 | M1 严格执行 `Prune=false` 观察期,先 dry-run,后放开 |
