## 一、背景与目标

- 部署、发布、监控、巡检、日常运维,保障稳定高可用

### 目标(一句话)

3. 每个里程碑的产物都能作为面试材料直接展示

> **能用现成的就用现成的,把时间花在「为什么这么设计」和「出问题怎么查」上,而不是手搓组件。**

### 2.3 盘点中发现的三个真实问题(M0 的预演)

**问题 1 — `helm list -A` 返回空,但资源上明明有 Helm 注解**

- 现象:`helm list -A` 什么都不显示;但 `monitoring-grafana` Deployment 上有
  `meta.helm.sh/release-name: monitoring` 注解
- 根因:**Helm 使用 kubeconfig 的当前 context**,而当前 context 是 `k3d-topo-demo`(项目三的集群),
  不是 `k3d-ai-cluster`。Helm 查的是**另一个集群**,自然为空
- 验证:`helm list -A --kube-context k3d-ai-cluster` → 正确列出 monitoring / traefik / traefik-crd
- **教训**:`kubectl` 和 `helm` 都隐式依赖当前 context;多集群环境下不带 `--context` 的命令
  是重大事故来源。**这条会写进 runbook 作为纪律**

**问题 2 — 两个命名空间的管理方式不同,M1 接管策略必须分开**

| 命名空间 | 管理方式 | ArgoCD 接管难度 |
|---|---|---|
| `monitoring` / `kube-system` | **Helm 管理**(有 release 记录) | 较难:需处理 Helm 所有权与 ArgoCD 的所有权冲突 |
| `ai-platform` | **手工 `kubectl apply`**(`MANAGED-BY: <none>`) | 较易:直接纳管,但要处理"资源已存在"的 adopt |

**这意味着 M1 不是一件事,而是两件不同的事** —— 这恰恰是最有价值的实操内容。

**问题 3 — PushPlus token 明文硬编码在公开仓库(见 2.4)**

### 2.4 ⚠️ 必修的安全缺陷

`sre-lab-gitops/production/monitoring/wechat-adapter.yaml`:

```python
PUSHPLUS_TOKEN = "28ea****(明文硬编码,已公开泄露)"
```

**修复路径**:① 轮换 token → ② 改用 **Sealed Secrets** 加密存储 → ③ Pod 从 Secret 挂载,不内联明文

**价值**:一次真实的自我安全审计 + 修复闭环,面试素材价值高于任何"我学过 XX"的表述。

### 3.2 数据流

```
① git push 代码到 GitHub
      ↓
② GitHub webhook → Jenkins Controller(集群内)
      ↓
③ Jenkins 通过 Kubernetes Plugin 动态创建 agent Pod
      │  (构建环境隔离,用完即销毁 —— 这是 Jenkins on K8s 的核心价值)
      ├─ lint / go test
      ├─ Buildah rootless 构建镜像(不挂 docker.sock,见第八节)
      ├─ Trivy 镜像漏洞扫描
      ├─ push 到 ghcr.io(镜像 tag = git short sha)
      └─ 回写 GitOps repo:更新 image tag → commit + push
                                    ↓
④ ArgoCD 轮询/webhook 发现期望状态变化
      ↓
⑤ ArgoCD 同步进 k3d 集群(自愈 / 漂移纠正 / 可回滚)
      ↓
⑥ Prometheus 抓指标 + Promtail 收日志 → Loki
      ↓
⑦ Grafana 面板 → 阈值触发 → Alertmanager → 通知网关 → 企业微信 → 手机
```

### DoD(不达标不往下走)

**M0** — 每个异常 Pod 都能说清:根因 / 用什么命令确认 / 该怎么处置。说不出根因不算完。

**M1** — ① ArgoCD 全绿 `Synced / Healthy`,且 Helm 管理的 monitoring 与手工创建的 ai-platform 都被纳管
② **同步策略对照实验做完**:全关 → 手动改副本数(只报告不动作)→ 开 `selfHeal` → 手动改被自动纠正回期望值 → 开 `prune` → Git 删资源集群真删
③ Git 仓库改一行 → 集群跟着变
④ 按应用性质**固定分级配置**:基础设施类 `selfHeal: true`,game-server `selfHeal: false`

**M2** — 触发一次故障 → **3 分钟内手机收到** `🔴` 告警;故障恢复后收到 `✅` 恢复通知。

**M3** — ① `git push` 一个改动 → 全程零手工 → 集群里 Pod 镜像 tag 变成新 git sha;且镜像已过 Trivy 扫描
② **push CD 对照组跑通**:同一个 Jenkinsfile 里直接 `kubectl set image` 部署,并记录 push vs pull 的差异观察表

**M4** — 推"坏版本" → Grafana 错误率曲线抬升 → 能指着面板完整复述:看到什么 / 判断依据 / 执行什么动作 / 恢复到什么状态。

## 五、技术选型与理由

| 项 | 选择 | 理由 | 备选与否决原因 |
|---|---|---|---|
| CI 引擎 | **Jenkins on K8s**(官方 Helm Chart) | 国内游戏/传统企业真实环境绕不开;**Kubernetes Plugin 动态 agent** 是生产标准姿势;官方 Helm Chart 一条命令即起,省去手搓 | GitHub Actions:个人项目友好,但企业内网/私有部署场景覆盖不到。**注:此处修正了 v1 的判断 —— Jenkins 只做 CI,ArgoCD 只做 CD,不是"两套 CD 混乱",而是标准分工** |
| 镜像构建 | **Buildah(rootless,Pod 内)** | CNCF Sandbox(2025-01 进入),daemonless、rootless 优先,契合 K8s Job 模型;**不挂 docker.sock** | 挂 `docker.sock`:等于把宿主机 root 权限交给构建容器,生产大忌。DinD:需 privileged,同样不安全。**Kaniko:2025-06 已被 Google 归档**,不再作为新项目选择 |
| CD 引擎 | **ArgoCD(GitOps)** | sre-lab 现成资产,复活成本远低于重建,行业主流 | Flux:无存量资产 |
| 镜像仓库 | **GHCR** | 零搭建,Actions/Jenkins 均可推,私有免费;与云厂商 registry 同构 | 本机 registry:insecure registry / 证书 / 存储坑多。**列为盲点专题,在复盘文档中讲透** |
| 告警渠道 | **企业微信机器人** | 一个 webhook 即可,零依赖零费用,支持 Markdown 卡片;国内企业真实在用 | PushPlus:第三方中转,企业不采用,且需先修 token 泄露 |
| 告警规则 | **samber/awesome-prometheus-alerts**(8.2k⭐) | 500+ 条现成规则(节点/K8s/Nginx/Redis/MySQL…),**每条附阈值依据说明** —— 既是省时工具,又是原理教材 | 手写:费时且质量不如社区沉淀 |
| 故障注入 | **Chaos Mesh**(7.9k⭐,CNCF) | k8s-native,CRD 声明式定义故障;**故障本身也能 GitOps 化**,是本设计的亮点 | ChaosBlade(阿里,6.5k⭐):更轻但非 K8s 原生。手写 chaos.sh:费时且不可复用 |
| 镜像扫描 | **Trivy** | CI 安全门禁的行业标准,一条命令接入 | 无扫描:生产级 CI 缺一大块 |
| 游戏服语言 | **Go**(标准库 `net`) | ~100 行教科书级 TCP 服务;JD 加分项明列 Go,与个人战略一致;不用框架更好讲 | 用 leaf/cherry 框架:会淹没在框架细节里,反而讲不清。"为什么不用框架"本身就是面试点 |
| 监控栈 | 复用 kube-prometheus-stack + 补 Loki/Promtail | 已在本机运行,省至少半天 | 重建:无收益 |

## 六、生产级对齐清单(最小但真实可用)

- [ ] 镜像 tag 使用 **git short sha**,禁用 `latest`(否则回滚无从谈起)
- [ ] **构建不使用 docker.sock**,采用 Buildah rootless(特权容器风险)
- [ ] CI 加 **Trivy 镜像扫描**门禁
- [ ] 每个工作负载配 `resources.requests/limits`
- [ ] 每个工作负载配 `livenessProbe` / `readinessProbe`
- [ ] Secret 走 **Sealed Secrets**,不落明文
- [ ] **构建失败时 GitOps 仓库绝不动** —— 保证期望状态永远可用(GitOps 铁律)
- [ ] Alertmanager 配 **group / route / inhibit**,防告警风暴
- [ ] 保留 `PodDisruptionBudget` / `HPA`(存量 YAML 已有,纳入接管范围)
- [ ] 命名空间隔离 + 资源配额
- [ ] **所有 kubectl/helm 命令显式带 `--context`**(多集群纪律,来自 2.3 问题 1)
- [ ] 一键重建脚本 `bootstrap.sh`,证明环境可复现

## 七、风险与诚实边界

| 风险 | 应对 |
|---|---|
| M0 诊断发现故障"太平淡"(如仅因 WSL 无 GPU 导致 vllm 起不来) | 如实告知用户;**注:2.3 已挖出两个有料的问题,此风险已显著降低** |
| **本机内存仅 19 GiB**,监控栈 + Loki + Jenkins + ArgoCD + Chaos Mesh 并存吃紧 | 停掉闲置的 `k3d-ew-cluster` 省内存;Loki 设 retention 上限;持续盯内存水位;必要时 Chaos Mesh 退化为脚本注入 |
| 企业微信机器人需要用户提供 webhook | M2 前向用户索取;不可得则退化为 PushPlus |
| **Helm 管理的资源被 ArgoCD 接管时所有权冲突** | M1 用 `Adopt` 注解 + 先 `Prune=false` 观察期,必要时 `Replace=true`;这正是 M1 的价值 |
| k3d 集群重启后状态丢失 | 所有配置入 Git,GitOps 的意义正在于此;写进 runbook |
| 接管存量资源时 ArgoCD 可能误删 | 严格执行 `Prune=false` 观察期,先 dry-run,后放开 |

```
├── 03_runbook/             ← 运维手册 + 演练步骤(告警演练/发布回滚)
├── 04_面试话术/            ← 每个考点一段可直接说的话
├── 05_学习笔记/            ← 【新】概念科普:XX 是什么、为什么这样设计

└── 99_决策日志.md          ← 【新】ADR:每个决策的背景/选项/选择/理由
```

### 三个新文档的分工

| 文档 | 记录什么 | 为什么单独建 |
|---|---|---|
| **05_学习笔记** | 概念问题("ArgoCD 到底是干嘛的") | 这类问题会反复出现,写成能回看的科普比一次性口头解答有价值 |
| **06_踩坑记录** | 报错现场,大小不论 | **忘得最快,也最像真实工作**。运维岗一天的日常就是出问题→查→解决 |
| **99_决策日志** | ADR 格式的决策记录 | 三个月后你会忘记为什么这么选;**写 ADR 本身就是加分项** |

### 记录纪律

1. **踩坑记录不设门槛**:命令打错、端口占用、YAML 缩进、镜像拉不下来——**全都记**。真实工作里 90% 时间花在这些上
2. **排查过程比结论重要**:面试就讲"我试了什么、排除了什么",不是直接给答案
3. **每个决策留 Reject 理由**:证明判断力,比只留 Adopt 清单更有价值
4. **文档随进展实时更新**,不攒到最后补
