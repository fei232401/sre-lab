# M4 发布回滚演练:声明式发布 → 收敛 → 回滚 → 收敛

> **一句话**:让集群用**运行时行为**自证"我现在跑的是哪个版本",然后声明式地把它退回去,再自证一次。
>
> **为什么值得做这一遍**:`编译 → 打包 → 部署` 只是这条链中间的一小段。真正区分"会写 Dockerfile"和"运维"的是两头的问题:**谁触发**、**怎么证明部署成功**、**出事怎么退回去**、**退回去之后怎么证明真退回去了**。

---

## 一、这次和昨晚那次有什么不同

昨晚(M4 上半程)已经跑通过 `git revert` 声明式回滚,机制是通的,但**那次证据不干净**:

- revert **之前**的集群状态,恰好等于 revert **之后**的值
- 于是"变了 → 回滚 → 变回来"这个过程**看不出来**

这次要的是**双向可视**:每一步的变化都要有肉眼可辨、且不依赖"我说它是新的"的证据。

---

## 二、关键设计:让运行时自己报名

### 问题:怎么证明"跑的是新版本"?

| 做法 | 够不够 |
|---|---|
| 看 Pod 上的镜像 tag | ⚠️ 只证明**调度器让它跑这个 tag**,不证明**它真的跑起来了**、也不证明**镜像内容对** |
| 看 `kubectl rollout status` | ⚠️ 只证明 Deployment 认为就绪 |
| **让程序自己报出版本号** | ✅ 从容器内部、经真实数据面取回来 |

### 做法

给 exporter 加一个指标:

```
sre_lab_build_info{revision="a14ce79"} 1
```

版本号从哪来?**构建期注入**,而不是运行时读环境变量:

1. `Dockerfile` 接一个 `ARG GIT_SHA`
2. `Jenkinsfile` 构建时传 `--build-arg GIT_SHA=${SHORT_SHA}`(`SHORT_SHA` = 源码仓该次提交的 7 位哈希)
3. 程序启动时读 `os.environ["GIT_SHA"]`,暴露成指标

**为什么不运行时注入 env**?因为那样镜像内容不再自含版本——同一个镜像换个 env 就"变成"另一个版本,又回到"标签说了算"。**构建期注入 = 镜像内容本身携带版本**,这才是不可变制品。

## 三、时间线(全部为实际观测,非事后推算)

| 时刻 | 动作 / 事件 | 观测到的证据 |
|---|---|---|
| 21:43 | 推送源码变更 `a14ce79` 到 Gitea | push 输出 `ef51c98..a14ce79 HEAD -> main` |
| 21:43–21:49 | **轮询没有自动触发** | 见第五节(这是个真缺陷) |
| 21:49 | 手动触发 build #10 | 构建 Pod `sre-lab-ci-10-...` 起 |
| ~21:51 | 流水线 SUCCESS,写回声明 | Gitea main 前进到 `d7a0b3e`(`ci: bump ollama-exporter to a14ce79`) |
| 21:52:33 | ArgoCD 认到新 revision | `sync.revision=d7a0b3e`,Pod 仍是旧镜像 |
| 21:53:03 | 新 Pod 起来 | Pod image = `a14ce79`,`startTime=13:52:22Z` |
| 21:53:1x | **行为证据(去)** | `sre_lab_build_info{revision="a14ce79"} 1`,同时 `ollama_up 1`(没改坏) |
| 21:53:38 | `git revert d7a0b3e` 并推送 | 声明里 image 回到 `e469f7f`,Gitea main = `09f0510` |
| 21:55:42 | ArgoCD 收敛回退 | `sync.revision=09f0510`,Pod image = `e469f7f`(新 Pod 名) |
| 21:55:59 | **行为证据(回)** | 同一个 `/metrics` 端点,`build_info` **整行消失**(0 行),`ollama_up 1` 仍正常 |

### 为什么"指标消失"比"指标变成旧值"更有说服力

旧镜像**根本没有这个指标**——它是在这次变更里才加进去的。所以回滚后的证据不是"值变了",而是"**这个能力整个不存在了**"。这是一个**结构性**差异,不可能是缓存、不可能是我看错了 tag。

## 四、可复现的命令

```bash
# 1) 造一次真变更(改 exporter.py / Dockerfile,或任何 03-ollama-exporter/ 下的文件)
# 2) 触发构建(本次是手动,webhook 接好后由 Gitea push 自动触发)
curl -X POST "$JENKINS/job/sre-lab-ci/build"        # 需 crumb,见 runbook

# 3) 等 ArgoCD 收敛,采行为证据
POD=$(kubectl --context k3d-ai-cluster -n ai-platform get pods --no-headers | grep ollama-exporter | awk '{print $1}')
kubectl --context k3d-ai-cluster -n ai-platform exec $POD -- python -c "
import urllib.request
print([l for l in urllib.request.urlopen('http://127.0.0.1:9101/metrics').read().decode().splitlines() if 'build_info' in l])"

# 4) 声明式回滚
git revert --no-edit <bump-commit>
git push <gitea> HEAD:main

# 5) 再采一次:应为空列表
```

> ⚠️ 容器是 `python:3.11-slim`,**没有 `wget` 也没有 `curl`**。采指标要用 python 自带的 `urllib`——这个坑本身值得记(见踩坑记录)。

## 五、演练顺带抓到的真缺陷:CI 静默不触发

推送后 6 分钟没动静。诊断过程(比结论值钱):

### 现象
```
Started on Sep 16, 2026, 1:49:41 PM
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
Done. Took 2 ms
No changes
```

### 关键判据:`Took 2 ms`
一次网络往返(去 Gitea 问"远端 HEAD 是什么")不可能在 2 毫秒内完成。**这个数字本身就说明它压根没去问。**

### 根因
轮询需要计算"本次推送改了哪些路径",这要有**上一次构建的工作区**。而我们的 agent 是**即用即销的 k8s Pod**——轮询运行的那一刻,那个节点**必然已经不存在**。于是它降级成"无变更",而且**不报错、不告警**。

### 决定性实验
起一个构建让 agent 活着,趁它活着手动轮询:

```
Started on Sep 16, 2026, 2:11:12 PM
ERROR: no such computer sre-lab-ci-10-1fsrd-r2tv3-bp24r   ← #10 的 agent,早就没了
Done. Took 0 ms
No changes
```

构建 #11 的 agent 明明在跑,轮询报的却是 **#10** 的节点——**它固定去找"上一次已完成构建"的 agent**。结论:**轮询模型和"临时 agent"这个架构根本不兼容**,不是配置问题。

### 教训
1. **"没收到告警"不等于"一切正常"**。CI 静默失效,所有面板全绿。
2. **诊断时先找"物理上不可能的数字"**。2ms / 0ms 这种时间量级异常,比任何日志都直接。
3. 我一度把元凶判成 `PathRestriction`(路径过滤),摘掉它之后**证伪**——轮询照样 0ms。**先复现再下结论**。

### 处置
触发方式从**拉(轮询)**换成**推(webhook)**:Gitea 一收到 push 就主动通知 Jenkins。详见 `03_runbook/04_发布与回滚手册.md`。

## 六、面试口径(可直接讲的版本)

> "我们做过一次发布回滚演练。为了让'跑的是哪个版本'这件事可证,我在构建期把 git SHA 注入镜像,程序通过 `/metrics` 自报版本号——**证据是从容器内部、经真实数据面取回来的**,不是看 Pod 上的 tag 字符串。
>
> 演练是双向的:部署后指标出现且版本号正确,`git revert` 声明式回滚后 Pod 换回旧镜像,**那个指标整行消失**——因为旧镜像根本没这个能力。这比'值变回去了'强得多,它是结构性的差异。
>
> 过程中还抓到一个真问题:我们的 CI 静默不触发了。日志显示轮询 `Took 2 ms` 就返回了 'No changes'——2 毫秒干不完一次网络往返,说明它没去问远端。根因是**轮询依赖上一次构建的工作区,而我们的 agent 是即用即销的 Pod**。这个模型和临时 agent 架构不兼容,所以我们把触发方式换成了 webhook 推送。"

## 七、收尾:触发链路的端到端验收(当晚补记)

M4 的"发布回滚"本身在上表就结束了。但当时触发是**手动**的——链路并没有真的通。当晚把触发补齐并验完:

| 构建 | 触发来源 | 触发原因原文 | 闸门判定 |
|---|---|---|---|
| #13 | 手动 | `Started by user Jenkins Admin` | 命中(`ci/Jenkinsfile`)→ **构建** |
| #14 | **SCM 轮询** | `Started by an SCM change` | 跳过(只改了 `sre-lab-gitops/`) |
| #16 | **webhook(重投)** | `Gitea push  () by ` | 命中(`ci/Jenkinsfile`)→ **构建 81cc34e** |
| #17 | **webhook** | `Gitea push refs/heads/main (bf43ff97...) by fei232401` | 跳过 → **循环终止** |

**#14 是个意外收获,也是我今晚唯一一次推翻自己结论的地方**——它是轮询触发的,而且成功了。详见 `06_踩坑记录.md` P18 的「修正」一节。

**#16 → #17 这一对是完整的闭环证据**:

- #16 是被 webhook 触发的真构建,推的是 `81cc34e`
- 它跑完写回 GitOps,那次 push 又触发 **#17**
- #17 判定"只改了 `sre-lab-gitops/`"**早退**,循环止步于此(没有 #18)

而且 #17 的控制台里能看到新逻辑生效:

```
本次推送范围: 81cc34e..bf43ff9(由 webhook 提供)
```

**收敛侧的行为证据**(最终态):

```
ArgoCD revision = bf43ff9  Synced / Healthy
Pod image       = .../ollama-exporter:81cc34e
sre_lab_build_info{revision="81cc34e"} 1
```

> ⚠️ **采这一条时踩了个小坑,值得单独说**:滚动更新期间集群里**同时存在新旧两个 Pod**,我第一次采到的是**正在退场的旧 Pod**,拿到 `revision="238c406"`——一个**过期的、但看起来完全正常的值**。
>
> **教训:"从容器里采到的"不等于"是对的"。** 采样前要先确认**你在采哪个 Pod**;容器编排系统在收敛过程中,任一时刻都可能有两代并存。**这也正是本项目坚持用"运行时自报版本"的原因——它至少能让这种错误暴露出来(值对不上),而只看 Pod 上的 tag 字符串连暴露的机会都没有。**
