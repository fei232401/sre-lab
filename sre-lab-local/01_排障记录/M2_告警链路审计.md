- **日期**:2026-09-16
- **对象**:`monitoring` helm release(chart `kube-prometheus-stack-87.19.1` / app `v0.92.1`,rev 4)
- **结果**:告警数 **39 → 1**,剩余 1 条是设计上永远 firing 的 `Watchdog`

## 一、先纠正 M0 的一处判断错误

M0 发现 3 写的是:

> **"Alertmanager 的 receiver 是出厂默认的 `null`。这是那 43 天。"**
> "绝大多数人装完就忘了这一步。"

**这个框定是错的。** 用户澄清:**当时是主动把告警打进黑洞的** —— 原因是频繁的无效告警 + 项目已完工 + 集群不必维护。

所以正确的表述是:**那不是"没人发现的疏漏",是"当时主动做的选择"。**

> **教训:判断"为什么是这样"时,不能只看现状,还得问当时的人。** 现状能告诉你 `receiver: "null"`,但告诉不了你它是"忘了配"还是"故意配的"。这两种情况的对策完全不同 —— 前者是修 bug,后者是先解决**为什么会有那么多无效告警**,再接通道。
>
> 这一条恰好印证了 M2 的顺序约束:**先降噪,再接通道**。当时的作者正是因为噪音太大才把通道关掉的;如果现在直接接上微信,等于让他重来一遍。

## 二、降噪:三条控制面假阳性

### 现象

```
firing  KubeControllerManagerDown
firing  KubeSchedulerDown
firing  KubeProxyDown
```

### 根因

**k3s 把 controller-manager / scheduler / kube-proxy 编译进单个 `k3s server` 进程**,不作为独立 Pod 运行,也不暴露独立的 metrics 端点。

这些告警的表达式是 `absent(up{job="kube-proxy"})` 这类形式 —— 靠"目标不存在"来判定组件挂了。而在 k3s 里**这些 job 根本不存在**(不是 down,是零 target),于是 `absent()` 恒为真。

配套证据(实测):三个组件对应的 Service / Endpoints 全是空的,selector 指向真 kubeadm 集群才有的标签(`component=kube-scheduler` 等)。

### 处置:关掉源头,而不是压制告警

```yaml
kubeControllerManager:
  enabled: false
kubeScheduler:
  enabled: false
kubeProxy:
  enabled: false
```

**为什么关 `enabled` 是最干净的**:chart 模板第一行就是 gating 条件,一次砍掉整组 ——

```
Service + ServiceMonitor + Endpoints(不再有空的 target)
+ 整组 PrometheusRule(KubeProxyDown 及其二级告警 KubeProxyInstanceUnreachable)
```

**实测验证**(渲染 + 集群双确认):

| 检查项 | 结果 |
|---|---|
| 渲染结果里这三个组件的任何资源 | 0 个 |
| 渲染结果里 `alert: (KubeProxyDown\|KubeSchedulerDown\|KubeControllerManagerDown)` | 0 次 |
| 集群里对应的 Service / ServiceMonitor | 已全部清除 |
| 集群里对应的 PrometheusRule | 已全部清除 |
| **Prometheus 实际告警数** | **39 → 1** |

**对比另外两条路:**

| 方案 | 评价 |
|---|---|
| `defaultRules.disabled: {KubeProxyDown: true}` | 只删这一条 alert,**保留空的 target**。Prometheus UI 里仍然是缺口。适合"留着 target 以备将来接真组件" |
| ~~同名 PrometheusRule 覆盖~~ | ❌ M1 已用 Watchdog 实验证伪:Prometheus 里同名规则**并存不覆盖** |

## 三、`k3s-kubeproxy-silence.yaml` 是一个**静默失效的假动作**

M1 保留了这条待定项。结论出来了:**它一条都压不住。**

### 机制

prometheus-operator 有个 `namespaceEnforcer`,会往 AlertmanagerConfig 生成的子路由里**强制注入 `namespace` matcher**(源码 `amcfg.go`):

```go
func (ne *namespaceEnforcer) processRoute(crKey types.NamespacedName, r *route) *route {
	r.Matchers = append(r.Matchers, Matcher{
		Name: "namespace", Value: crKey.Namespace, MatchType: MatchEqual,
	}.String())
	return r
}
```

生成的子路由实际是:

```yaml
- receiver: blackhole
  matchers:
    - alertname =~ "KubeProxyDown|KubeSchedulerDown|KubeControllerManagerDown"
    - namespace = "monitoring"     # ← operator 强行注入
  continue: true
```

### 致命点

**那三条告警的 label 里根本没有 `namespace`**(Prometheus CR 的 `externalLabels` 为空)。而 **matcher 对缺失的 label 不匹配**。

⇒ **这份文件从未生效过。** 它躺在仓库里,让人以为"k3s 假阳性已经处理了"。

> **比没有更危险。** 没有的时候你知道有问题;有一份看起来对的文件时,你会以为问题已经解决了。

**处置**:已由第二节的 `enabled: false` 从根上解决,该文件**删除**。

### 附带确证:AlertmanagerConfig 空选择器的语义

之前不确定 `alertmanagerConfigSelector: {}` 是"匹配全部"还是"匹配空"。源码 `apimachinery/pkg/apis/meta/v1/helpers.go`:

```go
func LabelSelectorAsSelector(ps *LabelSelector) (labels.Selector, error) {
	if ps == nil {
		return labels.Nothing(), nil     // nil -> 什么都不匹配
	}
	if len(ps.MatchLabels)+len(ps.MatchExpressions) == 0 {
		return labels.Everything(), nil  // {}  -> 匹配全部
	}
```

**`{}` = 匹配全部。** 这是 M3+ 如果用 AlertmanagerConfig 做路由必须知道的前提。

## 四、`AlertmanagerClusterCrashlooping`:**根因未确认**(诚实标注)

### 我曾经相信的错误解释

调研报告给出的结论是:**"不是真重启,是 k3d/WSL2 节点时钟漂移"**,证据是:

```
node_time_seconds - time()  三个节点分别为 -7.5 / -15.4 / -26.9 秒
```

### 这个解释是错的

我实测复查了这条查询,发现**它测的根本不是时钟偏差**:

| 查询 | 语义 | 实测结果 |
|---|---|---|
| `node_time_seconds - time()` | `time()` 是**查询求值时刻**,`node_time_seconds` 是**抓取时刻**的值 → 相减得到的是**样本年龄** | −12.81 / −1.30 / −23.32,**每次采样都不同** |
| `node_time_seconds - timestamp(node_time_seconds)` | 用 `timestamp()` 拿到该样本的抓取时刻,才是真正的偏差 | **+0.006 / +0.008 / +0.018 秒** |

**时钟是亚 20 毫秒级同步的,没有漂移。**

> **这是个值得记住的 PromQL 陷阱**:`metric - time()` 得到的是**样本年龄**,不是"指标值与当前时间的差"。要比较"指标里的时间戳"和"抓取时刻",必须用 `timestamp()`。
>
> 更普遍地说:**一个"看起来合理"的因果解释,如果不实测验证,就会变成文档里的幻觉。** 幸好这次在写进文档前复查了。

### 实际观测到的事实

规则原文:

```promql
count by (namespace, service, cluster) (
  changes(process_start_time_seconds{container="alertmanager",...}[10m]) > 4
) / count by (...) (up{...}) >= 0.5
for: 300s
```

即:**10 分钟内 Alertmanager 进程启动时间变更超过 4 次**才触发。

实测现状:

| 项 | 值 |
|---|---|
| `process_start_time_seconds` 序列数 | **1 条** |
| 该值 | `2026-09-15 23:32:50`(Pod 启动时刻) |
| `changes(...[10m])` | **0** |
| `kube_pod_container_status_restarts_total` | 8(43 天累计,非近期密集) |
| 当前规则状态 | **inactive** |

### 结论

- 该告警**当前不响**,是被这次 helm upgrade 重启 Alertmanager 清掉的
- **根因未确认。** `changes() > 4` 要求 10 分钟内 5 次以上启动时间变更,但 43 天累计重启才 8 次 —— **这两个事实对不上**,我没有找到成立的解释
- **不作处置,标记为观察项。** 不为一个自己没有验证过的现象写"修复"

## 五、当前告警链路状态(2026-09-16 更新:通道已打通)

```
Prometheus --(规则求值)--> Alertmanager --(route)--> email   ✅ 实测投递成功
   3 条 firing                              ├────────> quiet  (Watchdog,设计如此)
                                            └────────> null   (兜底,已无流量)
```

降噪在先、接通道在后,顺序没有反:

> **先降噪,再接通道。** 反过来的话,用户收到的第一条消息就是三条永不停止的假警报,几天之内他就会开始忽略告警 —— 这叫**告警疲劳**,是 SRE 领域公认的头号告警失效模式。

### 5.1 侧收获:那 5 个"存在但从未生效"的对象

接通道时顺带核对"哪些规则真的在跑",挖出 5 个在 etcd 里躺了 43 天、`status` 正常但 Prometheus 从未加载的对象——根因是 `release` 标签值写错。详见 `06_踩坑记录.md` P12、P13。

修复后实测(修复前同一命令无输出):

```
$ curl -s localhost:19090/api/v1/rules | grep -iE "sre-lab|ollama-slo|nginx-demo"
[monitoring-sre-lab-cluster-alerts-...]  sre-lab.k8s             rules=3
[monitoring-sre-lab-cluster-alerts-...]  sre-lab.node            rules=3
[ai-platform-ollama-slo-rules-...]       ollama.availability     rules=5
[ai-platform-ollama-slo-rules-...]       ai-platform.general     rules=2
[nginx-demo-nginx-demo-rules-...]        nginx-demo.availability rules=2
```

5 个里 4 个已真正生效。剩下的 `ServiceMonitor/nginx-demo-monitor` **有三处独立错误且修好了也不对**,已删除,理由见 P13。

### 5.2 通道打通的实测证据(三层各自独立取证)

接收端最终选**邮件**(而非 D12 的企微适配器;原因与完整决策见 `99_决策日志.md` D15)。

| 层次 | 取证方式 | 结果 |
|---|---|---|
| 配置生成 | 解出 `alertmanager-monitoring-kube-prometheus-alertmanager-generated` 里的 `alertmanager.yaml.gz` | 子路由 `receiver: monitoring/sre-lab-alerting/email`;**无注入的 namespace 匹配器**;`auth_password` 已解析 |
| 通道可达 | `alertmanager_notifications_total{integration="email"}` | **2** |
| 投递失败 | `alertmanager_notifications_failed_total{integration="email",reason=~".*"}` | **全 0** |
| 端到端 | 向 v2 API `POST /api/v2/alerts` 注入真实告警 | HTTP 200 → 进入 `active` → 触发投递 |

**为什么必须看 `notifications_total` 而不是看日志**:Alertmanager 默认 `log.level=info`,**成功的通知不写日志**,只有失败才写。所以"`kubectl logs` 里没有 error"完全不能证明消息发出去了——那一刻它可能一条都没发。计数器是这里唯一可信的证据。

### 5.3 一个差点踩进去的黑洞:namespace 匹配器注入

`AlertmanagerConfig` 是命名空间级 CRD,而 prometheus-operator **默认会往它生成的每一条子路由注入 `namespace = "<CR 所在命名空间>"` 匹配器**(`alertmanagerConfigMatcherStrategy.type` 默认 `OnNamespace`)。

我们的 CR 在 `monitoring` 命名空间。不改这个设置的后果:**只有带 `namespace=monitoring` 标签的告警能匹配到邮件路由,其余全部回落到根路由的 `null` receiver。**

这是本文档第三节那个机制的**另一次出现**——而且更隐蔽:配置生成成功、Alertmanager 加载成功、`notifications_total` 稳稳不动,**没有任何一处报错**。所以 D15 把 `alertmanagerConfigMatcherStrategy: None` 放在实施顺序的第一步。

### 5.4 仍然存在的边界(诚实标注)

- **邮件是兜底通道,不是主通道。** 手机邮件推送延迟显著高于 IM,不适合 P1 级故障的实时响应
- **`AlertmanagerClusterCrashlooping` 仍在响**,根因未确认(见第四节)
- **`Watchdog` 走 `quiet` receiver。** 它按设计永远 firing,走邮件等于制造噪音;但它仍留在 Alertmanager 中,`Alertmanager` 自身存活与否由它体现
- **`CPUThrottlingHigh` 在 `ai-platform` 观测到进入 `pending`。** pending 状态的告警**不会推送给 Alertmanager**(只有 firing 才推),所以目前不产生通知

## 六、接收端方案的已知约束(来自调研)

> ⚠️ **本节已被 `99_决策日志.md` D15 取代。** 企微群机器人方案因"个人版企微无法建群"在物理上走不通,最终改用邮件。本节保留,是因为其中对候选方案的调研结论、以及企微侧的硬约束数据仍然有效,将来拿到企业权限切回 IM 通道时可以直接复用。

### 现有 `wechat-adapter.yaml` 是最坏范式

```yaml
image: python:3.9-slim          # 启动时 pip install flask requests
args: [sh, -c, "pip install ... && python -c '<heredoc 塞源码>'"]
```

三个问题各自独立成立:

1. **启动依赖公网 PyPI,且不 pin 版本** → 同一次 commit 今天能跑明天可能跑不起来,构建**不可复现**
2. **必须可写根文件系统**(pip 要写 site-packages)→ 无法开 `readOnlyRootFilesystem`
3. **源码藏在 Deployment 的 `args` 里** → 无法 code review、无法单测、无法单独版本化

### 选定方案:`bougou/alertmanager-webhook-adapter`

| 项 | 值 |
|---|---|
| 语言 / 许可 | Go / Apache-2.0 |
| 最后 push | **2026-08-31**(调研日 2026-09-15 前两周) |
| 最新 release | v1.1.14(2026-08-30) |
| 支持渠道 | `weixin`(企微群机器人)/ `weixinapp` / `dingtalk` / `feishu` / `slack` |
| 交付形态 | Docker 镜像 + Helm chart + `deploy/k8s/` 原生清单 |

**它是能找到的唯一近 30 天仍有提交的中文告警适配器。** 其余候选全部停更 1~4 年。

**注意一个安全影响**:该项目的 token 走 **URL query**(`?channel_type=weixin&token=...`),而 URL 要写进 Alertmanager 的 `webhook_configs.url` → **token 就落进了 Alertmanager 的配置存储**(即那个 `-generated` secret)。

这**不比现状更糟**(Alertmanager 配置本来就是 Secret,不进 Git),但**密钥边界变了**:从"一个 k8s Secret + SealedSecret"变成"Alertmanager 配置本身"。而现状的坑恰恰是 Alertmanager 配置**不在 GitOps 里**。

> 所以方案里必须有一节专门解决:**receiver 配置怎么进 GitOps**。这是接通道之前的前置问题。

### 企微侧硬约束

| 约束 | 值 |
|---|---|
| 接口 | `POST https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=KEY` |
| markdown content 上限 | **4096 字节**(超出会被截断或报错) |
| text content 上限 | 2048 字节 |
| **限频** | **每个机器人 20 条/分钟** |
| 成功返回 | `{"errcode":0,"errmsg":"ok"}` |

**限频要自己做**:社区有"超频时仍返回 `errcode:0` 但消息实际被丢弃"的反馈(属社区经验,非官方承诺)。所以适配器**不能只靠 errcode 判断成功**,得自己做发送侧限速与聚合。
