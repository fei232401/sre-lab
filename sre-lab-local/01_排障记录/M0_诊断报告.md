## 发现 1:6 个僵尸 Pod 的四层盲区

### 现象

```
ai-platform   vllm-3b-7c59d66664-ddppp   0/1   ContainerStatusUnknown    5d
ai-platform   vllm-3b-7c59d66664-jlns7   0/1   ContainerStatusUnknown    7d4h
ai-platform   vllm-3b-7c59d66664-qp4k6   0/1   ContainerStatusUnknown    30d
ai-platform   vllm-3b-7c59d66664-t4jlb   0/1   UnexpectedAdmissionError  3d7h
ai-platform   vllm-3b-7c59d66664-v9mpx   0/1   ContainerStatusUnknown    18d
ai-platform   vllm-3b-7c59d66664-w2jzp   0/1   ContainerStatusUnknown    6d2h
```

而 Deployment 报的是 **`1/1 Ready`**——它认为自己完全健康。

### 为什么没有任何告警

这 6 个 Pod 的 phase 是 **`Failed`**。把 kube-prometheus-stack 的三条默认规则逐条比对:

| 规则 | 表达式 | 为什么看不见 Failed |
|---|---|---|
| `KubePodNotReady` | `kube_pod_status_phase{phase=~"Pending\|Unknown"}` **or** (`phase="Running"` 且 `ready=0`) | **phase 白名单里根本没有 `Failed`** |
| `KubePodCrashLooping` | `kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"}` | 终态准入失败的容器**从未进入 waiting 状态** |
| `KubeContainerWaiting` | `kube_pod_container_status_waiting_reason{reason!="CrashLoopBackOff"}` | 同上,容器不在 waiting |

### 为什么对象一直没被删

| 层 | 职责 | 为什么没动手 |
|---|---|---|
| ReplicaSet 控制器 | 维持期望副本数 | `status.replicas: 1`——它**只数活跃 Pod**,Failed 不算活跃。补到 1 个就走了,**不负责清理失败的** |
| kubelet | 回收本节点的 Pod | `UnexpectedAdmissionError` 意味着 **admission 阶段就被拒**,Pod 从未在 kubelet 上落地 |
| PodGC 控制器 | 清理全局终态 Pod | 仅在**全局终态 Pod 总数超过 `--terminated-pod-gc-threshold`(默认 1250)**时才动手。6 ≪ 1250 |
| 人 | 看监控 | 见发现 3——**告警压根发不出来** |

### 结论

> **四层机制,每一层都"以为别人会管"。** 这不是某个组件的 bug,是 Kubernetes 默认行为叠加出的**结构性盲区**。而 `UnexpectedAdmissionError` 这个状态本身具有**隐蔽性三连**:不重试、不 CrashLoop、不累积 restartCount——`kubectl get pods` 的表头看着干干净净。

### 修复方案(留给 M2)

需要一条 kube-prometheus-stack 默认集里**不存在**的规则,覆盖"终态失败":

```promql
kube_pod_status_phase{phase="Failed"} == 1
```

配合 `kube_pod_status_reason` 区分是 `Evicted` / `UnexpectedAdmissionError` / `NodeAffinity`,按 reason 分级。

## 发现 2:真因是 GPU 设备健康检查的窗口期

僵尸 Pod 的 status message:

```
Pod was rejected: Allocate failed due to no healthy devices present;
cannot allocate unhealthy devices nvidia.com/gpu, which is unexpected
```

**不是"WSL 没有 GPU",是"GPU 有一段时间被标记为不健康"。**

### 证据链

```
nvidia-device-plugin 日志:  I0915 14:24:57  Registered device plugin for 'nvidia.com/gpu' with Kubelet
vllm Pod 启动时间:          started = 2026-09-15T14:25:02Z
```

**间隔 5 秒。** 今天 14:24:57 之前 GPU 不可用,之后可用——vllm 立刻起来了。

### 时间线(与 WSL 重启一一对应)

| 僵尸 Pod 创建时间 | 距今 |
|---|---|
| 2026-08-16 01:20 | 30 天 |
| 2026-08-28 10:27 | 18 天 |
| 2026-09-08 11:51 | 7 天 |
| 2026-09-09 13:30 | 6 天 |
| 2026-09-10 15:21 | 5 天 |
| 2026-09-12 08:54 | 3 天 |

**6 次 WSL / 容器重启,每次留下一个。** 全集群 Pod 的 restartCount 集中在 8~13 且最近一次同步于 111 分钟前,佐证节点级重启。

### 机理

WSL2 通过 `/dev/dxg` 直通 GPU。每次 WSL 重启后:

1. k3s 节点容器重建 → kubelet 重新拉起
2. nvidia-device-plugin 重新探测设备 → **有一段"已注册但健康检查未通过"的窗口**
3. 此刻 ReplicaSet 正在补 vllm 的 Pod → Pod 带 `nvidia.com/gpu` 请求
4. kubelet admission:设备不健康 → **拒绝,并置为终态 `Failed`**

窗口只有几秒,所以每次重启通常只留下一具尸体。

### 为什么这是好素材

真实生产里对应的场景是**设备插件/驱动升级期间的设备抖动**,机理完全一致。面试可以讲:"我遇到的不是'GPU 坏了',而是'GPU 在某个窗口里被标记为不健康,而这个状态在 Kubernetes 里是终态,不重试'。"

## 发现 3:Alertmanager 的 receiver 是出厂默认的 `null`

`monitoring-kube-prometheus-alertmanager` 的配置原文:

```yaml
receivers:
- name: "null"
route:
  receiver: "null"
  group_by: [namespace]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
```

**`receivers:` 里只有一个叫 `null` 的空接收器,`route.receiver` 指向它。**

这是 kube-prometheus-stack 的**出厂默认值**——图表作者故意不给可用的 receiver,强制用户自己配。绝大多数人装完就忘了这一步。

### 这意味着

- 告警**规则正常求值**(39 条在 firing/pending,已实测)
- Prometheus **正常推送**给 Alertmanager
- Alertmanager **正常分组、正常抑制**
- **然后全部路由进一个什么都不做的接收器**

**链路 100% 健康,唯一断点是最后一跳。** 这就是那 43 天。

### 为什么这是 M2 最有价值的靶子

> "没有人听的告警等于没有告警。"

这句话在面试里如果只当口号讲,是空话;如果能拿出"我的集群里 Alertmanager receiver 是默认的 null,我把它挖出来了",就是**实证**。

## 发现 4:39 条告警在响,4 条是 k3s 结构性假阳性

实测 `/api/v1/alerts`:

| 状态 | 告警 | 判定 |
|---|---|---|
| firing | `KubeControllerManagerDown` | ❌ 假阳性 |
| firing | `KubeSchedulerDown` | ❌ 假阳性 |
| firing | `KubeProxyDown` | ❌ 假阳性 |
| firing | `AlertmanagerClusterCrashlooping` | ❌ 假阳性 |
| firing | `Watchdog` | ✅ 设计如此(死信开关) |
| pending | `PrometheusMissingRuleEvaluations` × 34 | ⚠️ 待定性 |

### 假阳性的原因

**k3s 把 controller-manager / scheduler / kube-proxy 编译进单个 `k3s server` 进程**,不作为独立 Pod 运行,也不暴露独立的 metrics 端点。kube-prometheus-stack 的默认规则是照标准 kubeadm 集群写的,于是这三条**永远 firing**。

### 为什么必须在接微信之前解决

如果直接接上企业微信,用户收到的第一条消息就是三条永不停止的假警报。**几天之内他就会开始忽略告警**——这叫**告警疲劳**,是 SRE 领域公认的头号告警失效模式。

> **这是 M2 的关键顺序约束:先降噪,再接通道。** 反过来做,等于亲手毁掉这套告警的可信度。

## 发现 5:仓库里有一整套写完但从未部署的 GitOps 结构

`sre-lab-gitops/production/` 下有 **31 个文件**,最后提交于 **2026-06-29**,集群里**一个对象都没部署**:

```
bootstrap/            root-app.yaml + 6 个 Application 定义(完整 App-of-Apps 模式)
apps/ai-platform/     namespace / hpa / ingress / pdb / ollama-stack / open-webui
apps/loki/            deployment.yaml
apps/promtail/        deployment.yaml
apps/nginx-demo/      namespace / deployment / service / ingress / middleware
apps/sealed-secrets/  controller.yaml + secrets-template.yaml
monitoring/           cluster-alerts / grafana-ingress / prometheus-ingress
                      k3s-alert-patches.yaml        ← 已经在解 k3s 假阳性
                      k3s-kubeproxy-silence.yaml    ← 已经在做 Alertmanager 黑洞路由
                      wechat-adapter.yaml
                      ollama-exporter / nginx-monitor / servicemonitor-patch
```

### 对 M1 的影响

**M1 不是"从零用 ArgoCD 接管存量",而是"审计 + 修复 + 部署这套已存在的结构"。**

三条必须先回答的问题:

1. **`root-app.yaml` 开了 `prune: true` + `selfHeal: true`,并且指向 `bootstrap/` 目录。** 一旦部署,它会创建 6 个子 Application。**这批子 Application 里有多少会立刻在集群里造出新东西?** 必须先 dry-run。
2. **目录结构是四份重复的**(`manifests/` / `production/` / `k3s-ai-platform/environments/prod/` / `k3s-ai-platform/reference/baseline-manifests/`),`wechat-adapter.yaml` 就有 4 个副本。**必须先决定哪一份是真相来源**,否则 ArgoCD 接管的是哪一份都说不清。
3. **`k3s-alert-patches.yaml` 的手法值得商榷。** 它用一条同名 `PrometheusRule` 覆盖默认规则,表达式写成 `absent(up{job="kube-proxy", namespace="k3s-does-not-have-kube-proxy"} == 1)`——**靠一个不存在的 namespace 让规则永远为 false**。这能工作,但是"降维打击"式的 hack:读者需要理解为什么这个 namespace 不存在。**更干净的做法是在 Helm values 里直接关掉对应的 rule,`production/apps` 里那条 `AlertmanagerConfig` 黑洞路由同理。**

> 这三点正是 M1 要拍板的内容。**已有的不等于正确的**——2026-06-29 那一版的作者(也是用户自己)当时显然卡在了某一步。

## 发现 6:硬约束——agent-0 内存 81%

```
Mem(宿主机 WSL): total 19G, used 8G, free 0, buff/cache 10G, available 8G

k3d-ai-cluster-agent-0    6.499GiB / 8GiB   ← 81%,且有 GPU
k3d-ai-cluster-agent-1    871MiB  / 8GiB   ← 11%,几乎空着
k3d-ai-cluster-server-0   699MiB  / 3GiB
k3d-ew-cluster-server-0   746MiB           ← 闲置(项目二)
k3d-topo-demo-*(5 个)     ~575MiB 合计     ← 项目三,只读
```

**问题**:监控栈(Prometheus,内存大户)整个跑在 agent-0,而 agent-0 也是唯一带 GPU 的节点。`Allocated resources` 显示 memory requests 已占 74%。

**加 Jenkins(~1-1.5G)+ ArgoCD(~0.5G)会直接顶爆。**

计划里写的"停掉闲置的 `k3d-ew-cluster`"只省 750MB,不够。候选方案:

| 方案 | 收益 | 代价 |
|---|---|---|
| 停 `ew-cluster` | ~750MB | 无(项目二已暂缓) |
| 提高 agent-0 的 8G 上限 | 直接 | 需要重建集群容器,**会丢当前状态** |
| 把新组件调度到 agent-1 | 避开瓶颈 | agent-1 无 GPU,但 ArgoCD/Jenkins 本来就不需要 GPU |
| 清理 docker 构建缓存 | 6.2GB **磁盘**(非内存) | 无 |

**倾向:停 ew-cluster + 用 nodeSelector 把 ArgoCD/Jenkins 钉在 agent-1。** 需要用户拍板。

## 安全问题:PushPlus token 泄露范围比记录的更大

| 项 | 记录值 | **实测值** |
|---|---|---|
| 泄露文件数 | 1 | **4** |
| 泄露 commit 数 | 未记录 | **3** |
| 仓库可见性 | 公开 | 公开 |

四个文件(同一 token,第 47 行):

```
sre-lab-gitops/production/monitoring/wechat-adapter.yaml
sre-lab-gitops/manifests/monitoring-stack/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/environments/prod/monitoring/wechat-adapter.yaml
sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/wechat-adapter.yaml
```

涉及 commit:`f76f69d` / `d4c66d1` / `e96165f`。

**并且这个 adapter 从未部署**(集群里 0 个对象)——即这个 token 目前是"公开挂在网上、但没有任何东西在用"。

### 处理顺序(有依赖关系)

1. **用户去 pushplus 后台吊销旧 token**(必须本人操作)
2. 生成新 token
3. 存成 k8s Secret
4. 用 Sealed Secrets 加密后入库(`production/apps/sealed-secrets/` 已有骨架)
5. 删除 4 个明文文件
6. **git 历史仍留有 token** — 已吊销的 token 留在历史里是可接受的;若要求彻底清除需 `git filter-repo` 重写历史并在 GitHub 强推,代价大
