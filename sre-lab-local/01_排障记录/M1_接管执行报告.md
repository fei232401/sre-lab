## 二、`ai-platform-app`:不 apply,理由有三层

这是本次最需要判断的一个。它的 `syncPolicy` 是 `automated{prune:false, selfHeal:false}` —— **看起来最保守**,但实际风险反而最需要拆开看。

### 第 1 层:它不是"纯接管",是"接管 + 新部署"

| 对象 | 集群现状 |
|---|---|
| `Deployment/ollama`、`Service/ollama-service` | **已存在 43 天**,手工 `kubectl apply`(有 `last-applied-configuration`,无 Helm、无 ArgoCD tracking) |
| `Deployment/open-webui`、`Service/open-webui-service`、`PVC/open-webui-pvc` | 不存在 |
| `HPA/ollama-hpa`、`HPA/open-webui-hpa` | 不存在 |
| `PDB/ollama-pdb`、`PDB/open-webui-pdb` | 不存在 |
| `Ingress/sre-lab-ingress` | 不存在 |

已逐字段比对:repo 里的 `ollama-stack.yaml` 与集群里 live 的 ollama **内容一致**(镜像 / 探针 / resources / nodeSelector / volume 全同)。

> **所以 apply 不会改坏正在跑的 ollama。** 但它会**新起一整套 open-webui**(含 PVC)+ 2 个 HPA + 2 个 PDB。

**问题不在于"会不会坏",在于"这是不是你现在想做的事"。** `open-webui` 是否要现在上线,是个产品决定,不是运维决定。

### 第 2 层:`ai-platform` 命名空间里有**不在 Git 里**的工作负载

实测该命名空间里还有:

```
ai-infra-gateway        40d   手工 apply   ← 不在 Git
vllm-3b                 40d   手工 apply   ← 不在 Git
cyberrouter-operator    40d   手工 apply   ← 不在 Git
```

**当前 `selfHeal:false` 所以暂时安全。** 但这是个装了引信的状态:**只要哪天有人为了"自愈"把 `selfHeal` 打开,ArgoCD 会认为这三个对象是"不该存在的",而 `prune` 是否触发取决于那时 `prune` 的值。**

> **规律:`selfHeal:true` + `prune:true` 的组合,对"半接管"的命名空间是危险的。** 一个命名空间要么完整交给 GitOps,要么完全不交 —— **中间态会在某次"顺手打开 selfHeal"时爆掉。**

### 第 3 层:路径约定不一致

`monitoring-app` 的 path 是 `production/monitoring`,而其余 5 个用的是 `production/apps/*`。**统一路径约定应该和 root-app 的落地一起做,不是现在单独动一个。**

### 结论

**留给用户拍板**,需要回答的是:

1. `open-webui` 现在要不要上线?
2. `ai-infra-gateway` / `vllm-3b` / `cyberrouter-operator` 要不要一并纳入 Git?(否则永远有第 2 层的引信)

## 三、`monitoring-app` 与 `root-app`:硬性拦下

### `monitoring-app`

`production/monitoring/` 下 7 个文件、12 个对象。其中 `wechat-adapter.yaml` **第 47 行硬编码明文 PushPlus token**。

实测:这 12 个对象**目前在集群里全部不存在**(已逐个 `get` 验证)。所以 `prune: true` 暂时是空转的,**真正的风险就是那一个 Deployment** —— apply 即把明文凭证部署进集群。

**前置条件**(见 `03_runbook/02_ArgoCD_运行手册.md` 第四节):

```
先重写/删除 wechat-adapter.yaml  →  确认目录里无明文  →  才能 apply monitoring-app
```

### `root-app`

`root-app` 的 path 是 `production/bootstrap`,里面装着**全部** Application 定义。

**apply 它 = 一次性创建所有子 App,包括 `monitoring-app`。** 而 `monitoring-app` 是 `automated`,会自动 sync。

> **所以 `root-app` 的 apply 被 `monitoring-app` 阻塞。** 这是"应用的依赖"而不是"集群的依赖" —— 光看 `root-app` 自己的定义看不出这层关系。

**这在面试里是个好例子**:**声明式系统里的依赖关系,不写在对象的 spec 里,藏在目录结构里。**

## 四、顺带发现的真实缺陷:promtail 挂了一个永远为空的目录

### 现象

promtail DaemonSet 挂了两个 hostPath:

```
pods-logs   -> /var/log/pods              (13 项,真实有内容)
docker-logs -> /var/lib/docker/containers (0 项,永远是空的)
```

节点上实跑确认:`/var/lib/docker/containers` 存在但**空**,`/var/log/pods` 有 13 项。

### 根因

**本集群是 k3s,k3s 用 containerd,不用 Docker。**

Docker 会把容器日志写到 `/var/lib/docker/containers/<id>/<id>-json.log`。containerd 不写这个目录,它写 `/var/log/pods/`。**这份清单是照 Docker 集群写的。**

### 影响

**不影响运行** —— DaemonSet 3/3 Ready,真正的采集走 `/var/log/pods`(已核对 promtail 配置,`__path__` 只用了 `/var/log/pods/*$1/*.log`)。

**但那个挂载点是无用的**,而且它是个**误导**:看清单的人会以为日志是从 docker 目录采的,排障时可能去查一个根本不相干的路径。

### 处置

**本次不动**(改了要重新同步,而收益只是删一个空挂载)。记录为待清理项。

> **面试价值**:这个坑的通用形态是 —— **清单是照 A 环境写的,搬到 B 环境后有一部分静默失效,因为不报错所以没人发现。** 和 M2 里那份"从未生效的告警静默文件"是同一类问题。

## 五、其他观察

| 观察 | 是否问题 |
|---|---|
| `production/helm-values/monitoring-values.yaml` 与 `production/argocd/argocd-values.yaml` 不被任何 Application 引用 | ❌ **不是**。这是 D14 的刻意设计 —— 监控栈与 ArgoCD 本身由 Helm 管理,values 由 `helm upgrade -f` 手工消费,不进 GitOps,避免双重管理 |
| `production/monitoring/` 不在 `production/apps/` 下 | ⚠️ 路径约定不一致,建议与 `root-app` 落地一起统一 |
| `ai-platform` 里的 `PVC/ollama-models`(20Gi, Bound)不在 Git 中 | ⚠️ 清单只以 `claimName` 引用,无冲突。但 PVC 不在 Git 里意味着**集群重建后数据声明会丢** |
| `loki` 被调度到 `server-0`(无 nodeSelector) | ⚠️ 与 ArgoCD / sealed-secrets 的"钉 agent-1"策略不一致,见 D7 |
