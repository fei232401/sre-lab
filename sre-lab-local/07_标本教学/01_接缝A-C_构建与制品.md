## 〇、心智模型:九段传送带,痛点在接缝

CI/CD 不是"一堆工具",是一条**从一行代码到集群里一个 Pod 的传送带**。把这条带子拆开,是九个段落:

```
① 代码 → [接缝A] → ② 构建 → [接缝B] → ③ 制品 → [接缝C] → ④ 登记 → [接缝D] → ⑤ 声明 → … → ⑨ 部署/回滚
   ↑                                                      ↑
 版本控制                                             镜像仓库
```

每一段本体都好理解:代码就是 git 仓库里的文件,构建就是 `docker build`,制品就是一个镜像,登记就是 `docker push`。

**真正吃人的是接缝。** 每一道接缝上,两边对"什么东西应该存在"的假设不一样,而这个不一致**通常不报错**:

| 接缝 | 两边的假设 | 假设不一致时的表现 |
|---|---|---|
| **A**:代码 → 构建 | 构建方假设"我要的文件在仓库里";仓库方并不知道构建方要哪些文件 | 构建根本跑不起来 —— **或者更糟:跑起来了,但产出的是另一个东西** |
| **B**:构建 → 制品 | 构建方假设"产物有个唯一身份";制品方只认你给它的那个字符串 | tag 和内容对不上,回滚回不到你以为的那个版本 |
| **C**:制品 → 登记 | 推送方假设"推上去了就能拉";拉取方对协议、认证、路径各有自己的默认值 | `ImagePullBackOff`,而且报错指向的那一层往往不是真因 |

本文件的三道接缝,分别对应三个**今晚真实发生过**的标本:

| 接缝 | 今晚的标本 | 一句话 |
|---|---|---|
| **A** | `ai-infra-gateway:v20` 跑了 30 天,却**无法从版本控制重建** | 传送带从源头就断了 |
| **B** | tag 从 v11 打到 v20,镜像里的代码**自称 v11.0** | 制品的身份和内容脱钩 |
| **C** | 本地 registry 拉不动,`registries.yaml` 要重启、`certs.d` 不用 | 同一个最终文件,两个写入者,两套生命周期 |

# 一、段② 构建:任何 CI 设计必须先回答的三个问题

在写第一行 `Jenkinsfile` 之前,构建这一段有三个问题必须先回答。**它们不是"最佳实践",是"没答案就写不下去"的前置条件。**

| # | 问题 | 决定了什么 |
|---|---|---|
| 1 | **在哪构建** —— 宿主机 / 集群内 Pod / 集群外专用构建机 | 信任边界、资源隔离、网络可达性 |
| 2 | **谁来构建** —— Docker daemon / DinD / rootless Docker / buildah / kaniko / BuildKit | 安全性、是否需要特权、能不能在 Pod 里跑 |
| 3 | **构建能不能看见外网** —— 基础镜像从哪拉、依赖从哪下 | 构建的可重复性与失败模式 |

## 1.1 在哪构建

**要解决什么问题**:构建过程需要 CPU、内存、磁盘,还需要一套能写文件的临时空间。这三样东西放在哪台机器上,直接决定了"构建能碰到什么"。

**有哪些可选方案**:

| 方案 | 信任边界 | 资源隔离 | 网络可达性 |
|---|---|---|---|
| **宿主机** | ❌ 构建脚本 = 宿主机上的一个进程,能读到宿主机的一切 | 无(和宿主机其他进程抢资源) | 最好(宿主机网络) |
| **集群内 Pod** | ✅ 边界 = Pod 的 securityContext + 挂载了什么 | ✅ requests/limits 隔离,用完即销毁 | 取决于集群网络(DNS 走 CoreDNS、拉镜像走 containerd 配置) |
| **集群外专用构建机** | ✅ 物理隔离 | ✅ 独占 | 需要打通到集群的网络和凭据 |

**为什么选这个**:**今晚选集群内 Pod**。理由不是"更先进",是三条具体的:

1. **一次拿下两个面试维度**。写 `Jenkinsfile` 是 CI 能力;维护"构建环境怎么起、怎么隔离、怎么销毁"是运维能力。
2. **动态 agent 是 Jenkins on K8s 的核心价值**。每次构建起一个 Pod,用完销毁 —— 构建环境天然隔离,不用常驻一堆 agent 机器。
3. **和集群已有的资源特征对齐**。构建不需要 GPU,那就别占 `agent-0`(唯一带 GPU、长期高负载的节点)。

**今晚的实测证据**(`ci/Jenkinsfile` 的 agent 定义):

```groovy
agent {
  kubernetes {
    yaml '''
apiVersion: v1
kind: Pod
spec:
  nodeSelector:
    node-role: cpu
  containers:
  - name: buildah
    image: quay.io/buildah/stable:v1.37.0
  - name: lint
    image: python:3.11-slim
  - name: git
    image: alpine/git:latest
'''
  }
}
```

三个容器各司其职,这是 K8s Plugin 的标准姿势:**同一个 Pod 里的容器共享网络命名空间和卷,但各自用各自擅长的镜像**。`lint` 容器装了 Python,`git` 容器装了 git 和 SSH,`buildah` 容器装的是构建器 —— 谁也不用为了另一个人的依赖把镜像撑大。

> ⚠️ **一个必须讲清楚的取舍**:`nodeSelector: node-role: cpu` 用的是**集群里已存在的标签约定**(`Deployment/ollama` 已经在用),不是新造的 `kubernetes.io/hostname`。
>
> 理由:节点重建后**名字会变,角色不会变**。写死主机名,集群一重建就失效;写角色,重建后依然成立。
>
> 决策过程见 `99_决策日志.md` D7(含一次实施中的修正)。

## 1.2 谁来构建

**要解决什么问题**:在 K8s Pod 里构建镜像,和在一台笔记本上敲 `docker build`,是完全不同的两件事。因为**传统的 `docker build` 需要一个常驻的 dockerd** —— 而 Pod 里没有。

**有哪些可选方案**:

| 方案 | 需要 daemon? | 需要特权? | 安全性 | 备注 |
|---|---|---|---|---|
| **挂载宿主机 `docker.sock`** | 用宿主机的 dockerd | ❌ 不需要 | ❌ **极差** | 等于把宿主机 root 权限交给构建容器 |
| **DinD(docker-in-docker)** | ✅ 自己起一个 dockerd | ✅ 需要 `privileged` | ❌ 差 | 特权容器 + 嵌套存储驱动,坑多 |
| **rootless Docker** | ✅ 需要 | 用户命名空间 | ✅ 好 | 内核/发行版要求高 |
| **BuildKit / buildx** | ✅ 需要(或 rootless 模式) | 视模式而定 | ✅ 好 | 构建性能最好,缓存最强 |
| **buildah** | ❌ **daemonless** | root 或 userns | ✅ 好 | 被 GitLab 等平台推荐为 Kaniko 的替代 |
| ~~**kaniko**~~ | ❌ daemonless | — | — | ⚠️ **2025-06 已被 Google 归档,不再维护,新项目不应选** |

**为什么选这个**:**buildah**。三条理由:

1. **不挂 `docker.sock`**。这是生产大忌 —— 挂上它,构建容器里的任意代码都能指挥宿主机的 dockerd,等于构建过程拥有了宿主机 root。**D5 已把它列进"明确不采用"清单,当反面教材。**
2. **daemonless**。不需要在 Pod 里再起一个守护进程,契合 K8s Job 模型:起 Pod → 构建 → 推送 → 退出。
3. **社区共识**。Kaniko 归档之后,GitLab 等主流平台把 buildah 列为推荐替代。

**今晚的实测证据**:`Jenkinsfile` 里给 buildah 容器设了三个环境变量 + 一段 securityContext:

```yaml
env:
- name: CONTAINERS_REGISTRIES_CONF
  value: /etc/containers/registries.conf
- name: BUILDAH_ISOLATION
  value: chroot
- name: STORAGE_DRIVER
  value: vfs
securityContext:
  runAsUser: 0
  allowPrivilegeEscalation: true
```

逐条解释这三个变量(它们不是"抄来的配置",每一个都在解决一个具体问题):

| 变量 | 值 | 解决什么问题 |
|---|---|---|
| `STORAGE_DRIVER` | `vfs` | 容器里**用不了 `overlayfs`** —— overlay 挂载需要内核级的 mount 权限,普通容器拿不到。`vfs` 是最笨但**一定能跑**的驱动(每层复制一份完整文件,慢、费盘,但不需要特权) |
| `BUILDAH_ISOLATION` | `chroot` | 默认隔离模式需要用户命名空间;`chroot` 是**不需要 userns 也能跑**的最低要求模式 |
| `CONTAINERS_REGISTRIES_CONF` | 路径 | 告诉 buildah 去读挂进来的 `registries.conf`,用来配"哪个仓库是 HTTP、哪个是 HTTPS" |

**⚠️ 一处需要诚实标注的差异**:`99_决策日志.md` D3 的决策写的是 **"Buildah rootless"**;而落地的 `Jenkinsfile` 用的是 `runAsUser: 0`(容器内 root)+ `--isolation chroot` + `STORAGE_DRIVER=vfs`。

这两者**不是一回事**:

- 严格意义的 **rootless** = 用**用户命名空间**,容器内 root 在宿主机上其实是个普通用户;逃逸了也只能拿到那个普通用户的权限。
- 落地的形态是 **root-in-container、无特权、无 userns**;逃逸面比挂 `docker.sock` 小得多,但**不是** rootless。

这个差异是"决策意图"和"落地实现"之间的常见缝隙 —— **主张用 rootless 的方案,最后常常因为 userns 在集群里默认不开而退化成 chroot**。标注在这里,不掩盖。(是否有意为之:待核实)

## 1.3 构建能不能看见外网

**要解决什么问题**:构建过程有**两条完全独立的网络路径**,它们经常被混为一谈:

| 路径 | 什么时候走 | 由谁决定 | 走不通的表现 |
|---|---|---|---|
| **拉基础镜像** | `FROM python:3.11-slim` | **节点的容器运行时**(k3s 的 containerd) | `FROM` 这一行就失败,构建根本没开始 |
| **下载构建期依赖** | `RUN pip install ...` | **Dockerfile 里写死的源** | 构建跑到一半失败 |

**这两条路必须分别设计。** 第一条走的是**集群侧**的镜像加速器/私有仓库配置(见本文件第五章"接缝 C");第二条走的是**Dockerfile 里那一行命令**。

**今晚的实测证据**:用 `docker history` 读 v20 镜像的构建步骤,能直接看到第二条路的源:

```bash
docker history --no-trunc --format '{{.CreatedBy}}' ai-infra-gateway:v20
```

输出中对应的那一层是:

```
RUN /bin/sh -c pip install --no-cache-dir -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple # buildkit
```

也就是说:**这个镜像当年在构建时,依赖是从清华 PyPI 镜像下的**。这是一个"写进 Dockerfile 的事实",`docker history` 会把它原样带出来 —— 这也是第四章"从镜像反推构建输入"的第一件工具。

同时,`docker history` 的最底层显示基础镜像是:

```
# debian.sh --arch 'amd64' out/ 'trixie' '@1785715200'
ENV PYTHON_VERSION=3.11.16
```

即 `python:3.11-slim` = Debian trixie + Python 3.11.16。**基础镜像的 digest 会随时间变**(`python:3.11-slim` 是个可变 tag),这一点在"构建可复现"这个目标下很关键 —— 见第三章。

## 面试可以怎么讲

> **"构建在哪儿做"**
>
> "我把构建放在集群内的动态 Pod 里,不是图新鲜。构建环境用完即销毁,天然隔离,而且一次能讲清两件事:写 Jenkinsfile 是 CI 能力,维护构建环境的隔离和资源边界是运维能力。构建 Pod 用 `nodeSelector` 钉在 CPU 节点上——集群里唯一带 GPU 的节点长期高负载,构建没有任何理由去占它。"

> **"为什么不能在 Pod 里跑 `docker build`"**
>
> "因为 `docker build` 需要一个常驻的 dockerd,而 Pod 里没有。有三条路:挂宿主机的 `docker.sock`——等于把宿主机 root 交给构建容器,生产大忌;起一个 DinD——需要 privileged,同样不安全;或者用 buildah 这种 daemonless 的构建器。我用的是 buildah,而且因为它跑在无特权容器里,用不了 overlayfs,存储驱动退化成 vfs,隔离模式用 chroot——**慢,但不需要任何特权**。"

> **"构建的网络"**
>
> "我会把构建的网络分成两条独立的路径看:拉基础镜像走的是节点的 containerd 配置,下载依赖走的是 Dockerfile 里写死的源。这两条经常出问题,而且失败点完全不同——第一条挂了是 `FROM` 那一行就失败,第二条挂了是构建跑到一半才失败。"

# 二、接缝 A:代码 → 构建

> **这是今晚最有价值的一处。**

## 2.1 核心命题

> **构建输入必须完整地存在于版本控制里,否则传送带从源头就断了。**

这句话听起来像废话。但它有一个**极其隐蔽的变体**:

> 不是"构建跑不起来",而是"**构建跑起来了,而且成功了,但产出的和线上跑的不是同一个东西**"。

第二种情况没有任何红灯:镜像构建成功、容器启动成功、健康检查通过、服务正常响应。**它唯一的破绽,是某个你还没走到的代码路径。**

## 2.2 今晚的标本:`ai-infra-gateway:v20`

**事实清单**(全部可复核):

| 项 | 事实 | 怎么确认的 |
|---|---|---|
| 镜像在集群里稳定运行 | **30 天** | `kube describe pod` 的启动时间 |
| tag 跨度 | `v10` ~ `v20`(+ 一个 `latest`) | `docker images` |
| v20 镜像的创建时间 | `2026-08-16 09:30:38 +08:00` | `docker inspect` 的 `.Created` |
| v11 镜像的创建时间 | `2026-07-29 23:58:00 +08:00` | 同上 |
| `latest` 的创建时间 | `2026-07-26 21:01:51 +08:00` | **比 v10/v11 都早** |
| 镜像内代码自称的版本 | **v11.0** | 镜像里的 `gateway_server.py` |

先注意最后两行:**`latest` 不是最新的**。它是整个 tag 序列里**最早**的一个。只用这一条,就已经能说明可变 tag 的问题 —— 但今晚的问题比这更大。

## 2.3 三条独立的漂移线

"漂移"在这里的意思是:**镜像里的东西和仓库里的东西,已经不是同一份了**。今晚是三处独立发生、互不相干的漂移。

### 漂移线 1 —— 镜像里的代码依赖一批仓库里不存在的文件

镜像内的 `gateway_server.py` 里有这几行 import:

```python
from snapshot_loader import SnapshotLoader
from router import decide, estimate_tokens
from prometheus_client import Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST
```

而仓库里:

| 文件 | 仓库状态 |
|---|---|
| `router.py` | **从来没有过** |
| `snapshot_loader.py` | **从来没有过** |
| `requirements.txt` | **从来没有过** |

这三个文件**只存在于镜像层里**。也就是说:**这个镜像没有出处。**

它现在能跑,但任何一次意外(节点重建、镜像被 GC、需要改一行代码)都会让它变成**不可恢复的** —— 因为你没法重新构建它。

### 漂移线 2 —— 仓库里那个同名文件,是另一条演化线

仓库里**确实有一个** `gateway_server.py`。但它和镜像里的是**两个完全不同的东西**:

| | 仓库版 | 镜像版 |
|---|---|---|
| 架构 | **v2.0 单后端 Ollama 代理** | **双后端路由(CPU Ollama + GPU vLLM)** |
| 可观测 | OpenTelemetry | 多个 Prometheus 指标(计数器/直方图/仪表) |
| 路由 | 无 | 基于 snapshot 的策略路由 |
| 熔断 | 全局 | **只保护 Ollama 分支** |
| 注释 | 带中文教程注释 | — |
| 版本号 | v2.0 | 自称 **v11.0** |

**tag 和内容对不上**:tag 一路从 v11 打到 v20,而 v20 镜像里的代码**自称 v11.0**。

> **一个可以直接拿去面试的观察**:"tag 是别人给你的标签,版本号是代码自己说的。当这两个都对不上现实的时候,你手上就没有任何可信的东西了。"

### 漂移线 3(最危险)—— 配置文件也是两份,而且差异是**运行时才炸**的那种

`config/gateway_config.yaml` 同样是两份。仓库版**缺 `cache_aware` / `backends` / `tiers` 三个段**。

实测两份文件的顶层键:

| 顶层键 | 仓库版(旧) | 镜像版(正统) |
|---|---|---|
| `server` / `ollama` / `auth` | ✅ | ✅ |
| `rate_limit` / `circuit_breaker` / `retry` | ✅ | ✅ |
| `cache_aware` | ❌ **缺** | ✅ |
| `backends` | ❌ **缺** | ✅ |
| `tiers` | ❌ **缺** | ✅ |

而镜像版的代码,**每处理一个被路由的请求**都会读其中一段:

```python
action, rule_id, reasons = decide(
    snapshot_loader.get(), token_count, cache_hit_prob,
    config["cache_aware"]["boost"],
)
```

注意这里用的是 `config["cache_aware"]["boost"]` —— **方括号下标,不是 `.get()`**。同一个函数里,`backends` 和 `tiers` 用的是带默认值的写法(`config.get("backends", {})`、`config.get("tiers", {})`),所以缺了它们只会**静默降级**;而 `cache_aware` 缺了就是 **`KeyError`**。

于是:

> **用仓库版的 config 去重建,容器会正常启动,然后在第一个请求上抛 `KeyError`。**

这是**最危险的一种漂移**:

| 检查项 | 这种漂移的表现 |
|---|---|
| 静态检查(语法/lint) | ✅ **全过** |
| `docker build` | ✅ 成功 |
| 容器启动 | ✅ 正常 |
| 健康检查 / `Pod` 变 Running | ✅ 通过 |
| **第一个真实请求** | ❌ **炸** |

缺的是**运行时才被读到的配置段**。任何"镜像能不能构建""容器能不能起来""服务活不活着"的检查,**全都发现不了它**。

> **这就是为什么"漂移"不能只靠"看它跑没跑"来发现。** 一个服务健康,只证明它**已经走过的代码路径**是好的;不能证明它**还没走的路径**也是好的。

## 2.4 方法论(一):怎么发现构建输入缺失

**发现"构建输入不在版本控制里",不是一个直觉,是一套可执行的动作。** 分解成三步:

### 第一步:`docker history` —— 看每一层干了什么

```bash
docker history --no-trunc --format '{{.CreatedBy}}' ai-infra-gateway:v20
```

**`--no-trunc` 是关键**:不带它,长命令会被截断成 `...`,`COPY` 了哪些文件、`RUN` 了什么就看不全了。

这个命令的价值在于:**它把 Dockerfile 的每一行还原出来了**。今晚读到的关键几层(自下而上是依赖顺序,`docker history` 默认自上而下列出):

```
COPY 01-gateway-server/config/ ./config/
COPY 01-gateway-server/router.py .
COPY 01-gateway-server/snapshot_loader.py .
COPY 01-gateway-server/gateway_server.py .
RUN /bin/sh -c pip install --no-cache-dir -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
COPY requirements.txt .
WORKDIR /app
CMD ["python3"]
```

**从这一段能直接读出三件事**:

1. **构建上下文是仓库根目录**(路径是 `01-gateway-server/config/`,不是 `config/`)—— 也就是说当年是在仓库根目录下 `docker build` 的。
2. **需要哪些文件**,`COPY` 列得清清楚楚:`gateway_server.py` / `router.py` / `snapshot_loader.py` / `requirements.txt` / `config/`。
3. **顺序**:`requirements.txt` 先 COPY 再 `pip install`,这是**利用层缓存**的标准写法 —— requirements 不变时,pip 那一层可以直接复用。

> **这就是"发现缺失"的核心手法:`docker history` 告诉你构建**需要**什么,然后拿这份清单去和仓库对。** 对不上的,就是缺失的。

### 第二步:`docker inspect` —— 看运行时契约

```bash
docker inspect ai-infra-gateway:v20 --format '{{json .Config}}'
```

今晚读到的:

```json
{
  "ExposedPorts": { "8000/tcp": {} },
  "Cmd": ["python", "gateway_server.py"],
  "WorkingDir": "/app"
}
```

**为什么要读这几项**:

| 字段 | 为什么重要 |
|---|---|
| `WorkingDir` | 决定"相对路径"从哪儿算起。`CMD ["python", "gateway_server.py"]` 是个相对路径,**只有知道 workdir 才知道它跑的是哪个文件** |
| `Cmd` / `Entrypoint` | 决定容器起来之后到底执行什么。重建时写错这一项,镜像就"长得一样但不干活" |
| `ExposedPorts` | 是**声明**,不是强制,但它记录了"这个服务打算监听哪个端口"的意图 |

**注意 `Config` 里没有 `Entrypoint`** —— 说明镜像只设了 `Cmd`。这是一个容易被忽略的细节:重建时如果自作主张加一个 `ENTRYPOINT`,行为就变了。

### 第三步:从运行中的容器 diff `/app` 和仓库

这是最直接的一步:**把镜像里的目录结构和仓库里的目录结构摆在一起看**。

```bash
docker run --rm --entrypoint ls ai-infra-gateway:v20 -la /app
```

> ⚠️ **注意**:这一步需要一个临时容器。本文件记录的是方法论,不代表今晚之后应该随手跑 —— 在真实生产环境里,对一个正在服务的镜像做这种事之前,先确认它不会影响任何人。

> **探测命令要先确认工具存在**:`--entrypoint ls` 能成立,是因为 `python:3.11-slim` 里**有 `ls`**。换一个 distroless 镜像就没有了 —— 见第六章,以及 P16 那条"工具缺失被读成网络不通"的教训。

**三步合起来就是一份"重建所需输入清单"**:`docker history` 给文件列表,`docker inspect` 给运行时契约,目录比对给差异。

## 2.5 方法论(二):怎么从镜像层里抢救源码

**镜像层是只读的,但还是有办法把文件捞出来。** 两条路:

### 路 A:一条命令直接 cat

```bash
docker run --rm --entrypoint cat ai-infra-gateway:v20 /app/router.py > /tmp/router.py
```

**适合**:单个小文件,且你知道确切路径。

**缺点**:**每个文件都要起一次容器**;而且 `cat` 会把内容打到 stdout,像二进制或者有编码问题的文件会很难受。

### 路 B:`docker create` + `docker cp`(更稳)

```bash
docker create --name rescue-v20 ai-infra-gateway:v20
docker cp rescue-v20:/app/router.py          /tmp/rescue/router.py
docker cp rescue-v20:/app/snapshot_loader.py /tmp/rescue/snapshot_loader.py
docker cp rescue-v20:/app/requirements.txt   /tmp/rescue/requirements.txt
docker cp rescue-v20:/app/config             /tmp/rescue/config
docker rm rescue-v20
```

**为什么这条更稳**:

1. **`docker create` 只创建不启动** —— 不需要镜像里有一个能跑的入口点,也不需要担心启动脚本产生副作用。
2. **`docker cp` 走的是归档通道**,目录可以整个拷(`docker cp ...:/app/config /tmp/`),二进制文件、符号链接都能保真。
3. **一次 create,多次 cp** —— 想捞几个就捞几个。

**今晚的处置**:以**镜像版为正统**,把三个缺失文件 + 配置文件从镜像层里捞出来。

> **为什么"以镜像版为正统"而不是"以仓库为正统"?**
>
> 因为**集群里跑的是镜像版,它已经稳定服务了 30 天,是事实**;仓库里那份从未部署过,是设想。
>
> 这是 D9 那条原则的又一次应用:**接管存量系统的第一原则,是让 Git 描述现实,而不是让现实服从 Git。**
>
> 顺序不能颠倒:先把现实固化下来(可重建)→ 有了基线之后,再单独评估"要不要改"。

## 2.6 方法论(三):怎么验证抢救的完整性

**捞出来不算完 —— 必须证明捞出来的和线上跑的是同一个东西。**

**唯一可信的办法:逐字节比对。**

```bash
md5sum gateway_server.py router.py snapshot_loader.py requirements.txt config/gateway_config.yaml
```

然后把同一组文件在镜像内算一遍,两边对齐。**全部一致,才算重建可信。**

> **为什么必须是 md5(或更强的哈希),而不是"看着一样"或者"启动成功了"?**
>
> 因为这次的漂移正是**"启动成功但内容不同"**。任何"行为层面"的检查都会被同一个陷阱骗第二次。**只有内容层面的比对,才能证明你拿到的是原件。**

今晚的处置结果(记录口径):

| 动作 | 结果 |
|---|---|
| 从镜像层捞出缺失的构建输入 | 完成 |
| 归档仓库版的旧分支到 `.archive/` | 完成(`gateway_server.repo-branch.py` / `gateway_config.repo-branch.yaml`) |
| 补一份 `Dockerfile`,还原真实构建步骤 | 完成 |
| **四个文件与镜像内的对应文件做 md5 逐字节比对** | ✅ **全部通过**(具体覆盖清单:待核实) |

补出来的 `Dockerfile` 长这样(注意它**没有注释** —— 理由在代码块外面):

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

COPY gateway_server.py .
COPY snapshot_loader.py .
COPY router.py .
COPY config/ ./config/

EXPOSE 8000

CMD ["python", "gateway_server.py"]
```

**这份 Dockerfile 是"反推"出来的,不是"记得"的** —— 每一行都能对应到 `docker history` 里的一层:

| Dockerfile 行 | 来源 |
|---|---|
| `FROM python:3.11-slim` | `docker history` 最底层(`debian.sh` + `PYTHON_VERSION=3.11.16`) |
| `WORKDIR /app` | `docker inspect` 的 `.Config.WorkingDir` |
| `COPY requirements.txt .` + `RUN pip install ...` | `docker history` 里那两层的**顺序和原文**(连 `-i` 后面的镜像地址都是原文) |
| 三个 `COPY` | `docker history` 里的 COPY 层 |
| `EXPOSE 8000` | `docker inspect` 的 `.Config.ExposedPorts` |
| `CMD ["python", "gateway_server.py"]` | `docker inspect` 的 `.Config.Cmd` |

> **⚠️ 一处仍需诚实标注的边界**:这份 Dockerfile 能让**文件内容**和线上镜像一致(md5 已证),但**不能保证构建出来的镜像 digest 和 v20 完全相同** —— 因为基础镜像 `python:3.11-slim` 是个**可变 tag**,今天拉到的和 2026-08-16 那天拉到的不是同一份。
>
> 要做到真正常量级的可复现,基础镜像必须**钉 digest**(`FROM python:3.11-slim@sha256:...`)。**这一点今晚没有做。**

## 2.7 教训

> **"能跑"不等于"能重建"。**

一个运行了 30 天、稳如泰山的服务,和一个"用仓库里的东西能重新构建出来"的服务,**是两件完全不同的事**:

- 前者只需要**产物**(一堆只读的层)。
- 后者才需要**完整的、可追溯的构建输入**。

三条漂移线合起来意味着:**这个镜像没有出处。**

> **这才是上 CI 最真实的动机。**
>
> **CI 的第一个价值不是自动化,是让构建可复现。**
>
> 自动化是"更快地做同一件事";可复现是"保证这件事是被定义过的、谁来做结果都一样"。
>
> **没有可复现性,自动化只是更高效地生产一个没人能解释的产物。**

这条结论和 P14 是**同一个规律的两种形态**:P14 是"过程指标全绿 ≠ 结果达成"(日志采集每一段都健康,却一条都没采到);这里是"构建成功 ≠ 产物正确"。

# 三、接缝 B:构建 → 制品

> **不变性从这一刻诞生。**

构建产出了一个东西,给它一个名字,把它推进仓库。**接缝 B 就是"给东西起名字"这一步** —— 而名字的质量,直接决定整条传送带后面所有的能力。

## 3.1 tag 策略是这一步的灵魂

**要解决什么问题**:一个制品需要一个标识,让人能引用它、找到它、回到它。

**有哪些可选方案**:

| 策略 | 例子 | 可变? | 可读性 | 回滚能力 |
|---|---|---|---|---|
| **可变 tag** | `latest`、`stable`、`prod` | ✅ **会变** | 高 | ❌ **无从谈起** |
| **git SHA** | `a3f9c21`(short)、`a3f9c21...`(full) | ❌ 不可变 | 低(要去查) | ✅ 精确 |
| **语义化版本** | `v1.4.2` | ❌ 约定不可变 | 高 | ✅ 精确 |
| **构建号** | `build-1284` | ❌ 不可变 | 中 | ✅ 精确 |
| **digest** | `sha256:da0c3e7c...` | ❌ **内容寻址,物理不可变** | 最低 | ✅ 最强 |

**为什么选 git SHA**:**今晚用的是 git short SHA(7 位)**。理由:

1. **不可变**。回滚有依据。
2. **自动可追溯**。`a3f9c21` 直接对应仓库里的一个 commit,不需要额外的映射表。
3. **零人工**。CI 里一行 `git rev-parse` 就能算出来,不需要有人决定"这次该打什么版本号"。

**代价也要说清楚**:short SHA **可读性差**。看到 `a3f9c21` 你无法一眼判断"这是新功能还是修 bug"。所以**生产上的常见组合是:git SHA 做 tag,另加一个语义化版本或构建号做展示**。

## 3.2 关键联结:回滚的粒度 = tag 的粒度

> **第 ⑨ 段(部署/回滚)能不能回滚,取决于这一步 tag 的粒度。**

这条联结值得单独写一节,因为它是很多人**装了一整套 CI/CD 之后才发现**的事:

| 你的 tag 策略 | 你的回滚粒度 |
|---|---|
| 只有一个 `latest` | **回滚不了** —— 你没有任何一个"旧版本"可以指回去 |
| 每天一个 tag(`2026-09-16`) | 能回滚到"昨天",回滚不了"昨天上午" |
| 每个 commit 一个 tag(`git SHA`) | 能回滚到**任意一次构建** |
| 每个 commit 一个 **digest** | 能回滚到**内容完全一致的任意一份副本** |

> **回滚不是部署系统提供的能力,是 tag 策略提供的能力。** 部署系统只是执行"把 tag 从 A 改成 B"。
>
> 如果 A 和 B 指向同一份内容(可变 tag),那次"回滚"就是**一次什么都没做的操作** —— 而且它不会报错。

## 3.3 `latest` 为什么在 K8s 里是反模式

在本地 `docker run` 的世界里,`latest` 的危害有限(顶多是你拉到的和上次不一样)。**在 K8s 里,它多了一层更隐蔽的故障模式。**

**机理**:

| 环节 | 行为 |
|---|---|
| Pod 的 `imagePullPolicy` 默认值 | tag 是 `latest` → 默认 `Always`;tag 是**其他任意值** → 默认 `IfNotPresent` |
| 于是 | 一旦用固定 tag,节点上**已经有这个 tag** 的镜像时,**不再去仓库核对** |
| 后果 | 如果那个 tag 是**可变的**,节点就会一直用**它本地那份**,而仓库里那份可能早就被覆盖了 |

**这就产生了 K8s 里最阴的一种故障**:

> **同一个 tag,在不同节点上是不同的内容。**
>
> 集群里有 3 个节点,滚动更新之后,可能有 2 个节点拉到了新内容、1 个节点用的还是旧内容(因为它本地已经有这个 tag 了)。
> **所有 Pod 都 Running,所有 `kubectl get` 都正常,但它们跑的不是同一个东西。**

排查这类问题时,`ImagePullBackOff` 是**不存在**的 —— 因为**根本没有发生拉取**。你只能去看每个节点上那个镜像的 **ID**:

```bash
docker inspect --format '{{.Id}}' <image>
```

> **这就是"可变 tag + `IfNotPresent`"的组合为什么被称作反模式**:它把一个"镜像一致性问题"变成了一个"**节点间不一致**问题",而后者在 K8s 的界面(`get pods`)上**完全看不出来**。

## 3.4 digest 的价值

**digest 是内容的哈希值。** 它的两个性质,是 tag 做不到的:

| 性质 | 含义 |
|---|---|
| **不可伪造** | 内容变一位,digest 就变。你没法给"同一份内容"造出两个不同的 digest,也没法给"两份不同内容"用同一个 digest |
| **内容寻址** | 同一个 digest **永远**指向同一份字节,不管它在哪个仓库、哪个节点、哪一年 |

**换句话说**:tag 是**人给的标签**(可以指向任何东西、可以随时改指),digest 是**内容的身份证**(改不了)。

> **一个可以直接讲的判断**:
>
> **tag 是给人看的,digest 是给机器用的。** 生产上的正确姿势是用 tag 做**人类可读的引用**,同时把它**解析成 digest** 写进部署清单 —— 这样人看到的是 `v1.4.2`,集群执行的是 `sha256:...`。

**今晚的边界**:digest 这条路**没有用起来**。用的是 short SHA tag,**没有把 digest 钉进部署清单**。这是本章最需要诚实标注的缺口 —— 也是"下一次可以立刻改进"的第一条。

## 3.5 今晚的做法与实测证据

**第一步:算出 tag**(`Jenkinsfile` 的 `Resolve Tag` stage)

```groovy
stage('Resolve Tag') {
  steps {
    script {
      env.SHORT_SHA = sh(script: 'git rev-parse --short=7 HEAD', returnStdout: true).trim()
      env.IMAGE_REF = "${env.REGISTRY}/${env.IMAGE_NAME}:${env.SHORT_SHA}"
      echo "镜像将构建为: ${env.IMAGE_REF}"
    }
  }
}
```

`--short=7` 是 7 位十六进制。**为什么要显式写 7 位**:`git rev-parse --short` 的默认长度会随仓库对象数量增长而**自动变长**(Git 会为避免歧义自动加位),显式指定可以保证格式稳定。

**第二步:构建、推送**(`Build` / `Push` stage)

```groovy
buildah bud \
  --storage-driver=vfs \
  --isolation=chroot \
  --format=docker \
  -t ${IMAGE_REF} \
  -f ${DOCKERFILE} \
  ${BUILD_CTX}
```

```groovy
buildah push \
  --storage-driver=vfs \
  --tls-verify=false \
  ${IMAGE_REF} \
  docker://${IMAGE_REF}
```

两处值得注意:

- **`--format=docker`** —— buildah 默认产出 OCI 格式,显式要求产出 Docker 格式。**这不是洁癖**:不同的运行时/仓库对两种格式的支持程度不同,写清楚比"看运气"好。
- **`--tls-verify=false`** —— 因为目标仓库是 **HTTP 的**(见第五章)。**这是一处"用一行命令绕过了一个本来该由配置解决的安全检查"** —— 之所以能这么写,是因为本机实验环境里那个仓库确实没有证书。**生产环境绝不能这么写。**

**第三步:验证真的推进去了**(`Verify In Registry` stage)

```groovy
curl -sf "http://${REGISTRY}/v2/${IMAGE_NAME}/tags/list" | tee /tmp/tags.json
grep -q "${SHORT_SHA}" /tmp/tags.json
```

**这个 stage 的设计意图值得单独讲**:它不是"推送命令没报错就算成功",而是**去仓库问一次"你现在有哪些 tag"**。

> **这和 P14 的教训是同一条**:**"命令成功"是过程指标,"仓库里真的有这个 tag"是结果指标。** 两者之间隔着网络、认证、仓库端拒绝等一整段,任何一段都可能静默失败。
>
> **推完去问一次终点,是这里的正确姿势。**

**今晚的实测产物**(`docker images` 可见):

| 镜像 | 说明 |
|---|---|
| `localhost:5111/sre-lab/ollama-exporter:bootstrap` | 本地 registry,首个手动推的"引导版" |
| `ghcr.io/fei232401/sre-lab/ollama-exporter:sha-af7d4414` | GHCR 路径上的同名镜像 |
| `ghcr.io/fei232401/sre-lab/ollama-exporter:latest` | 同一 image ID —— 即 `latest` 和 `sha-af7d4414` **指向同一份内容** |

最后一行是一个**可以现场演示的教学样本**:`latest` 和 `sha-af7d4414` 的 image ID 完全相同(`b1c667b2b18b`)。

**同 ID 说明此刻它们指向同一内容 —— 但这份保证是有保质期的**:下一次推 `latest`,`latest` 就会指向新的,而 `sha-af7d4414` 不会动。**这正是"可变 tag 和不可变 tag"的差别,能用一个 `docker images` 的输出直接演示。**

## 面试可以怎么讲

> **"你的镜像 tag 策略是什么"**
>
> "用 git short SHA。理由是回滚:回滚的粒度就等于 tag 的粒度。如果只有一个 `latest`,你手上根本没有一个'旧版本'可以指回去;用 git SHA,能精确回到任意一次构建,而且不需要额外的映射表——tag 本身就是 commit 的引用。"

> **"`latest` 在 K8s 里有什么问题"**
>
> "比在本地跑 `docker run` 多一层。K8s 的 `imagePullPolicy` 对非 `latest` 的 tag 默认是 `IfNotPresent`,所以只要节点上已经有这个 tag,它就不会再去仓库核对。如果那个 tag 是可变的,结果就是**同一个 tag 在不同节点上是不同内容**——滚动更新之后,有的节点是新版,有的是旧版,而 `kubectl get pods` 全绿,**连 `ImagePullBackOff` 都不会有,因为根本没有发生拉取**。要查只能去每个节点上看镜像 ID。"

> **"digest 呢"**
>
> "digest 是内容寻址,物理上不可伪造。我的理解是:**tag 是给人看的,digest 是给机器用的**。生产的正确姿势是用 tag 做人类可读的引用,同时解析成 digest 写进部署清单。**这一点我目前还没做到**——我用的还是 short SHA tag,没有把 digest 钉进清单。这是我知道的下一个改进点。"

# 四、段④ 登记:制品仓库

构建产出的东西要有个地方存。**这一段解决的是"存哪儿、谁能推、谁能拉"。**

## 4.1 私有仓库 vs 公网仓库:取舍

**要解决什么问题**:制品的存放位置,直接决定了谁有权限、能不能离线、以及"重建环境"要靠什么。

| 维度 | 公网托管(GHCR / Docker Hub) | 自建私有仓库(Harbor / k3d registry) |
|---|---|---|
| 搭建成本 | ✅ 零 | ❌ 要起、要配、要维护 |
| 访问控制 | ✅ 平台提供 | ⚠️ 要自己配(本地 k3d registry **没有**) |
| 内网/离线可用 | ❌ 依赖公网 | ✅ **内网可达** |
| 认证模型 | 平台自己的(见 4.2) | 标准 registry v2 |
| 生产对应物 | 小团队/公开项目 | **企业内网事实标准** |
| 存疑点 | 拉取受网络环境影响 | 备份、GC、容量要自己管 |

**取舍的核心不是"哪个好",是"这次要练什么"。** 这一次的目标是练"**给一个集群接一个私有仓库**"的全过程 —— 认证、协议、节点配置。这些是企业内网天天在做的事。

## 4.2 今晚的真实失败 1:GHCR 认证失败

**现象**:

```
docker login ghcr.io
→ {"errors":[{"code":"DENIED"}]}
```

**根因**:**`gh` CLI 拿到的 OAuth token 只有 `write:packages`,没有 `read:packages`。**

**为什么这件事值得单独讲**:因为它暴露了一个非常容易搞混的认知 ——

> **OAuth 的 scope 模型和容器仓库的 scope 模型,不是一回事。**

拆开说:

| 层 | 它说的"权限"是什么意思 |
|---|---|
| **GitHub OAuth scopes** | 你在 GitHub **整个平台**上能做什么(`write:packages` = 能往包仓库写) |
| **容器仓库的登录** | 一次**具体的认证交换**:客户端拿一个凭据去换一个 registry session token,这个 token 必须同时覆盖"读"和"写" |
| **`DENIED` 的含义** | **交换被拒绝了**,不是"你的密码错了" |

**关键的一点**:**推送和拉取是两个不同的权限。** 一个只能写不能读的 token,在"登录"这一步就会失败 —— 因为登录本质上是在建立**两个方向**的能力。

**教训**:

> **拿到一个 token 之后,不要假设它的权限范围。去看它的 scope,并且用"边界操作"验证它**——比如推一个测试镜像、再拉一次。

**正确做法**:用 **classic PAT(带 `read:packages` + `write:packages`)**,或者用**专为这个仓库/这个用途**创建的 token。

**这是 D16 的直接触发点**:项目进度被一个**外部流程**(等 PAT)卡住,而那个流程不在本项目能控制的范围里。

> **一条可以拿去讲的判断**:**一个实验要用到的组件,不该被它自己的认证流程卡住。** 所以当晚换成了本地 registry,把 GHCR 留作"第二站"。

## 4.3 今晚的真实失败 2:协议失败

**现象**:

```
failed to do request: Head "https://k3d-sre-registry:5000/v2/...":
http: server gave HTTP response to HTTPS client
```

**根因**:**containerd 默认走 HTTPS,而本地 registry 是纯 HTTP。**

**这行报错信息值得逐字读一遍**,因为它包含了完整的定位信息:

| 报错片段 | 它告诉你什么 |
|---|---|
| `Head "https://..."` | 客户端**发起的是 HTTPS 请求** |
| `k3d-sre-registry:5000` | **DNS 解析成功了**(拿到了主机名对应的地址,否则报的是 `no such host`) |
| `http: server gave HTTP response to HTTPS client` | **请求真的到达了 registry**,对方用 HTTP 回了一个我们能看懂的响应 |

> **报错里没有一个字说"网络不通"。它说的是"协议不对"。**
>
> **能区分这两件事,是排查能力的分水岭。** 如果把它读成"网络问题",你会去查 CoreDNS、查防火墙、查 Service —— 全部查不出东西,因为你查的层是对的但问题在另一层。

**这条报错也是第五章的入口。**

## 4.4 选型结论:本地 k3d registry(D16)

| 选项 | 结论 |
|---|---|
| **A. 本地 `k3d registry create`** | ✅ **选中** |
| B. 继续等 GHCR PAT | ❌ 被外部流程阻塞,且不是技术问题,无法预估何时解开 |
| C. 公网私有 registry 服务 | ❌ 引入第三方依赖与账号成本,对"本地可复现实验"没有增益 |

**选 A 的三条理由**:

1. **不被外部 token 阻塞**(见 4.2)。
2. **对 K8s 来说它就是真实私有仓库**。认证、tag、拉取语义**和企业内网 Harbor 完全一致** —— 本项目练到的"配私有仓库、给 containerd 加 `certs.d`、处理 HTTP/HTTPS 不一致"(见第五章)**是真实技能,不是玩具**。
3. **自包含、可复现**。本地仓库随 k3d 一起起、一起清,没有外部状态残留。

**代价(要诚实标注)**:

- **本地 registry 没有访问控制**。任何能访问 `localhost:5111` 的东西都能推送/拉取。**仅适用于本机实验环境。**
- **集群重建后仓库内容需要重建**(镜像不在,但仓库本身由 `k3d registry create` 一条命令恢复)。

**今晚的实测证据**:

```bash
k3d registry create sre-registry --port 5111
```

两个地址,注意它们的层级不同:

| 从哪访问 | 地址 | 为什么 |
|---|---|---|
| **宿主机** | `localhost:5111` | `--port 5111` 把容器内的 5000 端口**发布**到了宿主机的 5111 |
| **集群内(节点/Pod)** | `k3d-sre-registry:5000` | 走 Docker 网络里的**容器名 + 容器内端口** |

验证仓库内容的两个端点:

```bash
curl http://localhost:5111/v2/_catalog
curl http://localhost:5111/v2/sre-lab/ollama-exporter/tags/list
```

- `_catalog` —— 看**有哪些仓库**
- `tags/list` —— 看某个仓库**有哪些 tag**

> **这两个端点就是 `Verify In Registry` stage 用的那个端点**(见 3.5)。**用同一套 API 手工验证一次,再去 CI 里自动化它** —— 这个顺序不能反。

## 4.5 集群拉镜像的凭据体系是**节点级**的

> **这是很多人搞混的地方,单独写一节。**

**先分清两件完全不同的事**:

| | **仓库认证**(你是谁) | **传输配置**(怎么连) |
|---|---|---|
| 解决什么 | 证明我有权拉这个镜像 | 这个仓库是 HTTP 还是 HTTPS、用哪个 CA、走不走代理 |
| 配在哪 | 两种:**节点级** 或 **Pod 级** | **只能节点级** |
| K8s 里的载体 | ① 节点上 containerd 的配置 ② Pod 的 `imagePullSecrets` | containerd 的 `certs.d` / k3s 的 `registries.yaml` |
| 能按 Pod 区分吗 | ✅ 能(`imagePullSecrets`) | ❌ **不能** |

**关键结论**:

> **`imagePullSecrets` 是 Pod 级的,但它只能解决"认证"。**
>
> **传输层的配置(HTTP/HTTPS、CA、代理)永远是节点级的** —— 因为拉镜像这个动作是**节点上的 kubelet/containerd 干的**,不是 Pod 里的进程干的。**Pod 还没被创建出来,镜像就已经在拉了。**

这也是为什么:

- 给 Pod 加 `imagePullSecrets` **解决不了** `server gave HTTP response to HTTPS client`;
- 换一个"配了 `imagePullSecrets` 的 Pod" **不会**让一个 HTTP 仓库变得能拉;
- 唯一的解法是**改节点**。

> **一个可以直接讲的判断**:
>
> **"谁在拉镜像?"** —— 这个问题问出来,一半的镜像拉取问题就定位了。**是节点在拉,不是 Pod 在拉。** 所以凭据和配置的边界在节点上,不在 Pod 上。

## 面试可以怎么讲

> **"GHCR 认证为什么失败"**
>
> "`gh` CLI 拿到的 OAuth token 只有 `write:packages`,没有 `read:packages`,`docker login` 时 token 交换直接返回 `DENIED`。这件事让我意识到 **OAuth 的 scope 模型和容器仓库的 scope 模型不是一回事**:推送和拉取是两个不同的权限,而登录本质上是在建立两个方向的能力。教训是——拿到 token 不要假设它的权限范围,要去看 scope,并且用边界操作(推一个测试镜像再拉一次)验证它。"

> **"为什么最后没用 GHCR"**
>
> "因为它卡在一个**外部流程**上,不在我能控制的范围里。我换成了本地 k3d registry,理由有三条:一是不被外部 token 阻塞;二是**对 K8s 来说它就是真实私有仓库**,认证、tag、拉取语义和企业内网 Harbor 完全一致,练到的是真技能;三是自包含、可复现。代价我也清楚:**本地 registry 没有访问控制**,任何能访问宿主机端口的东西都能推拉,只适合实验环境。"

> **"集群拉镜像的凭据配在哪"**

> "这里有个很多人搞混的地方。要分成两件事:**认证**和**传输配置**。认证可以是 Pod 级的(`imagePullSecrets`),也可以是节点级的;但**传输配置——HTTP 还是 HTTPS、用哪个 CA、走不走代理——永远是节点级的**。因为**拉镜像的是节点上的 containerd,不是 Pod 里的进程**。Pod 还没创建出来,镜像就已经在拉了。所以给 Pod 加 `imagePullSecrets` 永远解决不了 `server gave HTTP response to HTTPS client`。问一句'谁在拉镜像',一半的这类问题就定位了。"

# 五、接缝 C:制品 → 登记

> **今晚最有价值的第二处。**

## 5.1 核心命题

> **containerd 加私有仓库不需要重启,但加镜像加速器需要 —— 因为这两个配置文件的"生命周期"不同。**

**同一个最终文件,两个不同的写入者,生命周期完全不同。**

这句话是本文件里最值得记住的一句。它解释的不是一个命令,是**一类问题**。

## 5.2 今晚的实测

**场景**:M3 需要一个能被 K8s 拉取的镜像仓库,用 k3d 起了本地 registry(见 4.4)。

**现象**:

```bash
k3d registry create sre-registry --port 5111
```

起好后接进 `k3d-ai-cluster` 网络,从节点内可以用 `k3d-sre-registry:5000` 访问。

但 Pod 拉取直接报错:

```
failed to do request: Head "https://k3d-sre-registry:5000/v2/...":
http: server gave HTTP response to HTTPS client
```

**读这个报错**(和 4.3 同一个报错,这里是第一次出现):

| 报错片段 | 结论 |
|---|---|
| `Head "https://..."` | 客户端发起的是 **HTTPS** |
| `k3d-sre-registry:5000` | **DNS 解析通了** —— 否则报 `no such host` |
| `server gave HTTP response to HTTPS client` | **请求已经到达 registry** —— 对方用 HTTP 回了一个响应 |

> **报错说明"请求已经到达了 registry,只是协议不对"。**
>
> 这个信息量非常大:**它一次性排除了 DNS、排除了网络可达性、排除了路由** —— 剩下的只有一件事:**告诉 containerd "这个仓库是 HTTP 的"。**

> **注意 4.3 和 5.2 是同一个报错的两次现身**:一次是手工 `docker login`/拉取时撞上,一次是集群里的 Pod 拉取时撞上。**同一个根因,两个不同的消费者。** —— 这正是"修好基础设施 ≠ 修好消费方"的又一个例子(P15 是 DNS 版本,这里是镜像拉取版本)。

## 5.3 两条路的对比

| 办法 | 做法 | 结论 |
|---|---|---|
| **走 k3s 的 `registries.yaml`** | 编辑 `/etc/rancher/k3s/registries.yaml` | ❌ **需要重启 k3s**,放弃 |
| **直接写 `certs.d/hosts.toml`** | 在节点里写 `/var/lib/rancher/k3s/agent/etc/containerd/certs.d/<registry:port>/hosts.toml` | ✅ **实测:不重启,立刻生效** |

`registries.yaml` 的形态(它是 k3s 的**前置输入**,不是最终产物):

```yaml
mirrors:
  "k3d-sre-registry:5000":
    endpoint:
      - "http://k3d-sre-registry:5000"
```

`hosts.toml` 的形态(它是 containerd **实际读取的最终配置**):

```toml
server = "http://k3d-sre-registry:5000"

[host."http://k3d-sre-registry:5000"]
  capabilities = ["pull", "resolve"]
  skip_verify = true
```

> ⚠️ 上面这段 `hosts.toml` 展示的是 **containerd `certs.d` 的标准格式**(这是 containerd 的通用约定,不是本项目的独有发现)。**节点上当时实际写入的字段以现场为准。**(待核实)

## 5.4 根因:谁写它、谁读它、什么时候读

**为什么改 `registries.yaml` 要重启,改 `certs.d/hosts.toml` 不用?**

| 文件 | 谁写它 | 谁读它、**什么时候读** |
|---|---|---|
| k3s 的 `registries.yaml` | 人 | **k3s**,启动时读一次,然后**渲染**进 `certs.d` |
| containerd 的 `certs.d/<registry>/hosts.toml` | 人(或 k3s 渲染) | **containerd**,**每次拉取镜像时动态读取** |

所以:

- 改 `registries.yaml` → 得让 **k3s 重新渲染** → 而 k3s 只在启动时渲染 → **只能重启 k3s**
- 直接写 `certs.d/hosts.toml` → **containerd 下一次拉取就会读到新文件** → **零重启**

**分层图**:

```
              registries.yaml          certs.d/<registry>/hosts.toml
                    │                              │
                    │  k3s 启动时读一次             │  containerd 每次拉取时读
                    ▼                              │
              k3s 渲染写入 ──────────────────────► │
                                                   │
                                                   ▼
                                            containerd 发起拉取
```

**同一个最终文件,两个不同的写入者**:

- 人直接写 `hosts.toml` → **那次写入立刻生效**
- k3s 间接写 `hosts.toml` → **要等 k3s 重启**

> **判断一个配置改动要不要重启,不能问"这是不是热加载",要去问那个消费方:它是在哪一刻读这个文件的。**

**前提条件(这条路默认是开着的)**:

k3s 的 containerd `config.toml` 里,`config_path` 已经指向 `/var/lib/rancher/k3s/agent/etc/containerd/certs.d`。

> **这一条是"为什么可以绕过 k3s 直接写文件"的前提。** 如果 `config_path` 指向别处,往这个目录写文件就是白写 —— **写进了一个 containerd 根本不读的目录**。
>
> 这类"文件写了、格式也对、但位置不对"的失效,和 P8 / P11 一样,属于**静默失效**:不报错,只是不生效。

## 5.5 踩坑附注:工具缺失 ≠ 网络不通

排查过程中一度判断"k3s 节点连不上 GitHub"。**这个判断是错的。**

**原因**:探测命令写的是

```bash
curl -sI https://github.com || echo "不通"
```

而 **k3s 节点镜像里根本没有 `curl`**:

- 命令不存在 → 返回非零退出码
- `||` 的右半边被触发 → 打印"不通"

**于是:"工具缺失"被读成了"网络不通"。**

> **教训:探测命令要先确认工具存在。**
>
> 一个"探测失败"的输出,可能来自"目标不可达",也可能来自"探测工具压根不存在" —— 这两者在下游看到的**是同一个非零退出码**。
>
> **凡是用来判定的命令,先单独验一次它能跑。**

**一个有意思的对比**:同一晚,`Jenkinsfile` 的 `Verify In Registry` stage 里**用了 `curl` 而且成功了** —— 因为那一句跑在 `quay.io/buildah/stable` 镜像里,那个镜像**有 curl**。

> **`curl` 在不在,取决于镜像,不取决于"这是不是一个容器"。** 这就是为什么"先确认工具存在"不是一句空话:**没有任何一个命令是可以假设其存在的。**

## 5.6 方法论:排查"拉不动镜像"的分层顺序

**要解决什么问题**:`ImagePullBackOff` / `ErrImagePull` 是同一个界面现象,但底下可能是五种完全不同的原因。**盲猜会浪费大量时间,分层可以一刀切掉大半。**

**分层顺序**(从上往下查,每一层有自己**独特的报错特征**):

| # | 层 | 问什么 | 典型报错特征 | 定位手段 |
|---|---|---|---|---|
| 1 | **DNS** | 这个名字能解析吗 | `no such host` / `server misbehaving` | 节点里 `nslookup` / `getent hosts` |
| 2 | **TCP 可达** | 这个地址的这个端口通吗 | `connection refused` / `i/o timeout` / `no route to host` | 节点里 `nc -zv` / `wget -T` |
| 3 | **协议** | 我发的和它说的是同一种吗 | **`http: server gave HTTP response to HTTPS client`** | `certs.d` / `registries.yaml` |
| 4 | **认证** | 我有权拉吗 | `DENIED` / `unauthorized` / `401` | `imagePullSecrets` / 节点凭据 |
| 5 | **内容** | 这个 tag/digest 存在吗 | `manifest unknown` / `not found` | 直接打仓库 API 的 `tags/list` |

**为什么这个顺序有效**:每一层**排除掉一批可能性**,而且**每层的报错特征几乎不会混淆**。

举两个例子:

- **第 1 层报 `no such host`,第 3 层报 `server gave HTTP response to HTTPS client`** —— 这两句话不可能互相冒充。**看到 DNS 相关的措辞,就不用查协议;看到协议相关的措辞,就不用查 DNS。**
- **第 5 层报 `manifest unknown`** —— 说明前面四层**全部通过了**(DNS 通、TCP 通、协议对、认证过),只是那个 tag 不存在。**报错停在哪一层,就说明它前面所有层都是好的。**

> **这是一个可以直接拿去用的排查纪律:"读报错,看它停在哪一层,然后只查那一层。"**

**验证手段的纪律**(从 5.5 继承):

> **用来判定的命令,先确认它存在。** 在 k3s 节点里没有 `curl` 的情况下,`getent hosts` / `wget` 是更可靠的替代 —— **但同样要先确认它们在不在。**

**今晚的定位过程**就是这条链的一个实例:

```
① 看到 http: server gave HTTP response to HTTPS client
   → 报错措辞是"协议",不是"找不到主机",也不是"连不上"
   → 第 1、2 层直接排除
② 剩下第 3 层:协议
   → 查 containerd 的仓库配置
   → 找到两条路,选定"不重启"的那条
③ 写入 hosts.toml → 下一次拉取立即生效
```

## 面试可以怎么讲

> **"改 containerd 的仓库配置,要不要重启"**
>
> "取决于你改哪个文件。k3s 的 `registries.yaml` 需要重启,因为它只是 k3s 的**前置输入**——k3s 在启动时读它,然后渲染进 containerd 的 `certs.d` 目录,改它必须让 k3s 重新渲染。而 containerd 的 `certs.d/<registry>/hosts.toml` 是 containerd **每次拉取镜像时动态读取**的,**直接写它,不重启、立刻生效**。**同一个最终文件,两个不同的写入者,生命周期完全不同。** 所以判断一个配置要不要重启,不能问'这是不是热加载',要去看那个消费方是在哪一刻读这个文件的。"

> **"`server gave HTTP response to HTTPS client` 你怎么理解"**
>
> "这行报错的信息量很大。它同时说明三件事:客户端发起的是 HTTPS;DNS 解析成功了(否则报的是 `no such host`);请求**真的到达了 registry**(否则不会收到一个 HTTP 响应)。所以它排除掉了 DNS、网络可达性、路由,只剩一个结论:**containerd 默认走 HTTPS,而这个仓库是纯 HTTP 的,得告诉它改协议。** 我不会把它读成'网络问题'——那样会去查 CoreDNS 和防火墙,而问题根本不在这几层。"

> **"拉不动镜像你怎么查"**
>
> "我按五层查:DNS 解析 → TCP 可达 → 协议 → 认证 → 内容。每一层的报错特征几乎不会混淆——`no such host` 是 DNS,`connection refused` 是 TCP,`server gave HTTP response to HTTPS client` 是协议,`DENIED` 是认证,`manifest unknown` 是内容。**报错停在哪一层,就说明它前面所有层都是好的,只查那一层就行。**"

> **"排查里踩过什么坑"**
>
> "有一次我判断'节点连不上 GitHub',后来发现是**节点镜像里没有 `curl`**,我的探测命令走了 `|| echo 不通` 的兜底分支——**把'工具不存在'读成了'网络不通'**。这两者在下游看到的都是同一个非零退出码。之后我养成了习惯:**用来判定的探测命令,先单独确认它能跑。**"

# 六、段③ 制品本体

前五章讲的是"**怎么把东西送过去**"。这一章讲"**送过去的那个东西本身**"。

## 6.1 镜像分层

**要解决什么问题**:一个应用镜像动辄几百 MB,如果每次改一行代码就要传几百 MB,CI/CD 就废了。

**镜像 = 一组只读层的叠加**。每一层是"相对上一层的一个变更集":

```
┌─────────────────────────────┐  ← 最上层:COPY gateway_server.py(几 KB)
├─────────────────────────────┤
│  COPY config/               │
├─────────────────────────────┤
│  pip install ...(几百 MB)   │  ← 这一层最重
├─────────────────────────────┤
│  python:3.11-slim 基础镜像   │  ← 这一层最大
└─────────────────────────────┘
```

**分层的三个直接后果**:

| 后果 | 含义 |
|---|---|
| **层可以共享** | 两个镜像如果前 3 层一样,它们**在磁盘上只存一份** |
| **层可以缓存** | 某一层的内容没变,**重建时直接复用**,不需要重跑 |
| **顺序决定缓存命中** | 层是**线性**的 —— 上面一层变了,它**下面**所有层全部失效 |

**第三条是唯一需要真正记住的**,它直接决定了 Dockerfile 的写法:

> **变得越少的,越往上放。**

今晚反推出来的 Dockerfile 正是这个写法:

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

COPY gateway_server.py .
COPY snapshot_loader.py .
COPY router.py .
COPY config/ ./config/
```

**`requirements.txt` 先 COPY、先安装,源代码后 COPY。** 因为:

- 依赖**很少变** → `pip install` 那一层(几百 MB)**很少失效**
- 源代码**每次提交都变** → 那几层(几 KB)**每次都重建**

**如果顺序反了** —— 先 COPY 源码再 `pip install` —— 那么**每次改一行代码,都要重新下载安装全部依赖**。构建时间从秒级变成分钟级。

> **这不是"优化",这是"能不能用"的问题。** 一个构建要 10 分钟的 CI,人会开始绕过它。

## 6.2 体积

**要解决什么问题**:镜像体积直接决定了三件事的成本:

| 成本 | 为什么受体积影响 |
|---|---|
| **构建/推送时间** | 体积越大,推到仓库越慢 |
| **部署时间** | 节点拉镜像的时间 = 扩容速度 / 回滚速度 |
| **攻击面** | 镜像里的每一行代码,都是一个潜在的漏洞入口 |

**今晚的实测数据**(`docker images` 的 `CONTENT SIZE` 列,即压缩后的内容大小):

| 镜像 | 内容大小 |
|---|---|
| `python:3.11-slim` 系(网关/exporter) | ~48–117 MB |
| `alpine/git:latest` | **38.9 MB** |
| `busybox:1.36` | **2.21 MB** |
| `hello-world:latest` | **9.49 kB** |

> **注意 `DISK USAGE` 和 `CONTENT SIZE` 是两列不同的数**。`DISK USAGE` 是**本地磁盘占用**(含共享层、未压缩);`CONTENT SIZE` 是**推送到仓库时实际传输的压缩内容**。**算推送/networking 成本时看的是后者。**

## 6.3 多阶段构建:何时该用

**要解决什么问题**:构建一个应用**需要**编译器、构建工具链、头文件;但**运行**它只需要一个产物。

**单阶段的问题**:所有构建工具都会跟着进最终镜像 —— 体积膨胀、攻击面扩大。

**多阶段的做法**:一个 Dockerfile 里写两个 `FROM`,前者产出产物,后者只拿产物。

**形态**(示意):

```dockerfile
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app .

FROM gcr.io/distroless/static
COPY --from=builder /out/app /app
ENTRYPOINT ["/app"]
```

**何时该用**(判断标准,不是"越用越好"):

| 该用 | 不该用 |
|---|---|
| 有**编译/构建步骤**,产物是单个/少量文件(Go、Rust、C++) | 解释型语言且依赖以包的形式存在(Python 的 `pip install` 已经在做同样的事) |
| 构建工具链很大(几百 MB ~ 1 GB+) | 构建工具链很小,省下的体积不值得多一层复杂度 |
| 需要把**构建期凭证**留在构建阶段(不进最终镜像) | 构建期和运行期用同一个基础镜像,且没有敏感内容 |

**今晚的实例是不是多阶段**:`01-gateway-server/Dockerfile` 和 `03-ollama-exporter/Dockerfile` **都是单阶段**。这在这个场景下是**正确的选择**:

- 两个都是纯 Python 应用(`COPY` + `pip install` + `CMD`),没有编译步骤
- Python 的依赖本身就是通过 pip 安装的,多阶段能省下的只有 pip 缓存 —— 而 `--no-cache-dir` 已经把缓存关了

> **一个可以直接讲的原则**:**多阶段是为了"丢弃构建期需要、运行期不需要的东西"。如果构建期本来就没有多余的东西,多阶段只是白加一层。**

## 6.4 基础镜像选择:slim / alpine / distroless

**要解决什么问题**:基础镜像决定了"镜像里默认有哪些东西" —— 而这个默认值,同时影响着体积、调试能力和兼容性。

**三方取舍**:

| 基础镜像 | 体积 | 调试能力 | glibc 兼容性 | 什么时候选 |
|---|---|---|---|---|
| **`debian` / `ubuntu`(完整版)** | ❌ 大 | ✅ 最全 | ✅ glibc | 需要就地排障、依赖编译工具链 |
| **`-slim`(如 `python:3.11-slim`)** | ✅ 小 | ✅ 基本齐全(`sh` / `ls` / `cat` 都在) | ✅ **glibc** | **默认首选** |
| **`alpine`** | ✅ 最小 | ⚠️ 有 `sh`,但工具少 | ❌ **musl libc** | 静态编译 / 不依赖 glibc 的场景 |
| **`distroless`** | ✅ 最小 | ❌ **没有 shell**,进不去 | ✅ glibc | 生产终态,安全优先 |

**核心矛盾**:

> **体积 和 调试能力 是直接冲突的。**

`distroless` 里**没有 shell** —— 意味着 `kubectl exec -it ... -- sh` **直接失败**。这在生产上是一个真实的取舍:

| 立场 | 理由 |
|---|---|
| **支持 distroless** | 镜像里没有 shell,攻击者拿到了也执行不了命令;攻击面最小 |
| **反对 distroless** | **出事的时候你进不去容器** —— 排障只能靠日志和指标,而故障现场恰恰是你最想进去看一眼的时候 |

**折中做法**:生产用 `distroless`,**但准备一个"调试版"同构镜像**(同样的代码 + slim 基础镜像),出事时临时切过去排障,排完切回。

**alpine 的坑要单独提一句**:**`musl libc` 和 `glibc` 不兼容**。表现是:

- 某些 Python 轮子(`manylinux` 的二进制包)**在 alpine 上装不上**,会被迫从源码编译
- 编译时间暴涨,而且需要额外装 `build-base`
- **"镜像小了,但构建时间和复杂度涨了"** —— 有时算下来是亏的

> **`python:3.11-alpine` 对纯 Python 项目往往不是好选择。** 而 `python:3.11-slim` 体积已经足够小,且是 glibc。**今晚两个 Dockerfile 用的都是 `python:3.11-slim`** —— 这个选择是对的。

## 6.5 今晚的实例:`ollama-exporter` 从"挂脚本"改成"烘进镜像"

**背景**:Ollama 原生不暴露 `/metrics`,所以需要一个 exporter 把它的状态转成 Prometheus 格式。

**改造前**(`sre-lab-gitops/k3s-ai-platform/reference/baseline-manifests/monitoring-stack/ollama-exporter.yaml`):

- 一个 `ConfigMap` 存 `exporter.py` **源码文本**
- 一个 `Deployment`,基础镜像 `python:3.11-slim`,把 ConfigMap **挂载成文件**当脚本跑

**改造后**:

- **删掉 ConfigMap**
- `03-ollama-exporter/Dockerfile` 把脚本 `COPY` 进镜像

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY exporter.py /app/exporter.py

EXPOSE 9101

CMD ["python", "/app/exporter.py"]
```

**为什么这个改动重要** —— 这不是"整理代码",是**把制品从可变变成不可变**:

| | 挂 ConfigMap 的脚本 | 烘进镜像的脚本 |
|---|---|---|
| **脚本在哪** | K8s 对象(etcd 里) | **镜像层里** |
| **版本怎么追** | ❌ **追不了** —— ConfigMap 没有"版本"这个概念,改了就是改了 | ✅ 镜像 tag / digest |
| **能回滚吗** | ❌ 不能 —— 改坏了只能凭记忆改回来 | ✅ 换回旧 tag |
| **和镜像的关系** | 脚本是**外部注入**的,镜像本身不完整 | 镜像是**自包含**的 |
| **改了脚本要做什么** | 改 ConfigMap + **重启 Pod**(见 P14 的第二个坑:符号链接刷新,进程监听不到) | 构建新镜像 → 推 → 换 tag,**走标准发布流程** |
| **能否被 CI 覆盖** | ❌ ConfigMap 是集群侧对象,CI 管不到 | ✅ 整个流程都在 CI 里 |

> **核心矛盾:ConfigMap 挂载的脚本是"可变制品",而可变制品和"不变性"是互斥的。**
>
> 上一章讲 tag 策略时说"回滚的粒度 = tag 的粒度"。**挂脚本的部署方式,把回滚粒度降到了零** —— 因为你连一个"版本"都没有,拿什么回滚?

**这个改动和接缝 A 是同一个道理的两种形态**:

| | 接缝 A(网关镜像) | 段③(exporter) |
|---|---|---|
| 问题 | 镜像里的代码**依赖仓库里没有的文件** | 部署依赖**镜像外的 ConfigMap** |
| 方向 | 构建输入**缺**在镜像外 | 运行时内容**散**在镜像外 |
| 共同点 | **制品不自包含 → 无法重建 / 无法回滚** | 同左 |

> **"自包含"是制品最基本的性质。** 一个需要外部文件才能跑的镜像,和一个需要外部文件才能构建的镜像,**是同一个病的两种症状。**

**今晚的实测证据**:改造后,`sre-lab-gitops/production/monitoring/ollama-exporter.yaml` 里的 `Deployment` 只引用镜像,不再有 ConfigMap:

```yaml
      - name: exporter
        image: k3d-sre-registry:5000/sre-lab/ollama-exporter:bootstrap
```

> ⚠️ **注意这个 tag 是 `bootstrap`** —— 它是**流水线跑通之前手工推的引导版**,不是 `git SHA`。**这是一个明确的中间态**:CI 跑通之后,这里的 tag 会被 `Update GitOps` stage 自动改写成 short SHA。
>
> **留下这个中间态是有价值的**:它记录了一个真实工程里常见的过程 —— **先用一个手工产物把链路打通,再用自动化替换它。** 但必须标注清楚,**因为它违反了 3.1 定的 tag 策略**。

## 面试可以怎么讲

> **"基础镜像怎么选"**
>
> "核心矛盾是**体积和调试能力的冲突**。`distroless` 最小最安全,但它**没有 shell**——出事的时候 `kubectl exec` 进不去容器,而故障现场恰恰是你最想进去看一眼的时候。所以生产上我倾向于 `distroless` 加一个同构的调试版镜像,出事临时切过去。另外 `alpine` 有个隐蔽的坑:它是 **musl libc,和 glibc 不兼容**,某些 Python 轮子在它上面装不上,会被迫从源码编译,镜像小了但构建时间涨了。纯 Python 项目我更倾向 `slim`——体积已经够小,而且是 glibc。"

> **"Dockerfile 里层的顺序有什么讲究"**
>
> "层是线性的,上面一层变了,下面所有层全部失效。所以原则是**变得越少的越往上放**。我把 `requirements.txt` 先 COPY 再 `pip install`,源代码后 COPY——依赖很少变,那个几百 MB 的安装层就很少失效;源码每次都变,但只有几 KB。顺序反过来的话,每次改一行代码都要重下全部依赖。**这不是优化,是能不能用的问题**——一个要 10 分钟的 CI,人会开始绕过它。"

> **"为什么要把脚本从 ConfigMap 改成烘进镜像"**
>
> "因为 ConfigMap 挂载的脚本是**可变制品**,而可变制品和不变性是互斥的。挂脚本的时候你连一个版本都没有——改了就是改了,追不了、回滚不了,而且改完还得重启 Pod 让它重读。烘进镜像之后,脚本有了 tag、有了 digest,能追、能回滚,而且整个流程都能被 CI 覆盖。这和我在另一个镜像上发现的问题是同一件事的两个方向:那个是**构建输入缺在镜像外**,这个是**运行时内容散在镜像外**,共同点是**制品不自包含**。"
