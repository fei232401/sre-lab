# 一、接缝 G:⑦ 运行 → ⑧ 观测

## 1.1 核心命题

**运行**和**观测**之间隔着一个"**我以为**"。

服务在跑是一个客观事实;"我认为服务在跑"是一个**由一堆信号拼出来的判断**。接缝 G 的全部风险在于:

> **信号存在 ≠ 信号被消费。**

这是本项目里反复出现的一类事故,统一名字叫 **静默失效**:

| 特征 | 说明 |
|---|---|
| 对象**存在** | Pod 是 Ready 的、ConfigMap 是 apply 成功的、规则是建好了的 |
| `status` **正常** | `kubectl get` 看起来完全健康 |
| **零报错** | 日志里没有 ERROR |
| **但消费方根本没读它** | 真正的功能一次都没发生 |

> **为什么它比"崩了"危险得多**:崩了会有人喊;静默失效**产生的信号和"一切正常"完全一样**。你的监控面板在两种情况下都是绿的。

## 1.2 本项目的标本:三条"全绿但没发生"

这三条都发生在 M2(可观测与告警)阶段,留痕在 `06_踩坑记录.md`。

**标本一:promtail 3/3 Ready、零报错,一条日志都没采到。**

日志里在欢快地打印 `Adding target`——**它在正常工作**。但采集到的日志是**零**。根因是配置里少了一个斜杠的位置(通配符路径写法),而 promtail 对"**匹配不到文件**"这件事**不打任何日志**。

> **它打印的是"我加了 target",不是"我读到了文件"。** 这两件事之间隔着配置解析、路径匹配、文件发现——**它只对第一件事负责,而你以为它说的是第三件事。**

**标本二:Alertmanager 的 receiver 是出厂默认的 `null`。**

告警**算出来了**,也**推给 Alertmanager 了**,然后**被丢掉了**——因为没人告诉它该发给谁。

> 这是"管道通了但末端没有接东西"。`Alertmanager` 的部署是成功的、Pod 是 Running 的——**从部署的角度看它 100% 健康**。

**标本三:三个告警规则 + 两个 ServiceMonitor 在 etcd 里躺了 43 天,从未生效。**

对象存在、schema 合法、apply 返回成功。**但没有被任何 Prometheus 选中。**

> **CRD 不知道自己没有被谁选中。** 它没有任何机制去发现"应该选我的那个选择器没选我"。

**标本四(今晚新增):CI 轮询静默不触发。**

详见 `06_踩坑记录.md` P18,以及本册 §三。

## 1.3 设防一:**去问消费者,不要看资源存不存在**

这是从三条标本里提炼出的**唯一一条通用动作**:

| ❌ 别这么验 | ✅ 这么验 |
|---|---|
| `kubectl get cm promtail-config` 存在 | 去问 promtail 的 `/targets` 端点,它认到了几个 target |
| `kubectl get alertmanager` 是 Running | 读 Alertmanager 的 `/api/v2/status`,看 **config 里实际的 receiver 是什么** |
| `kubectl get prometheusrule` 建好了 | 问 Prometheus 的 `/api/v1/rules`,`count()` 一下 |
| ServiceMonitor apply 成功 | 问 Prometheus 的 `/api/v1/targets`,看这个 job 在不在里面 |
| 镜像 tag 是新的 | 去容器里读它**自报的版本**(见接缝 H) |

**本册写作时现场核实(只读)**:

```
$ curl .../api/v1/rules   → 规则组 36 | 规则总数 249
$ curl .../api/v1/targets → 抓取目标 24 | up 24 | down 0
```

> **注意这里的动作是"问 Prometheus",不是"看 Kubernetes"。** 这两者能给出的信息**根本不是一回事**——后者只知道对象存在,前者才知道它有没有被读。

> **面试可以怎么讲**:
>
> "我踩过一个特别典型的坑:promtail 明明 3/3 Ready、日志里一直在欢快地打印 `Adding target`,但一条日志都没采上来。根因是配置里通配符路径写错了,而 promtail **对'匹配不到文件'这件事不打任何日志**。
>
> 这件事让我总结出一条:**验证要问消费者,不要看生产者有没有把东西放在那儿。** 'ConfigMap 存在'和'组件真的读了它'是两件事。所以我后来的验证一律是去问消费方的 API——问 Prometheus 的 `/api/v1/rules` 和 `/api/v1/targets`,而不是 `kubectl get prometheusrule` 看它建没建出来。"

## 1.4 设防二:告警链路要**端到端验四段**

一条告警从"条件成立"到"人知道",中间有四段,**每段都能单独断**:

```
① 规则求值(条件真的成立了被算出来)
   ↓
② Prometheus 推给 Alertmanager(推得出去)
   ↓
③ Alertmanager 路由(receiver 不为 null,路由规则匹配得上)
   ↓
④ 接收方收到(邮件真的进了收件箱)
```

> **前三段都是机器的,第四段是人的。**
>
> **"最后一跳是人,就只能由人来验证。"** 没有哪个 API 能告诉你"人看到了"。

**本项目的做法(D15)**:邮件通道做了**三层取证**,最后**由人确认收件箱**。这条在文档里被反复强调,因为它是唯一一种**不能自动化验收**的验证。

## 1.5 设防三:**先降噪,再接通道**

这是本项目一条很实在的经验:

> **告警疲劳是头号失效模式。**

一个每 5 分钟响一次的告警,和没有告警**在效果上是等价的**——它训练出的是"这个我不用管"的条件反射。

**本项目的标本**:降噪把告警数量**从 39 降到 1**。

> **顺序很重要:先降噪,再接通道。**
>
> 反过来做(先接通道再降噪)的后果是:通道接入的那一刻,**你的手机被 39 条告警淹没**,然后你会去关掉这个通道——**而这时你的结论会是"告警没用",而不是"我的告警没调好"**。

## 1.6 知识展开:静默失效为什么这么难防

把上面几条合起来看,能提炼出一个更有普适性的模型。

**任何一条链路都可以拆成三段**:

```
生产者 ——→ [配置/选择器/契约] ——→ 消费者
   ✅            ❓                 ✅
```

**生产者存在**是你能直接观测到的;**消费者存在**也是;**中间那段契约**——那个选择器、那个通配符、那个 receiver 名——**才是会断的地方,而且它断了以后两边都还是健康的。**

| 断在哪 | 现象 |
|---|---|
| 生产者不存在 | 好查:Pod 起不来、对象没有 |
| 消费者不存在 | 好查:目标 job 缺失 |
| **中间契约断了** | **两边全绿,什么都没发生** |

> **所以排查顺序要反过来:不要从"东西在不在"开始,要从"消费者收到了什么"开始往前推。**

> "我在可观测这块踩的坑有一个共同的形状:**东西都在,但事情没发生。**
>
> 比如 promtail 的 Pod 3/3 Ready、日志里一直在打印 `Adding target`,但一条日志都没采上来——因为配置里通配符路径写错了,而它对'匹配不到文件'不打任何日志。再比如 Alertmanager 的 receiver 还是出厂默认的 `null`,告警算出来了、也推过去了,然后被丢掉。还有三个告警规则在 etcd 里躺了 43 天从没生效过。

# 二、接缝 H:⑧ 观测 → ⑨ 回滚

## 2.1 核心命题:回滚能力是**发布时**决定的

**回滚这件事,在你发布的那一刻就已经被决定了。** 发布时留下的东西,决定了你回滚时有什么可用:

| 发布时 | 回滚时 |
|---|---|
| tag 是 `latest` | **回滚不了**——没有"旧的那一份"可指 |
| tag 是 git short SHA | 回滚粒度 = **每一次构建** |
| 镜像内容与 tag 脱钩 | 回滚了也不知道退到的是不是对的 |
| 没记 revision | 回滚完无法证明 |

> **一句话:回滚的粒度 = 制品标识的粒度。**

本项目选 `git short SHA` 作 tag,理由见 01 分册 §3.2;今晚的演练证明了这个选择**直接决定了回滚能做到什么程度**。

## 2.2 回滚不是倒放,是**一次新的部署**

重申开篇那句,并展开:

```
你以为的回滚:  ⑦运行 ──倒带──→ ⑦运行(旧)
实际的回滚:    ⑧观测 → 决定 → ⑤声明(改成旧的) → ⑥收敛 → ⑦运行(旧) → ⑧观测(再验一次)
```

**推论:**

1. **回滚也会失败。** 它走的是和发布完全一样的路径。
2. **回滚需要验证。** 终点校验要和发布时一样做——否则你只是**换了一种方式不知道自己在哪**。
3. **回滚失败是"二次事故"。** 此时系统**已经在异常状态**,再叠一次失败的变更,**归因会变得非常难**:你分不清某个现象是"原来的问题还没好"还是"回滚引入的"。

> **所以第三条纪律是:演练回滚,不要等真出事第一次做。** 真出事时你是在**同时**做三件事:排障、决定、执行——而这三件事会互相干扰。

## 2.3 今晚的完整演练(M4,实测)

### 演练目标

**让"跑的是哪个版本"这件事可证,然后双向地证明它变了、又变回去了。**

### 第一步:让运行时自己报名

给 exporter 加一个指标:

```
sre_lab_build_info{revision="a14ce79"} 1
```

**版本号是构建期注入的,不是运行时读环境变量:**

| 做法 | 问题 |
|---|---|
| 运行时 `env: GIT_SHA=xxx` | **同一个镜像换个 env 就"变成"另一个版本**——又回到"标签说了算" |
| **构建期 `--build-arg GIT_SHA=xxx`** | **镜像内容本身携带版本**,这才是不可变制品 |

`Dockerfile` 接 `ARG GIT_SHA`;`Jenkinsfile` 构建时传 `--build-arg GIT_SHA=${SHORT_SHA}`(`SHORT_SHA` = 源码仓该次提交的 7 位哈希)。

### 第二步:采证据的三种档次

| 做法 | 能证明什么 |
|---|---|
| 看 Pod 上的镜像 tag | ⚠️ 只证明**调度器让它跑这个 tag**。不证明它起来了,更不证明镜像内容对 |
| `kubectl rollout status` | ⚠️ 只证明 **Deployment 认为**它就绪 |
| **从容器内部经真实数据面取回自报版本** | ✅ 这才是行为级证据 |

采法(`python:3.11-slim` **没有 wget 也没有 curl**,用自带的 urllib):

```bash
POD=$(kubectl -n ai-platform get pods --no-headers | grep ollama-exporter | awk '{print $1}')
kubectl -n ai-platform exec $POD -- python -c "
import urllib.request
t=urllib.request.urlopen('http://127.0.0.1:9101/metrics',timeout=10).read().decode()
print([l for l in t.splitlines() if 'build_info' in l])"
```

### 第三步:双向证据(时间线全部为实际观测)

| 时刻 | 动作 | 证据 |
|---|---|---|
| 21:49 | 触发构建 #10 | — |
| ~21:51 | 流水线 SUCCESS,写回声明 | Gitea main 前进到 `d7a0b3e` |
| 21:52:33 | ArgoCD 认到新 revision | `sync.revision=d7a0b3e`,Pod 仍是旧镜像 |
| 21:53:03 | 新 Pod 起来 | image = `a14ce79` |
| 21:53:1x | **行为证据(去)** | `sre_lab_build_info{revision="a14ce79"} 1` |
| 21:53:38 | `git revert d7a0b3e` 并推送 | 声明里 image 回到旧 tag |
| 21:55:42 | ArgoCD 收敛回退 | Pod image 换回旧 tag |
| 21:55:59 | **行为证据(回)** | 同一个 `/metrics` 端点,`build_info` **整行消失**(0 行) |

### 为什么"指标消失"比"值变回去"更有说服力

> **因为旧镜像根本没有这个指标。**

这个指标是**在这次变更里才加进去的**。所以回滚后的证据不是"值变了",而是"**这个能力整个不存在了**"。

**这是一个结构性差异**——不可能是缓存、不可能是我看错了 tag、不可能是采样窗口的问题。

> **面试可以怎么讲(这是接缝 H 最该背的一段)**:
>
> "我们做过一次发布回滚演练。为了让'跑的是哪个版本'这件事可证,我在**构建期**把 git SHA 注入镜像,程序通过 `/metrics` 自报版本号——**证据是从容器内部、经真实数据面取回来的**,不是看 Pod 上那个 tag 字符串。
>
> 演练是双向的:部署后指标出现且版本号正确;`git revert` 声明式回滚后,Pod 换回旧镜像,**那个指标整行消失**——因为旧镜像根本没这个能力。这比'值变回去了'强得多,它是**结构性**的差异。
>
> 我特意没有用运行时注入环境变量。因为那样的话,同一个镜像换个 env 就'变成'另一个版本了,**又回到'标签说了算'**。构建期注入才让**镜像内容本身携带版本**,这才是不可变制品。"

## 2.4 GitOps 下,**手工回滚是无效动作**

这是今晚第二个重要发现。

**实验**:手工改镜像。

```bash
kubectl set image deployment/ollama-exporter ollama-exporter=<registry>/...:ea96824
# deployment.apps/ollama-exporter image updated   ← 命令成功
```

**t+5 秒,镜像已经变回去了。** 命令返回成功,`kubectl get` 头两秒也确实显示新值。

**根因**:

> **ArgoCD 对"它管理的资源"有 watch。那 3 分钟只是兜底的全量对账。**
>
> **`selfHeal` 不是"每 3 分钟修一次",是"发现即修"。**

**推论(这条比结论本身更值钱)**:

> **GitOps 下,手工 `kubectl` 改动是"无效动作",不是"临时有效动作"。**
>
> 更危险的是它**不报错**——命令成功、头两秒也确实生效。**如果我只看了这两秒,我会得出"改成功了"的结论并写进文档。**

**排障纪律**:看到"我明明改了啊",先问一句:**这个资源归 ArgoCD 管吗?**

**正确做法**:`git revert` 那次 bump 提交,让 ArgoCD 收敛。详见 `03_runbook/04_发布与回滚手册.md` 第四节。

> ⚠️ **为什么用 `revert` 而不是 force push**:历史保留——**谁在什么时候退的、为什么退的,可追溯**。回滚最需要的能力就是"事后说得清"。

## 2.5 ⚠️ 观测本身也会骗人:我采到了正在退场的旧 Pod

这是今晚**演练之后**采最终态时的真实失误,值得单独记。

滚动更新期间,集群里**同时存在新旧两个 Pod**。我用 `grep ... | awk '{print $1}'` 取第一个,**取到的正是正在退场的旧 Pod**:

```
sre_lab_build_info{revision="238c406"} 1     ← 一个过期的、但看起来完全正常的值
```

> **"从容器里采到的"不等于"是对的"。**

**教训:**

1. **采样前要先确认你在采哪个 Pod。** 容器编排系统在收敛过程中,**任一时刻都可能有两代并存**。
2. **这个错误恰好证明了为什么要用运行时自报版本**:值对不上能让你**察觉到不对**;而只看 Pod 上的 tag 字符串,**连暴露的机会都没有**。

> **面试可以怎么讲**:
>
> "有个细节我印象很深。演练完我去采最终证据,拿到了一个旧版本号。查下来不是系统的问题——**滚动更新期间新旧两个 Pod 并存,我采到了正在退场的那个。**
>
> 这件事本身没什么,但它反过来说明了一件事:**观测动作本身也是会出错的**。所以我采行为证据之前会先确认目标是谁。而这一点也正是我坚持用'程序自报版本'而不是'看 Pod 上的 tag'的原因——**值对不上至少能让我发现不对,看 tag 连发现的机会都没有。**"

## 2.6 小结:接缝 H 的三条纪律

| # | 纪律 | 一句话 |
|---|---|---|
| 1 | **回滚能力前置** | 发布时就要留好"旧的那一份"——tag 粒度决定回滚粒度 |
| 2 | **回滚要有验证** | 回滚是一次部署,终点校验和发布一样做 |
| 3 | **演练回滚** | 不要等真出事第一次做——那时你在同时排障、决定、执行 |

# 三、跨接缝:今晚抓到的五个"静默失效"

接缝 G 讲的"信号存在 ≠ 信号被消费",今晚在**别的地方**又抓到了五条同形状的。它们全部满足:

> **系统不报错、面板全绿、但事情没发生。**

| # | 现象 | 决定性判据 | 出处 |
|---|---|---|---|
| 1 | CI 轮询**静默不触发** | `Done. Took 0 ms` / `No changes` | `06_踩坑记录.md` P18 |
| 2 | Gitea **拒绝投递** webhook | Gitea 日志里那行 `ALLOWED_HOST_LIST` | P23 |
| 3 | 闸门里 `core.quotePath` 的隐患 | 看**真实输出**长什么样,而不是读代码逻辑 | `03_runbook/04_发布与回滚手册.md` §六 |
| 4 | 自激循环 | 触发源和写入目标是**同一个仓库** | P19 |
| 5 | ArgoCD `selfHeal` 秒级拉回 | t+5s 手工改动消失 | P22 |

**#1 是最值钱的一条**,因为它同时踩了两个陷阱:

**(a) 判据是"物理上不可能的数字"。**

```
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
Done. Took 2 ms
No changes
```

> **一次网络往返(去问"远端 HEAD 是什么")不可能在 2 毫秒内完成。**
>
> **排查心法:先找"物理上不可能的数字"。** 时间量级异常比任何日志文本都直接——`2 ms` 这个数字本身就宣告了"它压根没去问"。

**(b) 我在这条上判错过一次,而且是被自己的实验推翻的。**

我第一判断是 `PathRestriction` 需要工作区。**方向是对的**,然后我摘掉它重试——**照样 0ms**。

**当晚稍晚,Jenkins 因为装插件重启了一次,轮询自己好了。**

修正后的解释能同时解释所有观测:**那个"上次构建的节点"引用缓存在 JVM 内存里,改配置清不掉,只有重启才清。**

> **⚠️ 诚实边界**:这个修正后的解释**没有做受控实验验证**——它是从三个观测里推出来的最简解释,不是被单独证明过的。
>
> **要证伪它,得在保留路径过滤的前提下重启一次、看轮询是否恢复。没做。**

**这条的教学价值,恰恰在于它推翻的部分**:

> **我加粗强调的那句("轮询模型和临时 agent 架构根本不兼容"),正是我最有把握的那句,也正是错的那句。**
>
> 而推翻它用的不是更深的推理,是**一次意外的重启带来的新观测**。
>
> **所以:先复现,再下结论。** 而且——**下结论时的确信程度,不该超过证据的强度。**

**#2 的判据同样干净**:

```
手动 wget 那个端点 → 200 triggered:true     ← 我以为链路通了
真实 push          → 什么都没发生           ← 链路根本没通
```

> **"我手动测过了,是通的"是一个很容易骗过自己的证据。**
>
> 手动测试用的是**你的**身份、**你的**路径、**你的**策略;系统自动投递用的是**它的**。两者能通的路径**可能根本不重叠**。
>
> 根因:Gitea 默认 `ALLOWED_HOST_LIST = external`(**SSRF 防护**),拒绝一切私网目标。**网络一直是通的,是 Gitea 自己不肯发。**

**#3 是"没发作的 bug"**:

`git diff --name-only` 遇到非 ASCII 路径时,默认输出**加引号的八进制转义形式**——首字符变成了 `"`,而闸门靠 `p.startsWith('ci/')` 判定,**匹配必然失败**。

> **当前 `ci/` 下的文件名都是 ASCII,所以它没发作。**
>
> **这类 bug 不会在测试里暴露,只会等到某个特定的人做了某件特定的事,然后安静地什么都不发生。** 发现它的方式是**去看真实输出**,而不是去读代码逻辑。
>
> 修法:所有 `git` 调用带 `-c core.quotePath=false`。

# 四、把三册连起来:一条链上的九处"静默"

| 接缝 | 静默失效的形态 | 手册位置 |
|---|---|---|
| A 代码→构建 | 构建成功,**产物不是线上那个** | 01 §二 |
| B 构建→制品 | tag 与内容脱钩 | 01 §三 |
| C 制品→登记 | 报错说"协议",你读成"网络" | 01 §五 |
| D 登记→声明 | 写回失败但**流水线还绿着** | 02 §二 |
| E 声明→收敛 | `Synced` 只保证对一个**旧** revision 一致 | 02 §三 |
| F 收敛→运行 | PDB 看起来合理,`drain` 时才卡住 | 02 §四 |
| **G 运行→观测** | **对象都在,但消费方没读它** | **本册 §一** |
| **H 观测→回滚** | **手工改动被秒级拉回,且不报错** | **本册 §二** |
| (跨)触发 | **CI 静默不触发 / webhook 静默被拒** | 本册 §三 |

> **同一条链上九处,断的方式各不相同,但形状完全一样:**
>
> **它不告诉你它断了。**

**这就是这套教材真正的主题。** 具体的命令会过期,工具会换,但"**怎么知道它真的做了**"这个问题不会。
