## 〇、这份教材怎么用

### 0.1 读者假设

这套材料假设你:

- 会写 Python,能看懂 YAML 和一段 Groovy(`Jenkinsfile`)或 shell,**不需要**预先会写;
- 懂 K8s 基础(Pod / Deployment / Service / Namespace / kubectl 常用命令);
- 对 CI/CD 的认知是**碎片化的**——大概知道"要用 Jenkins 构建、用 ArgoCD 部署",但说不清这条链子中间断在哪、断了会怎样。

**它不假设**你已经在生产环境干过 CI/CD,也不假设你见过多集群。

### 0.2 全篇的主论点,先记住这一句

> **痛几乎从来不发生在段落内部,而是发生在接缝上。**

因为每一段本体都是**单机可测**的:你把输入喂给它,它给你输出,错了立刻知道。而接缝的两侧是**两个不同的人 / 系统 / 信任域**,信息在接缝处丢失,而且**丢失通常是静默的**。

这句话的推论才是真正有用的部分:

> **排查 CI/CD 问题,第一步不是"看哪一段坏了",而是"先问这道缝的两边各自以为发生了什么"。**

### 0.3 两条阅读路径

| 路径 | 顺序 | 适合谁 |
|---|---|---|
| **先干后枝**(推荐) | 00 读完 §一 §二 → 挑一个你正在做的段落到 01 / 02 里精读 → 回来读 §三 §四 | 正在搭环境、想边做边懂 |

## 一、主干:九段传送带

### 1.1 全景

一条从一行源码到"集群里一个正在服务、并且能被观测、还能被退回去"的传送带,拆开是九段:

```
 ① 代码 ──A──▶ ② 构建 ──B──▶ ③ 制品 ──C──▶ ④ 登记
                                              │
                                              D
                                              ▼
                                              ⑤ 声明 ──E──▶ ⑥ 收敛 ──F──▶ ⑦ 运行
                                                                              │
                                                                              G
                                                                              ▼
                                                                       ⑧ 观测 ──H──▶ ⑨ 回滚
```

把它读成一句话:

> **开发者写下源代码(①);构建器把源码变成制品(②);制品是分层的镜像(③);镜像被推进制品仓库(④);"该跑哪个镜像"这件事被写进 Git 清单(⑤);ArgoCD 把集群的实际状态拉向那份声明(⑥);工作负载真正跑起来(⑦);指标和日志告诉你它跑得怎么样(⑧);出了事你退回上一个版本(⑨)。**

九段里,**①–④ 是"把东西造出来并送出去",⑤–⑦ 是"把东西放到位并跑起来",⑧–⑨ 是"知道它好不好、以及怎么退回去"**。

### 1.2 逐段:这一段要解决什么问题

每一段下面四行是固定的:**解决什么 / 谁负责 / 产出物 / 常见失败**。

#### ① 代码

| 维度 | 内容 |
|---|---|
| 解决什么 | 提供**唯一可信的输入**。构建必须能指着某个 commit 说"就是这个版本" |
| 谁负责 | 开发者;但**"输入完不完整"是运维/CI 责任** |
| 产出物 | 一个 commit(有一个不可变的 SHA) |
| 常见失败 | 代码在,但**构建要的其它输入不在**(配置、依赖清单、本来就该在仓库里的模块)——见接缝 A |

**本项目的实例**:仓库 `fei232401/sre-lab` 一个仓装应用代码、GitOps 清单、排障记录三样东西;`ci/Jenkinsfile` 定义流水线;`03-ollama-exporter/` 是 CI 的第一个构建对象。**详细标本见 01 分册 §二。**

#### ② 构建

| 维度 | 内容 |
|---|---|
| 解决什么 | 把源码变成可运行的产物,并且**这个过程是被定义的** |
| 谁负责 | CI 系统(Jenkins);构建环境由运维负责 |
| 产出物 | 一个镜像(或别的不可变产物) |
| 常见失败 | 构建环境不能复现;构建器需要特权;构建看不到外网/看不到内网源 |

**本项目的实例**:Jenkins 的**动态 agent Pod**(每次构建起一个 Pod,用完销毁),三个容器各司其职——`buildah`(构建)、`lint`(Python 语法检查)、`git`(检出与写回)。构建器选 buildah 而非挂 `docker.sock`。**详细标本见 01 分册 §一。**

#### ③ 制品

| 维度 | 内容 |
|---|---|
| 解决什么 | 产物本身要**自包含、可追溯、可回滚** |
| 谁负责 | 构建侧 + 制品设计(镜像怎么写) |
| 产出物 | 分层镜像(层可共享、可缓存;顺序决定缓存命中) |
| 常见失败 | 制品不自包含(依赖镜像外的 ConfigMap);体积失控;基础镜像选择错误 |

**本项目的实例**:`ollama-exporter` 从"ConfigMap 挂脚本"改成"烘进镜像"——**把制品从可变变成不可变**。**详细标本见 01 分册 §6.5。**

#### ④ 登记

| 维度 | 内容 |
|---|---|
| 解决什么 | 制品存哪儿、谁能推、谁能拉 |
| 谁负责 | 运维(仓库搭建、凭据、传输配置) |
| 产出物 | 仓库里的一个 tag(内部指向一个 digest) |
| 常见失败 | 推不上去(认证);拉不下来(协议/凭据层级);仓库没有访问控制 |

**本项目的实例**:本地 k3d registry 容器,集群内域名 `k3d-sre-registry:5000`、主机侧 `localhost:5111`。**详细标本见 01 分册 §四。**

#### ⑤ 声明

| 维度 | 内容 |
|---|---|
| 解决什么 | 把"期望状态"从一串命令变成**一份存在版本控制里的文本** |
| 谁负责 | 写清单的人(本项目里由 CI 自动改一个 tag) |
| 产出物 | Git 仓库里的 YAML;一个 Application 对象描述"哪份清单管哪个命名空间" |
| 常见失败 | 监视目录里放了非清单文件;手工 `kubectl set image` 造成漂移;单仓 vs 双仓的权限边界 |

**本项目的实例**:`sre-lab-gitops/production/` 下 6 个 Application + 一个 App-of-Apps 的 `root-app`。**详细标本见 02 分册 §一。**

#### ⑥ 收敛

| 维度 | 内容 |
|---|---|
| 解决什么 | 让集群的实际状态**持续**被拉向声明状态 |
| 谁负责 | CD 控制器(ArgoCD,拉模式) |
| 产出物 | 与某个 revision 一致的集群状态 |
| 常见失败 | `Synced` 的含义被误读(它只保证相对**已知**的那个 revision 一致);prune 删了不该删的 |

**本项目的实例**:`selfHeal` / `prune` **按应用性质分级**——基础设施类全开,存量接管期的 `ai-platform` 两个都关。**详细标本见 02 分册 §1.5、§三。**

#### ⑦ 运行

| 维度 | 内容 |
|---|---|
| 解决什么 | 资源被创建之后,真的能跑、真的能接流量 |
| 谁负责 | 集群(kubelet / 调度器 / 控制器)+ 工作负载的作者 |
| 产出物 | 一个 Ready 并且**真的能服务**的 Pod |
| 常见失败 | 镜像拉不动;调度不上(GPU/资源/PDB);没有探针导致"就绪"是假信号 |

**本项目的实例**:三个节点 `agent-0`(GPU,内存 81%)/ `agent-1`(`node-role: cpu`)/ `server-0`(控制面);工作负载用 `nodeSelector: node-role: cpu` 避开 GPU 节点。**详细标本见 02 分册 §四。**

#### ⑧ 观测

| 维度 | 内容 |
|---|---|
| 解决什么 | 知道系统现在**真的**在发生什么,并且**在它变坏之前**收到信号 |
| 谁负责 | 运维(指标口径、采集选择性、告警阈值与路由) |
| 产出物 | 指标 / 日志 / 告警;一条**端到端验证过的**通知链路 |
| 常见失败 | 对象建了但没被消费(`ruleSelector` 白名单);告警进了黑洞;告警疲劳;过程指标全绿但结果没达成 |

**本项目的实例**:Prometheus + Loki/Promtail;降噪把告警数从 39 降到 1;接收端用 Alertmanager 原生 **email receiver** + SealedSecret,**端到端验证到"人打开收件箱看到了"**(D15)。**详细标本见 03 分册(待写);留痕见 `06_踩坑记录.md` P4/P5/P12/P13/P14。**

#### ⑨ 回滚

| 维度 | 内容 |
|---|---|
| 解决什么 | 出事的时候,把系统**退回到一个已知好的状态** |
| 谁负责 | 运维;但**回滚能力是 tag 策略给的**,不是部署系统给的 |
| 产出物 | 一次回到旧版本的变更(以及它自己的验证) |
| 常见失败 | 没有旧版本可回(只有一个 `latest`);回滚粒度太粗;回滚本身也失败 |

**本项目的实例**:tag 用 git short SHA,粒度 = 每次构建;发布与回滚演练在设计里属于 **M4**。**本册写作时该演练尚未落地**(`03_runbook/` 下只有 SealedSecrets / ArgoCD / Jenkins 三份手册,没有"发布与回滚"手册)——这是本文最需要诚实标注的空缺。**tag 粒度与回滚的关系见 01 分册 §3.2。**

### 1.3 一张总表

| 段 | 一句话职责 | 谁负责 | 产出物 | 最典型的失败 |
|---|---|---|---|---|
| ① 代码 | 提供唯一可信输入 | 开发者 | commit(SHA) | 构建输入不在仓库里 |
| ② 构建 | 把源码变成产物 | CI 系统 | 镜像 | 环境不可复现 / 需要特权 |
| ③ 制品 | 自包含、可追溯、可回滚 | 构建侧 | 分层镜像 | 不自包含 / 体积失控 |
| ④ 登记 | 存哪儿、谁能推拉 | 运维 | 仓库里的 tag | 认证 / 协议 / 无访问控制 |
| ⑤ 声明 | 期望状态落进 Git | 写清单的人 | YAML + Application | 目录边界错 / 手工改集群 |
| ⑥ 收敛 | 持续把集群拉向声明 | ArgoCD | 一致状态 | `Synced` 被误读 / prune 误删 |
| ⑦ 运行 | 真的跑起来、真的服务 | 集群 + 负载作者 | Ready 且能服务的 Pod | 拉不动 / 调度不上 / 假就绪 |
| ⑧ 观测 | 知道真实情况并提前报警 | 运维 | 指标日志告警 | 对象没被消费 / 告警黑洞 |
| ⑨ 回滚 | 退回已知好的状态 | 运维 | 一次回退变更 | 没有旧版本可回 |

### 1.4 为什么"段内"的痛比较少

不是因为它简单,是因为**段内的问题是自证的**:

| 段内失败 | 为什么好查 |
|---|---|
| 构建失败 | 构建器报错,退出码非零 |
| 镜像推不上去 | 命令直接失败 |
| Pod 起不来 | 状态列直接显示 `Pending` / `CrashLoopBackOff` |
| 告警发不出去 | 计数器有值(如果找了正确的计数器) |

而**段与段之间**的失败往往**没有非零退出码**:CI 全绿、ArgoCD 全绿、Pod 全 Running,而系统已经不对了。这就是第二章的全部内容。

## 二、接缝:痛点的真正所在地

### 2.1 接缝的定义

> **接缝(seam)= 相邻两段的交界处。**
>
> 它的本质不是"两个组件之间",而是**两个信任域 / 两套凭据 / 两种失败语义之间**。在接缝上:
>
> - 左边**看不到**右边的输出,右边也看不到左边的;
> - 双方对"什么东西应该存在"的假设**没有共同的语言来表达**;
> - 因此**接缝上的失败是静默的**——两边都是绿的。

**判断一道缝有没有出问题,只需要问三个问题**:

1. 这道缝**左边**的产出,右边**真的以它以为的方式**读到了吗?(格式/位置/时机)
2. 这道缝**右边**的失败,左边**能被通知到**吗?(失败是否被静默吞掉)
3. 这道缝上**谁**在做判断——是自动的,还是"看起来自动但其实需要有人去看一眼"?

### 2.2 八道接缝

下面每条给:**定义 / 典型翻车 / 设防手段 / 去哪一册精读**。

#### 接缝 A:① 代码 → ② 构建

**定义**:构建的**输入**是否完整地存在于版本控制里。

| | 内容 |
|---|---|
| 典型翻车 | **构建根本跑不起来**(显而易见);或者更糟——**它跑起来了、也成功了,但产出的是另一个东西**(隐藏) |
| 静默性 | 第二种形态**没有任何红灯**:镜像构建成功、容器启动成功、健康检查通过、服务正常响应。它唯一的破绽是你**还没走到的那条代码路径** |
| 设防 | ① 构建输入清单化:**用 `docker history` 从镜像反推它需要哪些文件**,再拿去和仓库对;② 从镜像层抢救缺失输入(`docker create` + `docker cp`);③ **逐字节哈希比对**证明捞出来的是原件;④ 基础镜像钉 digest(本项目未做) |

**本项目的标本**:`ai-infra-gateway:v20` 跑了 30 天却无法从版本控制重建,三条独立漂移线,其中最危险的是"配置文件缺一段,静态检查全过、容器能起、**第一个请求才 `KeyError`**"。

**去哪看**:01 分册 §二(整章)。留痕是 `06_踩坑记录.md` P17。

#### 接缝 B:② 构建 → ③ 制品

**定义**:给产物一个**标识**,让整条链子后面所有能力(部署、回滚、审计)有东西可引用。

| | 内容 |
|---|---|
| 典型翻车 | tag 和内容对不上(打了 `v20` 的镜像里代码自称 `v11.0`);`latest` 不是最新的;**可变 tag + `IfNotPresent` = 同一个 tag 在不同节点上是不同内容,而集群层面完全看不出来** |
| 静默性 | 没有 `ImagePullBackOff`,因为**根本没有发生拉取**。要查只能去每个节点上看镜像 ID |
| 设防 | ① tag 用不可变值(git short SHA);② 生产姿势是 **tag 给人看、digest 给机器用**(把 digest 钉进部署清单——本项目未做);③ 记住:**回滚的粒度 = tag 的粒度** |

**本项目的标本**:`ai-infra-gateway` 的 `latest` 比 `v10`/`v11` 都早;CI 用 `git rev-parse --short=7 HEAD` 做 tag。

**去哪看**:01 分册 §三(整章)。

#### 接缝 C:③ 制品 → ④ 登记

**定义**:东西**推得上去吗、拉得下来吗、凭据是谁的**。

| | 内容 |
|---|---|
| 典型翻车 | `DENIED`(OAuth scope 只有 `write:packages`,没有 `read:packages`);`http: server gave HTTP response to HTTPS client`(协议不对);`ImagePullBackOff` 但报错指向的那一层不是真因 |
| 静默性 | 这条缝的报错**信息量很大但极易读错**——"协议不对"很容易被读成"网络不通",然后去查 DNS 和防火墙,全部查不出东西 |
| 设防 | ① **五层排查顺序**:DNS → TCP 可达 → 协议 → 认证 → 内容,**报错停在哪一层就说明它前面所有层都是好的**;② 分清**认证**(Pod 级 `imagePullSecrets` 可以)与**传输配置**(只能节点级);③ 问一句"**谁在拉镜像?**"——是节点,不是 Pod |

**本项目的标本**:本地 registry 是纯 HTTP,containerd 默认走 HTTPS;`registries.yaml` 要重启 k3s、`certs.d/hosts.toml` 不用;一次"节点连不上 GitHub"的误判其实是节点里没有 `curl`。

**去哪看**:01 分册 §五(整章)。留痕是 `06_踩坑记录.md` P16。

#### 接缝 D:④ 登记 → ⑤ 声明

**定义**:哪个 tag 被写进清单、**谁写、什么时候写、用谁的身份写**。

| | 内容 |
|---|---|
| 典型翻车 | **写回失败是静默的**:流水线的成功标准和集群的成功标准是两个系统,CI 全绿只说明它的 stage 过了 |
| 静默性 | 没有 `set -e` 时,`git push` 失败后脚本继续往下走,最后一条 `echo` 成功 → **流水线显示绿色,而集群根本没变** |
| 设防 | ① 写回脚本 `set -e`(硬失败);② push 之后做**独立的读回验证**(`git ls-remote`),因为**写入命令自己的返回值不能证明远端收到了**;③ 凭据权限范围 = 需求范围(仓库级 deploy key,而不是 PAT);④ 并发用 `disableConcurrentBuilds` 或 rebase 重试 |

**本项目的标本**:`Update GitOps` stage 里的 `set -e` / `git diff --quiet` 短路 / 三次 rebase 重试;deploy key 的选型(D17)。

**去哪看**:02 分册 §二(整章)。

#### 接缝 E:⑤ 声明 → ⑥ 收敛

**定义**:ArgoCD **读到的**是哪一份清单,以及 **`Synced` 到底意味着什么**。

| | 内容 |
|---|---|
| 典型翻车 | **`Synced` 骗人两次**:push 了删除操作的 commit,UI 显示 `Synced` 但对象还在集群里;网络故障期间整个链路**静默半死**,所有信号都是绿的 |
| 静默性 | `Synced` 的准确含义是"集群 == **ArgoCD 上一次成功拉到的那个 revision**",**它和远端最新 commit 没有任何关系**。拉不到新的,它会继续拿旧的 rev 对账,**并且继续报绿色** |
| 设防 | ① 判定口径:**凡是以"当前状态 == 期望状态"表述的健康信号,都要先问"期望状态是谁的期望、哪个时刻的期望"**;② 验证要看 revision(`.status.sync.revision` vs `git rev-parse HEAD`),不一致就 hard refresh,不要等轮询;③ 判断"真故障还是中间态"**先看时间戳,不看报错内容** |

**本项目的标本**:CoreDNS 钉 IP 后 ArgoCD 立刻恢复而 Jenkins 纹丝不动(JVM 缓存 DNS);二十分钟后钉的 IP 也被封,**换 IP 是打地鼠**→ 转向集群内自建 Gitea。

**去哪看**:02 分册 §三(整章)。留痕是 `06_踩坑记录.md` P10 / P15。

#### 接缝 F:⑥ 收敛 → ⑦ 运行

**定义**:资源被创建之后,**它能不能真的跑起来、真的接上流量**。

| | 内容 |
|---|---|
| 典型翻车 | `imagePullSecrets`(Pod 级)配了也不解决协议问题(节点级);PDB `minAvailable` 等于副本数 → `disruptionsAllowed: 0` → **`kubectl drain` 永久挂起**;滚动更新的"先起后停"在**没有探针时是假的保护** |
| 静默性 | PDB 那个坑:apply 成功、`describe` 里 `MIN AVAILABLE: 1` 看起来完全合理,**只有真去 drain 的时候才发现卡住**——而那时你已经在做一次生产变更了 |
| 设防 | ① 探针是滚动更新语义的地基(**没有 readinessProbe,kubelet 认为"就绪"的标准只是"容器进程起来了"**);② PDB 数值**相对副本数**设,排查**先看 `expectedPods` 再看 `currentHealthy`**;③ 调度:`nodeSelector`/affinity 是 Pod 说"我想去哪",taints/tolerations 是节点说"谁允许来",**两者必须同时满足** |

**本项目的标本**:`ollama-pdb`(`minAvailable: 1` + 1 副本);`my-nginx` 3 副本、无 `strategy`、无探针 → 实际 `maxUnavailable` 取整后为 **0**。

**去哪看**:02 分册 §四(整章)。

#### 接缝 G:⑦ 运行 → ⑧ 观测

**定义**:系统在跑,但**你看到的和你以为你看到的不是一回事**——指标口径、采集选择性、告警阈值与真实用户体验之间的落差。

| | 内容 |
|---|---|
| 典型翻车 | promtail 3/3 Ready、零报错、日志在欢快打印 `Adding target`,却**一条日志都没采到**(通配符少了一个斜杠,而它对"匹配不到文件"**不打日志**);`Alertmanager` 的 receiver 是出厂默认的 `null`;三个告警规则 + 两个 ServiceMonitor 在 etcd 里躺了 43 天从未生效 |
| 静默性 | 这一类统一的形态叫**静默失效**:对象存在、`status` 正常、零报错,**但消费方根本没读它**。CRD 不知道自己没有被谁选中 |
| 设防 | ① **去问消费者,不要看资源存不存在**(Prometheus 的 `/api/v1/rules`、`/api/v1/targets`);② 告警链路**端到端验四段**:规则求值 → Prometheus 推送 → Alertmanager 路由 → 接收方收到,**最后一跳如果是人,就只能由人来验证**;③ 先降噪再接通道(告警疲劳是头号失效模式) |

**本项目的标本**:降噪把告警数从 39 降到 1;邮件通道三层取证 + 人工确认收件箱(D15);`promtail` 的 `separator: "/"` 修复 + 改 ConfigMap 后必须 `rollout restart`。

**去哪看**:03 分册(待写)。留痕是 `06_踩坑记录.md` P4 / P5 / P6 / P7 / P8 / P11 / P12 / P13 / P14。

#### 接缝 H:⑧ 观测 → ⑨ 回滚

**定义**:从"发现异常"到"做出回滚决定"再到"回滚真的生效",这条路上的**延迟、粒度、以及回滚本身也可能失败**。

| | 内容 |
|---|---|
| 典型翻车 | 发现了但没告警出去(接缝 G 的延续);决定回滚时**发现根本没有旧版本可回**;回滚粒度太粗(只能退回"昨天");**回滚本身也是一次部署,也会失败** |
| 静默性 | 回滚失败是"二次事故":此时系统已经在异常状态,再叠一次失败的变更,归因变难——你分不清某个现象是"原来的问题还没好"还是"回滚引入的" |
| 设防 | ① 回滚能力前置:tag 粒度决定了回滚粒度(**只有 `latest` 就是回滚不了**);② 回滚也要有验证(和发布一样的终点校验);③ 演练回滚,不要等真出事第一次做 |

**本项目的标本**:tag 用 git short SHA(回滚粒度 = 每次构建);但**完整的发布与回滚演练(M4)本册写作时尚未落地**——所以这一条缝在本项目里**只有机制、没有演练证据**。

**去哪看**:03 分册(待写);机制部分见 01 分册 §3.2。

### 2.4 从八条缝里抽出来的四条通用规律

这四条在整个项目里反复出现,值得背下来(02 分册 §B.3 有对应的五条版本):

> 1. **每一段只看得到自己的输出。接缝上的失败,两侧都看不见。**
> 2. **凡是以"当前状态 == 期望状态"表述的健康信号,都要先问:期望状态是谁的期望、哪个时刻的期望。**
> 3. **修好基础设施层不等于修好了消费方。** 改完上游,要按消费方逐个确认它什么时候才看得到(改 DNS 要重启 JVM;改 ConfigMap 要 `rollout restart`)。
> 4. **过程指标全绿不等于结果达成。** 验证必须去链路终点做,而且要用**独立的读取**,不能用写入命令自己的返回值。

### 2.5 反查表:从一个现象,倒推它在哪道缝上

上面是"从缝到现象"。真正排障时顺序是反的——**你先看到一个现象,然后要判断它属于哪道缝**。这张表就是干这个的。

| 你观察到的现象 | 最可能的接缝 | 第一件该做的事 | 精读 |
|---|---|---|---|
| 镜像构建成功、容器能起、健康检查通过,但一上真实流量就报错 | **A** | 不要查行为,查**内容**:把镜像里的文件与仓库里的做哈希比对 | 01 §2.6 |
| 同一个 Deployment、同一个 tag,不同节点上的行为不一样 | **B** | 进每个节点看**镜像 ID**,不看 tag;顺便看 `imagePullPolicy` | 02 §4.2 |
| `ImagePullBackOff` / `ErrImagePull`,报错措辞含糊 | **C** | 读报错**停在哪一层**(DNS / TCP / 协议 / 认证 / 内容),只查那一层 | 01 §5.6 |
| CI 绿了,但集群里什么都没变 | **D** 或 **E** | 先确认 CI 是否**真的写进去了**(写回独立读回验证),再确认 ArgoCD 拉到的 **revision** 是哪个 | 02 §2.5 / §3.2 |
| ArgoCD UI 绿色,但你刚 push 的改动没生效 | **E** | 比对 `.status.sync.revision` 与 `git rev-parse HEAD`;不一致就 hard refresh | 02 §3.2 |
| `kubectl drain` 卡住 / 驱逐返回 429 | **F** | 看 PDB 的 `expectedPods` 与 `disruptionsAllowed` | 02 §4.5 |
| Pod 全 Running、组件全 Ready,但下游拿不到数据 | **G** | 去**链路终点**问一次(仓库的 tag 列表 / Loki 的 label / 收件箱) | P14 / D15 |
| 要在 Grafana 上"回滚一下看看",却不确定该退到哪个版本 | **H** | 看 tag 里有没有一个旧的不可变值可指回去 | 01 §3.2 |

> **用这张表的方式**:不要试图一次判断准确,把它当**排除法**用——一个现象通常只能落在两三道缝里,**排除掉的那几道缝,就是你不需要去查的地方**。

## 三、多集群在这里分叉

### 3.1 分叉点:⑤–⑦

前四段(①–④)**天生是单集群的**:源码、构建、镜像、仓库,这些都不关心"你要部署到几个集群"。真正开始关心的是:

| 段 | 单集群 | 多集群 |
|---|---|---|
| ① 代码 | 一个仓 | 一个仓(**通常还是一个仓**) |
| ② 构建 | 一次构建 | 一次构建(**一次构建,多处部署**) |
| ③ 制品 | 一个镜像 | 一个镜像(**同一个 digest 部署到 N 个集群**) |
| ④ 登记 | 一个仓库 | 一个仓库(或 N 个镜像仓库,取决于网络边界) |
| **⑤ 声明** | **一份清单** | **一份清单 → N 份期望状态**(哪些差异是"刻意的",哪些是"漂移") |
| **⑥ 收敛** | **一个 Application → 一个集群** | **N 个 Application(或 ApplicationSet)→ N 个集群** |
| **⑦ 运行** | **一个集群的 Pod** | **N 个集群的 Pod,各自可能不同步** |

**一句话概括分叉**:

> **单集群时,"声明 → 收敛"是一对一;多集群时,它变成一对 N。**

而"一对 N"带来的**全部麻烦**,都可以归结成同一个问题:

> **这 N 份期望状态里,哪些差异是有意的(环境分级),哪些差异是意外的(漂移)?**

单集群时这个问题不存在——**只有一个状态,没有"不一致"可言**。

### 3.2 为什么"多集群可用"不是复制粘贴

最容易想到的做法是:**把单集群那套 YAML 复制一份,改改 `namespace`,起第二个 ArgoCD**。它在实验室里能跑,但它会在下面五件事上崩掉——**每一件都恰好落在接缝上**:

| # | 复制不走的东西 | 落在哪道缝 | 为什么复制不了 |
|---|---|---|---|
| 1 | **凭据** | C / D | 每个集群有自己的仓库凭据、自己的 Git 写权限。复制 YAML 不会复制**信任关系**;而凭据的权限范围是架构决策,不是配置细节 |
| 2 | **收敛目标** | E | Application 的 `destination.server` 决定"这份声明施加到哪个集群"。单集群时它是 `https://kubernetes.default.svc`(集群内的自己),**多集群时它变成一个真实的、外部的地址和证书问题** |
| 3 | **声明的归属** | D / E | 同一个仓库被 N 个控制器读:谁在什么时候改了 tag?哪个集群先拿到?**"声明"和"集群"之间从一对一变成多对多** |
| 4 | **命名与隔离** | F | 单集群里 namespace 就是隔离边界;多集群里"哪个名字在哪个集群里有意义"变成新问题(ClusterRole / ClusterSecret / 集群注册名) |
| 5 | **配置分叉** | A / B | 环境之间的差异(副本数、资源、镜像 tag、域名、外部依赖)必须有**结构化的表达方式**,否则它就会退化成"手改第二个集群的线上配置"——那等于把 §一 的漂移重新引入 |

**第 5 条是最要命的**,因为它把"多集群"从"复制粘贴的问题"变成了"**配置怎么表达的问题**"。

### 3.3 五个必须认识的概念

下面五个概念是多集群的基本词汇。**注意:本项目没有实施多集群**,所以这一节讲的是**概念与判断标准**,不是实测记录。

#### 概念 1:namespace 隔离

| | 内容 |
|---|---|
| 是什么 | 在**单集群内**用 namespace 把工作负载分开(本项目就是:每个 Application 一个目标 namespace) |
| 解决什么 | 单集群内的资源归属与配额 |
| 不解决什么 | **它不解决"集群之间"的问题**——两个集群的 `default` 互相看不见,但也互相不知道对方存在 |
| 什么时候不够 | 需要物理隔离(GPU 池、网络域、爆炸半径)、需要独立升级节奏时 |

#### 概念 2:ApplicationSet

| | 内容 |
|---|---|
| 是什么 | ArgoCD 的一个控制器:由**一个模板 + 一组生成器**生成 N 个 Application,而不是手写 N 个 |
| 解决什么 | 把"一对 N"从"N 份手写 YAML"变成"一份模板 + 一个集群列表";新增集群 = 往列表里加一项,而不是复制一份 Application |
| 与 App-of-Apps 的区别 | **App-of-Apps 是"我手写 N 个 Application,由一个父 Application 管着"**(本项目用的就是这个);**ApplicationSet 是"我写一个模板,由控制器生成 N 个"** |
| 何时上 | N 开始增长、或者 N 个 Application 之间**只有参数不同**的时候 |

**本项目的现状**:6 个 Application 是**手写的**,由 `root-app`(App-of-Apps,`prune: true` + `selfHeal: true`)统一管理。**没有用 ApplicationSet**——因为在 N = 1 个集群、6 个应用规模下,手写更直观,也更好讲清每一份声明的意图。

> **一处「待核实」**:本项目没有部署过 ApplicationSet,所以"它在你这个 ArgoCD 版本上生成器的确切行为"我无法从仓库里确认。**待核实**。

#### 概念 3:环境分级

| | 内容 |
|---|---|
| 是什么 | 明确声明"哪些配置按环境不同、哪些必须完全相同" |
| 硬规则 | **镜像 digest 必须相同,配置允许不同**。否则"预发验证通过"这句话没有任何意义 |
| 表达方式 | Kustomize overlay / Helm values per env / 目录分级 |
| 与本项目的关系 | 本项目已经有一个**同构的雏形**:`selfHeal` / `prune` 按应用性质分级(基础设施全开、存量接管期全关)。那是"**按应用分级**",多集群里要做的是"**按环境分级**"——同一个思路的放大 |

#### 概念 4:集群注册

| | 内容 |
|---|---|
| 是什么 | 让一个控制面知道"有哪些集群、用什么身份连它们、它们叫什么名字" |
| 解决什么 | Application 的 `destination` 需要一个**稳定的标识**:是 `server` 地址,还是一个注册出来的集群名 |
| 为什么是接缝问题 | 它本质上是**凭据 + 命名**问题:注册一个集群 = 移交一份能操作它的凭据。**权限范围 = 你希望这个控制面能控制多少东西** |
| 反面教材 | 把每个集群的 kubeconfig 交给同一个 CI(推模式的经典形态)——那等于把 N 个集群的钥匙放在一个地方 |

#### 概念 5:配置分叉的结构化表达

| | 内容 |
|---|---|
| 是什么 | 把"环境差异"从"人记住的差异"变成"仓库里能 diff 的差异" |
| 做法 | Kustomize(overlay 叠 base)/ Helm(values per env)/ 目录分级(`base/` + `environments/<env>/`) |
| 判断标准 | **如果一个差异没有在仓库里被表达出来,它就会以"线上手改"的形式存在** |
| 留痕证据 | 本项目接手时就撞上了这个问题的变体:同一个文件存在**四份副本**(`manifests/`、`production/`、`k3s-ai-platform/environments/prod/`、`reference/baseline-manifests/`)——**"哪一份是真相来源"没有人知道**(D6)。多集群会把这个问题的规模乘以集群数 |

### 3.4 本项目在哪:诚实边界

**必须说清楚:本项目没有做多集群。**

`00_设计定稿.md` 的第九节「明确不做(YAGNI)」里,第二条就是:

> ❌ **多集群 / 跨云管理**

理由不是"做不到",是**在单集群 19 GiB 内存的本机上,多集群换不来新的判断力**——而 D4 决定了要保留这个真实存在的脏集群。

**但本项目有两样和多集群直接相关的东西,这才是可讲的**:

**第一,我们确实在多集群环境里工作过,而且踩到了最经典的那个坑。**

本机同时存在三个 k3d 集群:`k3d-ai-cluster`(改造对象)、`k3d-ew-cluster`(已停,省内存)、`k3d-topo-demo`(另一个项目的资产)。而 `kubectl` 和 `helm` **隐式使用 kubeconfig 的当前 context**——于是:

| 你敲的命令 | 你看到的 | 实际发生的 |
|---|---|---|
| `helm list -A` | 只有表头,一个 release 都没有 | 它查的是 `k3d-topo-demo`——**另一个集群** |
| `kubectl config current-context` | `k3d-topo-demo` | 破案:当前 context 根本不在改造对象上 |

**命令静默地作用在了错误的集群上。** 这次是 `list`(无害),如果它是 `delete`,删的就是另一个集群的东西。**这条已经写进本项目 runbook 纪律:所有 `kubectl` / `helm` 命令显式带 `--context`。**

> **这就是"多集群"在运维侧的第一课,而且它落在接缝上**:接缝的两侧(kubectl 与集群)对"我现在操作的是哪个集群"没有共同的语言,所以**它不报错,只是安静地作用在错误的对象上**。

**第二,本项目里已经有一个"多集群接口"了。**

每个 Application 的 `destination.server` 字段,在当前配置下写的是:

```yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: monitoring
```

`https://kubernetes.default.svc` 是"**集群里的自己**"——这正是单集群的表达方式。**多集群要做的第一件事,就是把这个字段从一个自指的默认值,变成一个需要被管理的、外部的标识。**

**换句话说:多集群不是"另一种架构",是把一个现在写死的字段,变成一份需要治理的声明。** 这句话可以直接拿去面试。

### 3.5 什么时候该上多集群

判断标准不是"集群多显得厉害",是下面三条**至少满足一条**:

| 触发条件 | 说明 | 反例 |
|---|---|---|
| **爆炸半径** | 一个集群的故障不该带走全部业务 | 本机实验环境:炸了重启就是,不需要 |
| **物理边界** | GPU 池 / 网络域 / 合规要求(代码和数据不出某个边界) | 个人项目:没有合规约束 |
| **独立升级节奏** | 不是"环境不同",而是"不同团队/不同租户要各自决定什么时候升" | 一个人维护六个应用:不需要 |

三条都不满足时,多集群的代价是**纯负债**:N 份配置分叉、N 份凭据、N 份被同步的 `Synced` 信号要盯着。

> **一句话**:多集群买到的是**隔离**,付出去的是**一致性**。买之前先确认你要的隔离,是不是 namespace 加配额就能给。

### 3.6 如果真要做:本项目的最小改造清单(未实施)

下面这份清单是**推演**,不是执行记录(§4.3 已标注本项目未做多集群)。它的价值在于说明"多集群的改动量落在哪几处"——**你会发现改动几乎全部落在接缝上,而不是在段落内部**。形态参照 02 分册 §3.3 阶段六那份 Gitea 迁移清单。

| # | 要改什么 | 落在哪 | 为什么不能靠复制解决 |
|---|---|---|---|
| 1 | 每个集群**各自的 `destination.server`**(从 `https://kubernetes.default.svc` 改成真实集群标识) | 接缝 E | 单集群时它是自指的默认值,多集群时它变成一个需要被管理的标识 |
| 2 | **集群注册**:让 ArgoCD 知道有第二个集群、用什么身份连它 | 接缝 E | 注册一个集群 = 移交一份凭据,权限范围就是"这个控制面能控制多少东西" |
| 3 | **Application 从手写改成 ApplicationSet**(或按集群拆目录) | 段⑤ | N 份手写 YAML 会立刻退化成"手改第二个集群的线上配置" |
| 4 | **配置分叉结构化**:把环境差异写进 overlay / values,而不是写进人的记忆 | 接缝 A / B | 没被表达出来的差异,最终都会以"线上手改"的形式存在 |
| 5 | **镜像 digest 必须跨集群一致**;只有配置允许不同 | 接缝 B | 否则"预发验证通过"这句话没有意义 |
| 6 | **每个集群自己的仓库凭据与拉取配置**(`certs.d` 是节点级的) | 接缝 C | 复制 YAML 不会复制**信任关系**;传输配置永远在节点上 |
| 7 | **CI 的写回目标**:一个仓要服务 N 个集群,写回仍只有一个入口 | 接缝 D | 声明是一份,部署是 N 份——**"一次构建、多处部署"的不变量**必须在写回这层守住 |
| 8 | **Git/Gitea 自身的持久化与备份**(它现在是单点) | 段①(基础设施) | 自建把依赖变成可控,**但没有消灭依赖**,只是换成了"我来负责它" |

**关于第 8 条的一处「待核实」**:本项目当前的 Gitea 是一个独立 docker 容器(`gitea/gitea:1.22`,主机 `localhost:3001`),它在 K8s 之外。它的**数据持久化方式与备份策略**(是绑定挂载、命名卷,还是别的)我在仓库与集群里都无法确认——「**待核实**」。这一条与 D17 的"边界 1"(deploy key 未封存)是**同一类问题**:**"配置能工作"和"配置能重建"是两个独立判断。**

**两处仍然说不清的观察**,一并记在这里,当作"诚实边界"而不是"结论":

- **`probe` 这个仓库是什么?** 镜像仓库的 `_catalog` 里除了 `sre-lab/ollama-exporter` 还有一个叫 `probe` 的仓库。它不在本项目的任何文档里,我在仓库里也没找到创建它的记录——「**待核实**」。它的存在本身说明一件事:**一个没有访问控制的仓库,内容是会自己长出来的**。
- **ArgoCD 默认对账间隔的精确值**:本文与 02 分册都沿用 runbook 的"约 3 分钟"口径。这个值的**确切默认值**我没有从 ArgoCD 的配置里核实——「**待核实**」。它不影响任何结论(所有涉及它的论证都只用到"它会周期性重试"这个性质)。

> **这两条留在总纲里是有意的。** 一份教材里最危险的不是"不知道",是"不知道自己不知道"——所以凡是**当时没查清、也不影响主线**的,我宁可标出来,也不填一个看起来合理的答案。这和接缝 A 的"漂移"、接缝 E 的"静默半死"是同一个病:**一段自洽但没被验证的叙述,比一段空着更难被发现。**

## 五、面试可以怎么讲

下面 8 条是**可以直接背、也可以改写成自己的话**的口径。每条都围绕"我遇到过什么接缝问题、怎么定位、怎么设防"。**建议先理解再背**,并且**一定把"诚实边界"一起讲**——只讲成功会让整段话失去可信度。

> **1. 总纲:痛在接缝上**
>
> "我把从代码到线上 Pod 的这条链子拆成九段,但我发现**痛几乎从来不发生在段落内部,而是发生在接缝上**——因为每一段本体都是单机可测的,而接缝两侧是两个不同的信任域,信息在接缝处丢失,而且**丢失通常是静默的**。所以我的排查习惯是:先问这道缝的两边各自以为发生了什么。"

> **2. 接缝 E:`Synced` 骗了我两次**
>
> "ArgoCD 的 `Synced` 我踩过两次。它的准确含义是'集群和 **ArgoCD 上一次成功拉到的那个 revision** 一致',**和远端最新 commit 没有任何关系**。第一次是我 push 了一个删除操作,UI 绿的,但对象还在集群里;第二次是网络故障期间整个链路静默半死,所有信号都是绿的。这让我总结出一条:**凡是以'当前状态等于期望状态'表述的健康信号,都要先问期望状态是谁的期望、哪个时刻的期望。** 验证方法是去核对 revision,不一致就 hard refresh。"

> **3. 接缝 A:能跑不等于能重建**
>
> "我接手一个跑了 30 天的网关镜像,想纳入 CI,结果发现**它没法从版本控制重建**。三条漂移线:镜像里的主程序导入了三个仓库里从来没有过的文件;仓库里的同名文件其实是另一条演化线;配置文件也是两份,仓库版少三个配置段,而镜像代码每处理一个请求都会读其中一段——**用仓库版重建,容器能正常启动,第一个请求才 `KeyError`**。第三条最危险,因为它静态检查全过、镜像能构建、容器能起,任何'它还活着吗'的检查都发现不了。最后我从镜像层把文件捞出来,补一份从 `docker history` 逐行反推的 Dockerfile,再做 md5 逐字节比对。**捞出来不算完,必须证明捞出来的是原件。**"

> **4. 接缝 C:读报错要读它停在哪一层**
>
> "Pod 拉镜像报 `server gave HTTP response to HTTPS client`。这行报错信息量很大:客户端发起的是 HTTPS、DNS 解析是通的(否则报 `no such host`)、请求**真的到达了 registry**(否则不会收到 HTTP 响应)。所以它一次排除了 DNS、网络可达性和路由,只剩一个结论——协议不对。我后来固定了一个五层排查顺序:**DNS → TCP 可达 → 协议 → 认证 → 内容**,每层的报错特征几乎不会混淆,**报错停在哪一层,就说明它前面所有层都是好的**。"

> **5. 接缝 D:写回失败是静默的**
>
> "CI 写回 GitOps 仓库这件事里,最危险的一点是**写回失败是静默的**。因为流水线的成功标准和集群的成功标准是两个系统——CI 全绿只说明它的 stage 过了,不说明集群变了。所以我在写回脚本里加了 `set -e` 让它硬失败,提交前先 `git diff --quiet` 判空避免一堆空提交,并发用 `disableConcurrentBuilds` 串行化。更好的做法是 push 之后用 `git ls-remote` 做一次**独立的读回验证**——**写入命令自己的返回值不能证明远端收到了。**"

> **6. 接缝 F:PDB 把集群锁死**
>
> "我们有个单副本的工作负载配了 `minAvailable: 1`,算出来 `disruptionsAllowed` 是 0,后果非常具体:**节点驱逐永远返回 429,`kubectl drain` 会永久挂起**。这坑隐蔽在它不报错——apply 成功、`describe` 里 `MIN AVAILABLE: 1` 看起来完全合理,**只有真去 drain 的时候才发现卡住,而那时你已经在做一次生产变更了**。更细的一点:同样的 `disruptionsAllowed: 0` 有两种根因——副本数不够,或者 selector 写错导致 `expectedPods` 是 0 ——所以排查要**先看 `expectedPods` 再看 `currentHealthy`**。"

> **7. 接缝 G:全绿但一条数据都没进来**
>
> "我接日志链路时,DaemonSet 是 3/3 Ready、日志里在正常打印 `Adding target`、零报错。但我多做了一件事:**去问终点(Loki)有没有数据**——结果是空的。根因是生成采集路径时少了一个分隔符斜杠,通配符匹配不到任何文件,而**它对'匹配不到文件'这件事不打日志**。同一类事在告警上也发生过:规则在求值、Prometheus 在推送、Alertmanager 在分组,唯一断的是最后一跳,而它不报错。**所以我现在的原则是:对象存在不等于它被消费了,过程指标全绿不等于结果达成,校验必须去链路终点做——而且最后一跳如果是人,就只能由人来验证。**"

> **8. 多集群:它不是另一种架构,是把一个字段变成一份声明**
>
> "我理解的多集群分叉点在第五到第七段——声明、收敛、运行。单集群时'声明到收敛'是一对一,多集群时变成一对 N,所有麻烦归结成一个问题:**这 N 份期望状态里,哪些差异是有意的,哪些是漂移?** 单集群时这个问题不存在。我也有一手教训:本机有三个 k3d 集群,`helm list` 返回空,因为 `kubectl` 和 `helm` 隐式用 kubeconfig 的当前 context,命令**静默地作用在了错误的集群上**——这次是 `list`,如果是 `delete` 就删错集群了。所以'多集群可用'不是复制粘贴:凭据、收敛目标、声明归属、命名隔离、配置分叉这五样都复制不走。落到最实处:**多集群的第一件事,是把 Application 里那个写死的 `destination.server: https://kubernetes.default.svc`,从一个自指的默认值变成一份需要治理的声明。**"

## 六、名词速查

按"一段话讲清是什么、以及它在本文里为什么重要"来写。**想深挖某个词,去「在哪」列指的位置。**

### 制品与镜像

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **Tag** | 人给镜像起的名字(如 `:v1.4.2`),**可变**——同一个 tag 可以被指到另一份内容上 | 01 §3.1 |
| **Digest** | 内容的哈希(如 `sha256:da0c3e7c...`),**内容寻址、物理不可变**。一句话记:**tag 给人看,digest 给机器用** | 01 §3.4 |
| **Registry** | 存镜像的仓库。本项目是本地 k3d registry 容器,集群内 `k3d-sre-registry:5000` | 01 §四 |
| **`latest` 反模式** | `latest` 把**可变指针**当成**不可变标识**。在 K8s 里更毒:非 `latest` tag 默认 `IfNotPresent`,于是**同一个 tag 在不同节点上可能是不同内容**,而 `kubectl get pods` 全绿 | 02 §4.2 |
| **`imagePullPolicy`** | `Always` / `IfNotPresent` / `Never`。**它的正确性依赖 tag 是否不可变** | 02 §4.2 |
| **镜像分层** | 镜像 = 一组只读层。层可共享、可缓存,而且**顺序决定缓存命中:上面一层变了,下面所有层全部失效** | 01 §6.1 |
| **BuildContext** | `docker build` / `buildah bud` 时发给构建器的那个目录。**镜像里的路径能反推出当年是在哪个目录构建的** | 01 §2.4 |
| **多阶段构建** | 一个 Dockerfile 里两个 `FROM`,前者产出产物、后者只拿产物。**判断标准是"构建期有没有需要丢弃的东西"**,没有就是白加一层 | 01 §6.3 |

### 构建与 CI

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **动态 agent** | Jenkins on K8s 的核心:每次构建起一个 Pod,用完销毁。构建环境天然隔离 | 01 §1.1 |
| **buildah** | daemonless 的镜像构建器。**不挂 `docker.sock`**(那等于把宿主机 root 交给构建容器),是 Kaniko 归档后的推荐替代 | 01 §1.2 |
| **`docker.sock` 挂载** | 把宿主机的容器运行时交给构建容器。**生产大忌**,本项目当反面教材 | D3 |
| **Kaniko** | 曾经的 daemonless 构建器,**2025-06 已被 Google 归档**,新项目不应选 | 01 §1.2 |
| **rootless vs chroot** | 严格 rootless 用用户命名空间;本项目落地形态是"容器内 root + 无特权 + 无 userns"。**这两者不是一回事**,要诚实区分 | 01 §1.2 |

### CD 与 GitOps

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **GitOps** | 把**期望状态**变成存在版本控制里的文本;**集群是结果,Git 是原因**。所以"集群出问题"的第一反应是看 Git,不是进集群修 | 02 §1.1 |
| **推模式 / 拉模式** | 推:CI 拿 kubeconfig 去 apply。拉:集群内的控制器去 Git 拉。**拉模式的本质优势是集群不用把 kubeconfig 交给外部** | 02 §1.2 |
| **声明式 vs 命令式** | `apply -f`(幂等、可 diff)vs `set image`(一次性动作、改完 Git 不知道)。**在 GitOps 管辖范围内,命令式操作是反模式** | 02 §1.3 |
| **Drift(漂移)** | 集群实际状态偏离了声明的期望状态。**漂移有两种:`selfHeal` 会自动纠回去,或者永远 `OutOfSync` 且没人知道为什么** | 02 §1.5 / §2.3 |
| **`selfHeal`** | 管**漂移纠正**:集群里被手工改动的资源自动改回 Git 版本。关掉 → 手工改动留下来并显示 `OutOfSync` | 02 §1.5 |
| **`prune`** | 管**资源回收**:Git 里被删除的资源集群里也删除。注意它做的是**集合差**,而且**必须先拉到包含删除的那个 revision** 才会删 | 02 §1.6 |
| **`Synced` / `OutOfSync`** | `Synced` 的准确含义是"集群 == **ArgoCD 上一次成功拉到的那个 revision**",**不保证那个 revision 是最新的**。这是本册最该背的一条 | 02 §3.2 |
| **Application** | ArgoCD 的对象:描述"哪份 Git 清单、施加到哪个集群的哪个命名空间"。本项目**一个 Application 管一个目录** | 02 §1.5 |
| **App-of-Apps** | 用一个父 Application 管一组子 Application。本项目是 `root-app` 管 6 个子 App | 02 §1.5 |
| **ApplicationSet** | 用**模板 + 生成器**批量生成 Application,而不是手写 N 个。**本项目未使用**(N=1 集群时手写更直观) | 本文 §3.3 |
| **Sync Wave / Sync Options** | 控制同步顺序与行为。本项目用到的 `CreateNamespace=true` 属于 syncOptions——**让 ArgoCD 按需建 namespace,但不把 namespace 纳入生命周期管理** | 02 §1.6 / D10 |
| **Helm vs GitOps 的所有权冲突** | 同一个对象被 Helm 和 ArgoCD 同时管,两边都会认为对方漂移了。本项目用**混合模式**避免:监控栈主体归 Helm,补充对象归 GitOps | 02 §一 / D14 |

### 凭据

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **Deploy Key** | 绑定在**单个仓库**上的 SSH 公钥,可设只读或可写。**权限边界和需求正好对齐**(对比 PAT 是整个账号) | 02 §2.2 |
| **PAT** | 个人访问令牌,权限范围通常是**整个账号**。对"改一个 tag"这个需求来说权限过宽 | 02 §2.2 / D17 |
| **SealedSecret / `kubeseal`** | 把 Secret 加密成可以**安全提交进 Git** 的形态。**本项目集群里没装 `kubeseal` 二进制**,所以有一份 Secret 没被封存(重建集群会丢) | 02 §2.4 / D17 |
| **OAuth scope vs registry scope** | 两套不同的权限模型。`write:packages` 不代表能 `read:packages`,而**登录是建立两个方向的能力**——所以会 `DENIED` | 01 §4.2 |

### 运行时

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **`imagePullSecrets`** | **Pod 级**凭据,回答"**我是谁**"。**它解决不了协议问题**(HTTP/HTTPS),因为**拉镜像的是节点上的 containerd,不是 Pod** | 02 §4.1 |
| **`certs.d` / `registries.yaml`** | containerd 的仓库传输配置(节点级)。**改 `registries.yaml` 要重启 k3s,改 `certs.d/hosts.toml` 不用**——因为前者是"启动时读一次再渲染",后者是"每次拉取动态读" | 01 §五 / P16 |
| **liveness / readiness / startup** | 三个探针回答三个问题,失败动作完全不同:**readiness 失败摘流量(不重启),liveness 失败重启(不摘流量)** | 02 §4.4 |
| **滚动更新(`maxSurge` / `maxUnavailable`)** | `maxUnavailable` **向下取整**、`maxSurge` **向上取整**。3 副本 + 默认 25% → `maxUnavailable` 实际是 **0** | 02 §4.3 |
| **PDB** | 只限制**自愿中断**(drain / 驱逐)。`minAvailable` 等于副本数 → `disruptionsAllowed: 0` → **drain 永久挂起** | 02 §4.5 |
| **`nodeSelector` / affinity / taint** | `nodeSelector`、affinity 是 **Pod 说"我想去哪"**;taints/tolerations 是**节点说"谁允许来"**。**两者必须同时满足** | 02 §4.6 |
| **`rollout undo`** | Deployment 的回滚动作。**但它能回滚的前提是 tag 粒度够细**——只有一个 `latest` 就没有"旧版本"可指回去 | 01 §3.2 |

### 观测与可靠性

| 名词 | 一句话 | 在哪 |
|---|---|---|
| **`ruleSelector` / `serviceMonitorSelector`** | Prometheus Operator 的**白名单**:标签不匹配的对象会静静躺在 etcd 里,**零报错、零告警**。验证方法只有一个:去问消费者 | 02 §三 / P6 / P12 |
| **SLI / SLO** | SLI 是"你实际测到的那个数";SLO 是"你承诺的那个目标"。本项目有 `ollama-slo-rules` 一类的规则集 | P12 / 03(待写) |
| **Error Budget** | 允许"不达标"的额度 = `1 - SLO`。它把"能不能发版"变成一个**可以算的**问题 | 03(待写) |
| **Alert Fatigue(告警疲劳)** | 假警报太多 → 人**学会忽略告警** → 真警报混在里面被一起忽略。**所以正确顺序是先降噪、再接通道** | P5 / D13 |
| **过程指标 vs 结果指标** | "命令成功 / Pod Running / `Adding target`"是过程;"仓库里真有这个 tag / Loki 里真有数据 / 人真的收到了"是结果。**两者之间隔着一段,任何一段都可能静默失败** | P14 / D15 |
| **Runbook** | 出事了照着做的操作手册。本项目的 `03_runbook/` 有 SealedSecrets / ArgoCD / Jenkins 三份 | `03_runbook/` |
| **ADR** | Architecture Decision Record。**记的是"当时有哪些选项、为什么选这个"**,三个月后就是你的面试答案库 | `99_决策日志.md` |
