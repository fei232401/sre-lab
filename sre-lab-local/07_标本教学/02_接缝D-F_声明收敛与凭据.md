## 零、先建立心智模型:九段传送带与三处接缝

从一行代码到线上一个正在服务的 Pod,中间是一条**九段传送带**:

```
① 编码 → ② 提交 → ③ 构建 → ④ 登记(镜像入仓)
                                    ↓
                              【接缝 D】
                                    ↓
                              ⑤ 声明(Git 成为期望状态)
                                    ↓
                              【接缝 E】
                                    ↓
                              ⑥ 收敛(集群被拉向期望状态)
                                    ↓
                              【接缝 F】
                                    ↓
                              ⑦ 运行(Pod 真的起来、真的能服务)
```

**为什么盯"接缝"**:传送带上的每一段(构建、登记、运行)都是**单机可测**的——你把输入喂给它,它给你输出。而接缝是**两个系统的交界面**:两个不同的信任域、两套不同的凭据、两种不同的失败语义。运维事故绝大多数不在"段"里,在"缝"上,原因是:

> **每一段都只看得到自己的输出。接缝上的失败,两侧都看不见。**

今晚最典型的一次:CI 流水线**显示成功**,ArgoCD UI **显示绿色 `Synced`**,但集群里的东西**根本没变**。两边都是绿的,因为两边都在看自己那一侧的输出——中间那条缝断了,缝不发光。

**本册覆盖范围**:接缝 D(制品 → 声明)、接缝 E(声明 → 收敛)、接缝 F(收敛 → 运行),以及它们所连接的第 ⑤⑥⑦ 段。

**怎么用这份材料**:

1. 每个知识点按 **"要解决什么问题 → 有哪些可选方案 → 为什么选这个 → 今晚的实测证据"** 四步展开。
2. **代码块里没有注释**——所有"为什么"都写在代码块外面的正文里,这是本项目的硬纪律。
3. 每节结尾有 **「面试可以怎么讲」**,给的是可以直接背的凝练版本。**先理解,再背**;背的时候要能把"方案对比"和"诚实边界"两条也带出来,那才是分水岭。

## 一、段⑤ 声明:GitOps 的枢纽

### 1.1 核心思想:改的不是集群,是期望状态的文本

**要解决什么问题**

在 GitOps 之前,改集群的方式是"打开终端敲命令"。这带来四个问题:

- **不可追溯**:三个月后没人知道"当时谁把副本数从 3 改成了 1"
- **不可复现**:同一个集群,换个人来敲,敲出来的状态不一样
- **不可回滚**:"回滚"意味着你要记得上一条命令是什么,然后敲一条反向命令
- **不可审计**:变更没有 review,没有记录,没有责任边界

**核心思想**

> **把"期望状态"从"一系列命令"变成"一份存放在版本控制里的文本"。集群是结果,Git 是原因。**

这句话的推论比它本身重要:**如果集群是结果,那么"集群出问题了"的第一反应,不应该是"去集群里修",而是"去看是什么让 Git 指向了一个坏的期望状态"。** 这就是为什么 GitOps 系统里,手工 `kubectl edit` 是一种"治标"行为——它会立刻被下一次对账纠正回来(`selfHeal: true` 时)。

**今晚的实证**

仓库里 `sre-lab-gitops/production/` 下每一个目录,都是一份"期望状态的文本":

```
sre-lab-gitops/production/
├── bootstrap/         ← 6 个 Application 的定义(声明"哪些目录该被谁管")
├── apps/              ← 6 个被管的目录
│   ├── ai-platform/    ollama-stack.yaml, pdb.yaml
│   ├── loki/           deployment.yaml
│   ├── nginx-demo/     deployment.yaml, service.yaml, ingress.yaml, middleware.yaml
│   ├── promtail/       deployment.yaml
│   └── sealed-secrets/ controller.yaml
├── monitoring/        ← 补充对象(主体由 Helm 管,见 D14)
├── helm-values/       ← ⚠️ 刻意放在监视目录之外(见 1.5 的"目录边界")
└── ci/                ← Buildah 的 registries 配置
```

**「面试可以怎么讲」**

> "GitOps 的核心不是'用工具部署',是**把期望状态变成一份可 diff、可 review、可回滚的文本**。集群是结果,Git 是原因。所以在这个体系里,'集群出问题'的正确排查路径不是进集群改,而是去看 Git 为什么指向了一个坏的期望状态——因为集群里的手工改动,下一次对账就会被纠正回去。"

### 1.2 推模式 vs 拉模式

**要解决什么问题**

"让集群变成期望状态"这个动作,**由谁发起**?

**两种模式**

| | 推模式(Push) | 拉模式(Pull) |
|---|---|---|
| 谁发起 | CI 跑 `kubectl apply` | 集群内的控制器定时从 Git 拉 |
| 集群凭据在哪 | **CI 系统里**(必须持有 kubeconfig) | **集群里**(只需读 Git 的凭据) |
| 网络方向 | CI → 集群(需要入向可达) | 集群 → Git(只需出向可达) |
| 审计来源 | CI 的构建日志 | Git 的提交历史 |
| 多集群 | 每个集群一套 kubeconfig 交给同一个 CI | 每个集群自己拉,凭据各在本地 |
| 漂移检测 | **无**(没人持续比对) | **有**(控制器就是对账循环) |
| 失败语义 | 命令失败 = 这次没部署 | 拉取失败 = 状态陈旧(却是绿色的,见接缝 E) |

**为什么拉模式在安全边界上更优 —— 关键的一行**

> **拉模式下,集群不需要把 kubeconfig 交给外部。**

这一句要展开讲,因为它是整个 GitOps 安全模型的支点。

推模式要求 CI 系统持有一个能操作目标集群的凭据。而这个凭据的权限通常是**集群管理员级**——因为你要 apply 任意资源,你就得能创建任意资源。于是:

- CI 系统(或其 runner)被攻破 = **目标集群被攻破**
- 这个凭据一般长期有效,且往往被复制到多个地方(runner 环境变量、凭据库、部署脚本)
- 你无法回答"这个凭据到底被哪些人、哪些系统看到过"

拉模式把这个信任方向**反转**了:

```
推模式:  集群 ──信任──> CI(CI 持有集群的钥匙)
拉模式:  集群 ──信任──> Git(集群只持有一把"读 Git"的钥匙)
         Git  ──不需要信任──> 集群(Git 里躺着的只是文本,不是权限)
```

在拉模式里,**Git 仓库里没有任何能操作集群的东西**——它只有 YAML 文本。偷到 Git 的读权限,你得到的是"知道他们要部署什么";偷到推模式 CI 的 kubeconfig,你得到的是"他们的集群"。

审计与多集群一致性是同一个道理的两个侧面:

- **审计**:拉模式下,"谁在什么时候决定了集群该长什么样"的答案 = `git log`。推模式下,答案分散在 N 个 CI 系统的构建日志里,而且**一次 `kubectl apply` 之后,集群和 Git 之间没有任何机制保证它们还一致**。
- **多集群一致性**:拉模式下,同一个 Git revision 可以被 N 个集群各自拉取,每个集群用自己的证书连自己的 Git 端点。推模式下,你要给 CI 配 N 套 kubeconfig,每套都是一份高权限凭据。

**为什么本项目用拉模式**

ArgoCD 就是拉模式的实现:它跑在集群里,从 `https://github.com/fei232401/sre-lab.git` 拉清单,渲染后与集群实际状态比对,不一致就施加。**集群里没有任何一个组件持有 GitHub 的写权限**——ArgoCD 只需要读。

这和 Jenkins 的分工正好互补:Jenkins 需要**写** Git(见接缝 D),ArgoCD 只需要**读** Git。两者的权限范围不同,凭证也必须不同。

**「面试可以怎么讲」**

> "我们用的是拉模式,ArgoCD 跑在集群里主动去拉 Git。拉模式最本质的优势是**集群不用把 kubeconfig 交给外部**——推模式里,CI 必须持有一个等效于集群管理员的凭据,那个凭据一旦泄露就是整个集群。拉模式把信任方向反转了:集群只信任 Git,而 Git 里躺着的只是文本,不是权限。附带的好处是审计天然落在 `git log` 上,多集群一致性也变成'每个集群自己拉同一个 revision'。"

### 1.3 声明式 vs 命令式

**要解决什么问题**

同样是"把镜像从 A 换成 B",有两种表达方式。选错了会怎样?

**对比**

```bash
kubectl apply -f sre-lab-gitops/production/monitoring/ollama-exporter.yaml
```

```bash
kubectl set image deployment/ollama-exporter exporter=k3d-sre-registry:5000/sre-lab/ollama-exporter:abc1234
```

| | 声明式(`apply -f`) | 命令式(`set image`) |
|---|---|---|
| 提交的内容 | "我要这个文件描述的状态" | "请执行这个动作" |
| 幂等 | 是(重复跑结果相同) | 否(每次都是新动作) |
| 期望状态在哪 | **文件里**(可 diff、可 review) | **没有地方**(只存在于这条命令里) |
| 与 Git 的关系 | 文件本身就在 Git 里 | **集群变了,Git 没变** |
| 下一次对账 | 一致,什么都不做 | **检测为漂移** |

**为什么 `kubectl set image` 是反模式**

它有两个独立的致命问题:

1. **状态漂移**。命令执行后,集群里 Deployment 的镜像是 `abc1234`,而 Git 里那份 YAML 还是旧的。这时:
   - 如果 Application 是 `selfHeal: true` → 下一次对账把你的改动**改回去**,你会看到"镜像莫名其妙回滚了"
   - 如果 Application 是 `selfHeal: false` → 它会永远显示 `OutOfSync`,而且**没有人知道为什么**,因为 Git 里没有任何东西能解释这个差异
2. **无记录**。"为什么镜像是 abc1234"这个问题,答案只存在于**敲命令那个人的 shell 历史里**。三个月后那人离职了,这个状态就成了一个无法解释的既成事实。

**这不是"命令式工具不能用",是"命令式操作不能进 GitOps 管辖的范围"。** 在 GitOps 管的目录里,唯一合法的写入方式是改文件再 `git commit`。

**今晚的实证**

CI 流水线里"写回 GitOps"这一步,做的就是**改文件**而不是改集群:

```bash
sed -i "s|image: ${REGISTRY}/${IMAGE_NAME}:.*|image: ${IMAGE_REF}|" ${GITOPS_FILE}
git add ${GITOPS_FILE}
git commit -m "ci: bump ollama-exporter to ${SHORT_SHA}"
```

它**从不碰集群**——集群那边由 ArgoCD 自己去发现"文件变了"。这是推/拉分工在流水线里的具体体现:**CI 只负责生产新的期望状态文本,不负责施加。**

**「面试可以怎么讲」**

> "在 GitOps 管辖的范围内,`kubectl set image` 这类命令式操作是反模式——它改了集群但没改 Git,结果要么被 selfHeal 自动改回去,要么永久 `OutOfSync` 且没有任何东西能解释这个差异。我们的 CI 从头到尾不碰集群,它只做一件事:把新的镜像 tag 写进那份 YAML,然后 commit。**改的是原因,不是结果。**"

### 1.4 仓库组织:单仓 vs 双仓

**要解决什么问题**

应用代码和 GitOps 清单,放一个仓库还是两个?

**两种组织方式**

| | 单仓(Monorepo) | 双仓(App + GitOps) |
|---|---|---|
| 布局 | `<repo>/app/` + `<repo>/gitops/` | `<repo>-app` + `<repo>-gitops` |
| CI 写回时 | push 回**自己所在的仓库** | push 到**另一个仓库** |
| 凭据范围 | 整个仓库(含应用代码) | 只有清单仓 |
| 应用开发者权限 | 能改清单(可能不该改) | 天然隔离 |
| 部署历史 | 与应用提交搅在一起 | 清单仓的历史 = **纯部署历史** |
| 跨仓凭据 | 不需要 | 需要(本仓 + 目标仓) |
| 首次搭建成本 | 低 | 中(多一个仓、多一套权限) |

**单仓的取舍(今晚的选择)**

今晚是单仓 —— 应用代码、GitOps 清单、排障记录都在 `github.com:fei232401/sre-lab` 一个仓库里。取舍:

**收益**

- **一个 clone 拿到全部**。对单人项目,省掉"改一行清单要去另一个仓"的摩擦。
- **CI 不需要跨仓凭据**。写回的目标就是它 checkout 出来的那个仓,deploy key 一把就够。
- **改代码和改清单可以在一个 commit 里完成**。这对"改代码顺带改配置"的改动很自然。

**代价(要诚实说)**

- **权限边界 = 整个仓库**。CI 那把 deploy key 是 `read_only=false`,它**能改这个仓库里的任何东西**——包括应用代码本身、包括这份教学材料。虽然 deploy key 被锁在"这一个仓库",但这一个仓库里装的东西太多了。
- **CI 会 push 回自己**。构建是从这个仓 checkout 的,写回也是往这个仓 push。这意味着**构建过程中仓库在变**,两次构建之间可能读到不同的 HEAD。今晚靠 `disableConcurrentBuilds()` 规避了并发(见接缝 D 的 2.5),但这只是把问题变慢,没有消失。
- **部署历史不干净**。`git log` 里混着应用提交和 CI 的 "bump image" 提交,想单独看"这个服务什么时候上线过什么版本"要靠 grep。

**什么时候该转双仓**

判断标准不是"仓库大小",是**权限边界**:

> 当"能改应用代码的人"和"能改部署清单的人"不应该是同一批人时,单仓就撑不住了。

这是企业里的常态(开发提 PR,运维/SRE 管清单),所以生产环境**普遍是双仓**。现在单仓没问题,但要知道这是一条有明确终点线的路——**将来收紧权限时,双仓是自然演进**。

**「面试可以怎么讲」**

> "我们目前是单仓,GitOps 清单和应用代码在同一个仓库。它的好处是简单、不需要跨仓凭据;代价是 **CI 那把 deploy key 的权限边界等于整个仓库**,而且 CI 会 push 回自己 checkout 的那个仓,构建期间仓库在变。生产环境普遍用双仓,因为'能改代码的人'和'能改清单的人'通常不是同一批人——**什么时候转,取决于权限边界什么时候需要收紧,不是取决于仓库大小。**"

### 1.5 Application 的粒度,与 `selfHeal` / `prune` 的语义

**要解决什么问题**

ArgoCD 用 `Application` 这个对象来描述"哪份 Git 清单、该被施加到哪个集群的哪个命名空间"。粒度怎么定?`selfHeal` 和 `prune` 两个开关各是什么语义?

**粒度原则:一个 Application 管一个目录**

本项目 6 个 Application,每个 `spec.source.path` 指向一个目录:

| Application | `source.path` | 目标命名空间 |
|---|---|---|
| `ai-platform-app` | `sre-lab-gitops/production/apps/ai-platform` | `ai-platform` |
| `loki` | `sre-lab-gitops/production/apps/loki` | `logging` |
| `monitoring-app` | `sre-lab-gitops/production/monitoring` | `monitoring` |
| `nginx-demo-app` | `sre-lab-gitops/production/apps/nginx-demo` | `nginx-demo` |
| `promtail` | `sre-lab-gitops/production/apps/promtail` | `logging` |
| `sealed-secrets` | `sre-lab-gitops/production/apps/sealed-secrets` | `kube-system` |

**一条硬规则,今晚踩过**:

> **GitOps 监视目录的边界就是语义边界。目录里放什么,决定了 ArgoCD 会对什么动手。**

ArgoCD 会把 `source.path` 下的**所有 YAML**当作 k8s 清单去 apply。所以 Helm values 文件**必须放在监视目录之外**——本项目放在 `sre-lab-gitops/production/helm-values/`,该路径不在任何 Application 的 `source.path` 内。把一个 values 文件放进监视目录,后果是"ArgoCD 尝试创建一个不存在的 kind"。(详见 D13。)

**`selfHeal` 与 `prune` 的语义**

| 开关 | 管什么 | 关掉会怎样 |
|---|---|---|
| `selfHeal` | **漂移纠正**:集群里被手工改动的资源,自动改回 Git 版本 | 手工改动会**留下来**,并显示为 `OutOfSync`,需要人工点同步 |
| `prune` | **回收**:Git 里被删除的资源,集群里也被删除 | Git 里删了 YAML,集群里那个对象**继续存在**(成为孤儿) |

四个组合:

| `selfHeal` | `prune` | 行为 | 适合什么 |
|---|---|---|---|
| `false` | `false` | **只报告,不动手**。差异一直显示,人工决定何时同步 | 开发中的应用、存量接管期、高风险资源 |
| `true` | `false` | 纠漂移,但从不删东西 | 想防手工改动、但不希望 ArgoCD 删资源的场景 |
| `true` | `true` | **全自动收敛**。集群持续被拉向 Git | 基础设施、纯清单、所有权清晰的目录 |
| `false` | `true` | 少见且危险:不纠偏但会删 | 一般不用 |

**今晚的分级(实测,来自 `production/bootstrap/*.yaml`)**

| Application | `selfHeal` | `prune` | 理由 |
|---|---|---|---|
| `ai-platform-app` | `false` | `false` | 存量系统,接管期**不允许 ArgoCD 自动动手**(D9:先让 Git 描述现实) |
| `nginx-demo-app` | `false` | `false` | 发布演练对象,需要手工调试空间 |
| `loki` | `true` | `true` | 纯清单基础设施 |
| `monitoring-app` | `true` | `true` | 补充对象,GitOps 管辖清楚(主体仍由 Helm 管,见 D14) |
| `promtail` | `true` | `true` | 纯清单基础设施 |
| `sealed-secrets` | `true` | `true` | 基础设施 |

**这份分级本身就是面试素材**。它回答了一个真实的问题:"GitOps 会不会让开发变得很烦?" 答案是 **不会,只要你按应用性质分级**。用户当年对 ArgoCD 的负面体验("改了配置没 commit 就被改回去"),本质是**把所有开关都开到最大**,而不是 ArgoCD 的必然(详见 D2 / `05_学习笔记/01_ArgoCD到底是什么.md`)。

**「面试可以怎么讲」**

> "`selfHeal` 管漂移纠正,`prune` 管资源回收,两个是两个独立的维度。我们的做法是**按应用性质分级**:基础设施类(loki / promtail / sealed-secrets)全开,自动收敛;存量接管期的 ai-platform 和发布演练用的 nginx-demo 两个都关,让它只报告不动手。这样既拿到了 GitOps 的漂移检测,又不会在接管期被自动改动惊吓到——**'GitOps 在开发环境很烦'通常不是工具的问题,是把所有开关都开到最大的问题。**"

---

### 1.6 `prune` 的边界:只删"上一次同步跟踪过的"资源

**要解决什么问题**

`prune: true` 到底在什么条件下才会删东西?理解这一点,能直接解释今晚"我删了 YAML,集群里东西还在"的现象。

**机制**

ArgoCD 不"扫描集群找孤儿"。它的做法是**集合差**:

```
上一次同步时记录的资源集合   ───  这一次渲染出来的资源集合   =  要 prune 的集合
```

为了让"上一次同步记录了什么"这件事有据可查,ArgoCD 会在每个它管理的对象上留下一个**跟踪标识**:

```
argocd.argoproj.io/tracking-id: ai-platform-app:policy/PodDisruptionBudget:ai-platform/ollama-pdb
```

这个标识的形状是 `<Application 名>:<group/kind>:<namespace>/<name>`。它既是"这个对象归谁管"的答案,也是 prune 时**判断该不该删**的依据。

**由此推出的两个关键结论**

1. **要先拉到包含删除的那个新 revision,prune 才会发生。**

   如果 ArgoCD 根本没拿到你那次 `git push`(拉取失败),它的"这一次渲染结果"里**没有你删掉的资源**这个信息——它连你删了东西都不知道,自然什么都不会删。

   > **这就是今晚"删了 YAML,集群里对象还在"的完整机制。** 它的根因和"Synced 骗人"是**同一个**:ArgoCD 停在一个旧 revision 上。同一个根因的两个表现——一个是不更新,一个是不删除。

2. **没被跟踪过的对象,`prune: true` 也不会碰。**

   如果某个对象是通过 `kubectl apply` 手工创建的,ArgoCD 的资源清单里没有它。你在 Git 里"删掉"一个从来没被同步过的资源,对 ArgoCD 来说是"无事发生"。

**还有一个比 prune 更狠的边界:cluster-scoped 资源**

`Namespace` 和 `CRD` 是**删除边界**——删掉一个对象会级联删掉下面所有东西。把它们交给 `prune: true`,等于在仓库里放了一个"删一行 YAML 就删库"的开关。

| 资源 | 处置 | 机制 |
|---|---|---|
| `Namespace` | 从清单里删掉,改用 `CreateNamespace=true` | ArgoCD **按需创建**命名空间,但不纳入生命周期管理 |
| `CRD`(如 `sealedsecrets.bitnami.com`) | 清单里加 `argocd.argoproj.io/sync-options: Prune=false` | 逐对象豁免 prune |

本项目 6 个 Application 的 `syncOptions` 全部带了 `CreateNamespace=true`(实测),正是 D10 的落地。

**「面试可以怎么讲」**

> "ArgoCD 的 prune 不是'扫描集群找孤儿',是拿'上一次同步记录的资源集合'和'这次渲染出来的集合'做差集,所以**它必须先拉到包含删除的那个 revision,才会去删**。我们的 CI 环境里出过一次'删了 YAML 但集群里对象还在',根因就是它停在旧 revision 上——和'UI 显示 Synced 但其实已经半死'是**同一个根因的两个表现**。另外我把 Namespace 和 CRD 从 prune 的范围里摘了出来,因为它们删一个会级联删掉下面全部,交给自动回收等于装了个一键删库的开关。"

---

### 1.7 面试可以怎么讲(本节汇总)

> **一句话版本**:GitOps 把期望状态变成 Git 里的文本,集群只是结果;用拉模式让集群自己收敛,好处是**集群不用把 kubeconfig 交给外部**;`selfHeal` 和 `prune` 要按应用性质分级,而不是全开或全关。

## 二、接缝 D:制品 → 声明

> **核心命题:GitOps 写回必须有 git 写凭据,这是一个绕不过去的架构决策,不是配置细节。**

### 2.1 为什么绕不过去

**推理链条**

```
CI 构建出了新镜像          → 镜像的 tag 变了
tag 变了                   → "集群该跑哪个镜像"这个期望状态变了
期望状态变了               → 它必须落到 Git(因为 Git 才是期望状态的载体,见 1.1)
落到 Git                   → 需要一个能往这个仓库写东西的身份
```

**这条链上每一步都是必然的,所以"写凭据"不是可选项。** ArgoCD 是 pull 模型——它只会**读**,永远不会替 Jenkins 把 tag 写进去。CI 想要改变世界,就必须自己能写。

**为什么说它是"架构决策"而不是"配置细节"**

因为它决定了三件在架构层面才有意义的事:

| 决策点 | 影响 |
|---|---|
| **凭据的权限范围** | 泄露的影响半径:一个仓库?一个账号?整个组织? |
| **凭据存放在哪** | 信任域:CI 系统里?集群里?还是一个独立的凭据服务? |
| **谁来轮换、怎么轮换** | 运维成本:改一个 Secret 重启 Pod,还是点一下界面 |

一个"配置细节"的选择不会同时决定这三件事。所以它应该进 ADR(它确实进了 —— `99_决策日志.md` 的 D17)。

**「面试可以怎么讲」**

> "CI 要改镜像 tag,就必然要产生一个新的期望状态,而期望状态在 Git 里,所以**CI 必须有一个能写这个仓库的身份——这一条绕不过去**。它不是配置细节,因为它同时决定了三件事:凭据的权限范围有多大、它存在哪个信任域里、以及将来怎么轮换。我们当时就是按这三个维度去比方案的。"

---

### 2.2 可选方案与取舍

**要解决什么问题**

"给 CI 一个能写 Git 的身份",有哪些路?每条路的权限边界和运维成本分别是什么?

**方案表**

| 方案 | 权限范围 | 凭据存在哪 | 跨仓 | 轮换 | 评价 |
|---|---|---|---|---|---|
| **A. 仓库级 Deploy Key(SSH)** | **单个仓库** | 集群 Secret / 挂载进构建 Pod | ❌ 一仓一把 | 换密钥 + 更新 deploy key | ✅ **今晚选中**。权限 = 需求 |
| **B. PAT / 机器账号** | **整个账号或组织** | 任意(常被复制到多处) | ✅ 方便 | 后台吊销 | ❌ 对"改一个 tag"来说**权限过宽** |
| **C. Jenkins 原生 Credentials** | 由 Jenkins 授权模型管 | **Jenkins controller** | ✅ | Jenkins 界面里改 | ⚠️ 最"正统",今晚**尝试失败**(下详) |
| **D. GitOps 写回替代品** | **不需要 CI 写权限** | — | — | — | ArgoCD Image Updater / Flux image automation |

**方案 A:仓库级 Deploy Key(SSH)**

这是 GitHub 为 CI 设计的标准机制。Deploy key 是一把绑定在**单个仓库**上的 SSH 公钥,可以设 `read_only` 或可写。

它的价值就是**边界对齐**:

> **凭证的权限范围应该等于它要做的事的范围 —— 不要大于。**

CI 要做的事是"往这一个仓库写一个 tag",那么它需要的权限就是"这一个仓库的可写"。方案 A 恰好就是这个范围,**不多也不少**。

对比方案 B:一个 PAT 泄露 = 整个账号下所有仓库 + 所有 API 权限泄露;一个 deploy key 泄露 = **一个仓库**。这个差距不是量级差异,是**事故类型**的差异。

今晚的实现细节(实测):

- 密钥类型:**ed25519**(比 RSA 短、快,且不受 SHA-1 相关的历史包袱影响)
- 公钥注册为仓库的 **deploy key**,**`read_only=false`**(可写)
- 私钥以 **K8s Secret** 形式挂进构建 Pod 的 git 容器,挂载路径 `/root/.ssh`,`defaultMode: 0400`

**方案 B:PAT / 机器账号**

优点是跨仓库方便(一个 token 管所有仓)。但"方便"在这里是**反指标**:

- 权限范围是**整个账号**。CI 要做的事只是"改一个仓库里的一个 tag",拿到的却是"这个账号能做的一切"。
- PAT 通常长期有效(可以设过期,但很少有人设短)。
- 它经常被复制到多个地方:`~/.git-credentials`、CI 环境变量、部署脚本、某个人的笔记里。**你很难回答"它到底被谁看到过"。**

**判断标准**:如果 CI 出错或被攻破,你希望损害上限是什么?"一个仓库里多了一个 commit"和"整个 GitHub 账号"是两个完全不同量级的事故。

**方案 C:Jenkins 原生 Credentials —— 最正统,今晚尝试失败**

Jenkins 有一套自己的凭据库(`withCredentials` + `sshUserPrivateKey`),正确用法是:

```groovy
withCredentials([sshUserPrivateKey(credentialsId: 'gitops-deploy-key', keyFileVariable: 'SSH_KEY')]) {
    sh 'GIT_SSH_COMMAND="ssh -i $SSH_KEY" git push origin HEAD:main'
}
```

它的好处是**凭据不出 Jenkins 的凭据库**——构建日志里会被自动打码,凭据文件在构建结束时销毁,不需要在集群里单独维护一个 Secret。

**今晚没有走通**:用 Jenkins REST API 创建 `GitSSHUserPrivateKey` 类型的凭据时,**返回 HTTP 500**。时间原因改用挂载方案。

顺带记录一下这条路上踩到的两个 REST API 坑(完整版在 `03_runbook/03_Jenkins_运行手册.md` 第三节):

| 坑 | 现象 | 根因 |
|---|---|---|
| crumb 与会话绑定 | 403 | `crumbIssuer` 发的 crumb **绑定在会话上**,请求 crumb 和提交 crumb 必须是同一个会话,`curl` 必须同时带 `-c` 和 `-b` 共享 cookie jar |
| `createCredentials` 要 form 编码 | `400 Nothing is submitted` | 该端点**不接受裸 JSON body**,数据要放在名为 `json` 的 form 字段里,用 `--data-urlencode "json@<file>"` |

第二个坑有个很有价值的教训:

> **`400 Nothing is submitted` 容易被读成"请求体是空的",而实际请求体是满的,只是放错了位置。报错信息描述的是服务端看到了什么,不是你发了什么。**

**方案 D:替代品 —— 让 CI 根本不写回**

ArgoCD Image Updater 和 Flux 的 image automation 都做同一件事:**由 CD 侧的控制器自己去仓库里找新镜像,自己改 tag**。

这确实解决了"CI 需要写权限"的问题——因为根本不需要写回了。但它在本项目里被**主动放弃**,理由是 D5 定下的边界:

> **"用现成方案"不适用于学习目标本身。** "CI 回写 GitOps repo"是 GitOps 最核心的概念——交给工具等于跳过学习目标。判断标准:这个东西本身是不是我们要学的内容。

所以它是**被记录下来的替代路径**(作为面试时的"我知道有别的做法"的弹药),而不是本项目的实现。

**「面试可以怎么讲」**

> "给 CI 一个写 Git 的身份有四条路。我们选了 **仓库级 deploy key**,因为它的权限范围和需求正好对齐——CI 要做的事是'往这一个仓库写一个 tag',那它就该只有这一个仓库的可写权限。对比 PAT,一个 PAT 泄露是整个账号泄露,一个 deploy key 泄露是一个仓库泄露,**这是事故类型的差异,不是量级的差异**。我们知道还有 ArgoCD Image Updater 这类让 CD 侧自己改 tag 的方案,那样 CI 完全不需要写权限;我们没有用它,是因为'CI 回写 GitOps'这件事本身是我们想亲手做一遍的学习目标。"

---

### 2.3 今晚的做法(实测)

**凭据的生产与注册**

```
第一步  生成 ed25519 密钥对
第二步  公钥 → GitHub 仓库 Settings → Deploy keys → 勾选 Allow write access
第三步  私钥 → K8s Secret(名 jenkins-git-deploy-key,实测存在,Opaque,1 个 key)
第四步  Secret 以 volume 形式挂进构建 Pod 的 git 容器
```

**Secret 的挂载(来自 `ci/Jenkinsfile`,已去掉注释)**

```yaml
  - name: git
    image: alpine/git:latest
    command: ["sleep"]
    args: ["infinity"]
    volumeMounts:
    - name: deploy-key
      mountPath: /root/.ssh
      readOnly: true
  volumes:
  - name: deploy-key
    secret:
      secretName: jenkins-git-deploy-key
      defaultMode: 0400
```

**写回 GitOps 的那一段(来自 `ci/Jenkinsfile`)**

```bash
set -e
git config user.email "jenkins@sre-lab-ci"
git config user.name  "Jenkins CI"

OLD_IMAGE=$(grep -oP "(?<=image: )${REGISTRY}/${IMAGE_NAME}:\\S+" ${GITOPS_FILE} || echo "none")
echo "旧镜像: ${OLD_IMAGE}"
echo "新镜像: ${IMAGE_REF}"

sed -i "s|image: ${REGISTRY}/${IMAGE_NAME}:.*|image: ${IMAGE_REF}|" ${GITOPS_FILE}

if git diff --quiet -- ${GITOPS_FILE}; then
  echo "镜像 tag 未变化，跳过提交"
  exit 0
fi

git add ${GITOPS_FILE}
git commit -m "ci: bump ollama-exporter to ${SHORT_SHA}"
GIT_SSH_COMMAND="ssh -i /root/.ssh/id_ed25519 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null" \
  git push git@github.com:fei232401/sre-lab.git HEAD:main
echo "GitOps 已写回"
```

**这段代码里有五个值得单独拎出来的设计决策**(都在正文里解释,代码里没有注释):

| # | 写法 | 为什么 |
|---|---|---|
| 1 | `set -e` | **写回失败必须是硬失败**。没有它,`git push` 失败后脚本继续往下走,最后一条 `echo` 成功 → **流水线显示绿色**。这是接缝 D 最危险的失败形态(见 2.5)。 |
| 2 | `git diff --quiet` 短路 | tag 没变时不产生空提交。CI 会因为各种原因重跑,**没有这层判断,仓库历史会淹没在无意义的 "bump" 提交里**。 |
| 3 | `GIT_SSH_COMMAND` 显式指定私钥 | 不依赖 `~/.ssh/config` 或默认密钥名。挂载目录里只有这一把 key,显式指定让"用了哪把钥匙"这件事在代码里可见。 |
| 4 | `StrictHostKeyChecking=no` + `UserKnownHostsFile=/dev/null` | 构建 Pod 是一次性的,**没有 known_hosts 的历史**。不关掉这个检查,第一次连接会因为"未知主机"而失败。⚠️ **代价:失去了对中间人攻击的防护**——但这条链路的另一端是固定域名 `github.com`,且 CI 里没有可被中间人利用的机密(私钥只用于签名,不外传),风险可接受。**这是权衡,不是最佳实践。** |
| 5 | `HEAD:main` 的显式 refspec | 明确推"当前 HEAD 到远端的 main",而不是依赖"当前分支的上游追踪配置"。构建 Pod 是全新的检出一致性更高。 |

**目标文件(实测)**

写回的对象是 `sre-lab-gitops/production/monitoring/ollama-exporter.yaml`,里面的镜像行:

```yaml
        image: k3d-sre-registry:5000/sre-lab/ollama-exporter:bootstrap
```

当前还是 `bootstrap` 这个初始 tag —— 也就是说**这条写回链路还没有端到端成功过一次**。这本身是一个诚实的状态标注。

**「面试可以怎么讲」**

> "我们用一个专用的 ed25519 密钥对,公钥注册成仓库的 deploy key 而且开了写权限,私钥以 K8s Secret 挂进构建 Pod 的 git 容器,权限 0400。写回那段脚本里有几个我刻意加的东西:第一是 `set -e`,因为**写回失败如果不硬中断,流水线会显示绿色但集群根本没变**;第二是提交前先 `git diff --quiet` 判空,避免重跑产生一堆空提交;第三是显式写 `GIT_SSH_COMMAND` 指定私钥路径,不依赖默认配置。另外我们为了省事关了 host key 检查——**这是个权衡,不是最佳实践**,因为一次性 Pod 没有 known_hosts 历史,但代价是失去了中间人防护。"

---

### 2.4 诚实边界(两条,都是待办)

**边界 1:当前是普通 K8s Secret,没有走 Sealed Secrets 封存**

> **集群里没装 `kubeseal` 二进制**,所以这次是直接创建 Secret 的。

后果很具体:**k3d 重建后这个 Secret 会丢。** 这直接违背了 D4 选的"可重复重建"路线 —— 重建集群之后,CI 会因为找不到私钥而 push 失败。

**而这个失败点离根因很远**:表现为 `git push` 报错(认证失败),而不是"Secret 不存在"。排查的人会先去怀疑 deploy key 配置、密钥格式、GitHub 权限——**要绕一圈才会想到"这个 Secret 本来就不在集群重建的恢复清单里"**。

> **待办:补上 `kubeseal`,把这份 Secret 封存进 GitOps 仓库。**

这里有一个通用规律值得记:

> **"配置能工作"和"配置能重建"是两个独立判断。** 一个手工 `kubectl create secret` 创建的对象,在"当下能用"这个维度上完全合格,在"集群重建后还能用"这个维度上是零分。**所有手工创建的对象,都是重建路线上的一颗地雷。**

**边界 2:没有走 Jenkins 原生的 Credentials 机制**

尝试过用 Jenkins REST API 创建 `GitSSHUserPrivateKey` 类型凭据,返回 500,时间原因改用挂载。两条路的差异:

| | 挂载 K8s Secret | Jenkins 原生 Credentials |
|---|---|---|
| 凭据存在哪 | **K8s**(集群里) | **Jenkins**(controller 上) |
| 谁能用 | **只有挂了它的 Pod**(权限边界更窄) | 任何有权限的 Job |
| 轮换 | 改 Secret + 重启 Pod | Jenkins 界面里改(更简单) |
| 是否需要改 Jenkinsfile | 需要(声明 volume) | 需要(`withCredentials`,但是运行时注入) |

**挂载这条路的权限边界更窄**(只有构建 Pod 能看到私钥,别的 Job 看不到),代价是**轮换麻烦**。当前选择它,是因为**它先跑通了** —— 这是一个诚实的理由,不是技术上的最优解。

**「面试可以怎么讲」**

> "这次实现有两条我明确记下来的边界。第一,私钥走的是**普通 K8s Secret,没有用 Sealed Secrets 封存**,因为集群里没装 `kubeseal`——后果是 k3d 重建之后这个 Secret 会丢,而失败点离根因很远,表现为 git push 认证失败而不是'Secret 不存在'。第二,我们本来想用 Jenkins 原生 Credentials,但用 REST API 创建 `GitSSHUserPrivateKey` 时返回 500,时间原因改成了挂载 K8s Secret。挂载的权限边界更窄——**只有构建 Pod 能看到私钥**,但代价是轮换麻烦。**这两条我都当成待办记着,不打算美化。**"

---

### 2.5 方法论:并发、提交信息、写回失败的告警

这一节讲的是"写回"这件事本身的三类工程问题。它们和 Kubernetes 无关,是**任何"多写入者改同一份文本"的系统都要面对的**。

#### 2.5.1 并发:两个构建同时提交会怎样

**问题**

两个构建同时在跑,都 checkout 了同一个 HEAD,都改了同一个文件,都要 push:

```
构建 A: git push  ✅ 成功,远端 main 前进到 A 的 commit
构建 B: git push  ❌ 被拒(non-fast-forward)
```

Git 在这里是**正确的**——它拒绝覆盖别人的提交。但**流水线会失败**,而这失败看起来像"网络/权限问题",实际上是一个**并发控制问题**。

**今晚的应对:在 Jenkins 侧串行化**

```groovy
options {
  timestamps()
  disableConcurrentBuilds()
}
```

`disableConcurrentBuilds()` 让同一个 Job 的构建排队执行。**这是最简单有效的一招**,代价是构建吞吐下降。对单人项目完全够用。

**更通用的几种解法(在其他环境里适用)**

| 方案 | 机制 | 代价 |
|---|---|---|
| **串行化**(今晚) | 同一 Job 不并发 | 吞吐下降;多 Job 场景不适用 |
| **push 前 rebase 重试** | `git pull --rebase && git push`,`push` 被拒就重试 | 有重试上限;rebase 可能冲突 |
| **缩小冲突面** | CI 只改一个"单行 tag 文件",不同服务互不冲突 | 需要重新设计清单布局 |
| **换成分支 + 合并** | CI 推到独立分支,由人/机器人合并 | 引入人工环节,失去自动化 |
| **根本不写回**(方案 D) | ArgoCD Image Updater 自己改 | 跳过学习目标(见 2.2) |

**要记住的规律**

> **这是一个分布式写入问题。** 只要有 N 个写入者改同一份文本,就必然要面对"N 个写入者"的问题。选串行化还是选冲突消解,取决于**你对吞吐的需求**和**冲突的频率**。**当冲突频率低时,串行化几乎总是对的——它简单、可预测、没有隐藏状态。**

#### 2.5.2 提交信息规范

CI 产生的是**机器写的提交**。机器写的提交信息应该服务于机器和人两个读者:

```
ci: bump ollama-exporter to a1b2c3d
```

| 成分 | 作用 |
|---|---|
| `ci:` 前缀 | **可过滤**。`git log --grep '^ci:'` 一键拿到所有 CI 提交 |
| `bump <组件>` | **可追溯**。知道改的是哪个组件 |
| `to <sha>` | **可回溯**。顺着这个 sha 能追到构建、追到代码 |

**为什么这件事值得单独说**

因为 CI 提交是**污染 `git log` 的主力**。如果它们的格式是随意的(`update`、`fix`、`jenkins`),那这个仓库的历史就永久性地失去了可用性。反过来,一个稳定的前缀约定让"部署历史"变成一条可提取的信息流。

更严的做法是带上构建号(`ci: bump ollama-exporter to a1b2c3d (#142)`),这样**从 Git 能反查到具体的构建记录**,而不只是反查到代码。这是"双向可追溯"。

#### 2.5.3 写回失败怎么告警 —— 它为什么是静默的

**这是接缝 D 最重要的一条。**

**问题:流水线的成功标准和集群的成功标准是两个系统**

```
Jenkins 认为"成功" = 我的所有 stage 都过了
ArgoCD  认为"成功" = 集群收敛到了 Git 的当前 revision
```

这两件事**没有任何因果保证**。写回失败时:

| 环节 | 状态 |
|---|---|
| 构建 | ✅ 成功 |
| 镜像推送 | ✅ 成功 |
| **写回 Git** | ❌ **失败** |
| Jenkins 流水线 | ⚠️ **取决于有没有 `set -e`** |
| 集群 | ❌ 没变 |
| 人的感知 | 😀 "CI 绿的,应该上了吧" |

**防御措施,按强度排序**

| 强度 | 措施 | 说明 |
|---|---|---|
| 基础 | **`set -e`** | 写回失败 → 脚本中断 → stage 失败 → 流水线红 |
| 加强 | **写回后验证远端** | push 完立刻 `git ls-remote origin main`,确认远端 HEAD == 刚提交的 sha |
| 加强 | **`disableConcurrentBuilds` 已挡掉的失败重试** | 见 2.5.1 |
| 系统性 | **在 CD 侧监控"期望状态长期未收敛"** | 让 ArgoCD 的 `OutOfSync` 时长成为一个告警信号 |

**为什么"写回后验证远端"值得做**

因为 `git push` 返回 0 **不等于**"远端的 main 已经指向我的 commit"。中间可能有:

- 服务端 hook 拒绝了这次推送(但客户端拿到了非零退出码,这个还好)
- 推送到了一个你没预期的 ref
- 网络在"服务端已接收但客户端未收到确认"的窗口里断了,客户端重试,产生了重复提交

`git ls-remote` 是一次**独立的读取**,它回答的是"远端现在是什么",而不是"我刚才那条命令说了什么"。**验证要用独立的读取,不能用写入命令自己的返回值。**

**这条规律可以推广**

> **凡是"我发出去了"和"对方收到了"由两个系统分别判断的地方,都必须做独立的读回验证。**
>
> 这与接缝 E 的教训是同一个:**"过程指标全绿"不等于"结果达成"**。CI 的 stage 全绿是过程指标,集群真的变了才是结果指标。D15 里的告警链路验证也是同一个模式——SMTP 服务器返回 250 是过程指标,人打开收件箱看到邮件才是结果指标。

**「面试可以怎么讲」**

> "CI 写回 Git 这件事有三类工程问题。第一是并发,两个构建同时 push 会被 Git 拒绝——**这本质上是个分布式写入问题**,我们最简单的一招是 `disableConcurrentBuilds()` 在 Jenkins 侧串行化,冲突频率低的时候串行化几乎总是对的。第二是提交信息规范,CI 提交是污染 `git log` 的主力,一个稳定的前缀约定能让部署历史变成可提取的信息流。第三也是最重要的:**写回失败是静默的**。因为流水线的成功标准和集群的成功标准是两个系统——CI 全绿只说明它的 stage 过了,不说明集群变了。所以我们至少要用 `set -e` 让它硬失败,更好的做法是 push 之后用 `git ls-remote` 做一次**独立的读回验证**,因为写入命令自己的返回值不能证明远端收到了。"

### 2.6 一个反直觉点:省事和可控的经典权衡

**命题**

> **如果 CI 直接改集群(推模式),就根本不需要写凭据。**

推模式下,CI 有 kubeconfig,`kubectl set image` 一敲,集群就变了。不需要 deploy key、不需要 Git 写回、不需要处理并发提交、不需要考虑提交信息规范。**整条接缝 D 消失了。**

**代价是什么**

| 维度 | 推模式(没接缝 D) | 拉模式(有接缝 D) |
|---|---|---|
| 需要什么凭据 | **kubeconfig**(集群管理员级) | **deploy key**(单仓库写) |
| 凭据泄露的影响 | **集群被完全控制** | **一个仓库多一个 commit** |
| 状态漂移 | 必然发生(集群和 Git 脱节) | 被对账纠正 |
| 回滚 | 需要记住反向命令 | `git revert` |
| 审计 | 分散在 CI 日志 | `git log` |
| 多集群 | 每集群一套 kubeconfig | 每集群自己拉 |
| 排障 | "谁改的"没有答案 | "哪个 commit 改的"有答案 |

**这就是权衡的本质**

推模式**用"不可控"换"省事"**:

- kubeconfig 的权限范围**远大于**"改一个 tag"这个需求 —— 这是**权限扩散**
- 集群状态和 Git 状态之间**没有任何机制保证一致** —— 这是**状态漂移**
- "谁在什么时候改了什么"**没有一个统一的地方能回答** —— 这是**审计缺失**

而这三样东西,恰恰是**运维这个岗位的核心关切**。所以这不是"哪个更先进",而是:

> **你要的是"更快地把东西部署上去",还是"能说清楚集群现在为什么长这样"?**

对一个交付完就撤的项目,推模式往往是对的。对一个要长期运行、要多人协作、要能在事故后复盘的系统,**拉模式的每一分摩擦都买到了可观测性和可控性**。

**记住这个权衡的形状,因为它到处都在**

| 领域 | 省事的做法 | 可控的做法 |
|---|---|---|
| 部署 | `kubectl apply` 手敲 | Git commit + 对账 |
| 变更管理 | 直接改线上配置 | 走 PR + review |
| 密钥 | 环境变量里塞明文 | 走 Secret + 封存 |
| 网络 | 全放通 | 最小权限 |

**它们全都是同一个权衡的不同皮肤。**

**「面试可以怎么讲」**

> "这里有个反直觉的地方:**如果 CI 直接 `kubectl apply`,接缝 D 整个就不存在了**——不需要 deploy key、不需要写回、不需要处理并发提交。但代价是 **CI 必须持有 kubeconfig,那是集群管理员级的凭据**,而它要做的事只是改一个 tag,这是权限扩散;同时集群状态和 Git 状态之间再也没有机制保证一致,这是状态漂移。**这是'省事'和'可控'的经典权衡**——你要的是'更快地部署上去',还是'能说清楚集群现在为什么长这样'。"

---

### 2.7 面试可以怎么讲(本节汇总)

**关于凭据选型(背这一段)**

> "CI 要改镜像 tag,就必然要产生新的期望状态,而期望状态在 Git 里,所以**CI 必须有一个能写这个仓库的身份——这一条绕不过去,它不是配置细节**,因为它同时决定了凭据的权限范围、它存在哪个信任域、以及将来怎么轮换。我们比了四条路,最后选了**仓库级 deploy key**,因为它的权限范围和需求正好对齐:**一个 PAT 泄露是整个账号泄露,一个 deploy key 泄露是一个仓库泄露,这是事故类型的差异,不是量级的差异。** 有一条边界我要说清楚:我们**没有**走 Jenkins 原生的 Credentials 机制,因为用 REST API 创建 `GitSSHUserPrivateKey` 时返回了 500,时间原因改成了把私钥以 K8s Secret 挂进构建 Pod。挂载的权限边界更窄,但轮换更麻烦——**这是权衡,不是最优解。**"

**关于写回失败的静默性(背这一段)**

> "接缝 D 里最危险的一点是:**写回失败是静默的**。因为流水线的成功标准和集群的成功标准是两个系统——CI 全绿只说明它的 stage 过了,不说明集群变了。所以写回的脚本里至少要 `set -e` 让它硬失败,更好的做法是 push 完用 `git ls-remote` 做一次**独立的读回验证**——**写入命令自己的返回值不能证明远端收到了,验证必须用独立的读取。**"

## 三、接缝 E:声明 → 收敛

> **核心命题:收敛链路的断点是静默的。**

### 3.1 ArgoCD 的收敛循环

**要解决什么问题**

Git 里的文本变了,集群怎么知道?

**循环的四步**

```
① 拉取        定时(默认约 3 分钟)从 Git 拉 targetRevision
                ↓
② 渲染        把 source.path 下的 YAML 渲染成 k8s 对象清单
                ↓
③ 比对        与集群里的实际状态做 diff
                ↓
④ 施加        不一致则 apply(是否删除取决于 prune,见 1.6)
                ↓
              (回到 ①,永不终止)
```

**这是一个收敛式控制器(convergence controller)**。它和 Kubernetes 里所有控制器(Deployment、ReplicaSet、kubelet)是同一个模式:

> **我不关心"变化是怎么发生的",我只关心"当前状态是否等于期望状态"。不等于,我就动手;动手失败了,我下一轮再来。**

这个模式的**最大优点**是鲁棒:任何一次失败都会被下一轮重试覆盖,系统最终会收敛。

这个模式的**最大缺点**也正来自这里:**它掩盖了失败**。一次失败不是终点,是一个会被重试覆盖的中间状态。所以:

- **瞬时失败**:你真的看不见(下一轮就好了)
- **持续失败**:你会看到,但它和瞬时的长得一样(都是一条报错)——**区别在于它持续了多久**

> **判断"故障"还是"尚未成功的中间态",第一步是看时间戳,不是看报错内容。** 这个教训在 P10 里踩过一次,在接缝 E 的故障链里是同一个模式的第三次现形。

**重试机制的副作用**

同样的机制制造了今晚另一个坑:ArgoCD 会拿"上一次成功拉到的 revision"继续工作。如果它拉不到新的,它**不会停下来**,而是**继续用旧的 revision 对账**。而"相对旧 revision 一致"——恰恰会被报告为 `Synced`。

这就引出了本节的核心。

**「面试可以怎么讲」**

> "ArgoCD 的收敛循环是典型的控制器模式:定时拉 Git、渲染、和集群比对、不一致就 apply,然后永远循环。这个模式的鲁棒性来自重试——任何一次失败都会被下一轮覆盖。但**缺点也在这里:它掩盖失败**。一次失败是个会被覆盖的中间状态,你看到的那条报错可能三分钟前就已经好了。所以判断'真故障'还是'中间态',第一步是看这个状态持续了多久,而不是看报错内容。"

---

### 3.2 `Synced` 的语义陷阱(今晚它骗了我们两次)

**`Synced` 到底是什么意思**

```
status.sync.status == Synced
  ⟺ 集群状态 == ArgoCD 当前已知的那个 revision 的期望状态
```

**它和"仓库远端 HEAD"没有任何关系。**

**完整的语义链**

| 问题 | 答案 |
|---|---|
| `Synced` 保证了集群和什么一致? | ArgoCD **上一次成功拉到**的那个 revision |
| 那个 revision 是远端最新吗? | **不保证。** 也可能落后很多个提交 |
| 如果拉取一直失败会怎样? | 它会**继续用旧 revision 对账**,并且**继续报 `Synced`** |
| UI 上看得出来吗? | **看不出来。绿的就是绿的。** |

**今晚的两个实例(同一个陷阱,两次现形)**

**实例 1 —— 删了 YAML,对象还在**

push 了一个删除某个对象的 commit。ArgoCD 报 `Synced`,但那个对象**还留在集群里**。一查 revision,它还停在 push 之前的那个 commit 上。

**实例 2 —— CI/CD 全链路静默半死**

网络故障期间,`github.com` 解析到一个被阻断的 IP,ArgoCD 拉不到新代码。**但在此之前它一直显示 `Synced`** —— 那个 `Synced` 是相对**旧 revision** 而言的。

> **"静默半死"这个词很准确:系统没死,它在正常地对账一个陈旧的期望状态。所有健康信号都是绿的,而它已经不再反映现实。**

**这给了我们一条通用的规律**

> **凡是以"当前状态 == 期望状态"表述的健康信号,都要先问一句:期望状态是"谁的"期望、"哪个时刻"的期望?**

同构的健康信号还有很多,都是同一个陷阱的变体:

| 信号 | 它实际在说什么 | 它不保证什么 |
|---|---|---|
| ArgoCD `Synced` | 集群 == ArgoCD 已知的 revision | 那个 revision 是最新的 |
| `Deployment` `1/1 READY` | 活跃 Pod 数达标 | 进程没在报错(见 P2) |
| pod `Running` | 容器进程起来了 | 应用能服务(见 P11) |
| `promtail Adding target` | 目标注册成功 | 匹配到了日志文件(见 P14) |
| SMTP 返回 250 | 服务器接受了这封信 | 邮件进了收件箱(见 D15) |

**验证方法**

```bash
kubectl --context k3d-ai-cluster -n argocd get application <app> \
  -o jsonpath='{.status.sync.revision}{"\n"}'
git rev-parse HEAD
```

两个值不一致时,**不要等轮询**,直接触发 hard refresh:

```bash
kubectl --context k3d-ai-cluster -n argocd annotate application <app> \
  argocd.argoproj.io/refresh=hard --overwrite
```

**这是本册最值得背下来的一条。** 它不只是一个 ArgoCD 的知识点,是一种**读健康信号的方法**:先问清楚这个信号的定义域,再决定信不信它。

**「面试可以怎么讲」**

> "ArgoCD 的 `Synced` 骗过我两次。它的准确含义是'集群和 **ArgoCD 上一次成功拉到的那个 revision** 一致',**它和远端最新 commit 没有任何关系**。所以远端有新提交但拉取失败时,它会拿旧 revision 继续对账,并且**继续显示绿色**。我第一次踩到是 push 了一个删除操作,UI 显示 Synced,但对象还在集群里;第二次更严重,网络故障期间整个链路静默半死,所有信号都是绿的。这让我总结出一条:**凡是以'当前状态等于期望状态'表述的健康信号,都要先问期望状态是谁的期望、哪个时刻的期望。** 验证方法是去核对 revision,不一致就 hard refresh,不要等轮询。"

---

### 3.3 今晚的完整故障链(按时间顺序)

这是本册的精华。它展示了一个真实的运维事故是**如何从"一个网络问题"演化成一个架构决策**的。

#### 阶段一:故障出现,但它伪装成"有的坏了有的没坏"

**现象**

集群里 `github.com` 解析到 **`20.205.243.166`**(新加坡的一个 IP),这个 IP 被阻断。集群内拉取 Git 仓库超时。

ArgoCD 报:

```
ComparisonError: failed to load target state: rpc error: ...
  failed to list refs: Get "https://github.com/.../info/refs?service=git-upload-pack":
  context deadline exceeded
```

**⚠️ 极易误判的前置现象**

**不是所有 Application 都报这个错。** 有的还显示 `Synced`。

原因就是 3.2 讲的:**它们还停在各自的`上一次成功拉到的 revision` 上,相对那个 revision 确实是一致的。** 所以故障的表现是**一部分 App 红、一部分 App 绿** —— 这个不均匀的分布会诱导你往"某些 App 配置有问题"的方向排查,而真正的根因是**全局的网络路径**。

#### 阶段二:排查 —— 区分"GitHub 挂了"和"这条网络路径挂了"

**为什么这个区分重要**

"GitHub 挂了"你什么都做不了,只能等。"这条路径挂了"你可以换路。**这两种情况的应对方式完全不同**,所以第一步必须把它们分开。

**方法 1:逐个 IP 试**

`curl` 的 `--resolve` 参数可以把某个域名强制解析到你指定的 IP,绕过 DNS:

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  --resolve github.com:443:140.82.112.3 \
  "https://github.com/fei232401/sre-lab.git/info/refs?service=git-upload-pack"
```

结果:**8 个已知 IP 里,有的通、有的不通。** 这就排除了"GitHub 整体挂了"。

> **本册写作时的复测(只读)**:`140.82.112.3` / `140.82.113.3` / `140.82.121.3` / `20.205.243.166` 全部超时;`20.27.177.113` / `4.237.22.38` / `20.87.245.0` 返回 **200**。这与"换 IP 是打地鼠"的结论一致。

**方法 2:用真正被消费的那个端点验证(这一步是关键)**

> **`curl https://github.com` 返回 200,不能证明 git 能用。**

因为 git 走的**不是**首页。git 的智能 HTTP 协议实际请求的是:

```
https://github.com/<owner>/<repo>.git/info/refs?service=git-upload-pack
```

**这才是要被验证的端点。** 在指定可用 IP 时,它返回 **200,507 字节**。

**为什么要盯字节数**:507 字节是"服务端真的返回了 refs 列表"的证据。一个 200 但内容为空的响应同样会让 `curl` 报成功——**看状态码不够,要看它真的吐出了东西**。

> **通用规律:验证一个依赖,必须验证"你要用的那个入口",而不是"这个服务的任意入口"。** 这两者之间的差距,就是今晚 507 字节和一次 200 首页之间的差距。

**方法 3:横向对照,确认不是整体断网**

`codeload.github.com` / `pypi.org` / `quay.io` 全部正常。

**结论**:**不是整体断网,是针对特定域名/IP 的阻断。**

> 这个结论的形状值得记住:**域名本身可达、服务本身在服务,唯一出问题的一环是"这个域名解析到了这个具体 IP"。** 这类故障有个讨厌的性质——**任何"目标服务是否正常"的检查都会通过,因为你检的不是同一个东西。**

#### 阶段三:第一次修复 —— 成功的假象

在 `kube-system/coredns` 的 ConfigMap 的 `NodeHosts` 键里追加一行,把域名钉到一个可用 IP:

```yaml
NodeHosts: |
  ...
  140.82.112.3 github.com
```

该 hosts 块带 `reload 15s`,**热生效,不需要重启 CoreDNS**。

**结果:ArgoCD 立刻恢复,六个 Application 全部回到 `Synced/Healthy`。**

**⚠️ 但 Jenkins 仍然连不上!**

根因:**Jenkins 跑在 JVM 上,JVM 默认会缓存 DNS 解析结果(`networkaddress.cache.ttl`)。Jenkins 进程启动早于 CoreDNS 修复,一直用着缓存的坏 IP。**

**外部世界已经修好了,它不知道。**

**处置:重启 Jenkins Pod。** 根治写在 `jenkins-values.yaml` 里(实测已生效):

```yaml
controller:
  javaOpts: "-Dsun.net.inetaddr.ttl=30 -Dsun.net.inetaddr.negative.ttl=10"
```

- `sun.net.inetaddr.ttl=30` —— 正缓存只留 30 秒
- `sun.net.inetaddr.negative.ttl=10` —— 解析失败(负结果)也只缓存 10 秒

#### 阶段四:修复的代价 —— Jenkins 重启是分钟级的

**⚠️ 这是本项目最重要的一条运维纪律。**

重启 Jenkins 时,它的 **init 容器会重新下载全部插件**。插件源是 `mirror.ossplanet.net`,**该源不稳定、会重试**,整个重启因此是**分钟级**的。

```
重启 = init 容器重下全部插件(源不稳定 + 重试)= 分钟级不可用
```

**由此推出一条排期纪律**:

> **任何"改 JVM 参数"这类需要重启才生效的事,要趁早做 —— 不要等到出问题才重启。**

出问题的时候重启,你付出的代价是"分钟级不可用"**叠加在**"系统已经不正常"之上。这两件事在时间上会**混在一起**,让归因变难 —— 你无法立刻分辨某个新现象是"原来的问题还没好"还是"重启引入的"。

这就是为什么 `javaOpts` 那两个参数**已经预先写进了 values 文件**,尽管今晚并不需要重新应用它。

#### 阶段五:封锁追着走 —— 换 IP 是打地鼠

**大约 20 分钟后,钉的那个 IP `140.82.112.3` 也被封了**(连 TCP 443 都连不上)。

再扫一遍,**8 个 IP 只剩 1 个活着**。

> **本册写作时的复测**证实了 `140.82.112.3` 当前确实不可达(超时),而 `NodeHosts` 里那行 `140.82.112.3 github.com` **仍然留在 ConfigMap 里**(实测)——也就是说,这个"手工钉 IP"的修复**现在是一行过了期的配置**。这本身就是 1.6 / 2.4 讲的"手工对象是重建路线上的地雷"的又一个实例。

**结论**:

> **换 IP 是打地鼠。从该网络到 GitHub 的稳定性本身不成立。**

这一句是整个故障链的转折点。它把一个"运维问题"升级成了一个"架构问题":

- 前面四个阶段都在问 **"怎么修好这条路"**
- 从这里开始要问 **"为什么要把可用性建立在一条我不控制的路上面"**

#### 阶段六:架构决策 —— 集群内自建 Gitea

**决定**:改用**集群内自建 Gitea** 作为 git 源头,把整个 CI 环路搬进集群内。

**理由**

1. **不再依赖不可控的外网。** GitHub 的可用性不由我控制,也不由我观测。
2. **这正是企业内网自建 GitLab/Gitea 的真实形态。** 对运维岗是更硬的实践 —— 会自己运维一台 Git 服务,比会连 GitHub 更有含金量。

**诚实边界(要一起讲)**

- 自建 Gitea 之后,**Gitea 自己变成了单点**,需要自己负责它的备份和可用性。**它不是"消灭了依赖",是"把依赖换成了一个我能控制的依赖"。**
- 更要紧的一点:**Gitea 跑在同一个 k3d 集群里,而它管的正是这个集群的期望状态。** 集群挂了,Git 也没了 —— GitOps 的"Git 是唯一真相来源"这个前提,在本地实验里被动摇了。**真正的生产形态是 Git 在集群之外**(比如公司内网的一台独立 GitLab),今晚的"集群内 Gitea"是本地资源约束下的折中。
- **这部分迁移仍待核实落地状态**:本册写作时,集群里**还没有** Gitea 相关的 namespace 或工作负载(实测 `kubectl get ns` 无 gitea),六个 Application 的同步状态是 `Unknown`。所以下面的迁移清单是**待办**,不是已完成记录。

### 3.4 知识展开一:同一个 DNS 改动,不同消费方不同的缓存层级

**这是本节最有普适价值的运维教训。**

**现象回顾**:改一行 CoreDNS 配置后,ArgoCD **立刻**恢复,Jenkins **必须重启**才恢复。

**为什么**:因为"DNS 解析结果"这个信息,在到达一个进程之前要穿过**多层缓存**。而每一层的**失效方式不同**。

**四层缓存(按数据流向排列)**

| 层 | 机制 | 在本项目里的实例 | 失效方式 |
|---|---|---|---|
| **1. DNS 服务端** | hosts 文件的 `reload` + 响应 TTL | CoreDNS `hosts` 块 `reload 15s`、`ttl 60`;`cache 30` 插件 | `reload 15s` → 15 秒内重读文件 |
| **2. 系统解析器** | nsswitch / `/etc/hosts` / nscd | 宿主机与节点容器各自的 `/etc/hosts` | 立即(下次解析);nscd 需重启 |
| **3. 进程内缓存** | 语言运行时的解析器缓存 | **JVM 的 `networkaddress.cache.ttl`**;Go 的 `net` 包默认**不做缓存** | JVM 需重启或改参数;Go 每次重查 |
| **4. 连接层** | conntrack / TCP 连接复用 / HTTP keep-alive | 已建立的到 GitHub 的 TCP 连接 | **连接不断,就一直用旧 IP** |

**把它变成一张决策表**

> **改完 DNS,问自己:现在有多少个消费方,它们各自停在哪一层?**

| 消费方 | 停在的层 | 需要做什么 |
|---|---|---|
| ArgoCD(repo-server) | 层 3 无缓存(Go)+ 层 4 可能复用连接 | 通常**立即生效**;实在不行 hard refresh |
| **Jenkins(JVM)** | **层 3 有缓存** | **重启进程**,或预先设 `sun.net.inetaddr.ttl` |
| 宿主机上的 `curl` | 层 2(每次重新解析) | 立即生效 |
| 一个已经建立的长连接 | 层 4 | **连接不断就永远不生效** |

**今晚的教训正是这条**:

> **修好"基础设施层"不等于修好了"消费方"。** 时间线是:改 CoreDNS → ArgoCD 绿了 → 直觉上"网络修好了" → 但 Jenkins 依然红着。**如果只看 ArgoCD 就收工,会漏掉一个仍然故障的组件。**

**这条规律不只适用于 DNS**

它是"**上游改了,消费方什么时候知道**"这个大类问题的一个实例:

| 上游改动 | 有缓存的消费方 | 动作 |
|---|---|---|
| DNS 记录 | JVM | 重启进程 / 调 `networkaddress.cache.ttl` |
| ConfigMap 内容 | promtail(fsnotify 监听被替换的符号链接) | `kubectl rollout restart`(见 P14) |
| Secret 内容 | 任何把它读进环境变量的 Pod | 重启消费它的 Pod |
| 镜像 tag 指向的内容 | 节点上的 containerd 镜像缓存 | 拉取策略要匹配 tag 的可变性(见 4.2) |

**「面试可以怎么讲」**

> "我改了一行 CoreDNS 配置,ArgoCD 立刻恢复,但 Jenkins 还是连不上。原因是**同一个 DNS 变更,不同消费方停在不同层级的缓存上**:CoreDNS 自己的 hosts 块有 `reload 15s` 所以热生效;ArgoCD 是 Go 写的,标准库不做 DNS 缓存,所以立刻生效;而 **Jenkins 跑在 JVM 上,JVM 默认会缓存解析结果**,它的进程启动早于修复,一直攥着那个坏 IP 不放,必须重启才生效。这件事给我的教训是:**改完 DNS,要先问'现在有多少个消费方、它们各自停在哪一层缓存上'。修好基础设施层不等于修好了消费方,判断'修好了没有'必须按组件逐个确认。** 这个规律也适用于 ConfigMap、Secret——凡是带进程内缓存或者文件监听机制的系统,改完上游都要给它一个'忘掉缓存'的动作。"

### 3.5 知识展开二:CoreDNS 在 k3s 里的扩展点

**要解决什么问题**

k3s 集群里想加一条自定义 DNS 记录(比如把 `github.com` 钉到某个 IP),改哪里?改完会不会被 k3s 冲掉?

**k3s 的 CoreDNS 配置结构(实测读到的 Corefile)**

```
.:53 {
    errors
    health
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
      pods insecure
      fallthrough in-addr.arpa ip6.arpa
    }
    hosts /etc/coredns/NodeHosts {
      ttl 60
      reload 15s
      fallthrough
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
    import /etc/coredns/custom/*.override
}
import /etc/coredns/custom/*.server
```

**三个扩展点**

| 扩展点 | 是什么 | 谁维护 | 今晚是否用了 |
|---|---|---|---|
| `hosts /etc/coredns/NodeHosts` 块 | k3s **自动维护**的 hosts,内容主要是节点名 → IP 的映射 | **k3s** | ✅ 用了(往里追加了一行) |
| `import /etc/coredns/custom/*.override` | 官方的自定义插槽,挂在 `.` 块的**最后** | 用户 | ❌ 没用 |
| `import /etc/coredns/custom/*.server` | 用于整块新增 server 块(比如给某个域单独起一个 zone) | 用户 | ❌ 没用 |

**关键事实(实测)**:本集群的 `kube-system` 里**没有 `coredns-custom` 这个 ConfigMap**。

也就是说,`import /etc/coredns/custom/*.override` 这行**目前是一个空的扩展点** —— Corefile 里有它,但背后没有挂任何东西。这解释了为什么今晚只能去改主 ConfigMap。

**为什么这是有问题的做法(诚实标注)**

> **`NodeHosts` 这个键是 k3s 在维护的。** 里面三行节点记录(实测:`172.18.0.3/4/5` 对应三个节点)是 k3s 写进去的。往一个"别人在维护的文件"里手工追加一行,风险是**下次 k3s 重新生成这个键时,你加的那行会消失**。
>
> **具体触发条件(什么情况下 k3s 会重写 NodeHosts、是否保留手工行):待核实。** 但这是已知的一类风险,工程上的正确做法是**不要往 k3s 管理的键里写手工内容**。

**正确的做法应该是**

用官方的自定义插槽。创建 `coredns-custom` ConfigMap,把内容挂到 `/etc/coredns/custom/` 下,以 `.override` 结尾:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns-custom
  namespace: kube-system
data:
  sre-lab.override: |
    hosts {
      140.82.112.3 github.com
      fallthrough
    }
```

> ⚠️ 上面这段是**示意**(已去掉注释),**尚未在本集群实测**。写在这里是为了记录"如果重来一次该怎么做",不是已实施记录。**待核实**:该 ConfigMap 需要的确切挂载路径和 k3s 版本行为。

**两个 hosts 块的对比**

| | 直接改 `NodeHosts`(今晚做的) | 走 `coredns-custom`(推荐的) |
|---|---|---|
| 生效速度 | 热生效(`reload 15s`) | 热生效(同样是文件重载) |
| 谁维护 | 混在一起,k3s 也写、你也写 | **你的归你,k3s 的归 k3s** |
| 被 k3s 覆盖的风险 | **有** | 无 |
| 与集群重建的关系 | 集群重建后这行就没了 | 可以随 GitOps 一起管理 |

**这就是"边界"这个概念的又一次应用**:今晚的做法把"我的配置"和"k3s 的配置"塞进了同一个键里 —— **两个所有者写同一个文件,冲突只是时间问题**。这和 D7 里"先看现场有什么约定,再决定新增什么"是同一条原则。

**「面试可以怎么讲」**

> "k3s 里的 CoreDNS 有三个扩展点:一个是 k3s 自己维护的 `NodeHosts`,一个是 `import /etc/coredns/custom/*.override`,还有一个是整块新增 server 块的 `*.server`。我今晚为了应急直接往 `NodeHosts` 里追加了一行——**这个做法能用,但有持久性风险,因为那个键是 k3s 在维护的,它重新生成的时候我的手写行可能就没了**。我现在集群里的 `coredns-custom` ConfigMap 其实是不存在的,也就是说那个官方扩展点是个空的插槽。重来一次的话应该走 `coredns-custom`,而不是和 k3s 抢同一个文件的写权——**两个所有者写同一个文件,冲突只是时间问题。**"

### 3.6 知识展开三:依赖外网是可用性设计问题,不是"网络问题"

**要解决什么问题**

当"我们依赖的某个外部服务不稳定"时,把它当成网络问题去修,会陷入什么循环?

**当作"网络问题"修的路径**

```
换个 IP → 好了 → 又被封 → 再换 → 又好了 → 又被封 → ...
```

这就是打地鼠。它的特征是:**每一次修复都是有效的,但每一次有效都是暂时的。** 而且你看不到终点,因为你没有在改变**依赖的结构**,只是在改变**依赖的具体路径**。

**当作"可用性设计问题"看的路径**

问的问题是:

> **我的系统里,哪些可用性保证是建立在一个我不控制、也观测不到的下游上的?**

然后:

| 维度 | 依赖外网(公网 GitHub) | 内网自建 |
|---|---|---|
| DNS | 公网解析,结果可能被污染/阻断 | 自己控制 |
| IP | 会变、会被封 | 自己控制 |
| TLS | 证书由对方管 | 自己管 |
| 限流/配额 | 对方管,你看不到 | 自己管 |
| **故障时能否观测** | **很难**——你连"它到底挂了没有"都难证 | **能**——日志、指标在自己手里 |
| 故障时能否处理 | 只能等/换路 | 自己能动手 |

**关键的一行**:

> **你不可能把一个 SLO 建立在一个你看不见的下游上。**

今晚的排查最耗时的部分,恰恰是**证明"GitHub 没挂、挂的是这条路径"**。如果这个依赖在自己手里,你打开 Grafana 看一眼就知道了。

**但要把话说完整:自建不是免费的**

| 自建的代价 | 说明 |
|---|---|
| 单点 | Gitea 挂了,CI 环路全停 |
| 运维成本 | 备份、升级、容量 |
| 自己成为瓶颈 | 你的可用性上限 = 你能运维的水平 |

所以准确的表述不是"自建一定更好",而是:

> **当外部依赖的稳定性已经低于你的需求,并且你已经无法通过换路来改善时,"把它变成可控"就是正确的一步 —— 即使代价是你要为它负责。**

**企业内网为什么要自建 Git/镜像仓库**

因为对企业来说,这不是"保守",是**把不可控变成可控**:

- **合规与审计**:代码不出内网
- **可用性**:不因为公网的某次故障导致全公司的 CI 停摆
- **速度**:内网拉取比跨公网快一个数量级(镜像拉取体现得最明显)
- **可控的配额**:不会被上游限流

**这也是为什么今晚的这个决定对运维岗特别有价值**:

> **它不是一个"我学会了用 Gitea"的故事,是一个"我判断出了这个依赖的稳定性不成立,并动手改变了依赖结构"的故事。** 前者是工具使用,后者是架构判断 —— 面试官要听的是后者。

**「面试可以怎么讲」**

> "我处理这个问题的转折点在于:**当我发现换 IP 是打地鼠、二十分钟后新钉的 IP 也被封的时候,我意识到这不是一个网络问题,是一个可用性设计问题。** 我当时的问法从'怎么修好这条路'变成了'我的系统里,哪些可用性保证建立在一个我不控制、也观测不到的下游上'。我把 git 源头换成了集群内自建的 Gitea,理由很直接:**故障时我连'它到底挂了没有'都很难证明,而且我什么都做不了。** 我也清楚这个决定的代价——Gitea 自己成了单点,我需要为它的备份和可用性负责。**但它把不可控变成了可控,而企业内网自建 Git 和镜像仓库本来就是同样的逻辑。**"

### 4.1 kubelet 拉镜像:节点级凭据 vs Pod 级凭据

**要解决什么问题**

Pod 要拉一个私有镜像仓库的镜像,认证信息从哪来?

**两个完全不同层级的东西,极容易混淆**

| | `imagePullSecrets` | containerd 的 registry 配置 |
|---|---|---|
| **层级** | **Pod 级**(写在 PodSpec 里,或由 ServiceAccount 注入) | **节点级**(节点上的文件) |
| **管什么** | **用哪个账号**去拉 | **怎么连、信不信**这个 registry |
| **典型内容** | docker registry 的用户名/密码(一个 Secret) | 端点地址、是否 HTTPS、CA 证书、HTTP 明文例外 |
| **谁读它** | kubelet(在发起拉取前取凭据) | containerd(每次拉取时动态读取) |
| **本项目的实例** | 无(实测:全集群没有任何 imagePullSecrets) | 有:节点上的 `certs.d/<registry>/hosts.toml` |

> **一句话区分**:`imagePullSecrets` 回答的是 **"我是谁"**;节点级 registry 配置回答的是 **"这个仓库的地址和传输方式是什么"**。**两个都需要,缺一不可,但管的是不同的事。**

**本项目的实测状态**

全仓库 grep `imagePullSecrets`,**只有一处**,而且是空的:

```yaml
      imagePullSecrets: []
```

也就是说,集群拉本地私有仓库的镜像时,**完全没有用 Pod 级凭据**。这是怎么工作的?

因为它是**节点级**配置。节点上的 containerd 被配置成"这个 registry 用 HTTP 明文、不需要认证":

```yaml
    [[registry]]
    prefix = "k3d-sre-registry:5000"
    location = "k3d-sre-registry:5000"
    insecure = true
```

(这段来自 `production/ci/buildah-registries.yaml`,是给 **Buildah 构建容器**用的;节点侧 containerd 的对应配置在 `certs.d/hosts.toml`,见 P16。)

**这里有一个必须讲清楚的诚实边界**

> **本地 registry 没有任何访问控制。** 任何能访问 `localhost:5111` 的东西都能推送和拉取(D16 的诚实边界)。

所以今晚"没有 imagePullSecrets"**不是一个设计选择,是一个安全缺口**:私有仓库的"私有"只是"网络不可达",不是"需要认证"。

**有认证时的正确做法**

| 做法 | 说明 |
|---|---|
| PodSpec 里显式写 `imagePullSecrets` | 精确控制,但每个工作负载都要写 |
| 挂到 **ServiceAccount** 上 | **推荐**。同一 SA 下的所有 Pod 自动继承,不用逐个改 |
| 节点级 `certs.d` 里配 `username`/`password` | 可以在节点级配置凭据,**但那是"把凭据放在每个节点上"** —— 边界更宽 |

**规律**

> **Kubernetes 里凡是"认证信息"和"连接信息"被拆到不同层级的场景,都是排查事故的高发区。** 因为排查时你会在错误的层级找答案——"拉不下来镜像"你会先去查 Secret,而实际问题可能是节点的 `certs.d` 没配。

**「面试可以怎么讲」**

> "拉私有镜像有两个层级的配置,特别容易混:**`imagePullSecrets` 是 Pod 级的,回答的是'用哪个账号';而 containerd 的 registry 配置是节点级的,回答的是'这个仓库的地址和传输方式,信不信它的证书'。** 我们集群里实测是**没有任何 imagePullSecrets** 的,因为本地 registry 走的是节点级 `certs.d` 配的 HTTP 明文端点。但这里有个我必须说清楚的边界——**我们的本地 registry 根本没有任何访问控制**,所以'没有 imagePullSecrets'不是一个设计选择,是一个安全缺口,它的'私有'只是网络不可达而已。"

### 4.2 `imagePullPolicy` 与 tag 的关系

**要解决什么问题**

节点上已经有这个镜像了,kubelet 还要不要去仓库检查一次?

**三个取值**

| 取值 | 行为 |
|---|---|
| `Always` | 每次都去 registry 解析这个 tag 的当前 digest |
| `IfNotPresent` | 本地有就直接用,**不问 registry** |
| `Never` | 只用本地,绝不拉取 |

**默认规则**

Kubernetes 的默认行为:

| tag 形态 | 默认 policy |
|---|---|
| `latest`,或**没写 tag** | `Always` |
| 其它任何 tag | `IfNotPresent` |

**核心洞察:`IfNotPresent` 的正确性依赖 tag 不可变**

| tag 形态 | 配 `IfNotPresent` 的后果 |
|---|---|
| **不可变 tag**(如 `:a1b2c3d`) | ✅ **正确**。内容不会变,命中缓存省流量,**且各节点内容一致** |
| **可变 tag**(如 `:latest` / `:v1`) | ❌ **危险**。**各节点内容可能不一致** |

**为什么可变 tag + `IfNotPresent` 会导致各节点不一致**

```
节点 A:之前拉过 my-app:v1(那时 v1 指向内容 X) → 本地有 → IfNotPresent → 用 X
仓库:  my-app:v1 已经被重新推送,现在指向内容 Y
节点 B:从来没拉过 → 本地没有 → 去仓库拉 → 拿到 Y
```

**结果:同一个 Deployment、同一个 tag,节点 A 跑的是 X,节点 B 跑的是 Y。** 而集群层面**看不到任何异常** —— `kubectl get pods` 全绿,镜像字段显示的都是 `my-app:v1`。

> **这是一个"看清单看不出问题"的故障。** 你要进到每个节点里去看实际的镜像 digest 才能发现。

**`latest` 之所以是反模式,根因就在这里**

`latest` 把一个**可变的指针**当成了**不可变的标识**。而部署、回滚、审计这三件事**全都依赖"一个标识对应一份内容"**:

- **回滚**:"回到上一个版本"——如果 `latest` 已经指向别的内容了,你回滚到哪?
- **审计**:"生产上跑的是哪个版本的代码"——`latest` 回答不了
- **一致性**:见上面的节点 A / 节点 B

**今晚的做法**

CI 用 **git short sha** 做 tag:

```bash
env.SHORT_SHA = sh(script: 'git rev-parse --short=7 HEAD', returnStdout: true).trim()
env.IMAGE_REF = "${env.REGISTRY}/${env.IMAGE_NAME}:${env.SHORT_SHA}"
```

产物形如 `k3d-sre-registry:5000/sre-lab/ollama-exporter:a1b2c3d`。

| 这个 tag 的性质 | 带来的好处 |
|---|---|
| **不可变**(同一个 sha 永远对应同一份内容) | 可以用 `IfNotPresent` 省流量且保证一致性 |
| **可追溯**(tag 就是 commit sha) | 从集群里的镜像 tag **直接反查到源码版本** |
| **可回滚**(回到旧 sha 即可) | 回滚是一次正常的部署,不需要特殊操作 |

> **一个 tag 策略要同时满足"不可变、可追溯、可回滚"三条,`git sha` 是成本最低的答案。** 这也是 D16 / P17 那套"让产物有出处"的思路在 tag 层面的延续 —— P17 讲的是"镜像要能从版本控制重建",这里讲的是"镜像要能指回版本控制"。

**「面试可以怎么讲」**

> "`imagePullPolicy` 和 tag 的可变性必须配套。**不可变 tag 配 `IfNotPresent` 是对的,省流量而且各节点内容一致;但可变 tag 配 `IfNotPresent` 会导致各节点内容不一致** ——同一份 Deployment、同一个 tag,有的节点用旧内容、有的节点用新内容,而集群层面完全看不出来,因为镜像字段显示的一模一样。**`latest` 之所以是反模式,是因为它把一个可变的指针当成了不可变的标识**,而部署、回滚、审计这三件事全都依赖'一个标识对应一份内容'。我们用 git short sha 做 tag,它同时满足不可变、可追溯、可回滚三条。"

### 4.3 滚动更新:`maxSurge` / `maxUnavailable` 的真实语义

**要解决什么问题**

Deployment 换版本时,旧 Pod 什么时候停、新 Pod 什么时候起?

**两个旋钮**

| 参数 | 含义 |
|---|---|
| `maxSurge` | **超出**期望副本数的上限 —— "允许比目标多起几个" |
| `maxUnavailable` | **不可用**副本数的上限 —— "允许比目标少几个" |

**取整规则(这是最容易算错的地方)**

> **`maxUnavailable` 向下取整,`maxSurge` 向上取整。**

这个规则的设计意图很清楚:**保守优先**——宁可多起一个,也不肯少一个。

**今晚的真实案例(实测)**

`my-nginx` 的 Deployment:

```yaml
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: nginx
        image: nginx:alpine
```

**注意:没有写 `strategy` 字段** → 使用默认值:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 25%
```

**算一遍**:

```
replicas = 3
maxUnavailable: 25% × 3 = 0.75  →  向下取整  →  0
maxSurge:       25% × 3 = 0.75  →  向上取整  →  1
```

**结果:实际 `maxUnavailable` 是 0。**

这意味着一件非常具体的事:

> **滚动更新永远不会"先停后起"。它一定会先起一个新 Pod、等它就绪,然后才停掉一个旧 Pod。**

对 3 副本来说,更新过程中的副本数轨迹是 `3 → 4 → 3 → 4 → 3 ...`(峰值比目标多一个),而**可用副本数始终不低于 3**。

**这个默认值隐藏的两个行为**

**行为 1:更新会"卡住",但不会自动回滚**

如果新版本的 Pod 永远起不来(镜像拉不下来、探针过不去),滚动更新会**停在那里**:

```
旧 Pod: 3 个都在,继续服务          ← 服务没中断 ✅
新 Pod: 1 个一直 Pending/不 Ready   ← 更新永远不完成 ❌
```

Deployment 的滚动更新是**渐进式**的,**没有超时自动回滚**。你会一直盯着一个 `Progressing` 状态。要回滚,得手动 `kubectl rollout undo`(或者由 CD 侧检测到长期未完成来触发)。

> **"服务不中断"和"发布会完成"是两件事。** 前者是 `maxUnavailable: 0` 买到的,后者它不负责。

**行为 2:无探针时,整套保护是假的**

这才是最值得警惕的一点。

`maxUnavailable: 0` 的整个保护逻辑,建立在**"新 Pod 就绪了,才停旧 Pod"**这个前提上。而"就绪"的定义是什么?

> **没有 readinessProbe 时,kubelet 认为 Pod 就绪的条件是:容器进程起来了。**

它**不知道**应用是否真的能服务。所以:

```
新 Pod:  容器进程起来 → kubelet 标记 Ready → 滚动更新认为"可以停旧的了" → 停掉一个旧 Pod
         ↓
         (而新 Pod 的应用可能还没初始化完 / 配置读错了 / 第一个请求就崩)
         ↓
         流量打过来 → 报错
```

**"先起新再停旧"这个优雅的顺序,在无探针的情况下保护不了你** —— 因为"就绪"这个信号本身是假的。

**今晚的实测状态**:`my-nginx` 的 Deployment 里**没有任何探针**(三个探针一个都没有)。也就是说,它拿到的 `maxUnavailable: 0` 是一个"看起来安全、实际不设防"的配置。

**结论**

> **探针是滚动更新语义的地基。** 没有探针,`maxUnavailable` / `maxSurge` 只是在数**进程**,不是在数**能服务的实例**。

**与 PDB 的区别(别混淆)**

| | 管什么 | 什么时候生效 |
|---|---|---|
| 滚动更新参数 | **发布**:换版本时的节奏 | Deployment 控制器主动删 Pod |
| PDB | **自愿中断**:驱逐 / 节点维护 | `kubectl drain` / Eviction API |

**两者的 `maxUnavailable` 是两个不同的旋钮,解决的是不同的问题。** 见 4.5 的 PDB 陷阱。

**「面试可以怎么讲」**

> "滚动更新里 `maxUnavailable` 是**向下取整**、`maxSurge` 是**向上取整**,这个规则很容易算错。我们有个 3 副本的 Deployment 没显式写 strategy,用的是默认的 25%/25%——**25% × 3 = 0.75,向下取整之后 maxUnavailable 实际是 0**,所以它永远是先起新 Pod、等就绪、再停旧 Pod,可用副本数不会低于 3。但更值得讲的是这个保护的前提:**它依赖'就绪'这个信号是真的**。那个 Deployment 没有配任何探针,而**没有 readinessProbe 的时候,kubelet 认为'就绪'的标准只是'容器进程起来了'** ——它不知道应用能不能服务。所以'先起后停'这个优雅顺序在没有探针时保护不了你。**探针是滚动更新语义的地基。**"

### 4.4 探针:liveness / readiness / startup

**要解决什么问题**

容器"起来了"和容器"能干活"是两件事。kubelet 怎么知道是哪一件?

**三者的语义差别**

| 探针 | 回答的问题 | 失败后果 | 是否影响流量 |
|---|---|---|---|
| **livenessProbe** | 进程还活着吗? | **重启容器** | 重启期间不服务 |
| **readinessProbe** | 现在能接流量吗? | 从 Service 的端点列表里**摘除**(不重启) | **直接影响** |
| **startupProbe** | 启动完成了吗? | 在它成功之前,**抑制** liveness 和 readiness | 启动期不接流量 |

**关键区别(最容易被忽略的)**

> **readiness 失败 = 摘流量(不重启);liveness 失败 = 重启(不摘流量,但会中断服务)。**

这两个的失败动作**完全不同**,而它们的名字很像。配错方向会造成两类完全不同的故障:

**配错的后果**

| 配错的方式 | 后果 |
|---|---|
| **没有 readiness**(或配得太松) | **流量打进未就绪的 Pod** → 用户看到错误 |
| readiness **配得太紧** | Pod 永远不 Ready → **发布卡住**(配合 `maxUnavailable: 0` 就是完全卡死) |
| **liveness 配得太激进**(把"启动慢"当成"死了") | **无限重启循环**(CrashLoopBackOff),而且**永远起不来**——因为每次都在启动完成前被杀 |
| liveness **配得太松** | 进程僵死(deadlock)时不会被重启,一直占着资源不干活 |

**`startupProbe` 存在的理由**

它是为了解决"**慢启动应用**"这个具体矛盾:

```
没有 startupProbe 时,你只有两个坏选择:
  A. liveness 的 initialDelaySeconds 设得很大  → 简单粗暴,而且进程真的僵死时你要等很久才重启
  B. liveness 配得激进                          → 启动慢的实例被反复杀掉,永远起不来

有 startupProbe 时:
  startup 成功之前,liveness 和 readiness 都不生效
  → 启动期可以给到很长的预算(比如 5 分钟)
  → 而启动完成之后,liveness 可以配得很激进(比如 5 秒一次)
```

> **`startupProbe` 的价值在于它把"启动期"和"运行期"这两个对探针要求完全相反的阶段分开了。**

**本项目里的实际分布(实测)**

| 工作负载 | 探针情况 |
|---|---|
| `my-nginx` | **无任何探针** |
| `ollama-exporter`(基线版本) | liveness + readiness |
| `loki` | readiness + liveness |
| `ai-platform` 基线里的部分工作负载 | liveness + readiness,**其中一个同时配了 startup** |

这个分布本身就是一份很好的材料:**同一个集群里,探针配置是参差的** —— 有配全的、有只配两个的、有一个都没有的。而**没有探针的那个(nginx)恰好就是滚动更新案例里的主角**。

**「面试可以怎么讲」**

> "三个探针回答三个不同的问题:liveness 问'进程还活着吗',失败就重启;readiness 问'现在能接流量吗',失败就摘流量但**不重启**;startup 问'启动完了吗',在它成功之前抑制另外两个。最容易配错的是方向搞反——**readiness 配得太松会让流量打进未就绪的 Pod,配得太紧会让发布卡死;而 liveness 配得太激进会把'启动慢'当成'死了',造成无限重启循环,而且永远起不来**,因为每次都在启动完成前被杀。startupProbe 存在的意义就是解决这个矛盾:它把'启动期'和'运行期'分开了,启动期可以给很长的预算,运行期可以配得很激进。"

### 4.5 PDB 的真实语义与陷阱

**要解决什么问题**

节点要维护,上面的 Pod 会被驱逐。怎么保证"驱逐的时候服务不中断"?

**PDB 到底管什么(这是最必须讲清楚的一点)**

> **PDB 只限制「自愿中断」(voluntary disruption)。**

| 中断类型 | 例子 | PDB 管吗 |
|---|---|---|
| **自愿中断** | `kubectl drain`、节点维护、`Eviction API` | ✅ **管** |
| **非自愿中断** | 节点宕机、OOM Kill、进程崩溃、`kubectl delete pod` | ❌ **不管** |
| **滚动更新** | Deployment 换版本时删旧 Pod | ❌ **不管**(控制器不走 Eviction API) |

**所以 PDB 不是"高可用开关"。** 它保护的是**你主动做维护动作时**的服务可用性。节点真宕机了,PDB 一点用都没有。

**今晚的真实案例**

`ollama-pdb`:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: ollama-pdb
  namespace: ai-platform
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: ollama
```

而 `ollama` 这个工作负载**只有 1 个副本**(实测:`spec.replicas: 1`)。

**算一遍**:

```
minAvailable   = 1
期望副本数      = 1
→ disruptionsAllowed = currentHealthy - desiredHealthy = 1 - 1 = 0
```

**实测到的 status**:

```
conditions:
- reason: InsufficientPods
  status: "False"
  type: DisruptionAllowed
currentHealthy: 0
desiredHealthy: 1
disruptionsAllowed: 0
expectedPods: 0
```

集群里当前的实际状态(实测):

```
NAMESPACE     NAME         MIN AVAILABLE   ALLOWED DISRUPTIONS   AGE
ai-platform   ollama-pdb   1               0                     65m
```

**后果(这是本节的精华)**

> **`disruptionsAllowed = 0` 意味着:节点驱逐会永远返回 `429 Too Many Requests`,`kubectl drain` 会永久挂起。**

**这是一个"写了个 PDB 反而把集群锁死"的坑。** 写它的人本意是"保护这个服务别被中断",实际效果是"**这个 Pod 再也不能被合法驱逐了**"。当你想做节点维护、想升级节点、想缩容,都会卡在这里。

**为什么这个坑特别隐蔽**

因为它**不报错**:

- `kubectl apply` 成功
- 对象 `kubectl get pdb` 看得到
- `describe` 显示的 `MIN AVAILABLE: 1` **看起来完全合理**
- 只有真正去 drain 的时候,才发现卡住 —— 而那时你已经在做一次生产变更了

**正确的写法**

PDB 的数值**必须相对副本数来设**:

| 场景 | 错误写法 | 正确写法 |
|---|---|---|
| 1 副本 | `minAvailable: 1`(= 副本数) | **不要给单副本负载配 PDB**,或改用 `maxUnavailable` 并接受它没意义 |
| 3 副本 | `minAvailable: 3` | `minAvailable: 2`(disruptionsAllowed = 1) |
| 任意副本 | — | **用 `maxUnavailable: 1`** —— 它表达"最多坏一个",对副本数变化更鲁棒 |

> **`minAvailable` 等于副本数,等价于"永远不允许驱逐"。**

**⚠️ 更深一层:同一个 status 症状,两种完全不同的根因**

这是本项目里一个**特别值得记**的发现。看这两份 PDB 的 status:

| | `ollama-pdb`(Git 里当前版本) | 历史快照里的某个 PDB |
|---|---|---|
| `selector.matchLabels` | `app: ollama` | `app.kubernetes.io/name: ollama` |
| 集群里 Pod 的标签 | `app: ollama`(实测) | — |
| **`expectedPods`** | **1**(选得中) | **0**(选不中任何 Pod) |
| `disruptionsAllowed` | 0 | 0 |
| `reason` | `InsufficientPods` | `InsufficientPods` |

**两份的 `disruptionsAllowed` 都是 0、`reason` 都是 `InsufficientPods`,但根因完全不同**:

- 一个是"**选得中,但副本数不够**"(1 副本 + `minAvailable: 1`)
- 另一个是"**标签写错了,一个 Pod 都选不中**"

> **排查 PDB 问题的正确顺序:先看 `expectedPods`,再看 `currentHealthy`。**
>
> - `expectedPods = 0` → **selector 写错了**,去对 Pod 的标签
> - `expectedPods > 0` 但 `disruptionsAllowed = 0` → **数值设置问题**,去算 `minAvailable` 和副本数的关系

只盯着 `disruptionsAllowed: 0` 就下结论,会有一半的概率修错方向。

**PDB 与单副本的根本矛盾**

> **给一个单副本的工作负载配 `minAvailable: 1`,是在保护"零可用"。** 单副本本身就没有高可用可言 —— PDB 在这里**不可能**起到保护作用,它只能起到**阻断**作用。要想让 PDB 有意义,前提是**副本数 ≥ 2**。

**「面试可以怎么讲」**

> "PDB 有个很典型的坑,我用真实案例讲。我们有个单副本的工作负载配了 `minAvailable: 1` —— **算出来 `disruptionsAllowed` 是 0**,status 里原因是 `InsufficientPods`。后果非常具体:**节点驱逐永远返回 429,`kubectl drain` 会永久挂起**。这是个'写了个 PDB 反而把集群锁死'的坑,而且它特别隐蔽——`apply` 成功、`describe` 里 `MIN AVAILABLE: 1` 看起来完全合理,只有真去 drain 的时候才发现卡住,而那时你已经在做生产变更了。**`minAvailable` 等于副本数,等价于'永远不允许驱逐'。** 还有一个更深的点:我发现同样的 `disruptionsAllowed: 0`,有两种完全不同的根因——一种是副本数不够,另一种是 **selector 标签写错、`expectedPods` 是 0、一个 Pod 都没选中**。所以排查顺序应该是**先看 `expectedPods` 再看 `currentHealthy`**,只看 `disruptionsAllowed` 会有一半概率修错方向。"

### 4.6 调度约束:让 Pod 落到该落的节点上

**要解决什么问题**

集群有多个节点,特性不同(有的有 GPU、有的内存紧张)。怎么让 Pod 落到对的节点上?

**三种机制**

| 机制 | 方向 | 语义 | 强度 |
|---|---|---|---|
| **nodeSelector** | Pod → 节点 | 节点的**标签**必须完全匹配这几项 | 硬约束 |
| **nodeAffinity** | Pod → 节点 | 支持 `In`/`NotIn`/`Exists` 等操作符,以及 `preferred` 软偏好 | 硬 / 软 |
| **taints & tolerations** | 节点 → Pod | 节点标记"我排斥哪些 Pod",Pod 声明"我容忍哪些" | 硬约束 |

**关键区分(最容易混的一点)**

```
nodeSelector / affinity   =  Pod 说 "我想去哪"
taints / tolerations      =  节点说 "谁允许来"
```

**两者必须同时满足,Pod 才能落上去。** 一个是 Pod 的选择,一个是节点的准入,方向相反,不重叠。

**今晚的真实用法**

Jenkins 的构建 Pod(`ci/Jenkinsfile`):

```yaml
spec:
  nodeSelector:
    node-role: cpu
```

ArgoCD 的 `argocd-values.yaml`:

```yaml
global:
  nodeSelector:
    node-role: cpu
```

**为什么这么做(实测数据支持)**

| 节点 | 角色 | 内存使用(实测) |
|---|---|---|
| `agent-0` | **GPU 节点**(`nvidia.com/gpu: "true"`) | **6809Mi / 8GiB = 81%** |
| `agent-1` | **CPU 节点**(`node-role: cpu`) | 2396Mi / 8GiB = 28% |
| `server-0` | 控制面 | 1544Mi / 8GiB = 49% |

**理由**:

1. **构建 Pod 不请求 GPU。没有任何理由占用 agent-0。** 那是唯一带 GPU 的节点,而且它已经长期高负载(81%)。
2. **把工作负载放到内存宽松的节点上,是避免 OOM/驱逐最直接的手段。** 让 Jenkins 落到 agent-0,等于在一个已经 81% 的节点上再加 1~1.5GB —— 内存压力之下,kubelet 会开始驱逐。
3. **`node-role: cpu` 是集群里已有的约定**,不是新发明的标签(实测:集群里已有的 `Deployment/ollama` 就在用同一个 nodeSelector)。

**关于第 3 点,有一个 D7 里记下的教训值得重复**:

> **先看现场有什么约定,再决定新增什么。** 用自己的方式解决问题不算错,但和已有写法并存就是自找混乱。
>
> D7 原本写的是 `kubernetes.io/hostname: k3d-ai-cluster-agent-1`,实施时改成了 `node-role: cpu`。理由之一是**节点重建后名字会变,角色不会变** —— k3d 集群重建时 agent 的名字可能不同,但"CPU 节点"这个角色是稳定的。

**一个值得注意的组合风险(推论,未实测)**

`agent-0` 内存 81%。如果发生内存压力,kubelet 会驱逐 Pod 来回收内存 —— 而**驱逐走的是 Eviction API,是自愿中断,PDB 会介入**。如果被驱逐的对象恰好有 `disruptionsAllowed: 0` 的 PDB,驱逐会被拒(429),kubelet 只能去挑别的 Pod。

> **⚠️ 这条是推论,本项目未实测。** 写在这里是因为它是 4.5 和 4.6 两个知识点的交汇处,值得在真实环境里验证。**标注为待核实。**

**「面试可以怎么讲」**

> "调度的三种机制方向不同:`nodeSelector` 和 `affinity` 是 Pod 说'我想去哪',`taints` 和 `tolerations` 是节点说'谁允许来',两者必须同时满足。我们用 `node-role: cpu` 把 Jenkins 的构建 Pod 和 ArgoCD 钉在 CPU 节点上,理由是**唯一带 GPU 的那个节点内存已经占到 81% 了,而构建 Pod 不请求 GPU,没有任何理由占用它**——把它落到那个节点上,等于在内存紧张的时候再加一到 1.5G,直接触发 OOM 和驱逐。另外我们用 `node-role: cpu` 而不是主机名,是因为**节点重建后名字会变、角色不会变**。"

### 4.7 面试可以怎么讲(本节汇总)

**关于 PDB(背这一段)**

> "我们有个单副本的工作负载配了 `minAvailable: 1`,算出来 `disruptionsAllowed` 是 0,原因是 `InsufficientPods` —— 后果是**节点驱逐永远返回 429,`drain` 会永久挂起**。这是个'写了个 PDB 反而把集群锁死'的坑,而且 `describe` 里 `MIN AVAILABLE: 1` 看起来完全合理。**PDB 的数值必须相对副本数来设,`minAvailable` 等于副本数就是'永远不允许驱逐'。** 还有一点:同样的 `disruptionsAllowed: 0` 有两种根因 —— 副本数不够,或者 selector 写错导致 `expectedPods` 是 0,所以排查要先看 `expectedPods` 再看 `currentHealthy`。"

**关于滚动更新 + 探针(背这一段)**

> "滚动更新默认是 25%/25%,而 `maxUnavailable` **向下取整**——**3 副本时 25% × 3 = 0.75,取整之后实际是 0**,所以它永远是先起新 Pod 再停旧 Pod,可用副本数不会低于 3。但这个保护有个前提:**它依赖'就绪'这个信号是真的**。而**没有 readinessProbe 的时候,kubelet 认为 Pod 就绪的标准只是'容器进程起来了'**,它不知道应用能不能服务——所以'先起后停'的优雅顺序在没有探针时保护不了你。**探针是滚动更新语义的地基。**"

### B.3 本册的核心规律(背这五条)

> 1. **每一段只看得到自己的输出。接缝上的失败,两侧都看不见。**
> 2. **凡是以"当前状态 == 期望状态"表述的健康信号,都要先问:期望状态是谁的期望、哪个时刻的期望。**(`Synced` 陷阱)
> 3. **修好基础设施层不等于修好了消费方。** 改完上游,要按消费方逐个确认它什么时候才看得到。
> 4. **过程指标全绿不等于结果达成。** 验证必须去链路终点做,而且要用**独立的读取**,不能用写入命令自己的返回值。
> 5. **配置的权限范围应该等于它要做的事的范围 —— 不要大于。**(deploy key vs PAT;PDB 的 `minAvailable`;`imagePullSecrets` 的层级)
