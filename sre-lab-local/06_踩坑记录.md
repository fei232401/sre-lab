# 踩坑记录

> **这是什么**:按时间线记录**每一次报错和每一个"咦这怎么不对"**,不管大小。
>
> **为什么要记**:
> 1. **这类东西忘得最快**。三个月后你只会记得"当时好像有个坑",想不起是什么
> 2. **这最像真实工作**。运维岗一天的日常就是:出问题 → 查 → 解决 → 下次不再犯
> 3. **面试最爱问**。"你踩过什么坑"这个问题,有记录的人能讲十分钟,没记录的人只能说"遇到过一些兼容性问题"
>
> **记录标准**:不要求是"大坑"。命令打错、端口占用、镜像拉不下来、YAML 缩进错了——**全都记**。真实工作里 90% 的时间就花在这些上面。

### P<N> — <一句话现象>

## P1 — `helm list -A` 返回空,但资源上明明有 Helm 注解

- **日期**:2026-09-16
- **场景**:盘点本机 `k3d-ai-cluster` 里装了哪些东西,准备用 ArgoCD 接管
- **现象**:

  ```
  $ helm list -A
  NAME    NAMESPACE   REVISION   UPDATED   STATUS   CHART   APP VERSION
  (空,只有表头)
  ```

  但 `kubectl -n monitoring get deploy monitoring-grafana -o jsonpath='{.metadata.annotations}'` 明明显示:

  ```
  "meta.helm.sh/release-name": "monitoring",
  "meta.helm.sh/release-namespace": "monitoring"
  ```

- **排查过程**:
  1. 先怀疑 Helm 版本问题——本机 helm 是 **v4.3.0**,怀疑 v4 读不到 v3 格式的 release。**排除**:release secret 明明存在
  2. `kubectl -n monitoring get secret -l owner=helm` → 能看到 `sh.helm.release.v1.monitoring.v1` ~ `v4`,**release 数据在,是 Helm 没查到**
  3. 查 `kubectl config current-context` → **`k3d-topo-demo`** ← 破案

- **根因**:

  **Helm 和 kubectl 都隐式使用 kubeconfig 的「当前 context」。** 本机有三个 k3d 集群,当前 context 指向的是项目三的 `k3d-topo-demo`,不是 `k3d-ai-cluster`。**Helm 一直在查另一个集群**,当然是空的。

- **解法**:

  ```bash
  helm list -A --kube-context k3d-ai-cluster
  # NAME        NAMESPACE    REVISION  STATUS    CHART
  # monitoring  monitoring   4         deployed  kube-prometheus-stack-87.19.1
  # traefik     kube-system  1         deployed  traefik-27.0.201+up27.0.2
  # traefik-crd kube-system  1         deployed  traefik-crd-27.0.201+up27.0.2
  ```

- **经验**:

  > **多集群环境下,不带 `--context` 的命令是静默事故的主要来源。**

  它最危险的地方在于:**不报错,只是安静地作用在错误的集群上**。`kubectl delete` 少写了 `--context`,删的就是另一个集群的东西。

  **已写进本项目的 runbook 纪律:所有 `kubectl` / `helm` 命令显式带 `--context`。**

- **面试可以怎么讲**:

  > "多集群环境里我遇到过最阴的一个坑,是没有显式指定 context。`helm list` 返回空,但资源明明在——因为它查的是另一个集群。这个坑的危险在于它不报错。后来我在所有脚本里强制显式带 context,并且用 `kubectl config use-context` 切换到哪就说清楚。"

- **额外收获**:这次排查顺带确认了 `monitoring` 命名空间是 **Helm 管理**的,而 `ai-platform` 是**手工 apply** 的——**两种管理方式意味着 ArgoCD 接管需要两套策略**(见 D4 / M1)。

## P2 — 6 个 Pod 烂了 30 天,`kubectl get pods` 的表头看着干干净净

- **日期**:2026-09-16
- **场景**:M0 盘点存量集群,准备用 ArgoCD 接管
- **现象**:

  ```
  ai-platform   vllm-3b-7c59d66664-ddppp   0/1   ContainerStatusUnknown    5d
  ai-platform   vllm-3b-7c59d66664-t4jlb   0/1   UnexpectedAdmissionError  3d7h
  ...
  ```

  而 `kubectl get deploy vllm-3b` 报的是 `1/1 READY`。

- **排查过程**:
  1. 先查 ReplicaSet 的计数 → `{"replicas":1, "readyReplicas":1}` — **RS 认为一切正常**
  2. 查 Pod 的 `deletionTimestamp` 和 `finalizers` → 都是空,不是"卡在删除中"
  3. 逐条比对 kube-prometheus-stack 的默认规则表达式 → **发现没有任何一条能匹配 `phase=Failed`**
  4. 确认 PodGC 阈值 → 默认 `--terminated-pod-gc-threshold=1250`,6 ≪ 1250

- **根因**:**四层机制互相以为对方会管。**

  | 层 | 为什么没动手 |
  |---|---|
  | `KubePodNotReady` | phase 白名单是 `Pending\|Unknown` 或 `Running 但 ready=0`,**不含 `Failed`** |
  | `KubePodCrashLooping` | 查 `reason="CrashLoopBackOff"`,而终态准入失败的容器**从未进过 waiting** |
  | ReplicaSet 控制器 | 只数**活跃** Pod,Failed 不算活跃;补到 1 个就走,**不管清理** |
  | PodGC 控制器 | 只在**全局终态 Pod > 1250** 时才清理 |
  | 人 | Alertmanager receiver 是 `null`(见 P4) |

- **解法**(M2 实施):补一条默认集里不存在的规则

  ```promql
  kube_pod_status_phase{phase="Failed"} == 1
  ```

- **经验**:

  > **`UnexpectedAdmissionError` 有"隐蔽性三连":不重试、不 CrashLoop、不累积 restartCount。**

  三种最常见的"Pod 坏了"信号它**一个都不触发**。运维排查时,`STATUS` 列比 `READY` 列重要得多——`0/1` 可能是暂时的,`UnexpectedAdmissionError` 是**终态**。

  更普适的规律:**"默认告警规则集覆盖了什么"和"哪些故障模式存在"是两个集合,它们的差集就是你的盲区。** 装完监控栈必须主动去算这个差集,不能假设它覆盖全了。

- **面试可以怎么讲**:

  > "我接手一个跑了 43 天的集群,发现 6 个 Pod 烂了最多 30 天没人管。奇怪的是所有告警规则都在、Prometheus 也在正常求值。查下来是:`UnexpectedAdmissionError` 是**终态失败**,而 kube-prometheus-stack 默认的三条 Pod 告警规则——`KubePodNotReady` 的 phase 白名单里没有 `Failed`,`KubePodCrashLooping` 只认 CrashLoopBackOff,`KubeContainerWaiting` 只认 waiting 容器——**一个都匹配不上**。加上 ReplicaSet 只管补数不管清理、PodGC 阈值是 1250,四层机制互相以为对方会管,这就是它能烂 30 天的完整原因。」

- **关联**:P3(真因)、P4(为什么没人知道)、M2 降噪补规则

## P3 — Pod 被 kubelet 拒绝,报的是 "no healthy devices present"

- **日期**:2026-09-16
- **场景**:排查 P2 里那 6 个僵尸 Pod 的真因
- **现象**:

  ```
  Pod was rejected: Allocate failed due to no healthy devices present;
  cannot allocate unhealthy devices nvidia.com/gpu, which is unexpected
  ```

  第一反应是"WSL 里没有 GPU,所以 vllm 起不来"。

- **排查过程**:
  1. 查节点 allocatable → `nvidia.com/gpu: 1` **存在**,不是没有
  2. 查 device plugin 日志 → `Registered device plugin for 'nvidia.com/gpu' with Kubelet` 正常注册
  3. **但同一时刻有一个 vllm Pod 是 Running 的**,而且只跑了 111 分钟,restartCount 为 0
  4. 对时间戳:
     ```
     device plugin 注册:  I0915 14:24:57
     vllm Pod 启动:      2026-09-15T14:25:02Z   ← 间隔 5 秒
     ```
  5. 拉 6 个僵尸的创建时间 → 08-16 / 08-28 / 09-08 / 09-09 / 09-10 / 09-12,与全集群 restartCount 剧增的时间点吻合

- **根因**:**GPU 有一段时间被标记为不健康,而不是没有 GPU。**

  WSL2 通过 `/dev/dxg` 直通 GPU。每次 WSL 重启后,nvidia-device-plugin 重新探测设备,**"已注册"和"健康检查通过"之间有一个几秒的窗口**。此刻 ReplicaSet 正在补 vllm 的 Pod,而它带 `nvidia.com/gpu` 请求 → kubelet admission 时设备不健康 → **拒绝并置为终态 Failed**。

  窗口只有几秒,所以每次重启通常只留下一具尸体——**这正好解释了为什么是 6 个而不是 60 个**。

- **解法**:无(环境固有特性)。**正确做法是让它可见**——加一条规则把 `UnexpectedAdmissionError` 报出来,人就能立刻知道"又抖了一次"。

- **经验**:

  > **"设备不健康"和"设备不存在"是两种完全不同的故障,但都表现为 Pod 起不来。**

  排查时不要停在 `describe pod` 的错误信息上。这次如果停在 "no healthy devices present" 就下结论"WSL 没 GPU",会**完全错过真因**,而且会得出"这是环境问题没法修"的错误结论——实际上它是**可观测性问题**,有解。

- **面试可以怎么讲**:

  > "我们的推理服务每天莫名其妙挂一次,报错是 GPU 设备不可用。查下来不是卡坏了,是 device plugin 在节点重启后有一小段窗口,设备已注册但健康检查还没过,这时候创建 Pod 就在 admission 阶段被拒了——而且这个拒绝在 Kubernetes 里是**终态**,调度器不会重试。所以它不是'偶发失败',是'一次失败永久卡住'。后面我给这类终态加了专门的告警。"

- **关联**:P2(这批 Pod 为什么没人清理)

## P4 — 所有告警都进了黑洞,因为 receiver 叫 "null"(**但它不是疏漏**)

- **日期**:2026-09-16
- **场景**:P2 排查到"为什么没人发现",去看 Alertmanager
- **现象**:

  ```yaml
  receivers:
  - name: "null"
  route:
    receiver: "null"
  ```

- **排查过程**:
  1. 先确认规则**在不在**——`/api/v1/rules` 列出 190+ 条,`lastError: 0`,规则健康
  2. 再确认规则**响没响**——`/api/v1/alerts` 返回 **39 条** firing/pending
  3. 最后看 Alertmanager 配置——**`receivers:` 里只有一个叫 `null` 的空接收器,`route.receiver` 指向它**

- **根因**:**两层,第一层是技术,第二层是人的决策。**

  技术上:`null` 是 **kube-prometheus-stack 的出厂默认值**。图表作者故意不给可用 receiver,强制用户自己填。

  **但真正的原因不在这。** 排查到这里我下的结论是"前一位同事装完忘了配"——**这个结论是错的**。

  问过当事人后得知:**当时是主动把告警打进黑洞的**。背景是:那个阶段频繁收到无效告警,而项目当时刚好完工、集群也不需要维护,与其让一堆没意义的通知一直响,不如索性全推黑洞。

  > **教训:判断"为什么是这样",不能只看现状,还得问当时的人。**
  >
  > 现状能告诉你 `receiver: "null"`,但告诉不了你它是**"忘了配"**还是**"故意配的"**。
  >
  > 这两种情况的解法完全不同:
  > - 如果是**忘了配** → 配上 receiver 就完事了
  > - 如果是**故意打的** → 得先问"为什么会有那么多无效告警",**先把噪音解决掉,再接通道**
  >
  > 我一开始按前者理解,差点直接去接微信——那样做等于让这位同事的处境重来一遍。

- **解法**(M2,**分两步,顺序不能反**):

  1. **先降噪**:实测出"永远在响"的是哪几条,从源头关掉(见 P5)
  2. **再接通道**:降噪做完之后才配真实 receiver,走**企业微信机器人 webhook**

- **经验**:

  > **"告警规则存在" ≠ "告警会送达"。** 验证一条告警链路要**端到端**验,至少四段:规则求值 → Prometheus 推送 → Alertmanager 路由 → 接收方收到。任何一段断了,前面三段都看不出来。

  这次前三段**全部健康**——规则在求值、Prometheus 在推送、Alertmanager 在分组抑制。**唯一的断点是最后一跳**,而它不报错、不告警、界面上看不出来。

  和 P1 是**同一类错误的不同形态**:
  > P1 是 `kubectl` 静默作用在错误的集群上;**P4 是告警静默流进一个什么都不做的接收器。** 都是"不报错的错误"。

  但两者的**成因类别**不同,这个区分很重要:

  | | P1 | P4 |
  |---|---|---|
  | 性质 | **意外**——没意识到多集群的隐式 context | **决策**——知道,但当时有理由这么干 |
  | 对策 | 加 `--context` 纪律 | 先解决"为什么想关掉它",再谈打开 |

  **把所有"不报错的错误"都归为"意外",是排查里的一种偷懒。**

- **面试可以怎么讲**:

  > "我巡检的时候发现集群装了完整的 kube-prometheus-stack,190 多条告警规则,几十条正在 firing——但 Alertmanager 的 receiver 是图表默认的 `null`。我第一反应是'前一位同事忘了配',但去问了一下才知道:**那是他主动关的**——因为当时无效告警太多,而项目已经完工、集群不需要维护。
  >
  > 这个回答直接改变了我的方案。如果只是忘配,接上 receiver 就完了;但既然是因为噪音才关的,那我就得**先把噪音解决掉再接通道**,否则他几周后还会做出同一个决定。所以我先去实测哪几条告警是永远在响的,从源头关掉三条,把 firing 数从 39 降到 1,然后才动接收端。
  >
  > 这件事让我记住:**接手别人的系统时,'为什么是这样'的答案往往不在系统里,在人那里。**"

- **⚠️ 后补(2026-09-16,实测)**:上面这条排查**还有第三层**,当时没查到——`k3s-kubeproxy-silence.yaml` 那份文件是**静默失效**的,一条都压不住。详见 P8。

- **关联**:P1(同属"不报错的错误")、M2

## P5 — 装了监控栈之后,有 3 条告警从第一天起就永远在响

- **日期**:2026-09-16
- **场景**:P4 排查时顺手看 full alert 列表
- **现象**:

  | 状态 | 告警 |
  |---|---|
  | firing | `KubeControllerManagerDown` |
  | firing | `KubeSchedulerDown` |
  | firing | `KubeProxyDown` |
  | firing | `AlertmanagerClusterCrashlooping` |

- **排查过程**:
  1. 查这三个组件在集群里是不是真挂了 → `kubectl get pods -n kube-system`,**根本没有这三个 Pod**
  2. 查 k3s 架构 → k3s 把 controller-manager / scheduler / kube-proxy **编译进单个 `k3s server` 进程**,不作为独立 Pod 运行

- **根因**:**kube-prometheus-stack 的默认规则是照标准 kubeadm 集群写的**,假设这三个组件是独立 Pod 并有独立 metrics 端点。k3s 不满足这个假设,于是 `absent(up{job="kube-proxy"} == 1)` 永远为真,**永远 firing**。

  `AlertmanagerClusterCrashlooping` 同理——单副本部署不满足它要求的集群一致性条件。

- **解法**(M2,**必须先于接微信**):在 Helm values 里关掉对应规则,或在 Alertmanager 层加抑制/黑洞路由。

- **经验**:

  > **告警噪声比没有告警更危险。**

  没有告警,人知道自己没被保护;有 3 条永远在响的假警报,人会**学会忽略告警**。等真出事的时候,真警报混在假警报里被一起忽略掉。

  这在 SRE 里有名字:**告警疲劳(alert fatigue)**,是公认的头号告警失效模式。

  **所以正确顺序是:先降噪,再接通道。** 反过来做,等于亲手毁掉这套告警的可信度——第一天收到 3 条假警报,第三天就没人看了。

- **面试可以怎么讲**:

  > "我在 k3s 上装 kube-prometheus-stack,发现 `KubeProxyDown`、`KubeSchedulerDown`、`KubeControllerManagerDown` 三条从装上那天就在响。原因是 k3s 把控制面组件编译进单进程了,而 kube-prometheus-stack 的默认规则是照 kubeadm 集群写的,假设它们是独立 Pod。这三条不是配置错误,是**架构不匹配**——所以修法不是在 PromQL 里绕,是在 Helm values 里按集群形态剪裁规则集。接告警通道之前必须先做这件事,不然收到的是永不停止的假警报,几天内人就开始忽略告警了。"

- **关联**:P4、M2

## P6 — 精心写的告警补丁,标签少写一个,等于没写

- **日期**:2026-09-16
- **场景**:M1 审计存量 GitOps 目录,检查 `k3s-alert-patches.yaml` 能不能用
- **现象**:这份 `PrometheusRule` 定义了 `k3s-alert-overrides`,内容看起来很对——用同名规则覆盖 `KubeProxyDown` 的默认表达式。但它从未生效过。

- **排查过程**:
  1. 先看它带的标签:
     ```yaml
     labels:
       prometheus: kube-prometheus
       role: alert-rules
       app.kubernetes.io/part-of: kube-prometheus-stack
     ```
  2. 再看 Prometheus 实例**实际**用什么选规则:
     ```
     ruleSelector: {"matchLabels":{"release":"monitoring"}}
     ```
  3. **对不上。** 没有 `release: monitoring` → `PrometheusRule` 永远不会被加载
  4. 对照集群里**确实生效**的那条规则:`labels` 里有 `"release": "monitoring"` ← 差异确认

- **根因**:

  **Prometheus Operator 不会自动加载所有 `PrometheusRule` 对象——它按 `ruleSelector` 挑。**

  这是**白名单机制**:标签没匹配上,对象静静地躺在 etcd 里,`kubectl get prometheusrule` 看得见,但 Prometheus 完全不知道它的存在。

  这**不是配置错误,是设计如此**——`ruleSelector` 存在的意义就是让多个 Prometheus 实例共享集群时各管各的规则。

- **解法**:

  ```yaml
  labels:
    release: monitoring
  ```

  **同一类坑还有两处**:
  - `ServiceMonitor` 同样受 `serviceMonitorSelector` 约束,本项目里也踩过
  - `k3s-kubeproxy-silence.yaml` 的 `AlertmanagerConfig` 带的是 `release: kube-prometheus-stack`,而该项目实际用的是 `monitoring`——**名字像但不相等**

- **经验**:

  > **在 Prometheus Operator 的世界里,"对象创建成功"和"配置生效"是两件事。**

  `kubectl apply` 返回成功 ≠ 规则生效。中间隔着一个标签选择器。
  **每次新建 `PrometheusRule` / `ServiceMonitor` / `AlertmanagerConfig`,第一件事就是去对 Prometheus/Alertmanager 实例的选择器。**

  验证方法(**别猜,去查**):

  ```bash
  kubectl -n monitoring get prometheus <name> -o jsonpath='{.spec.ruleSelector}'
  kubectl -n monitoring get prometheus <name> -o jsonpath='{.spec.serviceMonitorSelector}'
  kubectl -n monitoring get alertmanager <name> -o jsonpath='{.spec.alertmanagerConfigSelector}'
  ```

  更省事的自检:去 Prometheus UI 的 **Status → Rules** 页面搜你的规则名。**搜不到就是没加载**,不用怀疑人生。

- **面试可以怎么讲**:

  > "我遇到过一条告警规则,写得很对、apply 也成功、`kubectl get` 也看得到,但它从来没生效过。查下来是 Prometheus Operator 的 `ruleSelector` 是个白名单,我漏了 `release: monitoring` 这个标签,规则就静静躺在 etcd 里,Prometheus 完全不知道它存在。**这类问题没有任何报错**——`apply` 返回成功,对象状态也正常。所以我后来养成了习惯:新建规则后一定去 Prometheus 的 Rules 页面搜一下,确认它真的被加载了。"

- **关联**:P1 / P4(同属"不报错的错误")、M0 的 `k3s` 假阳性、M1 审计雷 3 / 雷 4

## P7 — 用同名告警规则去"覆盖"默认告警,实测证明根本行不通

- **日期**:2026-09-16
- **场景**:M1 审计发现 `k3s-alert-patches.yaml` 想用一条同名 `PrometheusRule` 覆盖 `KubeProxyDown`。第一反应是"它标签写错了所以没生效",准备把标签补上。
- **转折**:补标签之前先问了一句——**如果标签对了,它真的能覆盖吗?**

- **实验设计**(零风险探针):

  `Watchdog` 是 kube-prometheus-stack 里**设计上永远 firing** 的告警(死信开关,表达式就是 `vector(1)`)。用它当探针:注入一条同名 `Watchdog`、表达式 `vector(0)` 的规则,看能不能把它"杀掉"。

  ```yaml
  apiVersion: monitoring.coreos.com/v1
  kind: PrometheusRule
  metadata:
    name: m1-experiment-override
    namespace: monitoring
    labels:
      release: monitoring        # 标签是对的,确保会被加载
  spec:
    groups:
      - name: m1.experiment
        rules:
          - alert: Watchdog
            expr: vector(0)
  ```

- **结果**:

  ```
  Prometheus 里名为 Watchdog 的规则:2 条   ← 并存,不是替换
  [m1.experiment]  expr='vector(0)'  → 活跃告警 0
  [general.rules]  expr='vector(1)'  → 活跃告警 1   ← 默认的照样在响
  ```

  **默认告警毫发无伤。**

- **根因**:

  **Prometheus 的告警是"并列求值",不存在覆盖语义。**

  每条规则独立求值;`alertname` 只是标签之一,不是主键。两条同名规则**同时存在、同时求值**。默认那条的表达式是真的,告警就是真的——另一条规则**没有任何机制能取消它**。

- **解法**:

  要消除一条告警,只有三条路:

  | 方案 | 做法 | 评价 |
  |---|---|---|
  | **停掉规则来源** | 在 Helm values 里关掉对应组件的 `enabled` | ✅ **最干净**,连 scrape target 一起消失 |
  | **Alertmanager 静默** | 在路由/静默层拦截 | ✅ 有效,但规则仍在求值(白烧 CPU) |
  | ~~同名规则覆盖~~ | — | ❌ **不成立** |

- **经验**:

  > **"用同名对象覆盖配置"这个模式,在不同系统里的语义完全不同。**

  - 在 **Kubernetes** 里:同名对象是**替换**(`kubectl apply` 覆盖)
  - 在 **Helm** 里:是同 release 的**升级**
  - 在 **Prometheus** 里:是**并存**,什么都覆盖不了

  **换一个系统就要重新问一次"这里的覆盖语义是什么",不能想当然。**

  这条思路如果没验证就写进文档,就会变成一个**看起来很有道理、实际完全不工作**的方案——比明显报错的 bug 危险得多。

- **面试可以怎么讲**:

  > "我们集群里 k3s 有三条控制面告警永远在响,因为 k3s 把组件编译进单进程了。前一位同事写了一版补丁,想用同名 PrometheusRule 覆盖默认规则。我发现它标签写错了所以没被加载,本来打算修标签——但修之前我先做了个实验:注入一条同名 `Watchdog`、表达式恒假的规则,看能不能把永远 firing 的 Watchdog 杀掉。结果是**杀不掉,两条规则并存求值**。所以那个补丁就算标签修对了也没用,整个思路是不成立的。最后改成在 Helm values 里直接关掉组件。"

- **关联**:P6(标签选择器)、M1 审计雷 3、M2 降噪

## P8 — 那份"屏蔽 k3s 假阳性"的文件,一次都没生效过

- **日期**:2026-09-16
- **场景**:M1 审计时发现 `production/monitoring/k3s-kubeproxy-silence.yaml`,是一份 `AlertmanagerConfig`,本意是把三条 k3s 假阳性告警打进黑洞。P6 里已经发现它**标签写错**(`release: kube-prometheus-stack` ≠ 实际的 `monitoring`)。在修标签之前,我决定先把它的机制彻底搞懂。
- **现象**:文件长这样,看起来完全合理:

  ```yaml
  spec:
    route:
      receiver: 'blackhole'
      matchers:
        - name: alertname
          value: KubeProxyDown|KubeSchedulerDown|KubeControllerManagerDown
          matchType: =~
      continue: false
  ```

- **排查过程**:
  1. 把标签修对的**假设情况下**,这份 `AlertmanagerConfig` 会被 operator 翻译成什么路由?
  2. 去读 prometheus-operator 的源码 `pkg/alertmanager/amcfg.go`,发现有个 `namespaceEnforcer`
  3. 看它对每条子路由做什么:

     ```go
     func (ne *namespaceEnforcer) processRoute(crKey types.NamespacedName, r *route) *route {
         r.Matchers = append(r.Matchers, Matcher{
             Name: "namespace", Value: crKey.Namespace, MatchType: MatchEqual,
         }.String())
         return r
     }
     ```

  4. 也就是说,operator 会**强行塞进一个 `namespace = "monitoring"` 的 matcher**,不管我写没写
  5. 那三条告警的 label 里**有 `namespace` 吗**?`kubectl -n monitoring get prometheus -o jsonpath='{.spec.externalLabels}'` → **空**。告警的 label 集里根本没有 `namespace` 这一项

- **根因**:

  **这份文件从头到尾就没有生效过,而且就算标签修对了也依然不会生效。**

  两个原因叠加,任一条单独成立就足以让它失效:

  | 层 | 问题 |
  |---|---|
  | 标签层(P6 已发现) | `release` 标签不匹配 `alertmanagerConfigSelector`,对象压根没被 operator 读取 |
  | **语义层(本次发现)** | **就算被读取了**,operator 注入的 `namespace` matcher 也匹配不上没有该 label 的告警 |

  而 **matcher 对不存在的 label 一律判定为不匹配**——不是"空字符串",是不匹配。

- **解法**:这份文件**删除**。同等需求由 P5 的解法(Prometheus 侧从源头关掉组件)覆盖,更彻底——连求值都不做了。

- **经验**:

  > **一份"看起来对"的失效配置,比完全没有配置更危险。**

  没有配置的时候,你至少知道这里有个洞,会去想办法。而仓库里躺着一份 `k3s-kubeproxy-silence.yaml`,任何后来的人(包括三个月后的自己)翻到它,都会得出"这个问题已经处理过了"的结论。

  **它的危害不是"没起作用",是"让人以为它起作用了"。**

  更普遍地说:**验证一份配置是否生效,不能看它写得好不好,要看它作用的那一层真正读到了什么。** 这次就是要一路追到 operator 源码里,才知道它被翻译成了什么。

- **面试可以怎么讲**:

  > "接手项目时我在仓库里发现一份 AlertmanagerConfig,专门用来屏蔽三条 k3s 的假阳性告警——写得很规范。但我查下来发现它**从来没生效过**,而且是两层失效叠加:一是标签没匹配上 operator 的选择器,二是就算匹配上了也还是不行——prometheus-operator 有个 `namespaceEnforcer`,会往每条 AlertmanagerConfig 生成的子路由里强制注入一个 `namespace` matcher,而那三条告警的 label 里根本没有 `namespace`,matcher 对缺失的 label 是不匹配的。所以这份文件的作用是让人以为问题已经解决了。我的处理是删掉它,改从 Prometheus 侧把这三个组件的规则整组关掉,更彻底。"

- **附带收获**(以后用 AlertmanagerConfig 必知):`alertmanagerConfigSelector: {}` 是**匹配全部**还是匹配空?去读 `apimachinery` 的 `LabelSelectorAsSelector`:

  ```go
  if ps == nil {
      return labels.Nothing(), nil     // nil → 什么都不匹配
  }
  if len(ps.MatchLabels)+len(ps.MatchExpressions) == 0 {
      return labels.Everything(), nil  // {} → 匹配全部
  }
  ```

  **`{}` = 匹配全部。** 这是 M3+ 如果用 AlertmanagerConfig 做路由的前提。

- **关联**:P6(同属"对象存在 ≠ 配置生效")、P7、P5、M2 降噪

## P9 — 一条"测时钟偏差"的 PromQL,测的其实是样本年龄

- **日期**:2026-09-16
- **场景**:排查 `AlertmanagerClusterCrashlooping` 为什么在响。调研给出的结论是"不是真重启,是 k3d/WSL2 的节点时钟漂移",证据是这条查询:

  ```promql
  node_time_seconds - time()
  → 三个节点分别 -7.5 / -15.4 / -26.9 秒
  ```

  秒级偏差,看起来很像时钟漂移。

- **排查过程**:
  1. 我复查了这条查询。多刷几次,发现**同一台机器的值每次都不一样**(-12.81 / -1.30 / -23.32)
  2. 时钟漂移应该是**稳定**的——一台机器的偏移量不会每分钟变十几次
  3. 那这个波动的数字是什么?去看这两个函数各自的语义:
     - `time()` = **查询求值的那一刻**
     - `node_time_seconds` = 该指标**被抓取的那一刻**记录的节点时间
  4. 所以 `node_time_seconds - time()` = **"抓取时刻" 减 "当前时刻"** = **这个样本有多旧**
  5. 换个写法验证:

     ```promql
     node_time_seconds - timestamp(node_time_seconds)
     → +0.006 / +0.008 / +0.018 秒
     ```

  `timestamp()` 返回的是**该样本的抓取时刻**。用它和小数点后的节点时间相减,才是真正的时钟偏差。

- **根因**:

  **`metric - time()` 得到的是"样本年龄",不是"指标值与当前时间的差"。**

  两者长得几乎一样,含义完全不同:

  | 写法 | 实际含义 | 用途 |
  |---|---|---|
  | `node_time_seconds - time()` | 样本年龄(抓取距今多久) | 差不多等于 scrape interval,用来发现抓取异常 |
  | `node_time_seconds - timestamp(node_time_seconds)` | **真正的时钟偏差** | 检测节点时钟漂移 |

  **实测结论:时钟是亚 20 毫秒级同步的,根本没有漂移。** "时钟漂移"这个根因是错的。

- **解法**:无需修复(PromQL 是错的,不是环境是错的)。改用 `timestamp()` 版本的查询重新确认。

- **经验**:

  > **`timestamp()` 是"指标里的时间"和"抓取这个指标的时间"之间的桥。**

  PromQL 里的 `time()` 永远是"现在",它和任何指标相减,得到的都是**这个指标有多旧**,而不是这个指标"说得对不对"。

  但要记的规律比这一条更大:

  > **一个"看起来合理"的因果解释,如果不实测验证,就会变成文档里的幻觉。**

  "时钟漂移导致指标异常"这个解释**太顺了**——k3d/WSL2 确实有时钟问题,数字确实是秒级,连方向都对(节点时间落后于现在)。它唯一缺的就是**它是错的**。

  这次好在是在**写进交付文档之前**复查了一遍。如果直接抄进报告,这份文档就会带着一个错误的根因流传下去,而且因为它逻辑自洽,后面的人很难发现。

- **面试可以怎么讲**:

  > "调查一个告警的根因时,拿到一个'节点时钟漂移'的结论,证据是 `node_time_seconds - time()` 显示三台机器分别慢了 7 到 27 秒。我没有直接采信,而是多刷了几次——发现同一台机器的数字每次都在变,几分钟内从 -12 变到 -23。时钟漂移应该是稳定的,会剧烈波动的数字说明我量错了东西。查下来:`time()` 是查询求值时刻,而 `node_time_seconds` 是抓取时刻的值,两者相减得到的是**样本年龄**,不是时钟偏差。换成 `node_time_seconds - timestamp(node_time_seconds)` 之后,三台机器是 **6 到 18 毫秒**,完全正常。那个根因是不成立的。"

- **关联**:P4 / P1(同属"不报错的错误"——一个错误的查询不会报错,它只会给你一个言之凿凿的错误答案)、M2 审计

## P10 — ArgoCD 报"同步失败",其实三分钟前就自己好了

- **日期**:2026-09-16
- **场景**:ArgoCD 接管 `sealed-secrets` Application 后,去查同步结果
- **现象**:`Application` 的状态里有报错,提示拉取 Git 仓库失败,伴随一条日志:

  ```
  grpc.time_ms=15001.801
  ... Client.Timeout exceeded while awaiting headers
  ```

  15 秒零 1 毫秒——**卡在超时上了**。当时我的判断是"GitHub 连不上,网络有问题,这是个持久故障"。

- **排查过程**:
  1. 先确认超时是不是可配的——翻 `argocd-repo-server` 的启动参数和可用的环境变量:

     ```bash
     grep -ao 'ARGOCD_REPO_SERVER_[A-Z_]*' /usr/local/bin/argocd-repo-server | sort -u
     ```

     **没有任何和 Git 操作超时相关的变量。**
  2. 那就先强制刷一次再说:

     ```bash
     kubectl --context k3d-ai-cluster -n argocd annotate application sealed-secrets \
       argocd.argoproj.io/refresh=hard --overwrite
     ```
  3. **秒变 Synced。**
  4. 回头去查被接管对象的创建时间:

     ```
     Deployment sealed-secrets-controller 创建于 16:44:33
     ```

     也就是说——**它早就成功了。我查到那条报错的时候,它已经同步完成。**

- **根因**:

  **不是持久故障,是一次冷连接的瞬时超时,而 ArgoCD 自己重试成功了。**

  ArgoCD 默认大约每 3 分钟重新对账一次。第一次拉取要建新连接(DNS + TLS 握手),在 WSL2 + 国内网络环境下偶尔会超过那个硬编码的 15 秒窗口。**下一次重试连接是热的,就过去了。**

  我犯的错是:**在重试还没发生之前就去查了结果,然后把这个瞬时状态当成了稳态。**

- **解法**:无需修复。重试机制本身就是为此设计的。

- **经验**:

  > **判断"故障"和"尚未成功的中间态"之前,先看时间戳。**

  ArgoCD 是个**收敛式控制器**——它的设计前提就是"失败会重试"。所以看到一次失败,第一件事应该是**等一个对账周期再确认**,而不是立刻下结论。

  这条对排查习惯的影响更大:

  > **一次采样 = 一个瞬时快照,不等于系统状态。**

  我同时也在这次会话里踩到了它的镜像版本(P9:一次查询 = 一个错的答案)。两次的教训是同一个:**不要用单次观测去断言一个持续性的结论。**

  有个简单便宜的办法:看**这个状态持续了多久**。ArgoCD 的 `Application` 状态里带时间戳,失败如果是几分钟前的、且期间没有新的失败,大概率已经自愈了。

- **面试可以怎么讲**:

  > "用 ArgoCD 接管资源的时候,我查到一条同步失败,日志显示卡在一个 15 秒的 Git 拉取超时上。我当时的判断是网络不通,准备去排查网络。但先去做了件事:强制 refresh 一次——结果立刻变 Synced。回头看部署的时间戳,发现那次同步其实**三分钟前就成功了**,我查到的是一个已经被重试覆盖掉的中间状态。ArgoCD 是个收敛式控制器,失败重试是它的正常工作方式,所以看到一次失败不该就下结论,而应该等一个对账周期再看。这个坑让我改进了一个习惯:**看状态的时候顺手看它持续了多久**,瞬时快照不代表系统状态。"

- **关联**:P9(同属"单次观测 ≠ 稳态")、M1

## P11 — promtail 挂了一个永远是空的日志目录,而它不报错

- **日期**:2026-09-16
- **场景**:M1 接管 `promtail` 后核对它的实际运行状态
- **现象**:DaemonSet **3/3 Ready**,看起来完全正常。但去看它挂了什么卷:

  ```
  pods-logs   -> /var/log/pods              (13 项,真实有内容)
  docker-logs -> /var/lib/docker/containers (0 项,永远是空的)
  ```

- **排查过程**:
  1. 进节点实跑,确认两个路径的状态:

     ```
     /var/lib/docker/containers  → 存在,但 0 项
     /var/log/pods               → 存在,13 项
     ```

  2. 这就矛盾了——为什么 Docker 的日志目录是空的?
  3. 查本集群的容器运行时 → **k3s,用的是 containerd,不是 Docker**
  4. 两边的日志落点完全不同:

     | 运行时 | 容器日志路径 |
     |---|---|
     | Docker | `/var/lib/docker/containers/<id>/<id>-json.log` |
     | containerd | `/var/log/pods/<ns>_<pod>_<uid>/<container>/*.log` |

  5. 最后核对 promtail 自己的抓取配置,看它**实际**用了哪个:

     ```yaml
     - job_name: kubernetes-pods
       # __path__ 只用了这个:
       - replacement: /var/log/pods/*$1/*.log
     ```

- **根因**:这份清单是**照 Docker 集群写的**,而本集群跑的是 containerd。那个 `docker-logs` 挂载点从装上那天起就是空的。

- **解法**:本次不动(改它要重新同步,收益只是删一个空挂载)。记为待清理项。

- **影响评估**:**不影响运行** —— 真正的采集路径 `/var/log/pods` 是通的,日志收得到。

  但它有**误导性**:看清单的人会以为日志是从 docker 目录采的;排障时可能去查一个根本不相干的路径,然后得出"日志采集配置有问题"的错误结论。

- **经验**:

  > **"Pod 是 Running 的"不能证明"它的每个配置项都是对的"。**

  这一条和 P8 是**同一个模式的两个实例**:

  | | P8 | P11 |
  |---|---|---|
  | 失效的东西 | 告警静默的标签 | 日志采集的挂载点 |
  | 为什么不报错 | 标签不匹配只是"不加载",不是错误 | 挂载不存在的路径只是"空目录",不是错误 |
  | 危害 | 以为假阳性处理过了 | 以为知道日志从哪来 |

  **共性:配置里有一部分静默地不起作用,而系统的健康状态完全看不出来。** 这类问题只能靠"逐项核对配置的实际语义"发现,不能靠看状态灯。

- **面试可以怎么讲**:

  > "我接管一个日志采集组件时发现它挂载了两个日志目录:一个 `/var/log/pods`,一个 `/var/lib/docker/containers`。第二个是空的。原因是那份清单是照 Docker 集群写的,而这个集群用的是 containerd——两个运行时的容器日志落点完全不同,Docker 写 `/var/lib/docker/containers`,containerd 写 `/var/log/pods`。不影响运行,因为真正生效的是第一条路径,但它在清单里留了个误导:下次有人排日志问题会去查一个死路径。**这件事让我意识到,'Pod 是 Running' 和 '配置是对的' 是两个独立的判断,后者必须逐项去核。**"

- **关联**:P8(同为"静默失效的配置")、P1 / P4(同为"不报错的错误")、M1 接管
