# 踩坑记录

> **这是什么**:按时间线记录**每一次报错和每一个"咦这怎么不对"**,不管大小。
>
> **为什么要记**:
> 1. **这类东西忘得最快**。三个月后你只会记得"当时好像有个坑",想不起是什么
> 2. **这最像真实工作**。运维岗一天的日常就是:出问题 → 查 → 解决 → 下次不再犯
> 3. **面试最爱问**。"你踩过什么坑"这个问题,有记录的人能讲十分钟,没记录的人只能说"遇到过一些兼容性问题"
>
> **记录标准**:不要求是"大坑"。命令打错、端口占用、镜像拉不下来、YAML 缩进错了——**全都记**。真实工作里 90% 的时间就花在这些上面。

### P<N> — <一句话现象>

## P1 — `helm list -A` 返回空,但资源上明明有 Helm 注解

- **日期**:2026-09-16
- **场景**:盘点本机 `k3d-ai-cluster` 里装了哪些东西,准备用 ArgoCD 接管
- **现象**:

  ```
  $ helm list -A
  NAME    NAMESPACE   REVISION   UPDATED   STATUS   CHART   APP VERSION
  (空,只有表头)
  ```

  但 `kubectl -n monitoring get deploy monitoring-grafana -o jsonpath='{.metadata.annotations}'` 明明显示:

  ```
  "meta.helm.sh/release-name": "monitoring",
  "meta.helm.sh/release-namespace": "monitoring"
  ```

- **排查过程**:
  1. 先怀疑 Helm 版本问题——本机 helm 是 **v4.3.0**,怀疑 v4 读不到 v3 格式的 release。**排除**:release secret 明明存在
  2. `kubectl -n monitoring get secret -l owner=helm` → 能看到 `sh.helm.release.v1.monitoring.v1` ~ `v4`,**release 数据在,是 Helm 没查到**
  3. 查 `kubectl config current-context` → **`k3d-topo-demo`** ← 破案

- **根因**:

  **Helm 和 kubectl 都隐式使用 kubeconfig 的「当前 context」。** 本机有三个 k3d 集群,当前 context 指向的是项目三的 `k3d-topo-demo`,不是 `k3d-ai-cluster`。**Helm 一直在查另一个集群**,当然是空的。

- **解法**:

  ```bash
  helm list -A --kube-context k3d-ai-cluster
  # NAME        NAMESPACE    REVISION  STATUS    CHART
  # monitoring  monitoring   4         deployed  kube-prometheus-stack-87.19.1
  # traefik     kube-system  1         deployed  traefik-27.0.201+up27.0.2
  # traefik-crd kube-system  1         deployed  traefik-crd-27.0.201+up27.0.2
  ```

- **经验**:

  > **多集群环境下,不带 `--context` 的命令是静默事故的主要来源。**

  它最危险的地方在于:**不报错,只是安静地作用在错误的集群上**。`kubectl delete` 少写了 `--context`,删的就是另一个集群的东西。

  **已写进本项目的 runbook 纪律:所有 `kubectl` / `helm` 命令显式带 `--context`。**

- **面试可以怎么讲**:

  > "多集群环境里我遇到过最阴的一个坑,是没有显式指定 context。`helm list` 返回空,但资源明明在——因为它查的是另一个集群。这个坑的危险在于它不报错。后来我在所有脚本里强制显式带 context,并且用 `kubectl config use-context` 切换到哪就说清楚。"

- **额外收获**:这次排查顺带确认了 `monitoring` 命名空间是 **Helm 管理**的,而 `ai-platform` 是**手工 apply** 的——**两种管理方式意味着 ArgoCD 接管需要两套策略**(见 D4 / M1)。

## P2 — 6 个 Pod 烂了 30 天,`kubectl get pods` 的表头看着干干净净

- **日期**:2026-09-16
- **场景**:M0 盘点存量集群,准备用 ArgoCD 接管
- **现象**:

  ```
  ai-platform   vllm-3b-7c59d66664-ddppp   0/1   ContainerStatusUnknown    5d
  ai-platform   vllm-3b-7c59d66664-t4jlb   0/1   UnexpectedAdmissionError  3d7h
  ...
  ```

  而 `kubectl get deploy vllm-3b` 报的是 `1/1 READY`。

- **排查过程**:
  1. 先查 ReplicaSet 的计数 → `{"replicas":1, "readyReplicas":1}` — **RS 认为一切正常**
  2. 查 Pod 的 `deletionTimestamp` 和 `finalizers` → 都是空,不是"卡在删除中"
  3. 逐条比对 kube-prometheus-stack 的默认规则表达式 → **发现没有任何一条能匹配 `phase=Failed`**
  4. 确认 PodGC 阈值 → 默认 `--terminated-pod-gc-threshold=1250`,6 ≪ 1250

- **根因**:**四层机制互相以为对方会管。**

  | 层 | 为什么没动手 |
  |---|---|
  | `KubePodNotReady` | phase 白名单是 `Pending\|Unknown` 或 `Running 但 ready=0`,**不含 `Failed`** |
  | `KubePodCrashLooping` | 查 `reason="CrashLoopBackOff"`,而终态准入失败的容器**从未进过 waiting** |
  | ReplicaSet 控制器 | 只数**活跃** Pod,Failed 不算活跃;补到 1 个就走,**不管清理** |
  | PodGC 控制器 | 只在**全局终态 Pod > 1250** 时才清理 |
  | 人 | Alertmanager receiver 是 `null`(见 P4) |

- **解法**(M2 实施):补一条默认集里不存在的规则

  ```promql
  kube_pod_status_phase{phase="Failed"} == 1
  ```

- **经验**:

  > **`UnexpectedAdmissionError` 有"隐蔽性三连":不重试、不 CrashLoop、不累积 restartCount。**

  三种最常见的"Pod 坏了"信号它**一个都不触发**。运维排查时,`STATUS` 列比 `READY` 列重要得多——`0/1` 可能是暂时的,`UnexpectedAdmissionError` 是**终态**。

  更普适的规律:**"默认告警规则集覆盖了什么"和"哪些故障模式存在"是两个集合,它们的差集就是你的盲区。** 装完监控栈必须主动去算这个差集,不能假设它覆盖全了。

- **面试可以怎么讲**:

  > "我接手一个跑了 43 天的集群,发现 6 个 Pod 烂了最多 30 天没人管。奇怪的是所有告警规则都在、Prometheus 也在正常求值。查下来是:`UnexpectedAdmissionError` 是**终态失败**,而 kube-prometheus-stack 默认的三条 Pod 告警规则——`KubePodNotReady` 的 phase 白名单里没有 `Failed`,`KubePodCrashLooping` 只认 CrashLoopBackOff,`KubeContainerWaiting` 只认 waiting 容器——**一个都匹配不上**。加上 ReplicaSet 只管补数不管清理、PodGC 阈值是 1250,四层机制互相以为对方会管,这就是它能烂 30 天的完整原因。」

- **关联**:P3(真因)、P4(为什么没人知道)、M2 降噪补规则

## P3 — Pod 被 kubelet 拒绝,报的是 "no healthy devices present"

- **日期**:2026-09-16
- **场景**:排查 P2 里那 6 个僵尸 Pod 的真因
- **现象**:

  ```
  Pod was rejected: Allocate failed due to no healthy devices present;
  cannot allocate unhealthy devices nvidia.com/gpu, which is unexpected
  ```

  第一反应是"WSL 里没有 GPU,所以 vllm 起不来"。

- **排查过程**:
  1. 查节点 allocatable → `nvidia.com/gpu: 1` **存在**,不是没有
  2. 查 device plugin 日志 → `Registered device plugin for 'nvidia.com/gpu' with Kubelet` 正常注册
  3. **但同一时刻有一个 vllm Pod 是 Running 的**,而且只跑了 111 分钟,restartCount 为 0
  4. 对时间戳:
     ```
     device plugin 注册:  I0915 14:24:57
     vllm Pod 启动:      2026-09-15T14:25:02Z   ← 间隔 5 秒
     ```
  5. 拉 6 个僵尸的创建时间 → 08-16 / 08-28 / 09-08 / 09-09 / 09-10 / 09-12,与全集群 restartCount 剧增的时间点吻合

- **根因**:**GPU 有一段时间被标记为不健康,而不是没有 GPU。**

  WSL2 通过 `/dev/dxg` 直通 GPU。每次 WSL 重启后,nvidia-device-plugin 重新探测设备,**"已注册"和"健康检查通过"之间有一个几秒的窗口**。此刻 ReplicaSet 正在补 vllm 的 Pod,而它带 `nvidia.com/gpu` 请求 → kubelet admission 时设备不健康 → **拒绝并置为终态 Failed**。

  窗口只有几秒,所以每次重启通常只留下一具尸体——**这正好解释了为什么是 6 个而不是 60 个**。

- **解法**:无(环境固有特性)。**正确做法是让它可见**——加一条规则把 `UnexpectedAdmissionError` 报出来,人就能立刻知道"又抖了一次"。

- **经验**:

  > **"设备不健康"和"设备不存在"是两种完全不同的故障,但都表现为 Pod 起不来。**

  排查时不要停在 `describe pod` 的错误信息上。这次如果停在 "no healthy devices present" 就下结论"WSL 没 GPU",会**完全错过真因**,而且会得出"这是环境问题没法修"的错误结论——实际上它是**可观测性问题**,有解。

- **面试可以怎么讲**:

  > "我们的推理服务每天莫名其妙挂一次,报错是 GPU 设备不可用。查下来不是卡坏了,是 device plugin 在节点重启后有一小段窗口,设备已注册但健康检查还没过,这时候创建 Pod 就在 admission 阶段被拒了——而且这个拒绝在 Kubernetes 里是**终态**,调度器不会重试。所以它不是'偶发失败',是'一次失败永久卡住'。后面我给这类终态加了专门的告警。"

- **关联**:P2(这批 Pod 为什么没人清理)

## P4 — 所有告警都进了黑洞,因为 receiver 叫 "null"(**但它不是疏漏**)

- **日期**:2026-09-16
- **场景**:P2 排查到"为什么没人发现",去看 Alertmanager
- **现象**:

  ```yaml
  receivers:
  - name: "null"
  route:
    receiver: "null"
  ```

- **排查过程**:
  1. 先确认规则**在不在**——`/api/v1/rules` 列出 190+ 条,`lastError: 0`,规则健康
  2. 再确认规则**响没响**——`/api/v1/alerts` 返回 **39 条** firing/pending
  3. 最后看 Alertmanager 配置——**`receivers:` 里只有一个叫 `null` 的空接收器,`route.receiver` 指向它**

- **根因**:**两层,第一层是技术,第二层是人的决策。**

  技术上:`null` 是 **kube-prometheus-stack 的出厂默认值**。图表作者故意不给可用 receiver,强制用户自己填。

  **但真正的原因不在这。** 排查到这里我下的结论是"前一位同事装完忘了配"——**这个结论是错的**。

  问过当事人后得知:**当时是主动把告警打进黑洞的**。背景是:那个阶段频繁收到无效告警,而项目当时刚好完工、集群也不需要维护,与其让一堆没意义的通知一直响,不如索性全推黑洞。

  > **教训:判断"为什么是这样",不能只看现状,还得问当时的人。**
  >
  > 现状能告诉你 `receiver: "null"`,但告诉不了你它是**"忘了配"**还是**"故意配的"**。
  >
  > 这两种情况的解法完全不同:
  > - 如果是**忘了配** → 配上 receiver 就完事了
  > - 如果是**故意打的** → 得先问"为什么会有那么多无效告警",**先把噪音解决掉,再接通道**
  >
  > 我一开始按前者理解,差点直接去接微信——那样做等于让这位同事的处境重来一遍。

- **解法**(M2,**分两步,顺序不能反**):

  1. **先降噪**:实测出"永远在响"的是哪几条,从源头关掉(见 P5)
  2. **再接通道**:降噪做完之后才配真实 receiver,走**企业微信机器人 webhook**

- **经验**:

  > **"告警规则存在" ≠ "告警会送达"。** 验证一条告警链路要**端到端**验,至少四段:规则求值 → Prometheus 推送 → Alertmanager 路由 → 接收方收到。任何一段断了,前面三段都看不出来。

  这次前三段**全部健康**——规则在求值、Prometheus 在推送、Alertmanager 在分组抑制。**唯一的断点是最后一跳**,而它不报错、不告警、界面上看不出来。

  和 P1 是**同一类错误的不同形态**:
  > P1 是 `kubectl` 静默作用在错误的集群上;**P4 是告警静默流进一个什么都不做的接收器。** 都是"不报错的错误"。

  但两者的**成因类别**不同,这个区分很重要:

  | | P1 | P4 |
  |---|---|---|
  | 性质 | **意外**——没意识到多集群的隐式 context | **决策**——知道,但当时有理由这么干 |
  | 对策 | 加 `--context` 纪律 | 先解决"为什么想关掉它",再谈打开 |

  **把所有"不报错的错误"都归为"意外",是排查里的一种偷懒。**

- **面试可以怎么讲**:

  > "我巡检的时候发现集群装了完整的 kube-prometheus-stack,190 多条告警规则,几十条正在 firing——但 Alertmanager 的 receiver 是图表默认的 `null`。我第一反应是'前一位同事忘了配',但去问了一下才知道:**那是他主动关的**——因为当时无效告警太多,而项目已经完工、集群不需要维护。
  >
  > 这个回答直接改变了我的方案。如果只是忘配,接上 receiver 就完了;但既然是因为噪音才关的,那我就得**先把噪音解决掉再接通道**,否则他几周后还会做出同一个决定。所以我先去实测哪几条告警是永远在响的,从源头关掉三条,把 firing 数从 39 降到 1,然后才动接收端。
  >
  > 这件事让我记住:**接手别人的系统时,'为什么是这样'的答案往往不在系统里,在人那里。**"

- **⚠️ 后补(2026-09-16,实测)**:上面这条排查**还有第三层**,当时没查到——`k3s-kubeproxy-silence.yaml` 那份文件是**静默失效**的,一条都压不住。详见 P8。

- **关联**:P1(同属"不报错的错误")、M2

## P5 — 装了监控栈之后,有 3 条告警从第一天起就永远在响

- **日期**:2026-09-16
- **场景**:P4 排查时顺手看 full alert 列表
- **现象**:

  | 状态 | 告警 |
  |---|---|
  | firing | `KubeControllerManagerDown` |
  | firing | `KubeSchedulerDown` |
  | firing | `KubeProxyDown` |
  | firing | `AlertmanagerClusterCrashlooping` |

- **排查过程**:
  1. 查这三个组件在集群里是不是真挂了 → `kubectl get pods -n kube-system`,**根本没有这三个 Pod**
  2. 查 k3s 架构 → k3s 把 controller-manager / scheduler / kube-proxy **编译进单个 `k3s server` 进程**,不作为独立 Pod 运行

- **根因**:**kube-prometheus-stack 的默认规则是照标准 kubeadm 集群写的**,假设这三个组件是独立 Pod 并有独立 metrics 端点。k3s 不满足这个假设,于是 `absent(up{job="kube-proxy"} == 1)` 永远为真,**永远 firing**。

  `AlertmanagerClusterCrashlooping` 同理——单副本部署不满足它要求的集群一致性条件。

- **解法**(M2,**必须先于接微信**):在 Helm values 里关掉对应规则,或在 Alertmanager 层加抑制/黑洞路由。

- **经验**:

  > **告警噪声比没有告警更危险。**

  没有告警,人知道自己没被保护;有 3 条永远在响的假警报,人会**学会忽略告警**。等真出事的时候,真警报混在假警报里被一起忽略掉。

  这在 SRE 里有名字:**告警疲劳(alert fatigue)**,是公认的头号告警失效模式。

  **所以正确顺序是:先降噪,再接通道。** 反过来做,等于亲手毁掉这套告警的可信度——第一天收到 3 条假警报,第三天就没人看了。

- **面试可以怎么讲**:

  > "我在 k3s 上装 kube-prometheus-stack,发现 `KubeProxyDown`、`KubeSchedulerDown`、`KubeControllerManagerDown` 三条从装上那天就在响。原因是 k3s 把控制面组件编译进单进程了,而 kube-prometheus-stack 的默认规则是照 kubeadm 集群写的,假设它们是独立 Pod。这三条不是配置错误,是**架构不匹配**——所以修法不是在 PromQL 里绕,是在 Helm values 里按集群形态剪裁规则集。接告警通道之前必须先做这件事,不然收到的是永不停止的假警报,几天内人就开始忽略告警了。"

- **关联**:P4、M2

## P6 — 精心写的告警补丁,标签少写一个,等于没写

- **日期**:2026-09-16
- **场景**:M1 审计存量 GitOps 目录,检查 `k3s-alert-patches.yaml` 能不能用
- **现象**:这份 `PrometheusRule` 定义了 `k3s-alert-overrides`,内容看起来很对——用同名规则覆盖 `KubeProxyDown` 的默认表达式。但它从未生效过。

- **排查过程**:
  1. 先看它带的标签:
     ```yaml
     labels:
       prometheus: kube-prometheus
       role: alert-rules
       app.kubernetes.io/part-of: kube-prometheus-stack
     ```
  2. 再看 Prometheus 实例**实际**用什么选规则:
     ```
     ruleSelector: {"matchLabels":{"release":"monitoring"}}
     ```
  3. **对不上。** 没有 `release: monitoring` → `PrometheusRule` 永远不会被加载
  4. 对照集群里**确实生效**的那条规则:`labels` 里有 `"release": "monitoring"` ← 差异确认

- **根因**:

  **Prometheus Operator 不会自动加载所有 `PrometheusRule` 对象——它按 `ruleSelector` 挑。**

  这是**白名单机制**:标签没匹配上,对象静静地躺在 etcd 里,`kubectl get prometheusrule` 看得见,但 Prometheus 完全不知道它的存在。

  这**不是配置错误,是设计如此**——`ruleSelector` 存在的意义就是让多个 Prometheus 实例共享集群时各管各的规则。

- **解法**:

  ```yaml
  labels:
    release: monitoring
  ```

  **同一类坑还有两处**:
  - `ServiceMonitor` 同样受 `serviceMonitorSelector` 约束,本项目里也踩过
  - `k3s-kubeproxy-silence.yaml` 的 `AlertmanagerConfig` 带的是 `release: kube-prometheus-stack`,而该项目实际用的是 `monitoring`——**名字像但不相等**

- **经验**:

  > **在 Prometheus Operator 的世界里,"对象创建成功"和"配置生效"是两件事。**

  `kubectl apply` 返回成功 ≠ 规则生效。中间隔着一个标签选择器。
  **每次新建 `PrometheusRule` / `ServiceMonitor` / `AlertmanagerConfig`,第一件事就是去对 Prometheus/Alertmanager 实例的选择器。**

  验证方法(**别猜,去查**):

  ```bash
  kubectl -n monitoring get prometheus <name> -o jsonpath='{.spec.ruleSelector}'
  kubectl -n monitoring get prometheus <name> -o jsonpath='{.spec.serviceMonitorSelector}'
  kubectl -n monitoring get alertmanager <name> -o jsonpath='{.spec.alertmanagerConfigSelector}'
  ```

  更省事的自检:去 Prometheus UI 的 **Status → Rules** 页面搜你的规则名。**搜不到就是没加载**,不用怀疑人生。

- **面试可以怎么讲**:

  > "我遇到过一条告警规则,写得很对、apply 也成功、`kubectl get` 也看得到,但它从来没生效过。查下来是 Prometheus Operator 的 `ruleSelector` 是个白名单,我漏了 `release: monitoring` 这个标签,规则就静静躺在 etcd 里,Prometheus 完全不知道它存在。**这类问题没有任何报错**——`apply` 返回成功,对象状态也正常。所以我后来养成了习惯:新建规则后一定去 Prometheus 的 Rules 页面搜一下,确认它真的被加载了。"

- **关联**:P1 / P4(同属"不报错的错误")、M0 的 `k3s` 假阳性、M1 审计雷 3 / 雷 4

## P7 — 用同名告警规则去"覆盖"默认告警,实测证明根本行不通

- **日期**:2026-09-16
- **场景**:M1 审计发现 `k3s-alert-patches.yaml` 想用一条同名 `PrometheusRule` 覆盖 `KubeProxyDown`。第一反应是"它标签写错了所以没生效",准备把标签补上。
- **转折**:补标签之前先问了一句——**如果标签对了,它真的能覆盖吗?**

- **实验设计**(零风险探针):

  `Watchdog` 是 kube-prometheus-stack 里**设计上永远 firing** 的告警(死信开关,表达式就是 `vector(1)`)。用它当探针:注入一条同名 `Watchdog`、表达式 `vector(0)` 的规则,看能不能把它"杀掉"。

  ```yaml
  apiVersion: monitoring.coreos.com/v1
  kind: PrometheusRule
  metadata:
    name: m1-experiment-override
    namespace: monitoring
    labels:
      release: monitoring        # 标签是对的,确保会被加载
  spec:
    groups:
      - name: m1.experiment
        rules:
          - alert: Watchdog
            expr: vector(0)
  ```

- **结果**:

  ```
  Prometheus 里名为 Watchdog 的规则:2 条   ← 并存,不是替换
  [m1.experiment]  expr='vector(0)'  → 活跃告警 0
  [general.rules]  expr='vector(1)'  → 活跃告警 1   ← 默认的照样在响
  ```

  **默认告警毫发无伤。**

- **根因**:

  **Prometheus 的告警是"并列求值",不存在覆盖语义。**

  每条规则独立求值;`alertname` 只是标签之一,不是主键。两条同名规则**同时存在、同时求值**。默认那条的表达式是真的,告警就是真的——另一条规则**没有任何机制能取消它**。

- **解法**:

  要消除一条告警,只有三条路:

  | 方案 | 做法 | 评价 |
  |---|---|---|
  | **停掉规则来源** | 在 Helm values 里关掉对应组件的 `enabled` | ✅ **最干净**,连 scrape target 一起消失 |
  | **Alertmanager 静默** | 在路由/静默层拦截 | ✅ 有效,但规则仍在求值(白烧 CPU) |
  | ~~同名规则覆盖~~ | — | ❌ **不成立** |

- **经验**:

  > **"用同名对象覆盖配置"这个模式,在不同系统里的语义完全不同。**

  - 在 **Kubernetes** 里:同名对象是**替换**(`kubectl apply` 覆盖)
  - 在 **Helm** 里:是同 release 的**升级**
  - 在 **Prometheus** 里:是**并存**,什么都覆盖不了

  **换一个系统就要重新问一次"这里的覆盖语义是什么",不能想当然。**

  这条思路如果没验证就写进文档,就会变成一个**看起来很有道理、实际完全不工作**的方案——比明显报错的 bug 危险得多。

- **面试可以怎么讲**:

  > "我们集群里 k3s 有三条控制面告警永远在响,因为 k3s 把组件编译进单进程了。前一位同事写了一版补丁,想用同名 PrometheusRule 覆盖默认规则。我发现它标签写错了所以没被加载,本来打算修标签——但修之前我先做了个实验:注入一条同名 `Watchdog`、表达式恒假的规则,看能不能把永远 firing 的 Watchdog 杀掉。结果是**杀不掉,两条规则并存求值**。所以那个补丁就算标签修对了也没用,整个思路是不成立的。最后改成在 Helm values 里直接关掉组件。"

- **关联**:P6(标签选择器)、M1 审计雷 3、M2 降噪

## P8 — 那份"屏蔽 k3s 假阳性"的文件,一次都没生效过

- **日期**:2026-09-16
- **场景**:M1 审计时发现 `production/monitoring/k3s-kubeproxy-silence.yaml`,是一份 `AlertmanagerConfig`,本意是把三条 k3s 假阳性告警打进黑洞。P6 里已经发现它**标签写错**(`release: kube-prometheus-stack` ≠ 实际的 `monitoring`)。在修标签之前,我决定先把它的机制彻底搞懂。
- **现象**:文件长这样,看起来完全合理:

  ```yaml
  spec:
    route:
      receiver: 'blackhole'
      matchers:
        - name: alertname
          value: KubeProxyDown|KubeSchedulerDown|KubeControllerManagerDown
          matchType: =~
      continue: false
  ```

- **排查过程**:
  1. 把标签修对的**假设情况下**,这份 `AlertmanagerConfig` 会被 operator 翻译成什么路由?
  2. 去读 prometheus-operator 的源码 `pkg/alertmanager/amcfg.go`,发现有个 `namespaceEnforcer`
  3. 看它对每条子路由做什么:

     ```go
     func (ne *namespaceEnforcer) processRoute(crKey types.NamespacedName, r *route) *route {
         r.Matchers = append(r.Matchers, Matcher{
             Name: "namespace", Value: crKey.Namespace, MatchType: MatchEqual,
         }.String())
         return r
     }
     ```

  4. 也就是说,operator 会**强行塞进一个 `namespace = "monitoring"` 的 matcher**,不管我写没写
  5. 那三条告警的 label 里**有 `namespace` 吗**?`kubectl -n monitoring get prometheus -o jsonpath='{.spec.externalLabels}'` → **空**。告警的 label 集里根本没有 `namespace` 这一项

- **根因**:

  **这份文件从头到尾就没有生效过,而且就算标签修对了也依然不会生效。**

  两个原因叠加,任一条单独成立就足以让它失效:

  | 层 | 问题 |
  |---|---|
  | 标签层(P6 已发现) | `release` 标签不匹配 `alertmanagerConfigSelector`,对象压根没被 operator 读取 |
  | **语义层(本次发现)** | **就算被读取了**,operator 注入的 `namespace` matcher 也匹配不上没有该 label 的告警 |

  而 **matcher 对不存在的 label 一律判定为不匹配**——不是"空字符串",是不匹配。

- **解法**:这份文件**删除**。同等需求由 P5 的解法(Prometheus 侧从源头关掉组件)覆盖,更彻底——连求值都不做了。

- **经验**:

  > **一份"看起来对"的失效配置,比完全没有配置更危险。**

  没有配置的时候,你至少知道这里有个洞,会去想办法。而仓库里躺着一份 `k3s-kubeproxy-silence.yaml`,任何后来的人(包括三个月后的自己)翻到它,都会得出"这个问题已经处理过了"的结论。

  **它的危害不是"没起作用",是"让人以为它起作用了"。**

  更普遍地说:**验证一份配置是否生效,不能看它写得好不好,要看它作用的那一层真正读到了什么。** 这次就是要一路追到 operator 源码里,才知道它被翻译成了什么。

- **面试可以怎么讲**:

  > "接手项目时我在仓库里发现一份 AlertmanagerConfig,专门用来屏蔽三条 k3s 的假阳性告警——写得很规范。但我查下来发现它**从来没生效过**,而且是两层失效叠加:一是标签没匹配上 operator 的选择器,二是就算匹配上了也还是不行——prometheus-operator 有个 `namespaceEnforcer`,会往每条 AlertmanagerConfig 生成的子路由里强制注入一个 `namespace` matcher,而那三条告警的 label 里根本没有 `namespace`,matcher 对缺失的 label 是不匹配的。所以这份文件的作用是让人以为问题已经解决了。我的处理是删掉它,改从 Prometheus 侧把这三个组件的规则整组关掉,更彻底。"

- **附带收获**(以后用 AlertmanagerConfig 必知):`alertmanagerConfigSelector: {}` 是**匹配全部**还是匹配空?去读 `apimachinery` 的 `LabelSelectorAsSelector`:

  ```go
  if ps == nil {
      return labels.Nothing(), nil     // nil → 什么都不匹配
  }
  if len(ps.MatchLabels)+len(ps.MatchExpressions) == 0 {
      return labels.Everything(), nil  // {} → 匹配全部
  }
  ```

  **`{}` = 匹配全部。** 这是 M3+ 如果用 AlertmanagerConfig 做路由的前提。

- **关联**:P6(同属"对象存在 ≠ 配置生效")、P7、P5、M2 降噪

## P9 — 一条"测时钟偏差"的 PromQL,测的其实是样本年龄

- **日期**:2026-09-16
- **场景**:排查 `AlertmanagerClusterCrashlooping` 为什么在响。调研给出的结论是"不是真重启,是 k3d/WSL2 的节点时钟漂移",证据是这条查询:

  ```promql
  node_time_seconds - time()
  → 三个节点分别 -7.5 / -15.4 / -26.9 秒
  ```

  秒级偏差,看起来很像时钟漂移。

- **排查过程**:
  1. 我复查了这条查询。多刷几次,发现**同一台机器的值每次都不一样**(-12.81 / -1.30 / -23.32)
  2. 时钟漂移应该是**稳定**的——一台机器的偏移量不会每分钟变十几次
  3. 那这个波动的数字是什么?去看这两个函数各自的语义:
     - `time()` = **查询求值的那一刻**
     - `node_time_seconds` = 该指标**被抓取的那一刻**记录的节点时间
  4. 所以 `node_time_seconds - time()` = **"抓取时刻" 减 "当前时刻"** = **这个样本有多旧**
  5. 换个写法验证:

     ```promql
     node_time_seconds - timestamp(node_time_seconds)
     → +0.006 / +0.008 / +0.018 秒
     ```

  `timestamp()` 返回的是**该样本的抓取时刻**。用它和小数点后的节点时间相减,才是真正的时钟偏差。

- **根因**:

  **`metric - time()` 得到的是"样本年龄",不是"指标值与当前时间的差"。**

  两者长得几乎一样,含义完全不同:

  | 写法 | 实际含义 | 用途 |
  |---|---|---|
  | `node_time_seconds - time()` | 样本年龄(抓取距今多久) | 差不多等于 scrape interval,用来发现抓取异常 |
  | `node_time_seconds - timestamp(node_time_seconds)` | **真正的时钟偏差** | 检测节点时钟漂移 |

  **实测结论:时钟是亚 20 毫秒级同步的,根本没有漂移。** "时钟漂移"这个根因是错的。

- **解法**:无需修复(PromQL 是错的,不是环境是错的)。改用 `timestamp()` 版本的查询重新确认。

- **经验**:

  > **`timestamp()` 是"指标里的时间"和"抓取这个指标的时间"之间的桥。**

  PromQL 里的 `time()` 永远是"现在",它和任何指标相减,得到的都是**这个指标有多旧**,而不是这个指标"说得对不对"。

  但要记的规律比这一条更大:

  > **一个"看起来合理"的因果解释,如果不实测验证,就会变成文档里的幻觉。**

  "时钟漂移导致指标异常"这个解释**太顺了**——k3d/WSL2 确实有时钟问题,数字确实是秒级,连方向都对(节点时间落后于现在)。它唯一缺的就是**它是错的**。

  这次好在是在**写进交付文档之前**复查了一遍。如果直接抄进报告,这份文档就会带着一个错误的根因流传下去,而且因为它逻辑自洽,后面的人很难发现。

- **面试可以怎么讲**:

  > "调查一个告警的根因时,拿到一个'节点时钟漂移'的结论,证据是 `node_time_seconds - time()` 显示三台机器分别慢了 7 到 27 秒。我没有直接采信,而是多刷了几次——发现同一台机器的数字每次都在变,几分钟内从 -12 变到 -23。时钟漂移应该是稳定的,会剧烈波动的数字说明我量错了东西。查下来:`time()` 是查询求值时刻,而 `node_time_seconds` 是抓取时刻的值,两者相减得到的是**样本年龄**,不是时钟偏差。换成 `node_time_seconds - timestamp(node_time_seconds)` 之后,三台机器是 **6 到 18 毫秒**,完全正常。那个根因是不成立的。"

- **关联**:P4 / P1(同属"不报错的错误"——一个错误的查询不会报错,它只会给你一个言之凿凿的错误答案)、M2 审计

## P10 — ArgoCD 报"同步失败",其实三分钟前就自己好了

- **日期**:2026-09-16
- **场景**:ArgoCD 接管 `sealed-secrets` Application 后,去查同步结果
- **现象**:`Application` 的状态里有报错,提示拉取 Git 仓库失败,伴随一条日志:

  ```
  grpc.time_ms=15001.801
  ... Client.Timeout exceeded while awaiting headers
  ```

  15 秒零 1 毫秒——**卡在超时上了**。当时我的判断是"GitHub 连不上,网络有问题,这是个持久故障"。

- **排查过程**:
  1. 先确认超时是不是可配的——翻 `argocd-repo-server` 的启动参数和可用的环境变量:

     ```bash
     grep -ao 'ARGOCD_REPO_SERVER_[A-Z_]*' /usr/local/bin/argocd-repo-server | sort -u
     ```

     **没有任何和 Git 操作超时相关的变量。**
  2. 那就先强制刷一次再说:

     ```bash
     kubectl --context k3d-ai-cluster -n argocd annotate application sealed-secrets \
       argocd.argoproj.io/refresh=hard --overwrite
     ```
  3. **秒变 Synced。**
  4. 回头去查被接管对象的创建时间:

     ```
     Deployment sealed-secrets-controller 创建于 16:44:33
     ```

     也就是说——**它早就成功了。我查到那条报错的时候,它已经同步完成。**

- **根因**:

  **不是持久故障,是一次冷连接的瞬时超时,而 ArgoCD 自己重试成功了。**

  ArgoCD 默认大约每 3 分钟重新对账一次。第一次拉取要建新连接(DNS + TLS 握手),在 WSL2 + 国内网络环境下偶尔会超过那个硬编码的 15 秒窗口。**下一次重试连接是热的,就过去了。**

  我犯的错是:**在重试还没发生之前就去查了结果,然后把这个瞬时状态当成了稳态。**

- **解法**:无需修复。重试机制本身就是为此设计的。

- **经验**:

  > **判断"故障"和"尚未成功的中间态"之前,先看时间戳。**

  ArgoCD 是个**收敛式控制器**——它的设计前提就是"失败会重试"。所以看到一次失败,第一件事应该是**等一个对账周期再确认**,而不是立刻下结论。

  这条对排查习惯的影响更大:

  > **一次采样 = 一个瞬时快照,不等于系统状态。**

  我同时也在这次会话里踩到了它的镜像版本(P9:一次查询 = 一个错的答案)。两次的教训是同一个:**不要用单次观测去断言一个持续性的结论。**

  有个简单便宜的办法:看**这个状态持续了多久**。ArgoCD 的 `Application` 状态里带时间戳,失败如果是几分钟前的、且期间没有新的失败,大概率已经自愈了。

- **面试可以怎么讲**:

  > "用 ArgoCD 接管资源的时候,我查到一条同步失败,日志显示卡在一个 15 秒的 Git 拉取超时上。我当时的判断是网络不通,准备去排查网络。但先去做了件事:强制 refresh 一次——结果立刻变 Synced。回头看部署的时间戳,发现那次同步其实**三分钟前就成功了**,我查到的是一个已经被重试覆盖掉的中间状态。ArgoCD 是个收敛式控制器,失败重试是它的正常工作方式,所以看到一次失败不该就下结论,而应该等一个对账周期再看。这个坑让我改进了一个习惯:**看状态的时候顺手看它持续了多久**,瞬时快照不代表系统状态。"

- **关联**:P9(同属"单次观测 ≠ 稳态")、M1

## P11 — promtail 挂了一个永远是空的日志目录,而它不报错

- **日期**:2026-09-16
- **场景**:M1 接管 `promtail` 后核对它的实际运行状态
- **现象**:DaemonSet **3/3 Ready**,看起来完全正常。但去看它挂了什么卷:

  ```
  pods-logs   -> /var/log/pods              (13 项,真实有内容)
  docker-logs -> /var/lib/docker/containers (0 项,永远是空的)
  ```

- **排查过程**:
  1. 进节点实跑,确认两个路径的状态:

     ```
     /var/lib/docker/containers  → 存在,但 0 项
     /var/log/pods               → 存在,13 项
     ```

  2. 这就矛盾了——为什么 Docker 的日志目录是空的?
  3. 查本集群的容器运行时 → **k3s,用的是 containerd,不是 Docker**
  4. 两边的日志落点完全不同:

     | 运行时 | 容器日志路径 |
     |---|---|
     | Docker | `/var/lib/docker/containers/<id>/<id>-json.log` |
     | containerd | `/var/log/pods/<ns>_<pod>_<uid>/<container>/*.log` |

  5. 最后核对 promtail 自己的抓取配置,看它**实际**用了哪个:

     ```yaml
     - job_name: kubernetes-pods
       # __path__ 只用了这个:
       - replacement: /var/log/pods/*$1/*.log
     ```

- **根因**:这份清单是**照 Docker 集群写的**,而本集群跑的是 containerd。那个 `docker-logs` 挂载点从装上那天起就是空的。

- **解法**:本次不动(改它要重新同步,收益只是删一个空挂载)。记为待清理项。

- **影响评估**:**不影响运行** —— 真正的采集路径 `/var/log/pods` 是通的,日志收得到。

  但它有**误导性**:看清单的人会以为日志是从 docker 目录采的;排障时可能去查一个根本不相干的路径,然后得出"日志采集配置有问题"的错误结论。

- **经验**:

  > **"Pod 是 Running 的"不能证明"它的每个配置项都是对的"。**

  这一条和 P8 是**同一个模式的两个实例**:

  | | P8 | P11 |
  |---|---|---|
  | 失效的东西 | 告警静默的标签 | 日志采集的挂载点 |
  | 为什么不报错 | 标签不匹配只是"不加载",不是错误 | 挂载不存在的路径只是"空目录",不是错误 |
  | 危害 | 以为假阳性处理过了 | 以为知道日志从哪来 |

  **共性:配置里有一部分静默地不起作用,而系统的健康状态完全看不出来。** 这类问题只能靠"逐项核对配置的实际语义"发现,不能靠看状态灯。

- **面试可以怎么讲**:

  > "我接管一个日志采集组件时发现它挂载了两个日志目录:一个 `/var/log/pods`,一个 `/var/lib/docker/containers`。第二个是空的。原因是那份清单是照 Docker 集群写的,而这个集群用的是 containerd——两个运行时的容器日志落点完全不同,Docker 写 `/var/lib/docker/containers`,containerd 写 `/var/log/pods`。不影响运行,因为真正生效的是第一条路径,但它在清单里留了个误导:下次有人排日志问题会去查一个死路径。**这件事让我意识到,'Pod 是 Running' 和 '配置是对的' 是两个独立的判断,后者必须逐项去核。**"

- **关联**:P8(同为"静默失效的配置")、P1 / P4(同为"不报错的错误")、M1 接管

## P12 — 8 个文件的 `release` 标签全写错了,5 个对象在 etcd 里躺了 43 天从未生效

### 现象

M2 接告警通道时顺带核对"哪些告警规则真的在跑",发现 `production/monitoring/` 目录下这 5 个对象在集群里**存在、`kubectl get` 得到、`status` 正常**,但 Prometheus 从来没加载过它们:

- `PrometheusRule/sre-lab-cluster-alerts`(6 条规则)
- `PrometheusRule/nginx-demo-rules`(2 条规则)
- `PrometheusRule/ollama-slo-rules`(7 条规则)
- `ServiceMonitor/nginx-demo-monitor`
- `ServiceMonitor/ollama-exporter-monitor`

### 根因

Prometheus 的 `ruleSelector` / `serviceMonitorSelector` 是**白名单**——它只加载带特定标签的对象。这套监控栈要的是 `release: monitoring`,而这 8 处文件的标签写的是 `release: prometheus-stack`。

**一个值的差异,零报错,零告警。**

实测确认(修复前):

```
$ curl -s localhost:19090/api/v1/rules | grep -i sre-lab
(无输出)
```

修复后同一个命令:

```
[monitoring-sre-lab-cluster-alerts-...yaml]  sre-lab.k8s             rules=3
[monitoring-sre-lab-cluster-alerts-...yaml]  sre-lab.node            rules=3
[nginx-demo-nginx-demo-rules-...yaml]        nginx-demo.availability rules=2
[ai-platform-ollama-slo-rules-...yaml]       ai-platform.general     rules=2
[ai-platform-ollama-slo-rules-...yaml]       ollama.availability     rules=5
```

### 教训

> **"对象在集群里"和"对象在起作用"是两个独立判断。** Kubernetes 里有大量"被声明了但没被消费"的对象:`PrometheusRule`、`ServiceMonitor`、挂错 selector 的 ConfigMap、没有任何 Pod 选中的 `NetworkPolicy`。它们 `status` 全都正常——因为 **CRD 本身不知道自己没有被谁选中**。

检验方法只有一个:**去问消费者**。不要用 `kubectl get prometheusrule` 看存在性,要去 Prometheus 的 API(`/api/v1/rules`、`/api/v1/targets`)里看它到底加载了什么。

- **面试可以怎么讲**:

  > "我接管一套监控栈时发现,三个告警规则文件和两个 ServiceMonitor 在集群里躺了 43 天,一次都没生效过。它们 `kubectl get` 得到、`status` 正常、没有任何事件报错——因为 Prometheus 的 `ruleSelector` 是个白名单,这几个对象的 `release` 标签值不对。**Kubernetes 不会告诉你'你声明了一个没人用的东西'。** 这之后我核验配置的习惯就变成了'去问消费方',而不是'看资源存不存在'。"

- **关联**:P6(同一类错误的前一次)、P8(同为静默失效)、P11(同为"不报错的错误")

## P13 — 那个 ServiceMonitor 有三处独立的错,修好任何一处都还是不通

### 现象

`ServiceMonitor/nginx-demo-monitor` 修好 `release` 标签(P12)之后依然不工作,Prometheus 的 targets 列表里查不到任何 nginx-demo 的 job。

### 根因(三处独立损坏)

| # | 位置 | 写的是 | 实物是 |
|---|---|---|---|
| 1 | `spec.selector.matchLabels` | `app: my-nginx` | Service 的**标签**只有 `app.kubernetes.io/part-of: nginx-demo` |
| 2 | `spec.endpoints[0].port` | `http` | Service **端口没有名字**(`name=` 为空) |
| 3 | `spec.endpoints[0].path` | `/` | nginx 在 `/` 上返回 HTML,不是 metrics 文本 |

**第 1 条最容易看错。** `app: my-nginx` 确实存在——但它存在于 **Pod 的标签**和 **Service 的 `spec.selector`** 里,而 `ServiceMonitor.spec.selector` 匹配的是 **Service 自己的 `metadata.labels`**。这是三个完全不同的字段。实测:

```
$ kubectl --context k3d-ai-cluster -n nginx-demo get pods --show-labels
my-nginx-d95f48764-2vxwh   app=my-nginx,app.kubernetes.io/part-of=nginx-demo,...   ← Pod 有

$ kubectl --context k3d-ai-cluster -n nginx-demo get svc my-nginx-svc -o jsonpath='{.metadata.labels}'
{"app.kubernetes.io/part-of":"nginx-demo"}                                          ← Service 标签没有

$ kubectl --context k3d-ai-cluster -n nginx-demo get svc my-nginx-svc \
    -o jsonpath='{range .spec.ports[*]}name={.name}{end}'
name=                                                                                ← 端口无名
```

**第 3 条是设计层面的错,不是笔误。** 原文件的注释写着"nginx 默认不暴露 metrics,这里用 blackbox 方式通过 HTTP GET / 检测存活",并配了一条 `metricRelabelings` 把**所有指标都 drop 掉**——意图是"不关心指标内容,只要 `up` 这个信号"。

这个想法不荒谬,但**实现方式是错的**:`metricRelabelings` 发生在**抓取正文解析成功之后**。nginx 在 `/` 返回 HTML,Prometheus 的解析器第一步就失败了 → 抓取失败 → `up=0`。**它想拿到的那个唯一信号,恰恰是它自己制造出来的假信号。**

### 处置

**删掉这个 ServiceMonitor,保留同文件里的 `PrometheusRule`。**

理由不是"修起来麻烦",而是**修好了也不对**:

- 前两条可以修(selector 改成 `app.kubernetes.io/part-of: nginx-demo`,端口命名或改用 `targetPort`)
- 第 3 条修不了——nginx 就是不吐 metrics。只修前两条的后果是:Prometheus 得到一个**永远 `up=0` 的 target**,Grafana 上常年飘红,还会污染任何基于 `up` 的告警

而**真正提供 nginx 可用性信号的规则根本不依赖它**:`nginx-demo.availability` 那两条规则用的是 kube-state-metrics 的 `kube_pod_status_ready` 和 `kube_deployment_status_replicas_available`。**这一点原文件自己的注释里就写了。**

要真做 HTTP 探活,正确组件是 **blackbox-exporter**(`probe_success` 指标),而不是拿普通 ServiceMonitor 去抓 HTML。

### 教训

> **一对极易混淆的字段:`ServiceMonitor.spec.selector` 选的是 Service 的标签,`Service.spec.selector` 选的是 Pod 的标签。** 名字一样、语法一样、作用域完全不同。写 ServiceMonitor 时脑子里想的是"这个 Service 选哪些 Pod",手就会自然地抄 Pod 的标签——错的就是这一步。

> **`metricRelabelings` 不能用来"容忍格式不对的响应"。** 它的执行时机在解析之后,解析不通过就到不了它。

- **面试可以怎么讲**:

  > "有个 ServiceMonitor 三处独立错误:ServiceMonitor 的 selector 抄成了 Pod 的标签,端口名对不上,抓取路径返回的还是 HTML 不是 metrics。我最后把它删了——不是修不动,是修好了也不对:只修前两条的结果是一个永远 down 的 target。真正提供 nginx 可用性信号的是 kube-state-metrics 那两条规则,和它没关系。**'能修'和'该留'是两个判断。**"

- **关联**:P12(同一次排查中发现)、P6(selector 失效)

## P14 — promtail 3/3 Ready、零报错,但它一条日志都没采到

### 现象

接管日志链路后核对"Loki 里到底有没有数据",发现:

```
$ curl -s localhost:3100/loki/api/v1/label/namespace/values
{"status":"success"}          ← 空
```

而 promtail 侧**完全正常**:DaemonSet 3/3 Ready、日志里在欢快地打印 `Adding target`、没有任何 error。

### 根因:生成的 `__path__` 通配符少了一个斜杠

promtail 用 relabel 拼出要 tail 的文件路径:

```yaml
- replacement: /var/log/pods/*$1/*.log
  separator: ""                    # ← 问题在这
  source_labels:
    - __meta_kubernetes_pod_uid
    - __meta_kubernetes_pod_container_name
  target_label: __path__
```

`separator` 是**多个 source_labels 拼接时的分隔符**。写空串 → 拼成 `<uid><container>`。而 containerd/CRI 的真实路径是:

```
/var/log/pods/<ns>_<pod>_<uid>/<container>/0.log
                              ↑ 这里有一个斜杠
```

于是最终 glob 是 `/var/log/pods/*<uid><container>/*.log`。

**字符串拼接能对上的部分全都对得上,只有中间那个斜杠没了。** 实测对比:

```
$ ls /var/log/pods/*46d33fa0-...-31eb2ae9266eexporter/*.log
ls: cannot access '...': No such file or directory        ← promtail 生成的

$ ls /var/log/pods/*46d33fa0-...-31eb2ae9266e/exporter/*.log
/var/log/pods/monitoring_gpu-exporter-8h8qx_46d33fa0-.../exporter/6.log   ← 真实的
/var/log/pods/monitoring_gpu-exporter-8h8qx_46d33fa0-.../exporter/7.log
```

**为什么它不报错**:promtail 的 file target manager 对"通配符匹配不到任何文件"这件事**不打日志**(至少在默认 info 级别下)。它照样把 target 注册进去,照样 `Adding target`,照样健康。

> 注意:`Adding target` **只说明目标注册成功,不说明匹配到了文件**。这行日志极其容易让人误以为"采集正常"。

### 修复

```yaml
separator: "/"
```

修复后实测:

```
$ curl -s localhost:3100/loki/api/v1/label/namespace/values
{"status":"success","data":["ai-platform","argocd","logging","monitoring","nginx-demo"]}
```

### 修复过程中的第二个坑:改了 ConfigMap,Pod 不会重读

改完 ConfigMap 后,Pod 内挂载的文件**确实更新了**(实测 `grep` 到了新的 `separator: "/"`),但 promtail 生成的 glob 依然是旧的——**它没有重新加载配置**。

原因是 kubelet 更新挂载的 ConfigMap 时,改的是 `..data` 这个**符号链接**的指向,而 promtail 的 fsnotify 监听的是 `promtail.yaml` 这条路径。**符号链接被换掉,监听不到。** 实测时间线:

```
容器启动    : 17:57:05
挂载刷新    : 17:58:32   ← 文件内容已更新,但进程不知道
```

**处置:`kubectl rollout restart ds/promtail`。** 变更 ConfigMap 后必须显式重启消费它的负载。

### 教训

> **一条链路"每一段都健康"和"端到端通"是两件事,必须去终点看。** 这次的检查动作全程只做了一件对的事:**去问终点(Loki)有没有数据**。如果只查 promtail 的 Pod 状态和日志,结论会是"日志采集一切正常"——而实际上一条都没采到。

> **`Adding target` / `ConfigMap 已更新` / `Pod 是 Running` 都是"过程指标",不是"结果指标"。** 过程指标全绿只能说明"该发生的动作都发生了",不能说明"达到了目的"。

> **症状和 P11 是同一个(含:都是 promtail),但根因完全不同。** P11 是"挂了一个永远不会用的目录"(无影响),这条是"该匹配的路径匹配不上"(致命)。**同一个组件、同一次接管、两个独立缺陷——所以"我查过 promtail 了"不构成"promtail 没问题"的论据。**

- **面试可以怎么讲**:

  > "我接日志链路时,DaemonSet 是 3/3 Ready 的,日志里在正常打印 'Adding target',零报错。但我去问 Loki'你有没有数据',发现是空的。根因是生成采集路径时把 Pod UID 和容器名拼接用空字符串做分隔符,而真实路径中间有个斜杠——通配符匹配不到任何文件,**但 promtail 对'匹配不到文件'这件事不打日志**。修完之后又踩了第二个坑:改了 ConfigMap,Pod 里文件确实更新了,promtail 却没重读,因为它监听的是被 kubelet 换掉的符号链接。**这两次都让我确认了一件事:过程指标全绿不等于结果达成,校验必须去链路终点做。**"

- **关联**:P11(同一组件、同一次接管)、P12 / P13(同为"存在但不生效")、P8(静默失效)

## P15 — ArgoCD 报了 Git 拉取失败,CoreDNS 改完立刻好,**Jenkins 却纹丝不动**

- **日期**:2026-09-16
- **场景**:M3 搭 CI/CD 流水线时,集群里 git 拉取开始超时

### 现象

`github.com` 解析到一个**被墙的 IP** `20.205.243.166`。集群内拉取 Git 仓库超时,ArgoCD 报:

```
ComparisonError: failed to list refs ... context deadline exceeded
```

**注意一个极易误判的前置现象**:ArgoCD 在此之前**一直显示 `Synced`**。那个 `Synced` 是在拿**旧的 revision** —— 仓库远端根本拉不到,它只是"相对旧 revision 一致",所以照样绿。

> 这已经是这个坑在**本项目里的第二次现形**,第一次记录在 `03_runbook/02_ArgoCD_运行手册.md`(§`Synced` 不等于"同步到了远端最新 commit")。

### 排查过程

1. **先证伪"GitHub 挂了"**。手动 `--resolve` 指定其它 IP 去拉:

   ```
   140.82.112.3      → 200
   20.27.177.113     → 200
   140.82.121.3      → 200
   4.237.22.38       → 200
   ```

2. **再验证 ArgoCD 真正用的那个端点**,而不是随便一个 URL。它走的是:

   ```
   https://github.com/<repo>.git/info/refs?service=git-upload-pack
   ```

   在指定 `140.82.112.3` 时返回 **200,507 字节**。

3. **横向确认不是全网问题**:`codeload.github.com` / `pypi.org` / `quay.io` 全部正常。

### 根因

**不是 GitHub 挂了,是"解析到的那个 IP 被阻断"。**

域名本身可达、GitHub 本身在服务 —— 唯一出问题的一环是**"这个域名解析到了这个具体 IP"**。这类故障的特点是:**任何"目标服务是否正常"的检查都会通过**,因为检的不是同一个东西。

### 解法

在 `kube-system/coredns` 的 ConfigMap 的 `NodeHosts` 键里追加一行:

```yaml
NodeHosts: |
  ...
  140.82.112.3 github.com
```

该 hosts 块带 `reload 15s`,**热生效,不需要重启 CoreDNS**。

### ⚠️ 关键坑:ArgoCD 立刻恢复,**Jenkins 仍然连不上**

CoreDNS 一改,ArgoCD 马上恢复正常,但 Jenkins **依旧连不上 `github.com`**。

原因:**Jenkins 是 JVM 进程**,JVM 默认会缓存 DNS 解析结果(`networkaddress.cache.ttl`)。Jenkins 进程**启动早于 CoreDNS 修复**,所以一直攥着那个缓存的坏 IP 不放手 —— 外部世界已经修好了,它不知道。

**处置:重启 Jenkins Pod。**

**根治**:在 `jenkins-values.yaml` 的 `controller.javaOpts` 里加两个参数,让 JVM 定期重解析:

```yaml
controller:
  javaOpts: >
    -Dsun.net.inetaddr.ttl=30
    -Dsun.net.inetaddr.negative.ttl=10
```

- `sun.net.inetaddr.ttl=30` —— 正缓存只留 30 秒,之后重新解析
- `sun.net.inetaddr.negative.ttl=10` —— 解析失败(负结果)也只缓存 10 秒

### 经验

> **同一个 DNS 问题,在不同进程里的"生效延迟"完全不同。**

| 消费方 | 缓存层级 | DNS 变更生效方式 |
|---|---|---|
| CoreDNS 自身 | hosts 块带 `reload 15s` | **热生效**(15 秒内) |
| ArgoCD(repo-server) | Go 进程,无长缓存 | 修复后**立即** |
| **Jenkins(JVM)** | **`networkaddress.cache.ttl`** | **必须重启进程** |

**修好"基础设施层"不等于修好了"消费方"。** 这次的时间线是:改 CoreDNS → ArgoCD 绿了 → 于是直觉上"网络修好了" → 但 Jenkins 依然红着。**如果只看 ArgoCD 就收工,会漏掉一个仍然故障的组件。**

> **规律:任何带进程内缓存的系统(尤其是 JVM),改完它依赖的上游后要给它一个"忘掉缓存"的动作。** 修 DNS 要重启 JVM、改 ConfigMap 要 `rollout restart`(参见 P14 的第二个坑)、改 Secret 要重启消费它的 Pod —— **同一类问题,不同组件不同的形态。**

- **面试可以怎么讲**:

  > "集群里 ArgoCD 报 Git 拉取超时。我先证伪了'GitHub 挂了'——手动指定四个不同 IP 去拉,全都返回 200,ArgoCD 真正用的那个 `info/refs` 端点也是 200。所以问题不在 GitHub,在于**域名解析到的那个 IP 被阻断了**。我在 CoreDNS 的 NodeHosts 里加了一行固定解析,热生效,ArgoCD 立刻恢复。
  >
  > 但 Jenkins 还是连不上。原因是 **Jenkins 跑在 JVM 上,JVM 默认缓存 DNS 解析结果**,Jenkins 进程启动早于修复,一直用着缓存的坏 IP。重启 Pod 才生效。后来我把 `sun.net.inetaddr.ttl` 显式设成 30 秒,让它以后能自己感知变更。这件事让我记住:**修好基础设施不等于修好了消费方,判断'修好了没有'必须按组件逐个确认**。"

- **关联**:P10 / P14(同为"配置改了但消费方没重读")、`03_runbook/02_ArgoCD_运行手册.md`(`Synced` 的相对性)

## P16 — containerd 加私有仓库不需要重启(registries.yaml 反而需要)

- **日期**:2026-09-16
- **场景**:M3 要一个能被 K8s 拉取的镜像仓库,用 k3d 起了一个本地 registry

### 现象

```bash
k3d registry create sre-registry --port 5111
```

起好后接进 `k3d-ai-cluster` 网络,从节点内可以用 `k3d-sre-registry:5000` 访问。

但 Pod 拉取直接报错:

```
failed to do request: Head "https://k3d-sre-registry:5000/v2/...":
http: server gave HTTP response to HTTPS client
```

**containerd 默认走 HTTPS**,而本地 registry 是纯 HTTP。

### 排查过程(两个办法,第二个成功)

| 办法 | 结论 |
|---|---|
| 走 k3s 的 `registries.yaml` | ❌ **需要重启 k3s**,放弃 |
| 在三个节点容器里写 `/var/lib/rancher/k3s/agent/etc/containerd/certs.d/<registry:port>/hosts.toml` | ✅ **实测:不重启,立刻生效** |

### 根因:两个文件的生命周期不同

**为什么改 `registries.yaml` 要重启,改 `certs.d/hosts.toml` 不用?**

| 文件 | 谁写它 | 谁读它、什么时候读 |
|---|---|---|
| k3s 的 `registries.yaml` | 人 | **k3s**,启动时读,然后**渲染进 `certs.d`** |
| containerd 的 `certs.d/<registry>/hosts.toml` | 人(或 k3s 渲染) | **containerd**,**每次拉取镜像时动态读取** |

所以:

- 改 `registries.yaml` → 得让 **k3s 重新渲染** → 只能重启 k3s
- 直接写 `certs.d/hosts.toml` → **containerd 下一次拉取就会读到新文件** → 零重启

前置条件是**这条路本来就开着**:k3s 的 containerd `config.toml` 里 `config_path` 已经指向 `/var/lib/rancher/k3s/agent/etc/containerd/certs.d`,所以直接往那个目录写文件是有效的。

### ⚠️ 附注:那一次的"节点连不上 github"是**误判**

排查过程中一度判断"k3s 节点连不上 GitHub",**这个判断是错的**。

原因:探测命令写的是

```bash
curl -sI https://github.com || echo "不通"
```

而 **k3s 节点镜像里根本没有 `curl`** —— 命令不存在 → 非零退出 → 直接走了 `|| echo "不通"` 这个兜底分支。于是**工具缺失被读成了网络不通**。

> **教训:探测命令要先确认工具存在。** 一个"探测失败"的输出,可能来自"目标不可达",也可能来自"探测工具压根不存在"——这两者在下游看到的都是**同一个非零退出码**。凡是用来判定的命令,先单独验一次它能跑。

### 经验

> **同一件事在不同组件的"生效时机"不同,取决于那个组件是"启动时读一次"还是"每次用的时候读"。** 这条规律和 P15 是**同一个道理的两面**:
>
> - P15:JVM **缓存了 DNS**,所以上游改了它不知道
> - P16:containerd **每次拉取都重读** `certs.d`,所以改完立刻生效
>
> 判断一个配置改动要不要重启,**不能问"这是不是热加载",要去看那个消费方的代码/文档:它是在哪一刻读这个文件的。**

- **面试可以怎么讲**:

  > "我给 k3s 集群接一个本地镜像仓库,Pod 拉取报 'server gave HTTP response to HTTPS client'——containerd 默认走 HTTPS。标准做法是改 k3s 的 `registries.yaml`,但那需要重启 k3s。我改用另一个办法:直接在节点的 containerd `certs.d/<registry>/hosts.toml` 里写明文 HTTP 端点,**不重启、立刻生效**。原因是这两个文件的生命周期不一样:k3s 的 `registries.yaml` 是 k3s 启动时读了再渲染进 `certs.d`,而 containerd 的 `certs.d` 是**每次拉取镜像时动态读取**的。搞清楚'谁在读、什么时候读',就知道该改哪个文件、要不要重启。
  >
  > 同一次排查里我还犯了个错:一度判断'节点连不上 GitHub',后来发现是 k3s 节点镜像里没有 `curl`,我的探测命令走了 `|| echo 不通` 的兜底分支——**把'工具不存在'读成了'网络不通'**。这之后我养成了习惯:用来判定的探测命令,先单独确认它能跑。"

- **关联**:P15(同为"改完上游,消费方什么时候生效")、P17(CI 的动机)

## P17 — 那个跑了 30 天的网关镜像,**根本没法从版本控制重建**

- **日期**:2026-09-16
- **场景**:M3 要给 CI 选第一个"构建对象",去看现成的 `ai-infra-gateway` 镜像能不能上流水线

### 现象

集群里跑着 `ai-infra-gateway:v20`,已稳定运行 **30 天**。但它的**构建输入不在版本控制里**。

### 根因:**三条独立的漂移线**

**漂移线 1 —— 镜像里的代码依赖一批仓库里不存在的文件。**

镜像里的 `gateway_server.py` 导入了 `router.py` / `snapshot_loader.py` / `prometheus_client`,而:

- `router.py` —— 仓库里**从来没有过**
- `snapshot_loader.py` —— 仓库里**从来没有过**
- `requirements.txt` —— 仓库里**从来没有过**

这三个文件**只存在于镜像层里**。

**漂移线 2 —— 仓库里那个同名文件是另一条演化线。**

仓库里的 `gateway_server.py` 和镜像里的是**两个完全不同的东西**:仓库版是 **v2.0 单后端 Ollama 代理**,带 OTEL,还有中文教程注释;而镜像里跑的是一套**双后端路由(CPU Ollama + GPU vLLM)+ 7 个 Prometheus 指标 + 基于 snapshot 的策略路由 + 熔断只保护 Ollama 分支 + 显式在 401 前计数**的实现。

顺带一个直观证据:**tag 和内容对不上**。tag 一路从 v11 打到 v20,但 **v20 镜像里的代码自称 `v11.0`**。

**漂移线 3(最危险)—— 配置文件也有两份,而且差异是运行时才炸的那种。**

`config/gateway_config.yaml` 同样是两份,**仓库版缺 `cache_aware` / `backends` / `tiers` 三个段**。

而镜像版代码**每处理一个被路由的请求**都会读 `config["cache_aware"]["boost"]`。也就是说:

> **用仓库版的 config 去重建,容器会正常启动,然后在第一个请求上抛 `KeyError`。**

这是**最危险的一种漂移**:

| | 静态检查 | 启动 | 第一个请求 |
|---|---|---|---|
| 这种漂移 | ✅ **全过** | ✅ 正常 | ❌ **炸** |

缺的是**运行时才被读到的配置段**。任何"镜像能不能构建""容器能不能起来"的检查——包括 `docker build` 成功、Pod 变 Running、健康检查通过——**全都发现不了它**。

### 处置:以镜像版为正统

**原则:以实际在跑的那个版本为真相来源。**(沿用 D9 的"让 Git 描述现实")。

1. 从**镜像层**里捞出三个缺失文件
2. 仓库里的旧版分支归档到 `.archive/`
3. 补一份 `Dockerfile`,**还原真实的构建步骤**(而不是让镜像继续当"没有出处的产物")
4. **四个文件与镜像内的对应文件做 md5 逐字节比对,全部通过** ← 这一步是"重建可信"的凭证

### 教训

> **"能跑"不等于"能重建"。**

一个运行了 30 天、稳如泰山的服务,和一个"用仓库里的东西能重新构建出来"的服务,**是两件完全不同的事**。前者只需要**产物**,后者才需要**完整的、可追溯的构建输入**。

上面三条漂移线合起来意味着:这个镜像**没有出处**。它现在能跑,但**任何一次意外(节点重建、镜像被 GC、需要改一行代码)都会让它变成不可恢复的**——因为它没法重建。

> **这才是上 CI 最真实的动机。**
>
> **CI 的第一个价值不是自动化,是让构建可复现。** 自动化是"更快地做同一件事",可复现是"保证这件事是被定义过的、谁来做结果都一样"。没有可复现性,自动化只是**更高效地生产一个没人能解释的产物**。

- **面试可以怎么讲**:

  > "我接手一个跑了 30 天的网关镜像 v20,想把它纳入 CI,结果发现**它没法从版本控制重建**。三条漂移线:第一,镜像里的主程序导入了三个仓库里从来没有过的文件——它们只活在镜像层里;第二,仓库里的同名文件其实是另一条演化线,是个完全不同的单后端代理;第三,配置文件也是两份,仓库版少了三个配置段,而镜像代码每处理一个请求都会读其中一段——**用仓库版重建,容器能正常启动,第一个请求就 KeyError**。
  >
  > 最后一条最危险,因为它**静态检查全过、镜像能构建、容器能起、健康检查也过**,只有在真实请求上才暴露。我的处理是以镜像为正统,从镜像层把缺的文件捞出来,补 Dockerfile 还原真实构建步骤,并做 md5 逐字节比对来证明重建的结果和线上跑的是同一个东西。
  >
  > 这件事让我理解了一件事:**'能跑'和'能重建'是两回事。上 CI 的第一个价值不是自动化,是让构建可复现**——没有可复现性,自动化只是更高效地生产一个没人能解释的产物。"

- **关联**:`03_runbook/03_Jenkins_运行手册.md`、D16(镜像仓库选型)、D9(接管存量:让 Git 描述现实)、P14(`过程指标全绿 ≠ 结果达成` —— 这里是"构建成功 ≠ 产物正确")

## P18 — CI **静默不触发**:推了代码,流水线一声不吭,所有面板全绿

- **日期**:2026-09-16
- **场景**:M4 发布回滚演练。推送源码变更 `a14ce79` 到 Gitea,等自动构建

### 现象

推完之后 **6 分钟没有任何动静**。Jenkins 没报错、没告警、UI 全绿。

翻轮询日志,只有这几行:

```
Started on Sep 16, 2026, 1:49:41 PM
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
ERROR: no such computer sre-lab-ci-9-ph703-sbhm3-2b8db
Done. Took 2 ms
No changes
```

### 关键判据:`Took 2 ms`

**一次网络往返(去 Gitea 问"远端 HEAD 是什么")不可能在 2 毫秒内完成。**

> **排查心法:先找"物理上不可能的数字"。** 时间量级异常比任何日志文本都直接——`2 ms` 这个数字本身就宣告了"它压根没去问"。

### 根因:轮询要算 diff,算 diff 要工作区,而工作区在一次性 Pod 上

轮询要算"**这次推送改了哪些路径**"(因为我们配了路径过滤),这需要**上一次构建的工作区**。而我们的构建 agent 是**k8s 里一次性的 Pod**,构建结束就销毁——**轮询执行的那一刻,它要去找的那个节点必然已经不存在**。

于是它降级成"无变更",直接返回。**不报错、不告警、不改红。**

> ⚠️ **这里我后来把话说大了,已在文末「修正」一节改回来。** 当时我写的是"轮询模型和临时 agent 架构**根本不兼容**"——这句话是错的。见下。

### 决定性实验(而不是猜)

在构建 #11 **正在跑**的时候手动触发一次轮询:

```
Started on Sep 16, 2026, 2:11:12 PM
ERROR: no such computer sre-lab-ci-10-1fsrd-r2tv3-bp24r   ← #10 的 agent,早就没了
Done. Took 0 ms
No changes
```

**#11 的 agent 明明活着,轮询报的却是 #10 的节点**——它固定去找"**上一次已完成构建**"的 agent。这不是"那个节点碰巧没了",是**它取节点的逻辑本身就取错了地方**。

### ⚠️ 我在这条上判错过一次(比结论值钱的部分)

我一度把元凶判成 **`PathRestriction`(路径过滤)需要工作区**——这个判断**方向是对的**。然后我按这个判断**摘掉了任务配置里的 `PathRestriction`,重新触发轮询,照样 `0 ms`**。

**结论被实验证伪,我上一条的判断错了。**

事后查上游,发现这个 bug 是有据可查的:[JENKINS-46468](https://issues.jenkins.io/browse/JENKINS-46468) 描述的**正是这个现象**——用户的轮询日志同样是 `no such computer` + `Took 0.58 sec` + `No changes`,而他的触发条件**恰好就是开了 "Polling ignores commits in certain paths"**。上游对该 issue 的解释与我们一致:**"假设节点总是可用"在云环境里是无效假设**。

但**上游的解释解释不了我这次摘掉过滤后仍失败**。可能的解释是"节点引用被缓存下来了,改配置不会清掉缓存"——**这一条我没有验证,标为待核实。** 无论如何,结论不变:

> **轮询模型与"临时 agent"这个架构不兼容。这不是配置问题,是模型问题。**

### 处置

触发方式从**拉(SCM 轮询)**换成**推(webhook)**:Gitea 一收到 push 就主动通知 Jenkins,由 `generic-webhook-trigger` 插件接收。**推送模型不需要工作区**——它从请求体里直接拿到 `before` / `after` 两个 revision,根本没有"去查一下变了啥"这一步。

详见 `03_runbook/04_发布与回滚手册.md` 第五节。

### 教训

1. **"没收到告警"不等于"一切正常"。** 这条链路上唯一的失败形态是"什么都不发生"——而"什么都不发生"和"本来就没事"在监控上长得一模一样。
2. **诊断先找物理上不可能的数字。**
3. **先复现,再下结论。** 我的第一判断方向正确但不足以解释现象,是靠"摘掉它再试一次"证伪的。

### ⚠️ 修正(2026-09-16 当晚补记):我把结论说大了

**当晚稍晚,Jenkins 因为装 webhook 插件重启了一次——重启之后,轮询自己好了。**

证据:构建 **#14** 的触发原因是 `Started by an SCM change`,而它的控制台里没有任何 webhook 载荷——**那就是轮询触发的,而且它成功了**。

所以"**轮询模型和临时 agent 架构根本不兼容**"这句是错的。**被推翻的部分是我加粗强调的那部分,恰恰因为我当时对它有把握。**

修正后的完整解释,能同时解释之前**所有**观测:

| 观测 | 解释 |
|---|---|
| 推了代码,轮询 `Took 2ms / No changes` | 路径过滤要求工作区,而 agent 节点已销毁 |
| **摘掉路径过滤,重试,还是 0ms** | 那个"上次构建的节点"引用**缓存在 JVM 内存里**,改配置文件清不掉 |
| Jenkins 为装插件**重启后**,轮询忽然能用了(#14) | **重启清掉了那份内存缓存** |

对应上游 [JENKINS-46468](https://issues.jenkins.io/browse/JENKINS-46468):报告者的现象一模一样(同样的 `no such computer` + `No changes`),而他的触发条件**正是开了 "Polling ignores commits in certain paths"**。上游的定性是:**"假设节点总是可用"在云环境里是无效假设**。

> **一句话:这是"缓存"问题,不是"模型不兼容"问题。** 轮询慢、脆、要重启才能清缓存——**它不该用,但它是能用的。** 这两句话的区别,决定了我下次遇到类似现象时会不会又下错结论。

**而且这里还藏着一个更有价值的对比**:轮询就算修好了,它**只能告诉我们"变了"**;webhook 的载荷里有 `before` 和 `after` **两个 revision**——于是 Trigger Guard 才能算"**整次推送**改了哪些文件",而不是只看最后一个提交。**这是推送模型能给、轮询模型结构上给不了的东西。**(见 P19 的"已知简化"原文,它现在已经被这条修掉了。)

> **留个诚实的尾巴**:修正后的解释**没有做受控实验验证**——"重启清了缓存"是我从三个观测里推出来的最简解释,不是我被单独证明过的。**要证伪它,得在保留路径过滤的前提下重启一次、看轮询是否恢复。没做。**

- **关联**:`03_runbook/04_发布与回滚手册.md` 第五节、P19(换成 webhook 之后立刻带出的新问题)、P21(同类:"改完上游,消费方什么时候生效")

## P19 — 修好了触发,**流水线开始无限自我触发**

- **日期**:2026-09-16
- **场景**:P18 之后,给流水线加了"写回 GitOps 清单"(CI 会把新镜像 tag 提交进**同一个仓库**)

### 现象

CI 的写回**也是一次 push**。于是:

```
有人改代码 → 触发构建 → 构建成功 → CI 写回清单 → 又触发构建 → 又写回(内容没变)→ 又触发……
```

> **根因是结构性的**:触发源和写入目标是**同一个仓库**。只要"构建产物"和"触发信号"共用一条通道,就会形成反馈回路。

### 第一版修法(错的)

在 Jenkins 的轮询配置里加**路径过滤**(`PathRestriction`):只有 `ci/` 或 `03-ollama-exporter/` 变了才构建。

**它引出了 P18。** 路径过滤**需要工作区**才能算 diff,而临时 agent 没有工作区 → 轮询静默失效。**修好了循环,弄死了触发。**

### 正解:**把判定下沉到"能算 diff 的地方"**

| | 触发层(路径过滤) | 流水线内(Trigger Guard) |
|---|---|---|
| diff 从哪来 | 要**工作区**,而 agent 已销毁 | 自己 checkout 了,**`git diff` 随手就能算** |
| 失败形态 | **静默**:不触发,不报错 | 看得见:日志里直接打印本次改了哪些文件 |

所以把路径判定从"**能不能触发**"挪到"**触发了之后要不要继续**":

```groovy
stage('Trigger Guard') {
  def changed = sh(script: 'git diff --name-only HEAD~1 HEAD', returnStdout: true).trim()
  def relevant = changed.readLines().any { p -> p.startsWith('ci/') || p.startsWith('03-ollama-exporter/') }
  env.SHOULD_BUILD = relevant ? 'true' : 'false'
}
```

后续 stage 全部挂 `when { expression { env.SHOULD_BUILD == 'true' } }`。

**效果**:写回那次 push **仍然会触发一次**流水线,但 Trigger Guard 认出"本次只改了 `sre-lab-gitops/`",**两步就停**。循环从"无限"变成"恒为 2"。

### 教训

> **同一个判断,放在不同的层,可靠性完全不同。**
>
> 放在**触发层**,它必须依赖"上下文还在"(工作区);放在**执行层**,上下文是它自己刚刚准备的。**能算 diff 的地方就算 diff,不要指望上游替你算好。**

> **另一个边界要说清楚**:Trigger Guard 只比对 `HEAD~1..HEAD`(最后一次提交)。多提交推送时,若最后一个提交不触及构建路径而前面的触及,会**漏构建**。生产做法是与"上一次构建的 revision"比对。**这是本环境的已知简化,不是设计优点。**

- **关联**:P18(它们是同一次修复的两面)、`03_runbook/04_发布与回滚手册.md` 第六节

## P20 — 远程触发令牌配好了,**照样 403**:凭证令牌和 CSRF 是两层

- **日期**:2026-09-16
- **场景**:P18 之后,想在换 webhook 之前先试试 Jenkins 自带的"远程触发"(`/build?token=X`)

### 现象

任务里配好了 `BuildAuthorizationToken`,三种写法**全部 403**:

```
GET  /job/sre-lab-ci/build?token=<TOKEN>            → 403
POST /job/sre-lab-ci/build?token=<TOKEN>            → 403
POST /job/sre-lab-ci/build?token=<TOKEN> (+ 管理员账号密码) → 403
```

报错统一是 `No valid crumb was included`。

### 根因:两层机制,配好一层不代表能过另一层

| 层 | 管什么 | 我配了没 |
|---|---|---|
| **凭证令牌**(`BuildAuthorizationToken`) | "**你是谁**,凭什么触发" | ✅ 配好了,值是对的 |
| **CSRF crumb** | "这个请求是不是**从本系统页面**发出来的" | ❌ 命令行裸请求没有会话,拿不到绑定会话的 crumb |

JCasC 里 `allowAnonymousRead: false`,匿名连"够得着任务"都做不到,于是 CSRF 拦在最外层——**报错说的是 CSRF,但让人以为是自己令牌填错了。**

### 弯路:配这个令牌本身也不顺手

`BuildAuthorizationToken` **不是** `JobProperty`:

- `addProperty(...)` → `MissingMethodException: addProperty`
- 反射塞 `String` → `IllegalArgumentException: Can not set ... BuildAuthorizationToken field ... to java.lang.String`
- 最后**反射直接 set 成 `new BuildAuthorizationToken(TOKEN)`** 才成功(`OK set, token class=hudson.model.BuildAuthorizationToken`)

**折腾到这一步的结论是:此路不通,换插件。**

### 处置

上 `generic-webhook-trigger` 插件。它提供自己的端点:

```
POST /generic-webhook-trigger/invoke?token=<TOKEN>
```

它**不受这条 CSRF 约束**;而且令牌可以放进 Jenkins **凭据**(`tokenCredentialId`),**令牌值因此不需要出现在任何仓库文件里**——比写死在 Jenkinsfile 里干净。

### 教训

> **认证和 CSRF 是**两个独立的关卡**。看到 403 别默认是"我的凭据不对"——先看**报错说的是哪一层**。
>
> `No valid crumb was included` 里根本没有"token"这个词,它从来没在质疑我的令牌。

- **关联**:`03_runbook/03_Jenkins_运行手册.md` 第三节坑 3

## P21 — 同一个 POST,少了 `charset=UTF-8` 就从 400 变成 **500**

- **日期**:2026-09-16
- **场景**:用 REST API 改任务的 `config.xml`(移除 P19 里那个 `PathRestriction`)

### 现象

```bash
# ❌ 不带 charset
curl -X POST -H "Content-Type: application/xml" --data-binary @config.xml \
  "$JENKINS_URL/job/sre-lab-ci/config.xml"
→ 500

# ✅ 带上 charset
curl -X POST -H "Content-Type: application/xml; charset=UTF-8" --data-binary @config.xml \
  "$JENKINS_URL/job/sre-lab-ci/config.xml"
→ 200
```

**同一个请求体,同一个端点,只差一个 `charset` 参数。**

### 根因

`config.xml` 里有中文(任务描述)。**不带 `charset` 时,Jenkins 按平台默认字符集解析**;声明与字节不匹配,解析在服务端炸掉,表现为 500。

### 教训

> **500 是"服务端内部错误",不是"你发错了"——但这不代表你没错。**
>
> 400 还肯告诉你"请求有问题",500 只会说"我炸了"。**当 400 正常、500 诡异、且请求体里有非 ASCII 字符时,先怀疑字符集声明。**

- **关联**:`03_runbook/03_Jenkins_运行手册.md` 第三节(它讲的两个坑分别是 403 和 400,这是第三个:**500**)

## P22 — **ArgoCD 的 selfHeal 是秒级的**,我从头到尾都没机会看见自己的手工改动生效

- **日期**:2026-09-16
- **场景**:M4 演练早期,想用命令式的方式"手动把镜像换掉"看看效果

### 现象

```bash
kubectl set image deployment/ollama-exporter ollama-exporter=<registry>/sre-lab/ollama-exporter:ea96824
# deployment.apps/ollama-exporter image updated  ← 命令成功了
```

**再看一眼,t+5 秒,镜像已经变回原来的了。** 没有任何报错,命令也返回成功。

### 根因:ArgoCD 对**它管理的资源**有 watch,3 分钟只是兜底

我之前一直以为"ArgoCD 轮询,所以手工改动大概能活几分钟"。

**错。** 那 3 分钟(`automated.selfHeal` 的**全量对账**周期)是**兜底路径**;对于 ArgoCD 已经管理的资源,它**有 watch 通道**,集群里一有变化**立刻**就发现、**立刻**就拉回。

> **`selfHeal` 不是"每 3 分钟修一次",是"发现即修"。**

### 教训

> **GitOps 下,手工 `kubectl` 改动是"无效动作",不是"临时有效动作"。**
>
> 更危险的形态是:它**不报错**。命令返回成功、`kubectl get` 头两秒也确实显示新值——**如果我只看了这两秒,我会得出"改成功了"的结论并写进文档。**

> 由此推出一条排障纪律:**看到"我明明改了啊",先问一句"这个资源归 ArgoCD 管吗?"**
>
> 这也解释了另一个现象:回滚时如果用 `kubectl rollout undo`,**你会看到自己白忙一场**。

- **关联**:`03_runbook/04_发布与回滚手册.md` 第一节、`02_ArgoCD_运行手册.md`(hard refresh / `Synced` 的准确含义)

## P23 — webhook 配得好好的,**Gitea 拒绝投递**:它默认不许往私网发

- **日期**:2026-09-16
- **场景**:P18 之后,webhook 链路全部配好(插件装了、凭据建了、Gitea hook 建了、手动打端点返回 `triggered:true`)。推代码——**没反应**

### 现象

推了代码,Jenkins 一声不吭。但**手动从 Gitea 容器里 `wget` 那个端点,返回 200 + `triggered:true`**。

> **"端点通了"和"链路通了"是两件事。** 我当时差点就卡在这里。

### 决定性证据:Gitea 自己的日志

```
Unable to deliver webhook task[3]: ...
dial tcp 172.18.0.5:30080: webhook can only call allowed HTTP servers
(check your webhook.ALLOWED_HOST_LIST setting), deny 'k3d-ai-cluster-server-0(172.18.0.5:30080)'
```

### 根因:**Gitea 默认只允许 webhook 发往公网地址**

这是 **SSRF 防护**:webhook 是"让服务器替我发起一个 HTTP 请求"的功能,而这类功能天然可以被用来**探测内网**(让 Gitea 去请求 `http://169.254.169.254/...` 这类云元数据地址,或者内网里任意一台机器的管理端口)。

所以 Gitea 默认 `ALLOWED_HOST_LIST = external`,**拒绝一切私网目标**。而我们的 Jenkins 在 `172.18.0.5`——私网。

> **为什么手动 `wget` 能通、Gitea 却不能**:手动测试**绕过的是 Gitea 的客户端策略**,不是网络。**网络一直是通的,是 Gitea 自己不肯发。**
>
> 这类"**同一台机器上,我手动能通、它自动不能通**"的现象,第一反应应该是:**不是网络问题,是某个组件自己的策略**。

### 处置

在 Gitea 的 `app.ini` 里放行本环境所在的网段(**不是** `*`):

```ini
[webhook]
ALLOWED_HOST_LIST = 172.18.0.0/16
```

改完 `docker restart gitea`,**之前排队失败的那次投递会自动重投**——构建 #16 就是这么起来的。

### 顺带发现:**webhook 令牌被 Gitea 明文写进了自己的错误日志**

失败那行日志里,完整的 URL 连同 `?token=ec663fc7...` 一起被打出来了。

> **这是"密钥不能放 URL 里"的具体代价**:URL 会被日志、代理、浏览器历史、Referer 头记录下来,而**请求体里的东西通常不会**。
>
> 这里的缓解是"令牌只对一个 Jenkins 凭据有效、且只能触发构建"——但**这是访问范围的控制,不是不泄露的控制**。**这条值得在面试里主动讲**:同一个信息放在 URL 里还是请求体里,**泄露面完全不同**。

### 教训

> **"我手动测过了,是通的"是一个很容易骗过自己的证据。** 手动测试用的是**你的**身份、**你的**路径、**你的**策略;而系统自动投递用的是**它的**。两者能通的路径**可能根本不重叠**。
>
> **正确做法:验证要走真实路径。** 这个坑的发现靠的是"去看 Gitea 的日志",而不是"再手动试一次"。

- **关联**:P18(触发链路的另一半)、P20(同为"配好了却 403/拒绝",但那次是 Jenkins 的 CSRF 策略——**两条都是"策略层"而非"网络层"**)
